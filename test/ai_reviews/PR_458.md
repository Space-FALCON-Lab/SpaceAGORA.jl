# Review record: PR 458: Start hinge, gimbal and firing state at each run's start

## Scope

**G-8 contract, restored for the hardware.** G-8 says two runs of one
configuration with `isolate_state=false` start equal. Batteries, actuator faults,
sensors and the GNC models (#394, #408) already met it. Hinge and gimbal angles
and the firing state of thrusters with firing dynamics did not; on this branch
they do. The evidence:

- **On `main`, the hardware drifts.** A probe runs one configuration three
  times with a hinge, a gimbal and a firing thruster, held by a mounted
  controller:
  - the hinge ends at 0.1, 0.2 and 0.3 rad;
  - the gimbal ends at 0.05, 0.1 and 0.15 rad;
  - the firing state and the final velocity change from run to run.
- **On the branch, the three runs start equal.** All three end as `main`'s
  first run does. The new tests check three runs of one configuration, for
  each part and for all three together: the solutions are bitwise equal, the
  parts' state is equal after every accepted step and at the end, and each run
  ends as a fresh configuration's does.
- **The tests discriminate.**
  - On `main` the new test file fails 23 assertions and errors in 4, while its
    resumed run passes.
  - Seven source mutants of the rule each fail it: no reset for the hinge, the
    gimbal or the firing state; edits not kept; no record at the tick; geometry
    not following; a resume treated as a run start.
  - Moving the run-state callback after the priority callbacks, after the
    sensors, or to the end fails the ordering testset.
- **Nothing else changes.** First runs and isolated runs are bitwise identical
  to `main`: the eight harness fingerprints and a probe of this hardware give
  the same bits.
- **A user's edit between two runs is kept** and becomes the start of later
  runs (#408's rule). A resumed run continues the checkpoint's state, as on
  `main`.

Giusy's decision of 2026-10-20: hinge, gimbal and thruster firing state reset at
a run's start, like batteries and sensors, in a behaviour PR of its own that
keeps the configured start apart from the running state. The finding came from
the C2b state map. With `isolate_state=false`, hinge and gimbal angles and the
firing state of mounted thrusters with firing dynamics (the ramp factor `κ` and
the held average thrust) had no run-start reset, so a repeated run continued
from the previous run's hardware. Example: a `PanelHinge` with
`max_rate_rad_s=0.1`, held at level 0.5 for 3 s with 1 s control ticks, ended at
0.1, 0.2 and 0.3 rad over three runs of one configuration. Batteries, actuator
faults and sensors were already reset at a run's start, and default isolated
runs were unaffected.

The rule is #408's, for the GNC models. Each part keeps the run state a run
starts from apart from its running state. At each run's start a value still
equal to the latest control tick's write returns to its value at the previous
run's start. A value changed since (a user's edit) is kept and becomes the
start of later runs. A run resumed from a checkpoint is not a run start, and its
state comes from the checkpoint as before.

- **The rule** (`ActuatorMounting._start_run_state!`) works field by field, as the
  GNC models' rule does (`SimulationLifecycle._run_start_entries`). A field still
  `isequal` to the last tick's write returns to `run_start`, and a field changed
  since is kept and becomes the next `run_start`. With no recorded write (a first
  run, or parts no tick wrote), the current state is kept. The link and thrust
  follow only after a run that wrote them.
- **Where writes are recorded.** `_note_run_writes!` runs after each mounted
  tick (`actuation_mode === :mounted`) and after a checkpoint restore. A resumed
  run skips the reset (`callback_resume`), so a resume continues from the
  checkpoint as before.
- **One reset per run.** The callback is built fresh for each run, and its
  `initialized` flag makes the reset happen once, not again at
  checkpoint-segment boundaries.
- **Callback order.** It is appended after the external-propagation sync and
  before the priority callbacks, the sensors, navigation, guidance and control.
  The new ordering testset fixes that position, and three mutants that move it
  are caught.
- **State types.** `run_start` and `run_written` are concretely typed
  (`Union{Nothing, …}` of an immutable state), so the per-tick record does not
  change the parts' field types.
- The branch merges cleanly with main `c22d7c5ee` and every open PR. No commit
  carries a trailer.

## Findings

Author's notes for the reviewer (no P1 known to the author):

- **Design, medium: where the reset runs.** In the callbacks' first
  initialization, as for batteries and faults. That comes after the GNC
  initializers and the checkpoint restore, and before the first right-hand-side
  evaluation. No setup step reads these parts before that: the right-hand side
  reads a hinged link's attitude live, and the initial conditions and setup
  buffers do not read hinge, gimbal or firing state. The callback is appended
  before the sensor, navigation, guidance and control callbacks, so a tick at
  the run's start sees the reset parts.
- **Design, medium (reused objects): the configured start is recorded at
  construction.** `run_start` holds the configured state from the part's
  construction, not from its first run. So a run on a reused object after a
  resumed run starts from the configured state too. If a user sets a field
  before the first run, that run keeps it, because there is no write yet to
  compare with.
- **Design, low: entries are field by field.** Each field returns or is kept on
  its own (as #408's controllers): a hinge's angle and its tick time, a gimbal's
  angle, tick time and previous angle, a thruster's `κ` and `thrust`. An edited
  angle keeps the edit while the tick time returns to NaN, so a rate-limited
  part's first tick records the time and holds, as at a first run.
- **Design, low: writes are recorded by the engine's tick, not by the parts'
  public move functions.** `move_hinge!` and `move_gimbal!` called by a user
  between runs count as edits and are kept. After a checkpoint restore, the
  restored state is recorded as the latest write.
- **Low: geometry follows only after a run that wrote.** When no run has
  written a part yet, its link attitude and thrust turn are left as they are,
  so first runs are unchanged. A hinge angle edited before a part's first tick
  does not turn its link until that tick, as on `main`.
- **Low, as in #408 and the burn scheduler: an edit equal to the last write is
  not seen.** It returns to the run's start.

## Residual Risk

- An edit equal to the last write is not seen (see Findings), as for #408's
  models and the burn scheduler.
- The records are not in checkpoints. They are configuration-side and need not
  be: a resumed run is not a run start.
- A checkpoint without a callback snapshot (written before snapshots existed)
  resumes a run with only hinges or gimbals by warning and starting them from
  their current values. Such a resume does not set `callback_resume`, so on a
  reused object the run-start rule applies to it.
- The CMGs' gimbal angles are integrated state and start from the
  configuration's values in each run already; they are not in scope.
- Not run locally: the EDG and HYPR companion suites and the full integration
  suites; CI runs them.
