# AI Review Artifact — PR #120

## Scope
The batched spherical-harmonics kernel holds a rolling three-row window over the associated-Legendre triangle instead of materialising the whole triangle. Degree `l` reads rows `l` and `l+1` and writes row `l+2`, so three rows are live; the full `[B, L+4, L+4]` workspace was 91.1 MB at B=4096, L=50, against a 64 MB L3. Performance change only — the kernel's outputs are unchanged bit for bit.

## Changed Files
- src/dynamics/coupled/perturbations.jl — `HarmonicsBatchWorkspace.A` becomes `[B, 3, L+4]`, row `r` in slot `((r-1) % 3) + 1`, with a new precomputed `diag::Vector` for the position-independent diagonal that previously lived in the triangle and was never overwritten. The sub-diagonal pre-pass (old Phase 2) folds into the degree loop, which now builds exactly one row per degree; its companion `row > max_recur_row` branch was dead (`max_recur_row` is `l+2` after iteration `l` while `row` is `l+1`) and is removed. Phase 4's accumulation reads slots rather than absolute rows.

## Findings
- **P1 (found and fixed during review): zonal-only fields (M = 0) were computed wrongly.** A rolling slot is reused every three degrees and again on the next call, so the one column per row that is read but never written has to be re-zeroed. The first implementation took that column as `M + 2`. The recursion's column bound is `min(max(M, 1) + 1, l)`, so at M = 0 it writes column 2 and the zeroing clobbered it immediately after — every component of every satellite wrong, not a small perturbation. Every M >= 1 was unaffected, since `max(M, 1) == M` there. Fixed by computing the zero column against `m_cap = max(M, 1)`. Verified against the untouched scalar kernel on the unmodified baseline first, to confirm the defect was introduced here and not pre-existing.
- **P2: this class of defect had no test coverage.** The square-degree benchmarks (L=M=20, L=M=50) and `test/probes/flat_route_parity_probes.jl` all use M >= 1, so nothing in the suite exercised the zonal-only path against an oracle. Addressed below.
- **P3: the win is in the parallel route, not the serial one, inverting what the single-thread kernel microbenchmark predicts** (1.22x at B=4096 serial, 1.10x at the B a worker actually gets). The binding constraint is aggregate L3 pressure across the twelve per-worker workspaces — about 95 MB live against 64 MB of L3 — not one thread's footprint. Serial holds one workspace and is bound elsewhere; L20 is flat because its 18 MB triangle already fit. Measured end-to-end on S1 (`PS_MISSION_S=600`, vacuum, `PS_NO_SPICE=1`) against `8c2a4cc2`: L50/N=4096/12 threads 2.983 / 2.952 s -> 2.536 / 2.465 s (1.19x, two independent runs); L50/N=1024/12 threads 1.09x; L50 serial and every L20 point 1.00x within noise.
- **P3: the removed `row > max_recur_row` branch was unreachable, not merely redundant.** It is deleted rather than preserved because the rolling window cannot hold the rows it would have written. Argument recorded in the source comment so a future reader does not restore it.

## P1 Assessment
One P1 (zonal-only M = 0 fields computed wrongly by the slot-reuse zeroing), introduced and resolved within this PR. Unresolved P1: No

## Tests Added/Updated
- test/unit/simulation/harmonics_batch_parity_tests.jl (new, registered in `test/unit/runtests.jl`): asserts `_harmonics_flat_batch_kernel!` reproduces `_harmonics_scalar_force_ii` **bitwise** (`===`, not `≈`) over a degree/order matrix that includes M = 0, M < L and M == L — (20,0), (12,3), (20,5), (30,7), (50,2), (50,10), (50,49), (20,20), (50,50) — each run twice on the same workspace so a slot left dirty by the previous call is observable, and again across shrinking and growing batch sizes (64, 7, 33, 1) on a pooled workspace sized by the widest prior run. Confirmed to fail on the M = 0 case with the fix reverted and pass with it applied.
- Pre-existing coverage relied on: `test/probes/flat_route_parity_probes.jl` (serial vs flat, bit for bit, mixed effector set) passes, as does the full default entrypoint (`test/runtests.jl`, exit 0, 18/18 probe drivers).
- Outside the suite, kernel outputs were captured from the unmodified tree before editing and compared bitwise afterwards: identical on all six (L, B) points at L in {20, 50} and B in {256, 1024, 4096}.

## Residual Risk
Low-to-moderate, and concentrated in one place. The arithmetic is untouched — same operands, same association, same order, which the bitwise tests confirm — so the risk is not numerical but structural: the correctness of slot reuse rests on the argument that exactly one column per row needs re-zeroing and on the identity of that column. That argument was wrong once already, for M = 0, and the new test exists because reasoning about it was not sufficient. The (L, M) matrix now covers the boundary cases the argument turns on, and the repeated-call and varying-batch-size checks cover the reuse paths, but anyone changing the recursion's column bound must revisit `m_cap` in the same edit. Benchmark figures are single-machine (Zen 5, 12 physical cores); the mechanism predicts a larger gain at 64 threads on the TRX50, which is unmeasured and should not be assumed in any paper number.
