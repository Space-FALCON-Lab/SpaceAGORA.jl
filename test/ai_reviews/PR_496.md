# Review record: PR 496: keep Float64 viewer positions above 64 spacecraft when the budget allows

## Scope

Review of the SpaceAGORA `viewer-position-precision` branch against main (47c32d969, after #488; the head is clean against main 0487e8226, the v0.6.0 release). This is C-5b of the constellations program's large-outputs step, built to the accepted C-5 design decision D-C5-8:

- Float64 positions at 64 or fewer spacecraft, as before;
- above 64, Float64 when it costs no frames;
- a `position_precision` keyword to force either;
- the same rule in the ensemble export.

What changes:

- `build_viewer_frames` works out the frames it keeps at 24 bytes per position and at 12. Above 64 spacecraft it embeds Float64 positions when both keep the same rows (the same regular stride, and with mission segments the same row limit) and the Float64 frames fit the budget.
- `build_ensemble_frames` does the same for its pseudo-spacecraft count, comparing the time axis it builds at each precision.
- `position_precision = :auto | :f64 | :f32` reaches both from every export entry point, which checks it before reading any results. `:auto` is the default; `:f32` gives main's payload above 64.
- Non-breaking: the keyword's default is the rule, which at 64 or fewer is today's behavior.

Commits: 568746fd8 on main 81431249c, then b78910262 (the in-house review's P3s), with main 47c32d969 merged in. Head: 7323d7193.

## Findings

No P1 or P2 findings.

- **Changed on purpose.** Above 64 spacecraft, a payload whose budget holds Float64 at the same frames now carries Float64 positions (`pos_dtype = "f64"`). Nothing else in it changes.
- **Independent review (coordinator, 2026-10-22, after the v0.6.0 release).** The head 7323d7193 is unchanged since the in-house review and its P3 round. `git merge-tree` against main `0487e8226` (the v0.6.0 release) is clean, and none of the files this PR changes moved on main after 47c32d969. It changes no public default at 64 spacecraft or fewer and adds one keyword, so it is placed in the 0.6.1 patch. No P1 or P2.
- **In-house review: Clear, no P1 or P2.** Its six P3s are addressed in b78910262:
  - **P3-1, the two-frame floor.** `:auto` picked Float64 when the budget held fewer than two frames, although the floor then put the page over the budget. The viewer and the ensemble export now keep Float32 there, and the size sentence under Residual Risk is corrected.
  - **P3-2, the ensemble test.** It now uses three spacecraft per sample, the 64 boundary at a budget where Float64 costs frames, and the axis-spacing case. A mutation run (under P1 Assessment) shows the sample-count, off-by-one, no-cutoff and axis-length mutants fail it.
  - **P3-3.** The visualization page says that `:f64` with mission segments can refuse an export `:auto` completes, and the refusal names the keyword.
  - **P3-4.** The keyword is checked at the entry points before any results are read, and a String or `nothing` gets the same message as an unknown Symbol.
  - **P3-5.** Main is merged again and the merge list below is current.
  - **P3-6.** The release-note wording: the keyword forces either precision, `:auto` applies the rule.
- **Design choices for review.**
  - **"Costs no frames"** compares the kept rows' inputs, not the frame-count arithmetic. In the viewer these are the stride and, with mission segments, the row limit. In the ensemble export it is the time axis. A comparison of the budgets' sizes would never match, since the budget's byte count always differs between the two precisions. Comparing the row limit only when there are mission segments is exact for runs without them, and at worst stricter (Float32) with them.
  - **Below two frames.** The frame budget never keeps fewer than two frames, so a budget too small for two Float64 frames keeps the same two at either precision, over the budget. `:auto` counts that as a cost and keeps Float32: the viewer checks that the Float64 frames fit the budget, and the ensemble export that the budget holds two Float64 frames.
  - **The keyword** takes `:auto`, `:f64` or `:f32`. Any other value, a String or `nothing` among them, gets an `ArgumentError` that lists the three. The export entry points check it before reading any results.
  - **The CLI** keeps the default rule; it gains no flag.

## Residual Risk

- **Payload size above 64 spacecraft.** Where `:auto` picks Float64, the position block doubles in size, and the frames stay within `data_budget_mb` as the frame budget counts them. A budget below two Float64 frames keeps Float32. A forced `:f64` follows the two-frame floor, as Float32 does.
- **The last row.** The frame budget counts the rows its stride reaches, and the kept rows add the last row when the stride does not reach it, one frame over that count. This is main's behavior at both precisions, and this PR does not change it.
- **Mission segments** compare the row limit too, so a run with them can keep Float32 where one without them would get Float64 at the same budget. With them, a forced `:f64` can refuse an export that `:auto` completes, since the boundary rows must fit as Float64 frames. The refusal then names the keyword, and the docs say so.
- **The CLI** has no flag for the keyword; a caller who wants Float32 above 64 calls the export functions.
