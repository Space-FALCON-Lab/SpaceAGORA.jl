Public API and compatibility

Use this page when you need to know which package surface is stable and which names your applications and extensions can depend on. The generated public API pages identify the supported symbols; internal implementation names can move.

Shortest stable package example:

using SpaceAGORA

What to read next:

  • Public API
  • Extensibility

SpaceAGORA now treats the root SpaceAGORA module as the only stable package surface.

Stable surface

The generated Public API reference and its linked Simulation Setup API, Terrain API, Mesh Aerodynamics API and Visualization API pages document the supported exported symbols. That surface currently includes:

  • simulation entrypoints such as run_simulation
  • typed runtime configuration objects
  • simulation setup types and helpers (SimulationConfiguration, SpacecraftModel, Link, InitialTime, make_example_config, ...), so using SpaceAGORA alone is enough to configure a run
  • no-GRAM baseline constructors and builders
  • selected abstract extension interfaces
  • selected extension hook functions
  • verification entrypoints
  • CLI and asset-report entrypoints

Documented versioned facades rooted at SpaceAGORA are also supported integration boundaries: HYPRServices, ExternalPropagationServices and EDGServices. Their documented metadata, lifecycle operations and explicit binding inventories define the supported boundary; use them by qualified name. Their adapter contract controls compatibility separately from package versions. Other symbols absent from the documented root API or a facade inventory should be treated as internal.

Compliant multibody and robot-arm names

Use the robot-arm names for kinematics and the compliant multibody names for spring-connected dynamics. The Robotics API and Compliant Multibody API document both the preferred names and the compatibility names. The model represents flexibility through discrete bodies and compliant joints; it is not a continuum cloth solver. The preferred names are aliases of the existing types and generic functions, so changing a call's spelling does not change its dispatch, state layout or physics.

For example, write arm = default_robot_arm_model() and pose = robot_arm_fk(arm, RobotArmBasePose([0.0, 0.0, 0.0]), q) when q contains the arm's joint angles. Existing calls using the historical names remain valid. The defining modules and types retain their identities, so printed types and serialized owner names may still contain Cloth. The root also provides the qualified module aliases SpaceAGORA.CompliantMultibody and SpaceAGORA.CompliantRobotArmDynamics. These aliases do not make every module member public; supported operations remain those listed in the public reference.

Some historical strings are configuration or data identifiers, rather than display names. Keep planner=:cloth_quintic, mode=:cloth, the retime_cloth_* configuration fields, and existing example filenames, output directories and CSV column names. The versioned HYPRServices.Cloth namespaces and their inventory retain their exact spellings; see the HYPR service contract. This compatibility change neither adds contact physics nor couples the core compliant model to MuJoCo. The optional MuJoCo companion has its own propagation ownership and coupling limits.

Internal modules

The following modules remain internal implementation detail namespaces:

  • RuntimeServices
  • SimulationModel
  • SimulationEngine
  • ParallelProfiles
  • TelemetryVerification
  • SpaceAGORACLI
  • subsystem modules under src/models/gnc, src/models/dynamics, src/orchestration/simulation, and src/orchestration/parallel

These modules are still used heavily inside the package and tests, but they are not the stable user contract. They may be reorganized without a deprecation window as long as the root exported API remains stable.

Extension hooks

For model authors, the stable extension contract is:

  • subtype the documented abstract interfaces exported by SpaceAGORA
  • implement the matching exported hook functions, which follow the Extension Conventions. By family:
    • force and torque models: wrench, environment_requirements, solver_partition and the gravity-backbone hooks;
    • atmospheres: getDensity and getDensityBatch!;
    • GNC ticks: update_control!, update_guidance! and update_navigation!;
    • control outputs: control_wrench, control_propellant_rate and control_wheel_torque;
    • actuators: actuator_wrench, actuator_limits and the optional actuator methods, actuation_mode and actuator_levels;
    • sensors: sensor_measure, sensor_dimension and the optional sensor methods;
    • planners: plan_rpo!, retime_rpo! and the GNC algorithm contract.

The Extension Hook Reference lists every hook with its shape, signature, fallback and status. This lets extension code stay rooted in SpaceAGORA.* rather than reaching into internal modules.

Deprecations

A public name that is renamed or retired keeps working for a deprecation window of at least one tagged release:

  • The old name is still exported, and its docstring opens with "Deprecated, use ...". The deprecated hooks are listed together on the Deprecated Hooks API page.
  • A model that implements a deprecated hook still runs. The pre-run check warns once per model type and old name before integration, never during the solve.
  • julia --depwarn=error turns these warnings into errors, so a test run can refuse deprecated hooks.
  • Deprecated hook names are removed in SpaceAGORA 0.5.0, or 1.0 if that comes first. They are not removed before a tagged release has carried the warnings and the companion packages have moved.
  • Release numbers follow version in Project.toml.

The deprecation rules give the details, and Migrating Extension Hooks maps every deprecated name to its replacement, with the schedule.

Internal modules are not covered: they may change without a deprecation window, as long as the root exported API stays stable.

Solver-side policy note:

  • split_imex now means the atmosphere-implicit IMEX partition
  • multirate still means the control-focused split
  • solver_partition is the public hook that places dynamic effectors on the implicit or explicit IMEX side
  • gravity_backbone_split is the public fixed-step gravity-backbone split mode with a symplectic gravity core plus explicit SRP / N-body velocity kicks
  • gravity_backbone_structure / gravity_backbone_acceleration_ii declare gravity-core participation
  • gravity_backbone_kick_structure / gravity_backbone_kick_acceleration_ii declare explicit translational kick participation
  • the current heat_loads state remains explicit because it is an accumulated heat-rate integral, not a thermal-capacitance model

Opt-in RPO planner surface

The root exports the neutral planner contracts and extension methods, DirectRPOPlanner, HYPRRPOPlanner, RetainedPathRPOPlanner, RPOPSOConfig, rpo_pso_config, RPOPlanningEvent, RPOPlanningError, make_rpo_configuration and rpo_run_report. SimulationSettings remains owned by the existing configuration module and has a root alias for output settings. The RPO Planner API lists these symbols. The pilot guide defines supported truth/static-RTN scope, failure policy and restart refusal. Internal lifecycle modules and the full SimulationModel are not public interfaces. The root also exports the seven comparison planners, HYPRComparisonPlanner, UnrefinedPSOPlanner, RRTConnectPlanner, RRTConnectBezierPlanner, RRTStarPlanner, CHOMPPlanner and STOMPPlanner; the comparison harness itself stays internal.
