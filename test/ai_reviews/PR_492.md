What it does:
- **The run's GNC scopes.** When the run starts, after the run-start
  initializers, the engine records each guidance, navigation and control model's
  scope and the run positions it acts on, and for each spacecraft the control and
  guidance models acting on it (`engine/gnc_run_scopes.jl`,
  `SharedBuffers.gnc_scopes`). A checkpoint's `gnc_scopes` entry (#476) is built
  from the same record.
- **Fixed for the run.** Each periodic tick, and once per accepted step for each
  event-driven control model, compares the scope it reads with the run's, and a
  difference stops the run.
- **Hooks follow the scope.** The right-hand side, the per-spacecraft readers,
  the atmosphere crossings and the burn scheduler's passes call a model's hooks
  only for the spacecraft its scope names, when some model acts on fewer than
  every spacecraft.
- **`SpacecraftSelection` for GNC models**, resolved once when the run starts.
- **Conformance:** an advisory `outputs_in_scope` check for control models.

Rule: every built-in run is bitwise unchanged. A user model whose output hooks or
levels act outside its declared scope loses that action, by decision (D-C3-4).

## Findings

- **F1 (the review's scope-change cases).** The design review found three cases
  with no baseline or no check. Each is handled and tested:
  - every run records its scopes, not only runs with member lists, so a model
    that acts on every spacecraft and then narrows its scope is refused;
  - an event-driven control model, which has no periodic tick, is checked once
    per accepted step by one callback after the models' own. Its condition never
    fires, so the state and the saved points do not change; it is added only to
    runs with event-driven models (the burn scheduler's), and it counts as one
    more discrete callback;
  - a `SpacecraftSelection` is compared with the run's own copy of its
    criteria, so a selection changed in place is refused. Its `where` is called
    once per spacecraft, at run start, in a checkpointed run too.
- **F2 (#476).** C-3b adds no checkpoint entry. The `gnc_scopes` entry is built
  from the run's scopes, by `_gnc_scope_record`: the same values #476's
  `_gnc_scope_baseline` gives (tested), except that a selection is recorded at
  the positions the run resolved, without a second call of `where`. A resumed
  run compares the entry before restoring any model's state, as #476 does.
- **F3 (positions outside the run).** A scope an initializer widens past the
  run is not refused at run start: its slot holds the positions its ticks visit,
  as #476 now records them, and the hooks follow the same positions.
- **F4 (contract, by decision).** The output hooks, `actuator_levels`,
  `control_thruster_levels` and `atmosphere_transition!` are called only for the
  spacecraft a model's scope names (D-C3-3, no opt-in per D-C3-4). The
  docstrings, the guide and the migration page say so; the migration page names
  the two kit demo models with a narrower scope, both of which return zero
  output outside it. A linked producer that changes its consumer's scope now
  stops the run, where 0.6 followed the change; #477's retargeting test expects
  the refusal now. No built-in producer does this (the RPO planner only checks
  its reference).
- **F5 (found by the fingerprints, fixed).** The first version shared the
  right-hand side's control-loop body between the two methods through an
  `@inline` helper. That changed how LLVM fuses the mounted wrench's
  StaticArrays arithmetic once inlined, so case 3 of the GNC probe (mounted
  magnetorquers and laser terminals on batteries, one bound controller per
  spacecraft) drifted from main in its last bits and then apart over two orbits.
  The member-list switch did not matter (both paths shared the helper), so only
  the comparison with main showed it. 596627049 writes main's loop statements out
  in both methods; case 3 then matched C-3a with the lists on and off, at one
  thread and on every forced route at four.
- **F6 (two smaller fixes).** Parameters built by hand for one right-hand-side
  evaluation (`link_gravity_sampling_tests`) carry shared buffers without the
  run's scopes; the lookups now treat them as a run without member lists. A
  mutant that reversed a spacecraft's member order survived the first tests, so
  a test now checks the call order at every evaluation.
- **F7 (main moved case 3).** Case 3 at four threads, on the automatic route,
  gives different bits on main 60c117c9d than on main 2088b4408, without C-3b.
  C-3b on main 60c117c9d gives main 60c117c9d's bits.

## Residual Risk

- **User models that act outside their scope** (D-C3-4, by decision). In a run
  where some GNC model acts on fewer than every spacecraft, a model's output
  hooks and levels are no longer called for spacecraft outside its scope, so
  any output it gave there is lost: a `CoupledSpacecraft` model's pushes on its
  partners included. Runs where every model acts on every spacecraft call every
  hook as before. The migration page lists the hooks, and the advisory
  `outputs_in_scope` check reports such a model.
- **Where `outputs_in_scope` cannot look.** It is skipped, with the reason, for
  a model that acts on every spacecraft of its fixture, and for one whose run
  or hooks fail on the copy of the spacecraft the check adds to a
  one-spacecraft fixture, as a model sized for one spacecraft does. Such a model
  is checked on a fixture of its own with a spacecraft outside its scope.
- **Thruster columns are sized before the run** (F8, P3-2). A model that returns
  `control_thruster_levels` for a spacecraft outside its scope still creates
  that spacecraft's columns, which then hold zeros, where 0.6 saved its levels.
- **Ensembles and GNC selections** (F8, P3-9). An ensemble does not refuse a
  configuration-level GNC model with a `SpacecraftSelection` yet:
  `ids=[2]` fails in the members without spacecraft id 2, and `positions=[1]`
  acts on every member, as `BoundSpacecraft((1,))` does on main. C-3d's
  ensemble refusal (D-C3-9) must cover selections and land in 0.7.0 with this
  PR.
- **Scope changes stop the run** (D-C3-2). A model, or a linked producer, that
  changed a scope during a run ran in 0.6 and is refused in 0.7.0. No built-in
  does this. A periodic tick checks the scope it already reads (once per tick,
  twice for a linked consumer, as on #477). The new reads are one per model at
  every run start, and one per accepted step for each event-driven control
  model; an accessor with observable state sees those calls.
- **The event-driven check runs once per accepted step.** An event-driven
  model that changes its scope and restores it within one step is not refused.
  Its hooks follow the run's scope in that step all the same, as they do
  everywhere: the check reports a change, and the run's scopes decide which hooks
  run.
- **One more discrete callback** in runs with an event-driven control model
  (the burn scheduler's). Its condition never fires. It counts toward the limit
  #482 sets for the callback tuple.
- **A selection's `where` is called once per spacecraft at each run start**,
  in a checkpointed run too (F2). A resumed run calls it at its own start, and a
  selection that resolves to other positions there is refused, as #476 refuses
  any scope that differs from the checkpoint's.
- **Parameters built by hand** without the run's scopes (F6) call every model
  for every spacecraft, as in 0.6.
- **The two right-hand-side loops** (F5) must stay the same statement for
  statement. A comment says so, the test with the member lists on and off
  compares them, and the fingerprints against main catch a change to both.
- **Text conflicts** on `docs/src/user/upgrading.md` with #489, which adds to the
  top of the page too; the later resolves it, keeping 0.7.0 above 0.6.1. #490
  conflicts with main itself there, and there are none with #500. Main has since
  gained #483 (0f03bbfce), which merges with this PR without conflicts. Against
  main this PR still changes 10 lines of `execution.jl`, all in
  `_start_run_models!`, and none of `resume_checkpoint.jl`.
- **Not run locally:** `builtin_conformance_tests` with the EDG companion, the
  EDG tests under `test/gnc/aerobraking`, the examples smoke and the whole unit
  tree in its own runner, and the coverage shards, which build native GRAM.
  Hosted CI runs all of them.
