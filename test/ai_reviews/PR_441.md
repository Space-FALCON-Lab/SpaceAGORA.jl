## Findings

No P1 or P2 findings. Points a reviewer should check:

- Medium, the checkpoint table must not over-claim. Each "refused" entry corresponds
  to an `ArgumentError` in the source on the base:
  - the EDG lifecycle's `_edg_preflight`, which serves both guidance and control;
  - `AlgorithmGuidance`'s preflight;
  - the RPO capability check with `checkpoint=true` for a planner without `restart`;
  - `run_mission`;
  - the external-propagation setup;
  - the GRAM density perturbation mode on resume;
  - the model-state checks in `resume_checkpoint.jl`, for a missing restore method
    and for a mismatched configuration;
  - the callback snapshot of #438, for a run with firing-dynamics thrusters resumed
    without their firing state (a version 1 or missing snapshot) and for a moved or
    changed thruster.

  "Outside the guarantee" lists what is neither refused nor saved:
  - the orbit counter: `ODEParams.orbit_counter` starts at one in every run,
    including a resumed one, and is not in the checkpoint;
  - callbacks from `gnc_callbacks`: built once per run and reused across
    segments, with no state of their own saved;
  - the `:multirate` mode's periodic ticks, which repeat because its sub-solves
    revisit intervals, with or without checkpoints;
  - solver modes other than `:tsit5`, `:dp8` and `:gravity_backbone_split`: the
    resume tests (articulated, sensors, power budget, interlinks, periodic ticks)
    use the first two, and two persistence testsets resume translational
    `:gravity_backbone_split` runs;
  - a spacecraft already inactive at a resume: a model other than the burn
    scheduler starts from its restored command (the residual risk in the record
    of #437, the burn-edge fix). The page qualifies it: with `skip_inactive`
    `true` and a release method that clears the command, a nonzero command can
    stay visible until the first tick; the default `release_command!` does not
    clear it, and a model with `skip_inactive` `false` keeps ticking. The
    right-hand side ignores that spacecraft meanwhile.
- Medium, the periodic-tick entry describes #440 (open, head `84336fc63`), not the
  base: a tick and a boundary that differ only by rounding count as one time; a
  checkpoint records the due ticks not yet taken, also at an early stop, and the
  resumed run takes them first, once; a 0.4.0 checkpoint written just before a tick
  resumes with that tick taken at the resumed run's start. This PR merges after
  #440 (Residual Risk).
- Low, the "supported" row repeats Simulation Outputs ("Checkpointing", as #438
  updates it for thrusters with firing dynamics) and Extensibility ("Run state in
  checkpoint files") and links them; it adds no claim that those pages do not
  make. User-defined actuator kinds have no checkpoint hook (#438's record), so
  their mutable state is listed as outside the guarantee.
- Low, the mismatch refusal is stated by recorded field: each sensor's short type
  name and position, and each model's when a model or sensor saves state; the
  batteries, faults, hinges and gimbals; each
  firing-dynamics thruster's mounting place (its position in the mounting order,
  its link's position and its position among that link's actuators) and its
  `max_thrust`, `cutoff_frequency`, `min_firing_time`, `level_on` and `level_off`,
  as `_callback_checkpoint_configuration` records them on the base; and the
  interlinks. The page says a change outside those fields is not detected.
- Low, the custom-callback duties are guidance for authors, not a new check. The
  inactive duty follows the model's declared `skip_inactive` policy. The
  engine adds `gnc_callbacks` results as they are (`get_control_callbacks`), so
  the page cannot promise more.
- Low, the alias section is placed at the end of the migration page, so it does not
  overlap #421's "Deprecated in 0.5.0" insertion; `git merge-tree` with #421's head
  merges the page cleanly.
- Note, `docs/contributing/gnc_ownership.md` was checked and needs no change after
  #421: it describes one RPO integration path and calls `RPOGuidanceModel` removed.

Review fixes, 2026-10-20, from two review threads on the checkpoint table:

- "Qualify model-kind mismatch detection": `_model_kinds` records
  `nameof(typeof(m))` for the navigation, guidance and control models and the
  sensors, and the callback snapshot records sensors the same way, so a same-named
  type from another module, or another parametrization of the same type, gives
  the same configuration and is not refused. The table's refused row and
  Extensibility's "Run state in checkpoint files" now say the models and sensors
  are compared by short type name and position, and what that does not tell apart.
  The table also says the models are recorded only when a model or sensor saves
  state with `checkpoint_state`: `_model_checkpoint_state` writes no snapshot
  otherwise. Simulation Outputs' "Checkpointing" makes no claim about kinds (it
  says "a different configuration of them") and is unchanged. The checkpoint
  identity is unchanged.
- "Include the tested gravity-backbone resume mode":
  `test/suites/03_persistence_units_and_rotational_tests.jl` resumes
  `:gravity_backbone_split` runs in "Gravity Backbone Checkpoint Resume + Save
  Fields" and "Gravity Backbone Kick Checkpoint Resume Parity", both with
  `orientation_sim=false`. The table now lists the mode with `:tsit5` and `:dp8`
  as tested, and says its tests resume translational runs: the mode integrates no
  attitude and refuses guidance, navigation and control models, mounted sensors,
  batteries and control moment gyros (`_gravity_backbone_reject_reason`,
  `_build_typed_solver_problem`).
