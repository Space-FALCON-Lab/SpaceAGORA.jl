# PR328 review: SolverConfig rejects unknown solver settings

## Scope

Review of the `solver-config-validation` branch against `main` at `980b35eda`: `git diff main solver-config-validation`. One commit. `SolverConfig` validates its solver names, counts and step sizes when it is built; the environment parsers check against the same name lists; `:symplectic` is refused with a pointer to `:gravity_backbone_split`; the unreachable `:symplectic` solver-policy branch is removed; the final Tsit5 branch runs only for `:tsit5`; the non-strict environment fallback warns.

Authorship disclosure: this record was drafted by the author of the PR. It lists what the author checked and what the independent reviewer must verify; it does not replace that review.

- `src/orchestration/simulation/config/solver_settings.jl`: the accepted-name tuples `_SOLVER_MODES`, `_SPLIT_IMEX_SOLVERS`, `_MULTIRATE_SOLVERS`; the shared `:symplectic` refusal text; `_solver_name_list`, `_check_solver_name`, `_check_positive`; an inner positional constructor that builds with `new` (field conversion unchanged) and then validates; the docstring lists the accepted values and states that `symplectic_dt_s` has no effect.

## Findings

Author's notes for the reviewer (no P1 or P2 known to the author):

- Low, behaviour change by design: `simulation_engine_config_from_env()` with the default `solver_strict=false` and `SPACEAGORA_SOLVER_MODE=symplectic` used to return a `:symplectic` configuration (a run under it then failed inside `run_simulation`); it now warns and returns `:tsit5`, like any other malformed value. The PR text puts the strict-by-default option to the PI.
- Low, compatibility: `symplectic_dt_s` and `SPACEAGORA_SYMPLECTIC_DT_S` are kept, validated and unused.
- Low, pre-existing, not changed: `auto_stiff_switch_max` is clamped to at least 1 on the environment path and passed through unchanged on the typed path.
- Low, pre-existing, not changed: the solver-mode lists in the articulated, compliant and external-propagation checks (and their messages naming "symplectic routes"), the `:symplectic` entry in `get_initial_force_output_callback`'s skip tuple, and the mission-segment list still name their own supported modes; none can now receive `:symplectic`.

Reviewer to verify:

- Every `SolverConfig` construction in `src/`, `test/`, `examples/`, `scripts/` and `benchmarks/` uses accepted values (the author's search found no construction with `:symplectic`, a non-positive count or a non-positive step outside the new tests).
- The parser rewrite: every spelling the `main` parsers accepted parses to the same symbol except `symplectic`, `kahanli8` and `verlet` (the author compared the old and new functions over 53 strings and three parsers, 159 cases, with only those spellings differing, case variants included).
- `:symplectic` was unreachable on `main` from any public entry: `_build_typed_solver_problem` returns a first-order `ODEProblem` for it, and `_solve_with_solver_policy` required a second-order problem; the only callers of `_solve_with_solver_policy` with a `SecondOrderODEProblem` are the gravity-backbone run path and tests.
- No code path constructs `SolverConfig` without the constructor in a way that would now skip validation and matter (deserialization of an already valid value is the only one the author found).
- The new tests fail on `main` (for example, `SolverConfig(solver_mode=:tsit)` constructs there).

## P1 Assessment

No P1 findings known to the author. Valid typed configurations construct exactly as before (the inner constructor converts with `new`, as the default constructor did); valid environment spellings parse to the same values; `run_simulation` reading the environment itself was already strict. Only invalid inputs change behaviour, and each now fails with a message naming the accepted values, apart from the non-strict environment path, which warns and keeps its fallback.
