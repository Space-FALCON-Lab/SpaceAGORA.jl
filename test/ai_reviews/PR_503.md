# Review record: PR 503: write results in a long layout on request

## Scope

Review of the SpaceAGORA `results-long-layout` branch. The follow-up integration
preserves the unpublished follow-ups through 9aa36d261 and includes #509 at
a402a29f6, incorporating main 59c264b07. This is C-5a of the constellations program's large-outputs step, built to the accepted C-5 design decisions:

- D-C5-1 to D-C5-7: the switch, two layouts, the long schema, files and manifest, row order, in memory, wide-only readers;
- D-C5-10: correcting the docs of `num_steps_to_save`.

C-4b will build its members table with this builder (D-C5-13).

What changes:

- **The switch.** `SimulationSettings.results_layout = :wide | :long`, `:wide` by default; any other value is refused when the run starts.
- **The long layout** writes a spacecraft table and a run table.
  - **The spacecraft table** has one row per spacecraft and saved time: `spacecraft`, `spacecraft_id`, `plane`, `slot` and `time`, then the per-spacecraft fields without `sc<i>_`.
  - **The run table** holds the run-wide fields.
  - **Files.** `simulation_results_spacecraft.*` and `simulation_results_run.*`, with a manifest at `schema_version` "2" and `layout` "long". No wide file is written.
- **In memory.** `SimulationResults` gains a `run_table` field; its four-argument constructor is kept. `run_table` and `long_table` are exported.
- **The viewer** reads a long run through views of the wide columns. `run_monte_carlo_visualization` refuses a long run.
- **The wide layout** is today's code path, byte for byte.

## Findings

No open P1 or P2 findings in the reviewed repair.

- **Follow-up P2, fixed:** the previous all-missing heuristic also removed real
  channels with no available measurements. The builder and wide-to-long conversion
  now record each flattened column's owning spacecraft as table metadata, saved
  in Arrow schema metadata. The viewer uses that ownership, validates it, and keeps
  present missing-valued channels. Older draft files without metadata retain the
  documented ambiguous fallback. The wide writer and its helpers are unchanged.

- **The in-house review (2026-10-23): Not clear.** It found one P1 and four P3s here. This round:
  - **P1-1, fixed.** A per-spacecraft field whose values differ in shape between spacecraft lost columns in the long layout, or failed the final save after the whole solve. The built-in cases are the thruster and actuator levels of a spacecraft with thrusters beside one without, and a user field could do the same. The long builder took the field's columns from spacecraft 1. It now flattens each spacecraft's series on its own, as the wide table does, and takes their union in first-seen order, with `missing` where a spacecraft has none. `long_table` follows the same rule, and the viewer's view of a long run leaves out a spacecraft's all-`missing` columns.
  - **P3-1, fixed:** the example runner reads the long layout's spacecraft CSV.
  - **P3-2, documented:** the long CSVs do not keep a concurrent writer's file, which the wide CSV does; the outputs page says so.
  - **P3-3:** the merge with #501 (I-6b) is for whichever lands second. The hand-over notes now include C-5c's early return and manifest writers.
  - **P3-4:** this record now names main 0f03bbfce, which is merged in.
- **The recheck (2026-10-23): Clear,** with one new P3:
  - **N2, fixed.** The wide view's change (a spacecraft's all-`missing` column left out) had no test that failed without it: the thruster block of the viewer counts thrusters from the scene, so the extra columns never reach it. A user channel does: the viewer offers one only when every spacecraft has its column. The ragged-field test now exports both runs' viewer payloads with channels for columns one spacecraft lacks and one both have. The long run offers the same channels as the wide one, and its frames are the same; without the change it offers the channels the wide run omits.

- **Design choices for review.**
  - **The viewer reads a long run through views.** The wide columns are strided views of the memory-mapped spacecraft table, rather than a pivot of the kept rows. The payload code is unchanged and reads only the rows it keeps, so the payload equals the wide run's. Rows in another order are read by their key, through a permutation; a table missing a row is refused.
  - **The scene struct gains a field.** The sidecar's layout has to reach the readers. A ten-argument constructor keeps the existing positional constructions working, and a wide sidecar is byte-identical.
  - **A long run without run-wide fields removes the run table files** an earlier long run left under the same prefix, since the manifest no longer names them.
  - **Wide files left by an earlier wide run are not removed.** The outputs page says so; the manifest names the current files.
  - **Telemetry verification needs no refusal.** It runs its cases with settings of its own, which are wide.
- **Not in this PR.** T6, C-4b's members table on this builder, comes with C-4b.

## Residual Risk

- **Older draft files and CSV.** Older long files without ownership metadata cannot
  distinguish absent fields from all-missing measurements. CSV alone does not
  retain the metadata; the documented fallback treats all-missing columns as absent.
- **Streaming integration.** #505 must preserve ownership metadata through stream
  creation, resume, finalization and returned tables; this repair alone does not
  qualify that dependent branch.
- **Ensembles.** The long builder lays out a single run's spacecraft. C-4b will reuse it for members, with `spacecraft` set to the member's position in the constellation; that is C-4b's change and test (T6).
- **Readers outside `src`** (scripts, studies) read the wide files. They work as before in the default layout. A long run must be read with the long names, or turned back with the views the viewer uses. The example runner in `src` reads both layouts.
- **Concurrent writers.** Two runs writing the long CSVs into one folder keep the last one's files; the wide CSV keeps both. The outputs page says so.
- **Memory.** The long layout writes the same values in fewer columns. It does not lower the in-run peak, since the saved rows are kept until the run ends; that is C-5c's streaming.
- **The public API page** grows by the two new docstrings, within its size limit.
