# Review record: PR 482: discrete callbacks in a vector when there are many

## Scope

Review of the SpaceAGORA `callback-vectors` branch against main 2088b4408
(v0.5.1, with #465, #468, #469 and #470). It is C-3c of the constellations
track:
- plan: the constellations and interlinks plan (2026-10-19), item C-3;
- design: the C-3 "GNC that scales" design (2026-10-21);
- decisions D-C3-1 to D-C3-11, accepted by Giusy as recommended (2026-10-21).
  C-3c carries D-C3-5 (A). Its limit follows Giusy's later decision
  (2026-10-21): the largest number of discrete callbacks at which the tuple is
  still no slower than the vector on whole engine runs.

What it does:
- Beyond 32 discrete callbacks, `run_simulation` hands the solver its discrete
  callbacks in a vector, in the same order. The continuous callbacks stay a
  tuple. Up to 32, the callback set is the run's own object, unchanged.
- It is applied last, after the interlink scheduler's wrapper, before the
  problem is built.

Why: the solver library applies a tuple of discrete callbacks by recursion over
it. Past 32 entries, where Base stops specializing on tuples, the recursion is no
longer compiled away, so each accepted step costs time and allocation that grow
with the square of the number of callbacks, and the solve's type inference grows
with it. A vector is applied
one callback at a time through one dynamic call each. A run with one periodic GNC
model per spacecraft has one discrete callback per model.

Rule: every run gives the same bits as before: final state, saved states and
saved times.

- **Where and when.** `_solver_callback_set` runs once in `run_simulation`, after
  every wrapper (the interlink scheduler's included), because building a
  `CallbackSet` from another flattens it back into tuples. Two cases return the
  run's own `CallbackSet` object, so today's code path runs unchanged:
  - discrete callbacks already in a vector (the solver library's erased form for
    its automatically specialized problems);
  - at most 32 discrete callbacks.
- **Beyond the limit.** It returns `CallbackSet(continuous, collect(Any, discrete))`:
  the same discrete callbacks in the same order, beside the unchanged continuous
  tuple. So event location keeps its code path. The record's forced-vector runs
  give the same bits.
- **The limit, 32.** Giusy's rule (2026-10-21): the largest count at which the
  tuple is still no slower than the vector on the engine. The builder's engine
  sweep over every count from 20 to 36 puts it at 32, the value D-C3-5 accepted.
  The numbers stay private. `_DISCRETE_CALLBACK_TUPLE_LIMIT` is a `Ref` so tests
  can force either container. Only tests change it.
- **What it leaves alone.** The `ODEFunction` specialization, everything under
  `src/orchestration/parallel/`, and the cached-integrator path. The tests check
  that a cached integrator is reused with the vector.
- **History.** Four commits on main 2088b4408, no trailers. It merges cleanly with
  main bfa32f6a4 and with the open #476 to #481.

## Findings

- **F1 (which runs it reaches).** Only a fully specialized problem keeps its
  callbacks in a tuple. The engine builds one only with a block-diagonal Jacobian
  prototype: a run of several spacecraft without cross-spacecraft coupling, in a
  solver mode other than `gravity_backbone_split` (`run_simulation`, where
  `jac_prototype` is set). The solver library erases the callbacks of its
  automatically specialized problems, every other run, into vectors of both
  kinds; the existing `_callbacks_for_cached_integrator` comment already
  describes this. So C-3c changes the container only for uncoupled
  multi-spacecraft runs with more than 32 discrete callbacks, which is the
  constellation case without interlinks. The comment on the limit says so.
- **F2 (an equivalent mutant).** Applying `_solver_callback_set` before the
  interlink wrapper instead of after it changes nothing today. A run with an
  interlink model counts as cross-spacecraft coupled
  (`_config_has_cross_satellite_coupling`), so it has no Jacobian prototype, and
  the solver library holds both kinds of callback in vectors at either limit. The
  container test now checks exactly that, at both limits, so a library change
  that stopped erasing them would fail it. The call stays last, so a later
  wrapper cannot rebuild the tuple.
- **F3 (code that rebuilds or reuses the set).** Three places read the
  containers:
  - the EDG heat observer (`edg_heat_observer.jl`) wraps every callback and
    splats them back into a `CallbackSet`. It runs inside `get_callbacks`, before
    `_solver_callback_set`, so it never sees the vector;
  - the GRAM density perturbation (`gram_density_perturbation.jl`) only iterates
    the discrete callbacks;
  - `_callbacks_for_cached_integrator` rebuilds a set as two vectors only when the
    cached integrator holds two vectors. With the mixed set it returns the run's
    set, whose type matches the cached integrator's, and the integrator is
    reused (tested, mutant M6).
- **F4 (the limit).** D-C3-5 set the limit at 32. Giusy then decided
  (2026-10-21) that the data chooses it: the largest number of discrete
  callbacks at which the tuple is still no slower than the vector on whole
  engine runs, from a sweep over 20 to 36. The branch first used 24, read off a
  coarse sweep that had no point between 25 and 33. Sweeps at every count, from
  18 to 40 on the solver alone and from 20 to 36 on the engine, put the change
  exactly between 32 and 33, which is Base's tuple-specialization limit:
  - on the solver alone, the tuple is the cheaper container per step at every
    count up to 32, and from 33 its per-step time and allocation jump;
  - on whole engine runs of an uncoupled constellation with one bound
    controller per spacecraft, at every count from 20 to 36 (the containers
    alternating, in three passes, one of them with paired rounds at 28 to 34),
    the tuple is no slower at any count up to 32, because the right-hand side
    dominates. From 33 the vector is faster and allocates less, in every pass;
  - so 32 is the largest count at which the tuple is no slower, and the limit
    is 32. The measurements are private.
- **What it leaves alone.** The problem and its `ODEFunction` are built as
  before, fully specialized where they were. Only the container of the discrete
  callbacks changes, and only past the limit. Up to the limit,
  `_solver_callback_set` returns the run's own set (`===`, tested), so the solver
  receives the same type and runs the same code as on main. Nothing under
  `src/orchestration/parallel/` changes: not the RHS plan, effector threading,
  the parallel policy or the routing sweep.
- No P1 or P2 finding.

## Residual Risk

- **The limit rests on today's compiler and solver library** (F4). If a later
  Julia or solver release moves the point where the tuple stops being compiled
  away, the limit is one constant to move, and the bits are the same with either
  container.
- **Runs it does not reach** (F1): interlink constellations and runs with
  coupling effectors already hold their callbacks in vectors, and a run's number
  of callbacks still grows with its models. Fewer callbacks is D-C3-5's
  alternative B, not in this PR.
- **The solver library's erasure.** F1 and F2 rest on the library erasing the
  callbacks of automatically specialized problems. If a later version stops
  doing so, interlink runs would hold tuples again. `_solver_callback_set` would
  then apply to them as well, because it runs last, and the container test's
  interlink check would fail and show the change.
- **Code outside `src` that reads `integrator.opts.callback.discrete_callbacks`**
  and assumes a tuple sees a vector in a run past the limit. Nothing in `src`
  or `ext` does.
- **The solver library's two paths for the mixed set.** At each step it applies
  the discrete callbacks through its loop over a vector, the one it uses for
  automatically specialized problems. When it initializes and finalizes the
  callbacks, once per solve and so at each segment start of a checkpointed run,
  it takes the mixed set (continuous callbacks in a tuple, discrete ones in a
  vector) through its generic recursion over all of them instead. That makes the
  same calls in the same order, so the bits are the same. A private scale probe
  at several hundred discrete callbacks, on the solver alone and in a checkpointed
  engine run, found no compile or inference blow-up there. Its time grows with the
  square of the number of callbacks, and stays small next to a run of that size.
- **Assembling many callbacks.** The engine still builds the run's callback set
  as a tuple, as main does, before this PR moves its discrete callbacks into a
  vector. At several hundred callbacks that construction's compile time grows
  quickly; the same probe puts nearly all of a first run's extra time there, and
  none in the vector. Building the vector from the start is a follow-up.
- **Not run locally:** the whole unit tree in its own runner, the conformance and
  aerobraking tests with the EDG companion, the examples smoke, and the threaded
  coverage probe, which needs GRAM data this checkout does not have. Hosted CI
  runs all of them.
