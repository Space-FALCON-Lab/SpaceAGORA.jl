# PR review: control output hooks (control_wrench, control_propellant_rate, control_wheel_torque)

## Scope

Review of PR 364, the `control-output-hooks` branch, one commit (f7bee87c7) on `main`
4d0206132; review `git diff 4d0206132 control-output-hooks`. It is H3 of the hook-signature
program (design v1.2.1, section 5 row 7 and sections 4.2 to 4.5), with plain
`StateSample` queries.

The PR:

- adds `control_wrench`, `control_propellant_rate` (positive: the propellant
  used) and `control_wheel_torque`, all `(model, x::StateSample, p, t)`;
- routes each through an engine bridge that calls the new hook when the
  effector's type has one, and the type's old method otherwise;
- deprecates `calcControlForceTorque`, `calcControlMassFlowRate` and
  `calcReactionWheelTorque`, with warnings before the run and on direct calls;
- migrates the built-in effectors, the template, three examples, the docs and
  the tests.

Authorship disclosure: the author of the PR drafted this record. It lists what the
author checked and what the independent reviewer must verify; it does not replace
that review.

## Findings

Author's notes for the reviewer (no P1 or P2 known to the author):

- Low: the bridges and the pre-run check query
  `hasmethod(new, Tuple{T, StateSample, typeof(p), Float64})`, as Giusy decided.
  - A user method typed `x::StateSample{MySpacecraft}` is not found.
  - The pre-run check then stops the run, and says that the effector has
    methods of `control_wrench` but none accepts the run's arguments.
  - The new docstrings say that a method typed `x::StateSample`, or untyped,
    is the one the dynamics call.
- Low: the built-ins' new hooks type `p::ODEParams`, as their old methods did
  (the momentum manager leaves `p` untyped, as before).
  - A direct old-name call that passes another `p`, such as `nothing`, does not
    reach the new hook.
  - `calcControlForceTorque` then raises a `MethodError` naming
    `control_wrench`, and the other two return their defaults.
- Low: as in #354, the direct-call warning is on the call path. A wrapper
  effector that calls an old name inside the right-hand side pays a log lookup
  per call after the first warning. The pre-run check warns only about types
  with methods of their own.
- Note: R-13 (an optional warning for a negative propellant rate) is not
  adopted. It would put a log call in the right-hand side, which R-2(d) rules
  out, and the pre-run check cannot see the sign. The docstrings, the guide's
  old-to-new table and the twin test lead with the sign.
- Note: the hook call inside each bridge carries a call-site `@noinline`
  (R-2(c)), so the new hook is compiled on its own as a run-time-dispatched hook
  is.
- Note: the state sample reads the mass by index (`x[7]`), as for the dynamic
  effectors. The engine always passes its own state view. A test that calls
  the accumulator with another layout gets an arbitrary mass in the sample; no
  built-in hook reads it.

Reviewer to verify:

- **No warning is reachable from the right-hand side or a callback.** A
  bridge's old branch runs only for a type without the new hook. A fallback
  warns only for a type with it, and both use the same query on the same
  argument types. A type's own old method is dispatched to directly, without a
  warning.
- **The accumulation is bitwise.** Check three things:
  - `mass_rate -= c` with `c = -r` equals `mass_rate += r`, and the accumulator
    never holds `-0.0` (design section 4.3);
  - the mounted return's flip, together with the subtraction;
  - RPO's per-jet sum: `-(((0 - r1) - r2) ...)` equals `((0 + r1) + r2) ...`
    under round-to-nearest.
- **The pre-run check** for each case: neither hook (refused, message names
  `control_wrench`), old only (accepted, warns), new only (accepted, silent),
  both (accepted, "never used"), and `:mounted` (no wrench hook needed).
- **The gate's sanctioned fallbacks:** four untyped arguments for
  `calcForceTorque` in `effector_sampling.jl`, five for each control name in
  `control_hook_bridges.jl`. A zero-argument definition must not count as
  sanctioned; the code compares against `nothing`.
- **Under `--depwarn=error`,** no test or probe makes a direct old-name call on
  an effector that implements the new hook, other than the compatibility file's
  child process, which expects the error.
