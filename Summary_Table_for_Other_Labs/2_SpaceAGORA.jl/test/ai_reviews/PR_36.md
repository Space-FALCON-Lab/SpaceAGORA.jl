# AI Review — PR #36: Re-initialize solver cache when resolved save options change

## Scope
Review of the SolverIntegratorCache staleness fix flagged by Codex on PR #31:
the cached-integrator reuse branch in `_solve_with_explicit_solver` ignored the
freshly resolved `save_everystep`/`save_on`/`save_start`/`save_end` values,
which DiffEq bakes into the integrator at `init`. Reviewed for correctness of
the reuse guard, coverage of both mixed-usage directions, cache-churn behavior
on matching options, and interaction with the `needs_full_solution` gating and
`SPACEAGORA_SOLVER_SAVE_*` env overrides introduced in PR #31.

## Changed Files
- `src/simulation/engine/solver_policy.jl`

## Findings
- P2 (fixed in this PR): a cache first initialized by a no-output run
  (`return_solution=false`, `results=false` → `save_on=false`) served its
  endpoints-only integrator to a later `return_solution=true` call, silently
  returning a two-point solution. Real usage pattern: the runtime-analysis
  benchmark harness shares one cache across warmup and measured batches.
- P3 (accepted): a flag flip on a shared cache re-initializes the integrator,
  so alternating no-output/full-solution calls pay init cost each time. This
  is correct-by-construction; callers wanting zero churn should use one cache
  per output mode.
- No other findings. Env-override semantics are unaffected: options are
  resolved before the guard, so explicit `SPACEAGORA_SOLVER_SAVE_*` settings
  participate in the match exactly like derived defaults.

Unresolved P1: No

## Tests Added/Updated
- `test/suites/04_solver_env_and_regression_tests.jl`: new testset
  "Solver Cache Re-Initializes When Save Options Change" covering the exact
  review scenario (no-output seed → full-solution reuse returns the full
  trajectory and re-inits), same-options reuse identity (no churn), and the
  downgrade direction (full-solution seed → no-output re-inits so campaign
  runs do not silently pay full-trajectory storage).
- Standalone smoke of the same three directions run against the working tree.

## Residual Risk
- The guard compares the four save options only; other init-baked options
  (tolerances, dtmax, maxiters) were already assumed stable per cache by the
  pre-existing design and are unchanged by this PR. Follow-up only if a caller
  ever varies those across a shared cache.
