# Review record: PR 442: composite value parameters in the interlink checkpoint identity

## Scope

Review of the SpaceAGORA `interlink-composite-identity` branch against main
(08b5a0e8e), a follow-up to #434.

The finding: a composite bits value used as a link kind's type parameter (a
`ComplexF64`) was recorded as `(type, value)` and compared with its own
`isequal`. That merges distinct link types whose parameter differs only in a NaN
payload. It comes from the fixed-head review of 2026-10-20
(`_Command_Center/SpaceAGORA_Release_050_Fix_Reviews_2026-10-20.md`, "merged #434
still conflates some composite value parameters", P2).

One commit (5086ca79c).

Authorship disclosure: this record was drafted by the author of the PR. The
plan assigns behaviour PRs an independent reviewer (the PI, or the second
reviewer when available); this record does not replace that review.

Independent review: the coordinator reviewed PR 442 at `5086ca79c` under Giusy's
delegation on 2026-10-20. It was a read-only review of the diff. Checked:

- **Which values change.** Only the generic `_interlink_kind_parameter` method
  changes, and only for `isbitstype` values that are not primitive. Primitive
  values (integers, `Bool`, `Char`) stay `(type, value)`; `IEEEFloat`, `Tuple`,
  `Union`, `Type` and `DataType` keep their more specific methods, so a tuple
  never reaches the composite branch.
- **Recursion ends.** Each field goes back through `_interlink_kind_parameter`.
  A bits value holds no references, so the fields are finite and the recursion
  stops at primitives and floats.
- **Exactness.** The composite's type identity carries its parameters (a
  `NamedTuple`'s names, a `Complex`'s element type), and each float field its
  bits, so neither `isequal` on the composite nor padding bytes decide.
- **Version 1.** The version 1 mapping is untouched, so 0.4.0 checkpoints still
  resume; only the unreleased version 2 identity changes.
- **The correction to `PR_434.md`.** The new sentence is appended to its
  paragraph in the same commit as this record.
- No trailer on the commit, and `## Changed Files` lists the one `src` file.

The coordinator did not rerun the tests; the author's evidence is under Tests
Added/Updated, and CI runs them.

## Findings

No P1 or P2 findings.

Points a reviewer should check:

- **Method order.** `DataType`, `Union`, `Type`, `Tuple` and `IEEEFloat`
  parameters keep their own methods. Only the generic method changes, and only
  for composite bits values. A singleton value (a struct with no fields) becomes
  `(type, fields=())`, which compares as its `(type, value)` did.
- **Recursion.** A field that is itself a composite, a tuple or a float is
  recorded by the same methods, so `Complex{Float64}` fields carry bits. Bits
  values hold no references, so the recursion ends.
- **Version 1.** The mapping builds the built-in laser kind's identity (no
  parameters), so 0.4.0 checkpoints resume as before. Only the version 2
  identity, unreleased, changes.
- **Correction to PR_434.md.** That record said the comparison "is still
  `isequal` on the whole identity, which the recorded types make exact". A dated
  correction now follows it: exact for scalar value parameters only, until this
  PR records composites field by field.
