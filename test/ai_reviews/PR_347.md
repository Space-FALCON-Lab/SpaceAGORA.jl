(merge base `fc64458c0`): `git diff main...gnc-algorithm-lifecycle`. Commits:

- `GNCAlgorithms` gains the shared lifecycle machinery: stream words, the

`planner_lifecycle.jl` until PR 7.

## Findings

Resolved in `ff3aecd54` and `61ca1191d`. Each of the three P2 findings from the
review of `29b62929d` now has assertions that fail on `29b62929d`:

- **P2, the runtime aliased the caller's seed words.** For a `Vector{UInt32}`
  input, `AlgorithmRuntime` stored the caller's vector. A caller that reused the
  vector changed `runtime.stream_words`, though not the stream already seeded. RPO
  never hit this, because `gnc_stream_words` returns `UInt64` words and the
  conversion copied them. The runtime now stores and seeds from one owned `UInt32`
  copy.
- **P2, the record hook ran inside the validation-to-install window.**
  `installed_record` received the very product and request that went on to
  `install!` and into the runtime (`installed_request` is the retained request that
  `is_current` reads). The fix has three parts:
  - The driver now resolves the link and copies the product before validation.
  - Between validation and installation only `install!` and the runtime update run.
  - `installed_record` runs afterwards, on copies of the request, result,
    validation and product.

  On the rejection paths, `rejected_record` and `fallback_product` also receive
  copies. On `:install_fallback` the rejection is recorded before the fallback is
  resolved and installed.
- **P2, a `GNCAlgorithmError` thrown by algorithm code escaped unwrapped.** The
  driver rethrew any `GNCAlgorithmError`, so one thrown by a third-party `propose!`,
  `propose_revision!` or family hook skipped `exception_reason` and the binding's
  failure record. Now only the failure raised by this request's
  `fail_algorithm_request!` passes through unwrapped. Every other error becomes this
  binding's failure with `exception_reason`, and the original is kept as the cause.
  No global state is used. This supersedes the earlier low note that "the exception
  filter is wider".

Resolved in `6f0d506b9`. One P2 finding came from the independent review of
`c76285f6c`, and its assertions fail on `c76285f6c`:

- **P2, the algorithm and its family were resolved outside the failure boundary.**
  `run_algorithm_request!` advanced the request counter, then called
  `bound_algorithm` and `algorithm_family` before its protected block. An error
  from either, ordinary or a foreign `GNCAlgorithmError`, escaped unwrapped, with no
  failure record and no `exception_reason`. Both calls now run inside the block.
  Such an error becomes this binding's failure with `exception_reason`, and the
  original is kept as the cause. The request still counts (the counter stays
  advanced), as on every other failure path, including a failing
  `build_algorithm_request`. The docstring says so.

Author's notes for the reviewer (no open P1 or P2 known to the author):

- **Low, semantics: one changed edge case.** On main, an RPO planner whose own code
  threw an `RPOPlanningError` saw it escape as is. It now fails as
  `:planner_exception` with the planner's error as the cause. In `src/` and
  `packages/`, only the binding's own failure function constructs an
  `RPOPlanningError`, so no built-in planner is affected. The RPO contract page
  states this.
- **Low, contract: `proposed_product` now runs before validation.** It runs on every
  proposal of the family's result type, so it must return, not throw, for one that
  validation will refuse. `AbstractAlgorithmResult` already describes the product
  as present only for candidates. The two existing methods read a field, and the
  docstring states the requirement.
- **Low, contract: `fail_algorithm_request!` must throw.** If a binding's failure
  function returns, the driver throws an `ArgumentError` naming the binding rather
  than continuing with a rejected result.
- **Low, API:** 14 more exported names under G-2. `install!` gains required
  keywords; it had no methods before this PR.
- **Note: stream-word types.**
  - `gnc_stream_words` returns the same vector type the RPO mapping always
    returned (`sum` of `UInt32` values widens).
  - The runtime converts the words to its own `Vector{UInt32}`, as `PlannerRuntime`
    stored them, and seeds `MersenneTwister` from that copy.
  - A check showed `MersenneTwister` gives the same stream for either element type.

Reviewer to verify:

- **The driver's order** (the test "Shared request driver" pins the calls into
  family and binding code as `propose`, `link`, `product`, `validate`, `install`,
  `record`):
  1. the counter advances; inside the protected block the algorithm and its
     family are resolved, the request is built, and its record is pushed before
     the capability check;
  2. the proposal receives `deepcopy(request)`, plus `deepcopy(runtime.product)` for
     a retime;
  3. the result is type-checked, then deep-copied;
  4. the link is resolved and the product deep-copied;
  5. the copy is validated against the retained request;
  6. `install!` and the runtime update follow, with nothing between validation and
     installation;
  7. the install record is built from copies and pushed last.

  On main the old `request_plan!` took the product after validation and built the
  record before installing. Both were trusted inline code there, not hooks. For RPO
  the result is identical: the product is a field read, the RPO `install!` copies
  the reference without changing it, and the RPO record copies its inputs. The
  parity probe confirms this.
- **Failure calls are unchanged for the built-in planners:**
  - the capability refusal fails without details;
  - the validation refusal fails with `(termination, diagnostics, validation)`;
  - exceptions fail with `:planner_exception`, the cause and the backtrace.

  A `GNCAlgorithmError` thrown by planner code now takes the exception path.
- **`GA.install!` for `RPOPlanBuffer` builds the same `RPOPlan`:**
  - copies of the reference arrays;
  - `cost=NaN`;
  - diagnostics `(request_id, validation, planner=deepcopy(diagnostics))`;
  - then `update_rpo_plan_buffer!`.
- **The controller-lookup scans are untouched,** as agreed for PR 7.

## Residual Risk

- External code that read `PlannerGuidance.runtime.reference` or
  `.last_planning_time` must use `.product` or `.last_request_time`. These are
  internal fields; `rpo_run_report` keeps its keys.
- An external RPO planner that throws its own `RPOPlanningError` now fails as
  `:planner_exception` with that error as the cause.
- A contributor's `proposed_product` that throws for a refused result now fails the
  request with `exception_reason` instead of the validation's reason.
