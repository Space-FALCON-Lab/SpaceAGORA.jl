# Review record: PR 491: keep a resumed run's earlier results rows

## Scope

Review of the SpaceAGORA `resumed-run-rows` branch against main (bfa32f6a4, after #472). It fixes a data-loss bug in resumed runs, for 0.6.0.

The bug: a run resumed from a checkpoint (`resume_from_checkpoint=true`) wrote and returned only the rows saved after the resume. It replaced the earlier run's results in the same `results_directory`, and a crash's partial results with them:

- the CSV;
- the feather;
- the manifest, whose `steps` counted only the new rows;
- the `return_results` table.

A resume from a checkpoint at the mission's end rewrote all three files with no rows.

What changes:

- **The rows are kept.**
  - A checkpointed run that saves results keeps its rows beside the checkpoint, in `simulation_checkpoint.results.bin`, and adds the new rows at each checkpoint.
  - The file is only appended to: a record can drop rows from the end of those before it.
  - The checkpoint's optional `results_rows` entry (version 1) records how much of that file is its own, and a token that the file's header also carries.
- **Resume.**
  - A resumed run takes the rows back, cuts the file back to its checkpoint's length, and builds its results as an uninterrupted run does.
  - A resume that solves nothing (its checkpoint is at or past the mission end) writes no files. It returns the rows up to its checkpoint, or an empty table when the checkpoint holds no usable rows, and reads no rows when it returns no table.
  - A checkpoint without usable rows resumes with a warning. Its results start at the resume and are written to `resumed_at_<t>s` inside `results_directory`, so the earlier files are kept; the returned configuration names that folder.
- **The results manifest** gains `first_time_s` and, for a resumed run, `resumed_from_s`.
- **Unchanged.** Runs without checkpoints, and checkpointed runs never resumed, write the same CSV and feather as before; their manifest gains only `first_time_s`.

- **The bug is real.** An in-house check on 2026-10-21 confirmed it: a resumed
  run kept only its post-resume rows and overwrote the earlier files, and a
  resume from a finished checkpoint rewrote them empty.
- **The storage design.** Rows are appended to one stream beside the checkpoint,
  and each checkpoint records the stream's length at its time. A resume reads
  exactly that length and cuts the stream back to it, so rows a crash wrote after
  the checkpoint are dropped. A short or unreadable stream reads as "no rows",
  which takes the fallback rather than mixing rows from two runs.
- **The fallback never overwrites.** A resume without usable rows (an older
  checkpoint, other save fields, another spacecraft count, a Julia version that
  cannot read the stream) writes to `resumed_at_<t>s` and warns, so the earlier
  files are kept. Since #476 a run with GNC models refuses an older checkpoint
  before this point, and the outputs page says so.
- **Compatibility.** The checkpoint schema stays 1: `results_rows` is optional,
  as the activity and scope entries are. The manifest gains two keys, and the
  readers that rewrite it keep unknown keys.
- **History.** Built on main `bfa32f6a4`, with `25355f3a9` and `60c117c9d` merged
  in as merges. The second merge keeps both `gnc_scopes` (#476) and this branch's
  `results_rows` at the five lines where they met. No trailers. It merges cleanly
  with #473, #479, #482 and #487. #478 and #486 meet it only in the migration

Found by hosted CI and by an outside review, and fixed. The in-house review of 01ac8b0a4 (2026-10-21) verdict was "Changes needed"; it found the design sound and reproduced each of these:

- **P1: hosted CI was red. Seven unit files asserted the old behavior.**
  - The first push left hosted CI red. Seven unit files outside the 16 run locally checked that a resumed run's table, or a resumed member's feather, starts at the resume:
    - an actuator stuck across checkpoints;
    - a compliant attachment;
    - an articulated chain;
    - interlink data and power;
    - a power budget that keeps shedding;
    - a Monte Carlo ensemble member.
  - Coverage shards 2, 4, 9, 12 and 13 failed on the same files, and suite 09 reported them.
  - There was no behavior problem: only those checks failed, and the ensemble members' resumed rows equal their first legs' bit for bit.
  - Why the first push missed them: the local unit runs covered only the checkpoint and results files, chosen by name. No search was made for other tests reading a resumed table. These seven read it inside feature tests (actuators, attachments, articulation, interlinks, power, ensembles) that were not run locally.
  - Each old check was also the test's only sign that the run resumed rather than started again; the final-state comparisons would pass after a restart too. Each test now checks two things a restart would fail:
    - the manifest records `resumed_from_s` at the resume time;
    - the rows before the resume equal the first leg's. Where ticks fall at the resume time, only the rows strictly before it are compared.

    Each also checks that the table starts at 0, and keeps its own checks on the rows from the resume on. Two checks that a table starting at 0 would make pass trivially were moved: the interlink data counter (now read at the resume time) and the power budget's shedding (now over the rows from the resume on).
  - A search of `test/`, `examples/`, `benchmarks/` and `scripts/`, of every file that resumes from a checkpoint, found no other reader of a resumed table, CSV or feather. It looked for reads of the first time or first row, `nrow` comparisons and CSV or feather reads. The other resume tests check the final state, the ticks, the interlink history or sensor samples. In `src`:
    - the conformance checks compare the solution;
    - the mission workflow refuses resume;
    - the ensemble export reads the member feather, which holds the whole run, as its scene timeline does.
- **P2: extending a finished run rewrote the rows file before the checkpoint that describes it existed.**
  - The retake of the restored last row (c6954222d) started the stream anew at the extension's first checkpoint.
  - If that checkpoint was then not written (a failed write, or a kill), the finished run's checkpoint no longer matched the stream. The next resume fell back to `resumed_at_2.0s`.
  - Fix: the stream stays append-only. The restored row is dropped by a `drop` in the next record, which the reader applies, and earlier records stay as they are.
  - A test makes the extension's first checkpoint fail (read-only checkpoint directory); a later resume holds the whole run.
- **P3: another run's stream of the same length was accepted silently.** The stream's header and each checkpoint's entry now carry the same token, made from the clock and the process, without drawing on a random stream. A mismatch takes the fallback with a warning. A test changes the entry's token.
- **P3: a failed extension's partial save replaced the finished run's CSV with one missing its last row.** The restored row is now dropped only when the first segment's own row at that time arrives. A test fails the extension's first segment and finds the CSV unchanged.
- **P3: wording.**
  - The gravity backbone keeps a rows file even when it neither writes nor returns results.
  - A no-solve resume without usable rows returns an empty table, and its warning now says so instead of naming a folder it never writes.
  - The plume page now says the cumulative mass column falls back to zero after the resume time, and the interlinks page that the table, unlike the history, holds the whole run.
  - The PR text and this record no longer say runs without checkpoints are unchanged (their manifest gains `first_time_s`), or that resumed manifests are equal (their `steps` and `first_time_s` are).
- **P3: the fallback's returned configuration named the original results directory.** It now names `resumed_at_<t>s`. A test checks it.
- **P3: a no-solve resume that returns no table read every row.** It now reads none. A test damages the rows file and expects no warning.
- **Fixed: a resumed run lost the earlier results rows** (the bug above). It overwrote them in the same `results_directory`, after a crash too.
- **Found while testing and fixed (c6954222d): the row at the resume time of an extended run.**
  - A run extended from the end of a finished run first takes the ticks due there. The finished run's last row was saved before those ticks.
  - With 6c3f75d61 alone, the restored table kept that row. At 2 s it held the level commanded at 1.875 s, where an uninterrupted run holds the level commanded at 2 s.
  - The checkpoint tick test caught it, because it checked the resumed run's own row there.
  - The resumed run now drops the restored row and saves it again after the ticks. The rows file is written anew at its next checkpoint.
  - This applies only when the checkpoint lists ticks pending at its time and the resumed run solves. The gravity backbone keeps the restored row, since its rows come from the solution, which has no row of its own at the start.
- **Design choices for review.**
  - **Format.** The rows file is a stream of serialized records: a header naming the save fields, the spacecraft count and the stream's token, then one record per checkpoint, which may first drop rows from the end. The checkpoint records the stream's length and token at its time, so rows a crash wrote after the checkpoint are cut away on resume, and a stream another run wrote is not used.
  - **Fallback.** Results that cannot include the earlier rows go to `resumed_at_<t>s`. This is the simplest safe choice: appending to the existing files would need proof that they come from the same run up to the checkpoint. The rule is general: results go to the usual files only when their rows start at 0.
  - **No-solve resume.** It writes nothing, because its files would equal the existing ones.
  - **Schema.** The checkpoint schema version stays 1; the new entry is optional, as the activity and scope entries were. The results manifest's `schema_version` stays 1; every reader tolerates the two new keys (see the PR text).
- **For a later step (C-5c).** C-5c's large-output log should reuse this protocol, not this format:
  - one append per checkpoint, before the checkpoint is written;
  - the length recorded in the checkpoint;
  - cut back to that length on resume.

## Residual Risk

- **Julia version.** The rows file uses Julia's `Serialization`, as the checkpoint does. A checkpoint is for resuming with the Julia version that wrote it. Rows that cannot be read take the fallback, with a warning.
- **Size.** The rows file holds every saved row before thinning, so it grows with the run, to about the size of the results CSV for the same rows. It is kept after the run, like the checkpoint files, and nothing removes it automatically.
- **The gravity backbone, extended from a finished run.** It keeps the finished run's last row, saved before any ticks due at the extension time, because its rows come from the solution, which has no row of its own at the start. Its times match the uninterrupted run (suite 03).
- **The rows before a resume are the first leg's.** Where a run's results depend slightly on its mission length, a resumed table holds the first leg's rows, not those of a longer run. The outside review saw round-off differences between a 2 s run and the first 2 s of a 4 s run; the effect does not come from this PR.
- **The token** comes from the clock, the process and the file path. Two streams could share one only if they started at the same nanosecond, in the same process, at the same path.
- **A real kill mid-write was not tested.** Crashes were simulated by a failing checkpoint write and by junk or partial records. A kill in the middle of an append leaves a stream longer than the checkpoint records, which the resume cuts back. A kill while a new stream's header is written leaves a stream the checkpoint cannot use, which takes the fallback.
- **A no-solve resume without usable rows** writes nothing, but its returned configuration names `resumed_at_<t>s`.
- **The copy in `_results_destination`.** It carries the settings by `fieldnames`. Once #479 merges, it should use `_with_fields`.
