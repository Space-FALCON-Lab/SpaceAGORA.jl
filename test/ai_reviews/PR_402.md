# Review record: PR 402: concurrent conformance runs take turns under code coverage

## Scope

Review of the SpaceAGORA `conformance-concurrency-turns` branch against main
(33fcb4c50, which has #394). The contributor kit's `concurrent_equals_sequential`
check runs a fixture twice on two threads, kept in step after every solver step,
and compares the runs with two sequential ones. Under `--code-coverage=user` the check cost
several times two sequential runs (#394 shortened its joint-reference simulation
to stay inside the coverage shards' time limit). The change makes the two runs
take turns, one solver step each, whenever Julia counts line executions (code
coverage or allocation tracking); without counting the check is unchanged. One
commit (275ab9c78) and a merge of main (894bbd02e).

Diagnosis behind the design (measured with four threads; the numbers are recorded in
the lab notes): under coverage, two concurrent runs with no synchronisation at all
already cost several times two sequential runs, and a blocking wait on a
`Threads.Condition` costs about as much as the per-step yield loop. The cost is the
instrumented code itself: Julia counts each line in one counter for all threads, so
two threads running the same lines at once keep taking that counter's cache line
from each other. A blocking wait, or waiting every k steps, cannot get below the
unsynchronised cost; only keeping the runs from stepping at the same moment does.

Authorship disclosure: this record was drafted by the author of the PR; it does
not replace an independent review.

Independent review: the coordinator reviewed the change under Giusy's delegation on
2026-10-18. Without line counting, `turns` is false and the lag is 0, so each wait is
the former loop unchanged. Taking turns, run 2 sets its run up once run 1 reaches its
first checkpoint and then waits for one checkpoint more of run 1 at each step, so the
runs' steps alternate and a state they share is still caught; a finished run still
releases the other. Giusy accepted the trade-off on 2026-10-18: under coverage the two
runs take turns, and races inside one simultaneous step are caught only by the plain
shards and the contributor workflow.

## Findings

No P1 or P2 findings. Points a reviewer should check:

- P3, by design (documented in the docstring): taking turns, the two runs never
  step at the same moment, so a race that needs both runs inside a step at once
  (a global scratch buffer written and read within one call) can only show
  without line counting. A state carried from one step to the next, which is what
  the shared-state controls model, is caught in both modes. CI's plain shards run
  the conformance tests with four threads and no coverage, and the contributor
  workflow runs without coverage, so both keep the simultaneous mode.
- Low: the start gate (run 2 waits for run 1's first checkpoint or its end) has no
  deadline. Run 2 holds nothing there, so no model of run 1 can wait on it, and
  run 1's task marks itself finished in a `finally`; a run 1 that never ended would
  stall `fetch` in either design. It also keeps a slow first compile of run 1's
  solver (instrumented code compiles in the process) from counting as a timeout.
  The per-step waits keep their counted 60 s deadline.
- Low: no circular wait. In step, a run at checkpoint n waits for the other to
  reach n; taking turns, run 1 at n waits for run 2 to reach n and run 2 at m waits
  for run 1 to reach m + 1. Both waiting would need n > m and n < m + 1 at once.
  Either run finishing or failing releases the other (`finished`).
- Low: the engine calls the initialize callback (checkpoint 1) before its first
  right-hand-side evaluation, so every model call of a run, the step-size probe
  included, falls inside one of its turns (checked by the probe test below).
- Low: the remaining cost of taking turns under coverage is the handoff between
  threads after every step; turns of 16 steps cost less but
  would run a short fixture (five steps) as two sequential runs and miss the shared
  scratch controls, so turns stay one step long. A pause-spin before yielding
  saved only a few percent and could starve the other run; not taken.

## P1 Assessment

No P1 findings. Without line counting the code path is the previous one: `lag`
is 0, there is no start gate, and `_await_checkpoint` is the former loop, so the
check's behaviour and cost in plain runs are unchanged.

## Tests Added/Updated

- `test/unit/conformance/negative_controls_tests.jl`:
  - the stall control (`NcStallsOnce`) now runs in step and taking turns: both
    report the runs out of step, and equal results do not rescue the check;
  - new `NcFailsOnce`: one concurrent run fails; in both modes the check reports
    that run's error and no timeout, so the failed run released the other (a run
    left waiting would wait out the 30 s limit and be reported out of step);
  - new `NcProbe`: in step, both runs are inside the model at once (the probe
    waits up to 10 s for that meeting); taking turns, never (at most one call in
    flight), while their calls switch between the runs at least eight times (two
    sequential runs switch once);
  - shared state in both modes: the shared-scratch force model, sensor and control
    model fail and their clean counterparts pass, in step and taking turns,
    whichever mode the process uses by default. The existing negative-control loop
    runs every control in the process's default mode: in step in plain shards,
    taking turns in coverage shards.
