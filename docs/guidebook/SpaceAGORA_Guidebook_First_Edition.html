About this edition

This is the first integrated guidebook draft for the current SpaceAGORA repository. It explains the supported workflow, configuration layers, model families, planets, numerical engines, GNC systems, examples, outputs, and extension contracts. The source tree remains authoritative when this draft and code differ.

Scope convention. “Public API” means names exported by SpaceAGORA. Some examples also use names re-exported by included repository support files. Underscore-prefixed helpers and nested-module internals are implementation details and are not stable interfaces.

1. System map

SpaceAGORA is a Julia spacecraft mission simulation framework. A simulation combines initial state, environment, spacecraft, force/torque effectors, GNC models, solver policy, callbacks, and output policy into a SimulationConfiguration, then executes it through run_simulation.

SimulationConfiguration
 ├─ MissionConfiguration + InitialTime
 ├─ EnvironmentModel (planet, atmosphere, ephemerides, EI, wind, terrain)
 ├─ DynamicsModel (spacecraft + force/torque effectors)
 ├─ GuidanceModel / NavigationModel / ControlModel
 ├─ IntegrationTolerances + SolverConfig
 └─ SimulationSettings + FilePaths
                 │
                 ▼
        run_simulation(...)
                 │
       solution + callbacks + CSV/Feather/manifest

2. Installation and assets

Base environment

cd /path/to/SpaceAGORA.jl
julia --project=. -e 'using Pkg; Pkg.instantiate()'
julia --project=. examples/AGORA_Basic_Quickstart.jl

The project environment in Project.toml/Manifest.toml should be activated for examples, tests, CLI calls, and development. Do not silently substitute a global Julia environment.

Asset tiers

  • No-GRAM baseline: analytic/tabulated atmospheres and simple ephemerides; intended for portable runs and CI.
  • SPICE-backed: kernel assets support body frames and higher-fidelity ephemerides.
  • GRAM-backed: GRAMSuite assets and installation are optional and must be configured separately.
  • Geometry assets: RPO station CAD/point-cloud data are checked and loaded through package paths.
julia --project=. src/cli/main.jl assets check

check_assets returns an AssetCheckReport; render_asset_report formats it. The CLI surface supports run, telemetry, benchmark, and assets check.

3. First simulation

The fastest health check is:

julia --project=. examples/AGORA_Basic_Quickstart.jl

For a fuller portable Earth case:

julia --project=. examples/AGORA_Earth_NoGRAM.jl

Canonical construction pattern

using SpaceAGORA

planet = Earth()
spacecraft = SpacecraftModel(...)
args = SimulationConfiguration(
    mission_configuration = MissionConfiguration(...),
    environment_model = EnvironmentModel(
        planet=planet,
        density_model=ExponentialAtmosphereModel(planet),
        ephemerides_model=SimpleEphemeridesModel()),
    dynamics_model = DynamicsModel(
        spacecraft=[spacecraft],
        dynamic_effectors=(InverseSquaredJ2GravityModel(),)),
    initial_time = InitialTime(...),
)
sol = run_simulation(args; return_solution=true)

In repository examples, examples/common.jl supplies convenience builders such as make_example_config. That function is an examples-layer helper, not the core configuration type. Production integrations should understand the resulting SimulationConfiguration.

User-owned mission values. Planet, orbit, epoch, EI altitude, forces, atmosphere, GNC mode, constraints, numerical limits, output location, and solver settings belong in the mission/example file. Avoid hidden Earth defaults in a Mars, Venus, Titan, or Moon scenario.

5. Initial conditions and reference frames

InitialCondition supports orbital-element construction, including apoapsis/periapsis radii and angular elements. CartesianInitialCondition accepts position/velocity state directly. Be explicit about units: repository orbital radii and Cartesian positions are SI unless a field is explicitly labeled otherwise; example angular inputs follow constructor documentation.

Frame and orbit utilities

  • orbitalelemtorv, rvtoorbitalelement: orbital elements ↔ Cartesian state.
  • r_intor_p!, r_pintor_i: inertial ↔ planet-fixed states.
  • rtolatlong, latlongtor, latlongtoOE: planetographic conversions.
  • rtn_dcm_from_inertial, inertial_to_rtn_relative_state, rtn_to_inertial_relative_state, rtn_accel_to_inertial: RPO/RTN transformations.
  • Quaternion utilities cover derivatives, multiplication, Cayley maps, DCM conversion, and Euler-angle conversion.

Oblate-body altitude, planet orientation, and epoch matter. Do not treat a spherical radius subtraction as equivalent to the configured topographic/oblate altitude model.

6. Planets and environments

Included planet constructors

Venus()VEX/Magellan and dense-atmosphere missions
Moon()Airless-body orbital dynamics
Titan()Titan atmospheric flight/aerobraking

make_no_gram_planet, make_no_gram_density_model, and make_no_gram_environment provide portable environment construction.

Atmospheric interface (EI)

EI is primarily a named altitude boundary used by atmosphere-aware solver policy, tolerances, callbacks, and mission logic. For most density models it is not automatically a physical gate that forces density/aerodynamics to zero above EI. A model may explicitly declare that its density vanishes above the interface.

Therefore an Earth choice near 300 km can be a sensible interface or reference cutoff for a particular study, but it is not universal. Select EI from the planet, atmosphere, trajectory, and desired numerical transition.

Use getDensity for scalar samples and getDensityBatch! for batch evaluation. Atmosphere samples can carry density, temperature, wind and related state through AtmosphereSample/EnvironmentSample.

Ephemerides

  • SimpleEphemeridesModel: portable analytic/simple path.
  • SpiceEphemeridesModel: SPICE-based frames/body positions and optional cache paths.
  • prewarm_nbody_ephemeris_cache and load_nbody_ephemeris_cache!: reuse deterministic ephemeris samples across campaign workers.

Gravity and external perturbations

  • ConstantGravityModel, InverseSquaredGravityModel, InverseSquaredJ2GravityModel.
  • NBodyGravityModel for third bodies.
  • GravitationalHarmonicsModel for degree/order gravity fields.
  • SolarRadiationPressureModel, EddyCurrentDampingModel, MagneticTorqueRodModel, gravity-gradient and attitude-related effectors.

InverseSquaredJ2GravityModel is defined/exported from src/environment/gravity/gravity_effectors.jl. The aerobraking MPC adapter inspects the configured dynamics to select the corresponding prediction gravity model.

Aerodynamics and thermal response

Aerodynamic effectors convert relative flow, facet geometry, density, gas-surface properties and attitude into force/torque. AerodynamicCoefficientfM is the free-molecular coefficient effector used in the current MPC example. Thermal implementations include convective, radiative/combined calculation paths and MaxwellianHeat through getHeatRate.

8. Dynamics and force/torque architecture

State propagation

  • Translational: position derivative, acceleration from force, mass derivative, full/slow/control-only/force-only RHS assignment.
  • Rotational: quaternion derivative, angular acceleration, body torque and angular velocity, torque combination.
  • Coupled: spacecraft effectors share sampled state/environment and return force, torque, mass flow, or partition information.

Effector contract

New physical models subtype AbstractForceTorqueModel. The main calculation surfaces are calcForceTorque and the newer sampled wrench interface. environment_requirements declares what an effector needs, and solver_partition classifies it for split/multirate execution. Gravity-backbone functions expose acceleration structure for symplectic and split solvers.

Typed samples include StateSample, PlanetFrameSample, AtmosphereSample, SolarEphemerisSample, ThirdBodyEphemerisSample, and EnvironmentSample.

9. Spacecraft, components, actuators, and thermal models

Spacecraft assembly

  • SpacecraftModel contains links, joints, a root link, initial condition and spacecraft-level properties.
  • Link represents rigid bodies and attached components; Joint defines connectivity/motion.
  • Facet supplies area, normal, attitude and surface properties for aero/SRP/thermal calculations.
  • add_body!, add_joint!, add_facet!, add_magnet!, add_thruster! assemble a model.
  • create_facet_list builds repeated facet definitions.

Actuators

  • Thrusters: BaseThrusterModel, SixAxisThrusterModel, Schmitt-trigger and impulse integration hooks.
  • Reaction wheels: ReactionWheelAssembly and allocation/control paths.
  • Magnets/magnetic torquers and momentum management.
  • Generic hooks: apply_actuator_hook!, apply_actuator_hooks!.

Control effector contract

Control models subtype AbstractControlEffectorModel and implement the appropriate combination of calcControlEffect!, calcControlForceTorque, and calcControlMassFlowRate. Control rates are assigned in ControlModel.

10. Guidance, navigation, and control

Guidance

  • Aerobraking campaign propulsive maneuver guidance.
  • Apoapsis-target/periapsis-raise guidance.
  • Energy-depletion guidance with maximum-depletion and terminal-targeting strategies.
  • RPO plan buffers, guidance models, HYPR/RRT planning and replanning.

Navigation

Navigation is configured independently through NavigationModel. RPO navigation includes CubeSat/station reference geometry, KD-tree-backed station geometry, relative-frame states, and reference geometry loaders.

Control

  • Solar-panel angle-of-attack control.
  • Aerobraking energy-depletion control with heat rate, heat load, structural load and targeting logic.
  • Aerobraking MPC with constrained area commands.
  • RPO LQ-MPC, six-axis thruster allocation and reaction-wheel allocation.
  • Magnetic momentum management and LVLH/cascade attitude control.
  • Robot-arm joint MPC and reaction effectors.

11. Aerobraking MPC

Purpose and modes

The controller predicts a drag passage in Kustaanheimo–Stiefel coordinates, linearizes the prediction, condenses it into a quadratic program, solves it with OSQP, commands exposed area, and maps that area to solar-panel angle of attack.

ModeObjective
TargetEnergyModeDrive predicted terminal specific orbital energy toward a user-defined target.
MaxEnergyDepletionModeMaximize energy removal while respecting active constraints and regularization.

Constraint selection

mpc_constraints activates a subset of :heat_rate, :heat_load, :drag, and :slew. Inspect with constraint_names/constraint_active; apply a set with apply_constraints. Limits and weights live in AerobrakingMPCConfig, including heat-rate/load bounds, drag bound, area slew, area/energy/slack weights, and OSQP tolerances.

Constraint meaning. A declared numeric limit is not active unless its constraint is selected. Validate the saved histories after every scenario. Slack-enabled optimization may preserve feasibility by reporting a violation; audit solver status, active limit, slack, and measured/predicted constraint traces.

SpaceAGORA integration

  • mpc_params_from_spaceagora derives μ, radius, rotation and prediction parameters from the configured planet.
  • mpc_prediction_gravity_model maps the main dynamics model into MPC gravity fidelity.
  • spacecraft_mass_kg and spacecraft_reference_areas derive vehicle data.
  • mpc_config_from_spaceagora builds an MPC configuration from the scenario plus user overrides.
  • density_and_gradient_from_spaceagora/density_function_from_spaceagora adapt atmosphere evaluation.
  • build_reference_drag_pass, build_mpc_problem, and solve_mpc_qp form the prediction/optimization pipeline.

Area-to-AOA callback path

QP area command
  → commanded_area_fraction(config, area)
  → alpha_from_commanded_area(..., min_alpha_rad, max_alpha_rad)
  → apply_commanded_area!(...)
  → controlled panel link attitudes updated by AerobrakingMPCControlModel
  → aerodynamic effector sees the new exposed geometry

The inverse mapping commanded_area_from_alpha supports validation. mpc_control_save_fields exposes controller telemetry including commanded area and constraint quantities.

When does it solve?

The integrated AerobrakingMPCControlModel is called at control_dt_s. A new QP solve is permitted according to solve_interval_s; reference rebuilding follows build_reference_on_tick and the reference configuration. h_cut_m is the reference drag-pass cutoff. It is not, by itself, a universal callback saying “solve exactly once when altitude crosses 300 km.”

In examples/AGORA_MPC_Aerobraking.jl, the current settings are control_dt_s=0.5 s, solve_interval_s=10 s (60 s in smoke mode), and h_cut_m=300 km. The configured environment EI is 160 km for that Mars case.

Mars energy correctness

The example does not hard-code −6.41 MJ/kg. It computes:

target_apoapsis_radius_m = ra - 50e3
target_energy_mj_kg = -planet.μ /
    (target_apoapsis_radius_m + rp) / 1e6

This is the specific orbital energy −μ/(2a), with 2a = ra + rp, using Mars().μ. Energy targets must be derived from the selected planet and orbit.

Example-owned MPC settings

The example exposes planet, mode, orbit, epoch, constraint selection, every limit, QP weights/tolerances, controlled links, AOA bounds, control and solve periods, reference cutoff/step limits, density/ephemerides/gravity/aero choices, and output directory. It also asserts heat-rate, drag, area-slew, and nonconstant area-command histories after the run.

12. Simulation engine and solver policy

Engine configuration

SimulationEngineConfig groups ParallelConfig, engine SolverConfig, RuntimePolicyConfig, and ArtifactConfig. simulation_engine_config_from_env maps supported environment variables into an explicit configuration.

Solver families

  • Adaptive general-purpose integration (default mode commonly :tsit5).
  • Split/IMEX integration (configured e.g. with :kencarp4).
  • Symplectic/gravity-backbone integration with explicit backbone step.
  • Multirate execution separating force/effect update cadence where model partitions permit.

Atmosphere/orbit step caps and group tolerances matter during sharp drag passages. Use solver changes as scenario decisions, then verify conservation, event timing, constraint traces, and convergence against a tighter reference.

Isolation

run_simulation defaults to isolate_state=true, deep-copying configuration so mutable controller/campaign state is not shared accidentally. Use isolate_state=false only when the caller owns the configuration and accepts mutation/reuse risks.

13. Parallel execution, Monte Carlo, and constellations

Profiles and routing

ParallelProfile/ParallelProfileConfig provide named execution policies. Functions parse profiles, expose profile environment pairs, and run code under a selected profile. Adaptive outer routing uses OuterRouteFeatures, tuning/state, candidate selection, statistics, and feedback.

Campaigns

  • MonteCarloSpec: seeds, thread count and fail-fast policy.
  • run_monte_carlo: serial, threaded, process, or adaptively routed sample execution.
  • MonteCarloSampleResult/MonteCarloResult: per-sample and aggregate results.
  • run_constellation_ensemble: ensemble execution for multi-spacecraft studies.
  • campaign_route_features/campaign_outer_route_state: inspect campaign routing context.

Processes

ProcessPool, campaign_process_pool, ensure_process_workers!, and shutdown_process_pool! manage worker processes. Prewarm and load ephemeris caches per worker when SPICE/N-body work is repeated.

Reproducibility requires explicit seeds, isolated mutable configurations, recorded profile/environment settings, and stable assets—not merely the same thread count.

14. Callbacks, persistence, outputs, and verification

Callbacks and saved fields

SaveFielddefault_save_fields(args) provides the standard set; get_callbacks assembles callbacks. Controller-specific fields can be appended, as the MPC example does with mpc_control_save_fields.

Outputs

Depending on SimulationSettings and artifact policy, runs can produce CSV, Feather, manifests, plots, checkpoints, and related metadata beneath the selected results directory. Keep each campaign/sample in a unique output path.

Checkpointing

Checkpoint/resume settings are part of SimulationSettings. Resume compatibility depends on scenario, model state and code version; treat checkpoint files as versioned artifacts and validate continuation results.

Verification

VerificationRequest describes a telemetry/study request; run_verification, run_verification_cli, and run_study execute verification workflows and return VerificationResult. Benchmarks and smoke tests answer different questions: smoke tests establish execution, while verification establishes numerical/physical agreement against declared acceptance criteria.

15. RPO, robotics, and compliant cloth

Rendezvous and proximity operations

RPO features include RTN-state transformations, station/CubeSat reference geometry, point-cloud/CAD loading, RRT/HYPR planning, buffered guidance, replanning, HCW-based LQ-MPC, six-axis thruster allocation, reaction-wheel allocation, and batch/planner-comparison examples.

Robot arm

  • Geometry/state: ClothArmBasePose, links, joints, model, pose and state.
  • Kinematics: forward kinematics, end-effector pose, inverse kinematics, reach, closest-surface target.
  • Planning: RobotArmPlannerConfig, RobotArmPlan, collision spheres, HYPR configuration/result, planning and sampling.
  • Control: joint MPC, reference preview, measured joint state, held actuation and control/reaction effectors.

Compliant multibody and cloth

CompliantBody, CompliantJoint, topology nodes/edges/build results, joint actuators/loads, inertia helpers, rectangular grids, state packing, dynamics and RK4/implicit-midpoint stepping support flexible structures. Coupled cloth–robot-arm functions initialize and propagate combined state and simulate a planned motion. The solar-panel deployment demo exercises the same compliant machinery.

17. Extension and validation guide

Add a force/torque model

  1. Subtype AbstractForceTorqueModel.
  2. Declare environment needs.
  3. Implement wrench or the compatible force/torque contract.
  4. Declare solver partition/backbone behavior where applicable.
  5. Add unit tests, a minimal example, and conservation/limit checks.

Add an atmosphere

  1. Subtype AbstractDensityModel.
  2. Implement scalar density and, when performance matters, batch evaluation.
  3. Specify units, valid altitude/time domain, EI behavior, extrapolation, and required indices/assets.
  4. Test boundary continuity, vacuum behavior and gradients used by controllers.

Add a controller

  1. Subtype AbstractControlEffectorModel.
  2. Implement the effect/force/mass-flow interfaces needed by the actuator.
  3. Make update cadence explicit in ControlModel.
  4. Expose commands, solver status, limits and fallback state as saved fields.
  5. Test saturation, inactive/active constraints, update timing and failure fallback.

Mission validation checklist

  • All quantities use the selected planet’s μ, radii, rotation and atmosphere.
  • Initial radius/energy are physically compatible with that planet.
  • Epoch and ephemerides/assets are available.
  • EI and atmosphere validity ranges are deliberate.
  • Every intended constraint is both numerically set and activated.
  • Commands vary when expected and remain within actuator geometry/rate limits.
  • Control callbacks actually alter the geometry/actuator consumed by dynamics.
  • Solver status, fallback, slack and saved telemetry are audited.
  • Results converge under tighter tolerances/smaller steps.
  • A benchmark or independent physics check is recorded.
