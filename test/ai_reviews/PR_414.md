# Review record: PR 414: Keep the built-in GNC models' run state in checkpoint files

## Scope

Review of the SpaceAGORA `builtin-checkpoint-state` branch against main
(c7db8b6fb, v0.3.1): 0.4.0 PR 3b, the follow-ups of #405 that the checkpoint
design note (2026-10-18) decided as built: D-4, the built-in models adopt
`checkpoint_state` / `restore_checkpoint_state!`; D-5, a conformance check that a
model's run state round-trips through a checkpoint. Not stacked on #413 (3a, the
boundary tick); the tests compare resumed runs with runs checkpointed at the same
times, which hold with and without #413. Commits: the adoption and the check
(40539f523), tests and a line moved so #413 and this PR merge cleanly in either order
(1dd7c3c0b), the restart check covering a run set to resume (6999b6c32), stronger
restore tests (fb4914315), and this record.

D-4. Every built-in guidance and control model that keeps run state saves it:

- the momentum manager (accumulator, held torque and dipole, tick time and count, mounted levels);
- the Apollo descent guidance (its spacecraft's entries of the shared `ApolloDescentState`) and control (its spacecraft's actuator state);
- the periapsis-raise guidance (command states);
- the burn scheduler `BaseThrusterModel` (schedule, burn windows and flags, mounted levels, refusal records);
- the RPO planner binding `PlannerGuidance` (the request runtime: random stream, installed request and reference, records, the algorithm's own state; the triggers; the plan buffer it writes);
- the deprecated `RPOGuidanceModel` (its run-written entries and plan buffer);
- the RPO MPC controller (held command, warm start, the OSQP solver's dual iterate and adapted step size, mounted levels, command log);
- the robot-arm controller (held command, MPC warm start).

Each also saves its record of its last write (G-8, #408), so the next
`isolate_state=false` run resets as it would after an uninterrupted run. The
models without run state of their own (the campaign propulsive-maneuver guidance,
the panel actuator) need nothing.

Refusals: the RPO planner binding refused checkpoint writing and resume in its
preflight; that refusal is lifted. On a resume its initializer makes no initial
request, since the engine restores the binding's state right after the run-start
initializers (`SharedBuffers.model_resume`, set when the checkpoint holds model
state); a fresh request at the resume time could fail where the uninterrupted run
did not. A checkpointed run refuses a planner that keeps state of its own
(`initialize_planner` returns something) and does not declare `restart`, the
contract's existing capability for it; the built-in planners keep none. Still
refused, unchanged: the energy-depletion guidance and control (`_edg_preflight`)
and the GNC algorithm adapter `AlgorithmGuidance`.

What EDG would need (its lifecycle lives in core, its provider in the
SpaceAGORAEDG companion; not part of this PR):

- the shared `AerobrakingEnergyDepletionState` saved by its producer (mode, targeting and bracketing flags and counters, target and bracket energies, the control clock), as the Apollo guidance saves its shared state;
- the passage heat accounting (entry and exit heat loads, boundary flags and times), whose initializer refuses a start after 0 (`_edg_initialize_heat_accounting!`), and the heat observer's callback state (`_edg_observe_heat_callbacks`);
- the panel actuator's held command inside the EDG control;
- any run state the companion's provider keeps, and the family's capability check (`validate_capabilities(...; checkpoint=true)` returns `:restart_unsupported`);
- then lifting the refusal in `_edg_preflight`.

`AlgorithmGuidance` would save its `AlgorithmRuntime` as the RPO binding does,
plus each family's link (the burn-plan slot, the robot-arm plan buffer, the EDG
state).

D-5. `SpaceAGORA.Conformance` gains `checkpoint_round_trip` for guidance,
navigation and control models and sensors. The check runs the fixture with a checkpoint halfway,
interrupts the run after the checkpoint (an extra callback throws at the first step past it), resumes from
the file, and compares the second half with an uninterrupted run with the same
checkpoints: the states and the model's own state at the end (a sensor's
measurements from halfway on), bit for bit. Checkpoint segments are fresh solves,
so the two second halves integrate identically when the run state is restored
exactly. It is skipped when the fixture refuses checkpointed runs at setup (an
`ArgumentError` other than the engine's missing-restore refusal, which fails it).
Added in 0.4.0 (`since = v"0.4.0"`), it reports `:advisory_fail` in 0.4 and `:fail`
from 0.5.0 (K-4). The kit's state comparison `_same_state` now compares `BigInt`
and `BigFloat` by value: a `MersenneTwister` holds a `BigInt` whose limb pointer
differs between copies, which made any two copies of a run's random stream compare
unequal.

## Findings

No P1 findings. Found and fixed while building, before review: restoring a model's held
command by marking it as the run's write left its write record differing from an
uninterrupted run's (the kit's new check caught it on the momentum manager and the RPO
MPC controller); the models now save and restore the record. The CI unit runner found
that the RPO lifecycle test expects a run set to resume to be refused for the example's
hold planner (it keeps state and declares no restart); the restart check covered only
`checkpoint_enabled` and now covers `resume_from_checkpoint` too (6999b6c32).

Points a reviewer should check:

- Low, by design: the MPC solver state is read and written through OSQP.jl's `Workspace` struct (`unsafe_load(model.workspace)`), as OSQP.jl's own `solve!` and `dimensions` read it; it ties the code to OSQP.jl 0.8's layout, the compat bound already in `Project.toml`. The public `warm_start_y!` takes an unscaled dual and rescales it, which does not reproduce the scaled iterate bit for bit.
- Low: the round trip compares the model's whole state like the run-level checks; a model that holds native handles (whose addresses differ between copies) or wall-clock timings fails it as it fails `repeatable_run`. The built-in MPC instance of the kit has no controller; the new unit test compares a planner-driven MPC's run state without its solver workspace and last result.
- Low: the planner binding's initializer reads `p.shared_buffers.model_resume`, an engine flag, as #401's sensor callbacks read `callback_resume`.
- Low: `restore_checkpoint_state!` refuses a checkpoint whose controller kind differs (MPC, robot arm) or whose scheduler serves another number of spacecraft; the engine checks model kinds by position only.
- Pre-existing, noted: `p.is_active` is restored only for interlinked runs, so a run resumed after an Apollo touchdown (or an impact) reactivates the spacecraft; the campaign propulsive-maneuver guidance counts orbits through an engine callback whose count a checkpoint does not hold.
