Troubleshooting

Each section starts from what you see, an error message or an unexpected result, and gives the usual cause and the fix. Run the commands from the repository root unless a section says otherwise.

What to read next:

  • GRAMSuite Setup
  • Assets & Modes
  • Simulation Configuration

Wrong Julia version

Symptom: julia --version prints something other than julia version 1.12.x. What fails next depends on the command:

  • Setting up the Odyssey example environment, or any Pkg.add, Pkg.update or Pkg.resolve, stops with an error saying that the julia = "~1.12" compat entry does not include your Julia version. The wording depends on the release, for example julia version requirement for package at ... not satisfied.
  • The documented root instantiate, Pkg.instantiate(julia_version_strict=true), stops with The active manifest file has dependencies that were resolved with a different julia version (1.12.3). The version in parentheses is the one recorded in Manifest.toml.
  • A plain Pkg.instantiate() prints that sentence only as a warning and fails later, with messages such as Could not locate the source code for the ... package. Are you trying to use a manifest generated by a different version of Julia? or a long list of precompilation errors.
  • On Julia 1.11 or older, the strict command fails with type Context has no field julia_version_strict, because that package manager predates the option.

Cause: SpaceAGORA is tested and supported on Julia 1.12 only, and the committed manifest was resolved with 1.12. The documented commands refuse other releases rather than run an untested combination.

Resolution:

  • Install a Julia 1.12 release: with juliaup, juliaup add 1.12 and then juliaup default 1.12; otherwise the 1.12 installer from julialang.org.
  • Make sure that release is the julia on your PATH and, in VS Code, the one selected by the Julia extension's executable-path setting.
  • Rerun the instantiate command from the repository root. Each Julia release keeps its compiled caches in its own ~/.julia/compiled/v1.x directory, so an earlier attempt on the wrong release needs no cleanup.

Wrong working directory

Symptom: A documented command fails on a path it cannot find, for example ERROR: SystemError: opening file ".../examples/AGORA_Basic_Quickstart.jl": No such file or directory, or using SpaceAGORA fails with Package SpaceAGORA not found in current path. On Windows, a terminal that opened in C:\Windows\System32 adds permission errors.

Cause: --project=. means "the project in the current directory", and every relative path in the documentation is relative to the repository root: the checkout directory that contains Project.toml, src/ and examples/. Started anywhere else, julia --project=. quietly creates an empty environment there. Pkg.instantiate() then reports No packages added to or removed from .../Project.toml and leaves a stray Manifest.toml behind.

Resolution:

  • Change to the checkout before every terminal command (cd works on all three platforms) and confirm with ls Project.toml on Linux and macOS or dir Project.toml on Windows.
  • Delete any Project.toml or Manifest.toml that an earlier attempt created outside the checkout.
  • In VS Code, open the checkout folder as the workspace so that its integrated terminal starts there; the editor itself is not a shell.
  • In a Julia REPL, Base.active_project() must return the checkout's Project.toml (for a default clone, a path ending in SpaceAGORA.jl/Project.toml). pwd() shows the directory Julia was started in, and cd("/path/to/SpaceAGORA.jl") changes it without leaving the session.

Examples environment not prepared

Symptom: An example stops with Prepare the examples environment first: run julia --startup-file=no examples/setup.jl, the command-line tool's run, telemetry or benchmark command stops with The examples environment is not prepared, or a plotting script fails with Package Plots not found in current path.

Cause: The examples, the plotting scripts and the benchmark studies run in the examples environment (examples/Project.toml), which adds Plots, Roots and the other packages they use to SpaceAGORA. The root project does not provide those packages. The examples environment's manifest is generated, not committed, so a fresh clone does not have it. Checkouts older than 0.6.0 ran the examples in the root project; Upgrading describes the change.

Resolution:

  • Prepare it once from the repository root, after the root instantiate: julia --startup-file=no examples/setup.jl.
  • Run examples and plotting scripts with --project=examples.
  • Run the setup again after a pull that changes the root Manifest.toml, and whenever an example reports that the examples environment does not provide this checkout's SpaceAGORA. The setup copies the root manifest into the examples environment each time, so the examples follow the versions it records.

Shell command typed into the Julia REPL, or Julia code typed into the shell

Symptom: At the julia> prompt, julia --project=examples examples/... fails with ParseError: ... invalid operator, cd SpaceAGORA.jl or git clone ... with extra tokens after end of expression, and a PowerShell line such as $env:GIT_LFS_SKIP_SMUDGE = "1" with syntax: "$env" is not a valid function argument name. At the shell prompt, using SpaceAGORA or include("...") is reported as an unknown command (command not found: using, or PowerShell's is not recognized) or as a syntax error.

Cause: Two different programs read the line. The shell (PowerShell, Command Prompt or a terminal) runs julia, git and cd; the Julia REPL runs Julia code such as using, include and function calls.

Resolution:

  • Blocks marked "Terminal" go to the shell prompt (PS C:\...> or $); blocks marked "Julia REPL" go to the julia> prompt.
  • Start the REPL from the repository root with julia --project=. (or julia --project=examples/odyssey_surrogate_env for the Odyssey example); exit() or Ctrl-D returns to the shell.
  • A line that starts with ] is a package-manager command: typing ] at the julia> prompt switches to the pkg> prompt, and Backspace switches back.
  • Running a script does not need the REPL at all: julia --project=. path/to/script.jl from the shell runs it and exits.

Precompilation errors

Symptom: Pkg.instantiate() or the first using SpaceAGORA ends with ERROR: LoadError: Failed to precompile SpaceAGORA [afbfb69f-5c0b-4832-b760-43725dff8540] ... or The following N direct dependencies failed to precompile:, usually after a long trace.

Cause: Most often the wrong Julia release (see above). Otherwise an interrupted first instantiate, a partially downloaded dependency, or a compiled cache left by a different checkout of the package.

Resolution:

  1. Confirm that julia --version prints 1.12.x.
  2. From the repository root, rerun julia --project=. -e "using Pkg; Pkg.instantiate(julia_version_strict=true); Pkg.precompile()".
  3. If the same package fails again, delete ~/.julia/compiled/v1.12/SpaceAGORA (Windows: %USERPROFILE%\.julia\compiled\v1.12\SpaceAGORA) and repeat step 2. A failing dependency has its own directory under the same parent.
  4. When asking for help, quote the first line that names the failing package and the error it reports; the rest of the trace repeats it.

First run is very slow

Symptom: The first julia --project=. ... command runs for a long time before it prints anything.

Cause: Julia compiles package code the first time it is loaded and caches the result. SpaceAGORA depends on ODE solver, atmosphere and geometry libraries that take a while to precompile, and the examples environment adds its plotting packages. Later runs in the same session, and later sessions that find the cache, start much faster.

Resolution:

  • Let the first run finish; nothing is wrong.
  • The compiled cache persists across sessions. Julia compiles again only after SpaceAGORA, one of its dependencies or the Julia release changes, for example after a pull that updates Manifest.toml.
  • To fill the cache without running a simulation:
    julia --project=. -e "using SpaceAGORA"
  • The Odyssey surrogate example shows the same effect inside one run: its first passage includes compilation and reports a much longer run time than the second, whatever the panel caps are.
  • Lines such as WARNING: Imported binding Logging.termlength was undeclared at import time during import to WebSockets. can appear while the examples environment's plotting packages precompile. They come from a dependency, not from your setup, and the run continues. Only an ERROR: line needs action (see Precompilation errors).

Odyssey surrogate: setup, offline runs and native_gram_loaded = false

Symptom: One of these on the native-free Odyssey route:

  • the setup script stops in git submodule update --init for packages/gnc/SpaceAGORAEDG.jl, or while adding GRAMSuite, with a network or Git error;
  • examples/odyssey_surrogate.jl --offline stops with a missing-asset error;
  • git status shows examples/odyssey_surrogate_env/Project.toml as modified;
  • every summary.toml says native_gram_loaded = false.

Cause and resolution:

  • The first setup needs network access. It clones the EDG guidance companion from GitHub, and the package manager downloads the GRAMSuite wrapper and the remaining packages. The first example run then downloads the preset grid and the public scenario assets. Neither step needs native GRAM or a GRAM data directory; see the Odyssey walkthrough.
  • --offline refuses to download, so it works only once the assets are installed. Run the example once with network access: that installs both the preset grid and the scenario's SPICE kernels and gravity coefficients. The named surrogate data command assets fetch --preset=odyssey_p20_frozen_v1 --version=1.0.0 installs only the grid, so an offline run still needs the scenario assets afterwards.
  • The modified Project.toml is expected: the setup adds the companion to the example environment. Leave it as it is, or restore it with Git before committing other changes.
  • native_gram_loaded = false is the correct value for this route. If an error mentions GRAM Suite 2.0, libGRAM or SPICE_PATH, you ran one of the GRAM-backed examples such as AGORA_Odyssey.jl, not the surrogate example.

GRAM assets not found

Symptom: julia --project=. src/interfaces/cli/main.jl assets check reports gram_root or spice_directory as missing-optional or pointer-only-optional, or both are usable but a GRAM-backed example fails as it loads.

Cause: gram_root and spice_directory are folders of the public GRAMSuite.jl wrapper, the submodule at data/GRAMSuite.jl. The asset check only looks for downloaded files in them:

  • missing means the submodule was never checked out;
  • pointer-only means the wrapper is checked out but its Git LFS files, which include the SPICE kernels, were not fetched;
  • usable means the wrapper and its LFS files are in place. The wrapper alone is enough for that, so the check cannot tell whether the NASA GRAM Suite files were copied in. The NASA delivery adds Build and the planet folders to data/GRAMSuite.jl/GRAM Suite 2.0; when a GRAM-backed run fails on load although the wrapper is present, those are usually what is missing.

Resolution: GRAMSuite Setup has the full procedure. In short:

  1. For missing, check out the submodule:
    git submodule update --init --recursive -- data/GRAMSuite.jl
  2. For pointer-only, fetch the LFS files from inside the submodule:
    cd data/GRAMSuite.jl
git lfs pull
  3. Copy the contents of the NASA delivery's GRAM Suite 2.0 directory into the wrapper's folder of the same name, so that Build sits next to SPICE and simulation:
    data/GRAMSuite.jl/GRAM Suite 2.0
  4. Build or verify the native shared library:
    julia --project=. scripts/ensure_gram_native.jl
  5. Confirm that both entries are usable, then confirm the NASA files and the native library with a GRAM-backed run, which the asset check does not test:
    julia --project=. src/interfaces/cli/main.jl assets check
julia --project=examples examples/AGORA_Basic_GRAMEarth.jl

If the submodule checkout fails with Git LFS no space left on device, free disk space and see GRAMSuite Setup.

Native GRAM library missing or stale

Symptom: GRAM assets are present but GRAMAtmosphereModel raises a library load error at runtime.

Possible causes: The native libGRAM is missing, was copied from an incompatible host, or cannot load one of its native dependencies.

Resolution:

julia --project=. scripts/ensure_gram_native.jl

This command skips the build when the expected library file exists; it does not check whether that binary is compatible with this host. If you copied a populated GRAM build from another machine, or suspect a stale local build, force a rebuild:

julia --project=. scripts/ensure_gram_native.jl --clean

If loading still fails, keep the complete error message. GRAMSuite Setup lists the build prerequisites and the expected output, including the GNU Make requirement on macOS.

Solver stalls or takes extremely long during entry

Symptom: The integrator slows to a crawl during an aerobraking or entry pass, with many rejected steps.

Cause: Below the entry interface (EI), the run caps the step size at dt_max_atmosphere (default 1 s) and uses reltol_atmosphere and abstol_atmosphere. On a steep entry the aerodynamic forces change quickly, and a 1 s cap lets the adaptive solver attempt steps that its error control then rejects.

Resolution: Reduce dt_max_atmosphere in the configuration's IntegrationTolerances. This fragment shows the fields involved (SM is SpaceAGORA.SimulationModel):

SM.IntegrationTolerances(
    dt_max_atmosphere = 0.1,    # or 0.5 for moderate entries
    reltol_atmosphere = 1e-9,
    abstol_atmosphere = 1e-11
)

For very steep entries (ballistic coefficient above 500 kg/m², flight path angle steeper than −15°), start with dt_max_atmosphere = 0.05.

Output CSV is not written

Symptom: The simulation completes but no CSV appears in the output directory.

Cause: One of these settings is off:

  • simulation_settings.results = false writes no result files at all;
  • simulation_settings.save_csv = false skips the CSV but can still write the Feather bundle;
  • most examples, started directly with SPACEAGORA_EXAMPLE_SMOKE=1, turn both off unless SPACEAGORA_EXAMPLE_SMOKE_RESULTS=1 is also set. The command-line tool's run --smoke sets both variables.

The CSV is simulation_results.csv in results_directory, or simulation_results_spacecraft.csv (and simulation_results_run.csv) with results_layout = :long. A relative results_directory is resolved against the directory Julia runs in.

Resolution: Check the SimulationSettings in your configuration:

SM.SimulationSettings(
    results   = true,
    save_csv  = true,
    results_directory = "output"
)

With make_example_config, the results and results_directory keywords control this. Its other required keywords are elided here:

make_example_config(
    ...
    results           = true,
    results_directory = "output/my_run"
)

Concurrent runs overwrite each other's output

Symptom: Parallel runs write to the same CSV, or the results directory holds extra files named simulation_results.<timestamp>.<process id>.<random number>.csv.

Cause: Several run_simulation calls are writing to the same results_directory.

Resolution: Give each run its own results_directory when you build its configuration: pass results_directory= to make_example_config, or set it in the SimulationSettings you construct for that run. A function that builds the configuration for a given directory, called once per run, does this cleanly. Mission Workflows shows a complete one, and its run_mission refuses a directory that is not empty.

The extra files are a safety net. When a run finds that another run created or modified simulation_results.csv while it was writing its own, it saves its rows under that unique name first and then overwrites simulation_results.csv, so the last writer's rows end up there.

isolate_state and mutable-state aliasing

Symptom: Repeated calls to run_simulation with the same configuration object produce different results, or the configuration appears modified after the first run.

Cause: By default (isolate_state=true) run_simulation deep-copies the configuration and runs the copy. With isolate_state=false it runs your objects themselves, so state the run writes into its models, such as a controller's held command or a model's log, stays in your configuration and the next run starts from it. A model is expected to reset its run state in its run-start initializer, and the conformance kit's initialize_resets check tests exactly that; a model of your own that skips the reset carries state from one run into the next.

Resolution: Keep the default unless you need the run's state afterwards. With isolate_state=false, do not share one configuration object between overlapping runs, and do not reuse it after a run that changes it:

run_simulation(config)                        # runs a deep copy of config
run_simulation(config; isolate_state=false)   # runs config itself; do not share or reuse it

NRLMSISE00AtmosphereModel network errors

Symptom: NRLMSISE00AtmosphereModel(use_space_indices=true) fails on the first atmosphere evaluation above 80 km with a network or download error.

Cause: With use_space_indices=true, the model reads F10.7 and Ap from CelesTrak space-weather data through SpaceIndices.jl, which downloads them on first use. Below 80 km it uses fixed values and needs no data, so the download happens at the first evaluation above that altitude.

Resolution: Fetch the data in a session with network access before the run, for example on a cluster login node before submitting the job:

init_nrlmsise_space_indices!()

Or use fixed indices instead:

NRLMSISE00AtmosphereModel(f107a=150.0, f107=150.0, ap=4.0)

GRAMAtmosphereModel not defined

Symptom: GRAMAtmosphereModel raises UndefVarError even though GRAM assets are present, or SM.GRAMAtmosphereModel(planet_name="earth") fails with a MethodError.

Cause: GRAMAtmosphereModel is not exported by using SpaceAGORA; it lives in SpaceAGORA.SimulationModel (SM.GRAMAtmosphereModel). Its keyword constructor comes from the SpaceAGORAGRAMSuiteExt package extension, which loads only after GRAMSuite is imported into the session.

Resolution: In a script, include examples/common.jl and call setup_gram_example!(). It imports GRAMSuite (from the data/GRAMSuite.jl submodule when needed) and defines GRAMAtmosphereModel in the calling module:

using SpaceAGORA
include(joinpath(pkgdir(SpaceAGORA), "examples", "common.jl"))
setup_gram_example!()
# GRAMAtmosphereModel is now defined in this module

Otherwise import GRAMSuite yourself and call SM.GRAMAtmosphereModel.

Verification study threshold failures

Symptom: julia --project=. src/interfaces/cli/main.jl telemetry quick --enforce=1 exits non-zero, prints Threshold failures: with the failing rows, and stops with Telemetry orbit accuracy thresholds failed for N row(s).

Cause: Either the simulation output diverges from the reference telemetry, or the thresholds are tighter than the model's current accuracy. The thresholds are the tolerances_quick and tolerances_full tables of each scenario in test/telemetry_benchmark_manifest.toml.

Checklist:

  1. Open telemetry_orbit_accuracy_summary.csv in the output directory (output/telemetry by default, or the one given with --output-dir). Each row has a pass column and the separate checks behind it (pass_points, pass_abs, pass_nmae, pass_rmse) beside the limits.
  2. Check the solver_retcode column to confirm each scenario's solve finished.
  3. The study sets its own solver tolerances and step caps for each profile. If you exported any SPACEAGORA_TELEMETRY_RELTOL_*, SPACEAGORA_TELEMETRY_ABSTOL_* or SPACEAGORA_TELEMETRY_DT_MAX_* variables, unset them and rerun.
  4. If GRAM is involved, verify the asset layout with julia --project=. src/interfaces/cli/main.jl assets check.
