Writing a GNC Algorithm

Which guide you need depends on what you are adding. A controller or estimator updates a value at each tick. A planner proposes a product, and an existing family checks that product before anything uses it. Defining the rules of a new family, or a service boundary for a companion package, is a change to SpaceAGORA itself.

What you want to addStart here
A controller that holds a command, or an estimator that holds an estimateFeedback controllers and estimators
A planner for an existing family: RPO, burn plans, joint references or EDGPlanning algorithms
A new family, its trusted validation, or a companion service boundaryContributor kit integrations

To keep your work in a repository of your own, see Building Your Own Research Repository: which starter to choose, how to pin SpaceAGORA and how to run the shared checks. Read Your First Script and the Extension Conventions before either algorithm guide. The Extension Hook Reference lists every hook's signature and default.

Which profile?

Use the feedback profile when each tick computes a command or an estimate from the current state. Use the planning profile when the algorithm proposes something that can be checked before it is used: a trajectory, a burn plan, a joint path or a guidance decision. One design can use both. In the RPO pilot a planner proposes references and an MPC controller tracks them, and the two share a link.

The two profiles use the same terms:

StepFeedback profilePlanning profile
Inputthe state at the tick, or a measurementan owned request snapshot built by trusted code
Outputa command or an estimatea product proposed in a result
Checkyour own limits, applied in the tickvalidation by the family, which can reject the product
Keepheld until the next tickinstalled into a link and used while it is current

The family side

The functions below belong to trusted code in SpaceAGORA. An algorithm for an existing family does not implement them; it implements the planning hooks instead. The GNC Algorithm Contract API gives their signatures.

PartFunctions
The familyvalidate_capabilities and validate_proposal check capabilities and proposals; install! installs an accepted product; is_current says whether an installed product may still be used; on_rejection and fallback_product decide what a refusal does; family_contract_version and algorithm_result_type declare the contract version and the result type; is_revision_request marks a request that revises the installed product; proposed_product reads the product from a result; installed_record and rejected_record write the run report's entries
The family's simulation integration, for AlgorithmGuidancefamily_request builds the owned request, family_link resolves the install target, and preflight_family checks the configuration before a run
The bindingalgorithm_runtime, bound_algorithm, bound_family and bound_link return its run state, algorithm, family and install target; build_algorithm_request builds an owned request; trusted_queries supplies queries that do not come from the algorithm; fail_algorithm_request! records a failed request and throws a GNCAlgorithmError

A new family follows Adding a GNC algorithm family, and a new family or companion service boundary goes through the Contributor kit integrations checklist. Both start with a pull request to SpaceAGORA. An algorithm for an existing family needs no such pull request and stays in your own repository.

House rules for both profiles

  • Draw random numbers only from the rng you are given, never from Julia's global stream. Planning functions take an explicit stream and have no default one, and the conformance checks rerun your model with the global stream reseeded.
  • Keep run state in the model (feedback) or in the state initialize_algorithm returns (planning), never in globals. A model resets its run state in its initialize_*! hook.
  • Keep a change a user makes between two runs. Some values are both user configuration and written by the run, such as a held command or a plan buffer's plan. Record a copy of each such value the model writes. In initialize_*!, reset an entry that still equals that copy to its value at the previous run's start. An entry that differs from it was changed by the user, so keep it as the new configuration. The built-in models follow this rule, and the burn scheduler applies it to its schedule. A robot-arm or RPO controller given a held command and no plan, for example, holds that command for the whole of every run.
  • Survive deepcopy. run_simulation runs a copy of the configuration unless isolate_state=false, and a link that two models share is still shared in the copy.
  • Give each spacecraft's copy fresh run state in bind_spacecraft.
  • Keep the output hooks pure: no control law, no warnings, no I/O and no large allocations. They run at every evaluation of the equations of motion.

Test your algorithm

Run SpaceAGORA's conformance checks on a configuration that exercises your model. The feedback guide shows the controller and estimator checks, and the planning guide shows each planner's requests and simulation. Start Julia with two or more threads so that the checks can compare concurrent runs with sequential ones. A pass shows that the interface behaves as the contract requires; validating the science is still your job.
