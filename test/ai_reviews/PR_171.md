## Findings

### P1 (must fix before merge)

**P1-1 (fixed): the precompile warmups stored this machine's topology in the package image.**

- The problem: the campaign warmups in `src/precompile_workload.jl` reach `machine_topology()` through `_machine_parallel_class()` (`adaptive_routing.jl:1120` and `:317`). That filled `ParallelProfiles._TOPOLOGY_CACHE`, which was then serialized into the pkgimage. Every process that loaded the image used the precompiling host's cores, affinity, cgroup quota and memory, and the `SPACEAGORA_CORE_BUDGET` and `SPACEAGORA_PHYSICAL_CORES` overrides stopped working at run time.
- The fix (afd5d9155, verified in code):
  - `_reset_process_local_state!` (`src/precompile_workload.jl:104-175`) clears the topology cache under its lock, and also the other process- or host-specific caches the workloads fill: the RHS calibration machine label and loaded store, hint overhead and state, the policy context, the ensured-constants set, the planner's constants, corrections and warm pool, the route-state and exit-hook flags, and the native-lock counters.
  - It runs at the end of both setup blocks (`precompile_workload.jl:199`, `src/SpaceAGORA.jl:469`) and again from `__init__` (`src/SpaceAGORA.jl:480`). A cache that a future workload forgets to clear is therefore still refilled in the process that loads the image.
- The test: `test/unit/parallel/precompile_state_tests.jl` runs, in a fresh subprocess, the workload bodies plus the reset. It checks:
  - every `const` `Ref`, `Atomic`, `Dict` and `Set` in the package's module tree against its value at load;
  - that the topology is unfilled at load and filled by the workload;
  - that `SPACEAGORA_CORE_BUDGET=3` is honored afterwards (`USABLE_CORES=3 SOURCE=override`).

  This runs the workload at run time, not through real precompilation, but the reset from `__init__` covers the difference. `test/probes/coverage_targeted_90_probes.jl` checks that the setup block clears the loaded flags (3d340db44).

### P2 (should fix)

**P2-1 (fixed): concurrent flagged `run_simulation` calls left the R7 environment behind.**

- The problem: two tasks running `SolverConfig(parallel=true)` did not nest, and `withenv`'s per-call save and restore left R7 in `ENV` after both had finished.
- The fix (72bd6cca9 and 95cc6bdf5; `src/simulation/engine/adapters/from_env.jl:490-548`, `:351-406`, `:464-488`):
  - The flag's variables go through a process-wide overlay under `_PARALLEL_FLAG_ENV_LOCK`. The first entry saves and applies them, later entries only count, and the last exit restores what the first saved, whatever order the calls finish in and whether or not they threw.
  - The engine-config path sends the flag's pairs through the same overlay and undoes its own per-call writes inside it.
  - `_with_parallel_flag` merges into the engine override set only within its own call chain (`_IN_ENGINE_ENV_SCOPE`).
- Tests: `test/unit/parallel/parallel_flag_concurrency_tests.jl`.
- Residual, accepted: while any flagged run is active, every task in the process, including a concurrent flag-off run, sees the R7 environment. A flag-off `withenv` on another task that interleaves with the overlay can still restore a flag value it saved mid-overlay. `_engine_active_config_ref` and `_engine_active_overrides_ref` remain process-global (pre-existing). Mixing flagged and unflagged runs concurrently in one process remains unsupported and should be stated in the guide.

**P2-2 (fixed, with a residual): plans that give each sample more than one thread were priced from single-simulation rows.**

- The problem: under an outer split the RHS heuristic serializes the flat routes and effector threading (`setup.jl:1418`, `:1471`, `:1593`), while the inner-speedup curve pooled `outer=0` and `outer=1` rows.
- The fix (3609b0bcd):
  - `rhs_inner_speedup_curve(stem; outer)` (`src/simulation/engine/rhs_calibration.jl:509`) filters rows by the outer flag.
  - `_run_campaign_predictive` builds two curves (`adaptive_routing.jl:1101`, `:1150-1151`): split plans (`threads@W+b`, mixed local slots at `b`) are priced only from `outer=1` rows, and the serial plan on the whole pool only from `outer=0` rows.
  - With no rows for a runtime, its multi-thread plans are not offered (`predictive_planner.jl`, `_predictive_inner_candidates!`).
- Tests: `test/unit/parallel/inner_speedup_curve_outer_tests.jl`.
- Residual: an `outer=1` row records what a plan pinned by a sweep under the split achieved. A sample reaches that speedup only if the store actually pins a plan for its own signature, which includes the thread budget. Otherwise the heuristic still clamps to one thread and the plan is overpriced. This is performance only; the margin rule bounds it.

**P2-3 (fixed): automatic calibration saved whatever conditions it ran under, and never redid it.**

- The fix (970e2d961; `src/parallel/cost/machine_calibration.jl:699-790`, `src/parallel/cost/cost_terms.jl`):
  - `MachineConstants.measured_threads` is recorded. Constants count as current only when they were measured with at least the current thread count; files that predate the field count as current.
  - Processes that share a working directory serialize on an exclusive-create `path.lock`. A lock older than 900 s counts as stale. Waiters wait up to 120 s and then read the saved file, or return `:deferred` without measuring.
  - Every persisted policy file is written through `RuntimeServices.write_file_atomically` (`src/simulation/runtime_services.jl:367`), with a temporary name unique to the host, process and write: machine constants, corrections, the RHS calibration store, and persistent hints.
- Tests: `test/unit/parallel/machine_constants_concurrency_tests.jl`.
- Accepted: a calibration can still run while unrelated load is on the machine, and processes in different working directories do not coordinate.

**P2-4 (accepted): the `:auto_stiff` solver changes for configurations with SRP, even with the flag off.**

- Where: `src/simulation/engine/solver_policy.jl:126-152`, commit ae99d0a3f.
- What changes: gravity-plus-SRP stacks now take the explicit Tsit5 fast path instead of `AutoTsit5(Rodas5P)`. This is a deliberate solver change, documented in the code and in `docs/architecture/third_body_cost.md`.
- Rationale for accepting it:
  - SRP's shadow model has kinks, not discontinuities, and the dynamics are not stiff.
  - On the 256-spacecraft case, AutoTsit5's false stiffness detection paid 5.58x the derivative evaluations plus the Rosenbrock path.
  - `SolverConfig.auto_stiff_gravity_tsit5=false` restores the old path.
- Trajectories differ only where the stiffness detector fired, and within solver tolerance. The PR description's "with it off routing and trajectories are unchanged" should mention this exception.

**P2-5 (fixed for `run_monte_carlo`; ensembles noted): `run_monte_carlo(...; parallel=true)` planned without knowing the workload.**

- The fix (6200274c6; `src/simulation/campaigns/monte_carlo.jl:941-956`): without `route_features`, `_monte_carlo_flag_tuning` sets `process_max_workers=1`, so the planner chooses only among in-process routes. A caller that describes the workload with `route_features` gets the process route back. The guide now says what a worker process needs.
- Tests: `test/unit/parallel/parallel_flag_process_route_tests.jl`.
- Still open, accepted: `run_constellation_ensemble` with the flag can still choose process workers. Its features come from the `SimulationConfiguration`, so the density family, spacecraft count and mission length are known and the GRAM and memory guards apply. What the features cannot see:
  - a custom model type defined in the script's `Main` (a density model, effector or guidance model);
  - SPICE kernels outside the default set.

  An ensemble built on either would fail per member on the pool. The guide's worker requirements apply to it too.

**P2-6 (accepted, documented limitation): the per-spacecraft native GRAM memory charge fell from 90 MB to 2 MB.**

- fb67c06cf states the measured domain in code (`src/parallel/routing/machine_topology.jl:256-271`) and in the guide: arcs of at most 1800 s, `num_steps_to_save = 20`, and no returned solutions.

The guide tells operators to set `SPACEAGORA_GRAM_SAT_MEMORY_MB` or `SPACEAGORA_PERF_WORKER_MEMORY_GB` from a measured worker. No term was invented for the unmeasured domain, which is consistent with the repository's "never invent a number" rule.

**P2-9 (open): the isolated GRAM pool does not reproduce the locked path's winds under perturbed wind mode.**

- The GRAMSuite revision CI pins defaults to perturbed winds, which are a random walk over each native instance's own call history. c2aac0ea0 restricts the pool identity test to `SPACEAGORA_GRAM_WIND_MODE=nominal`, because pooled winds diverge otherwise. Density and temperature match in both modes.
- When it bites: the pool is `auto` by default (`src/simulation/callbacks/density_callbacks/config.jl:89-127`), independent of the flag. It is active whenever `nthreads() > 1` and at least 1024 items in one callback reach native GRAM. So a large native-GRAM constellation with the environment's wind enabled, run under perturbed winds, now gets different winds, and therefore a different trajectory, than the locked path. The winds also depend on the pool width, which follows the thread count.
- Severity is P2 rather than P1:
  - the locked path's perturbed winds are themselves call-order dependent and are a stochastic model, so neither result is more correct;
  - the case is narrow: 1024 or more native-GRAM spacecraft in one simulation, winds on, perturbed mode.
- What is wrong regardless: reproducibility across thread counts is lost, and the pool's docstring (`config.jl:82-88`) still says "bit-identical to the locked path" without qualification.
- Fix: keep the pool `off` under `auto` when perturbed winds feed the dynamics, or seed each instance deterministically per spacecraft. At minimum, qualify the docstring and the user docs.

**P2-10 (fixed in 02799024c; the pattern predates this PR): the shared depot cache held a compiled image of the private dev GRAMSuite.**

- The `depot` job (`.github/workflows/julia-ci.yml:50-107`) runs the setup action with the default `gram: source` and `gramsuite-smoke: "true"`. That fetches the private `dev-GRAMSuite.jl` wrapper and SPICE kernels, instantiates `data/GRAMSuite.jl`, and loads GRAMSuite, which precompiles it into `~/.julia/compiled/v1.12/GRAMSuite/`. Before `actions/cache/save`, the job deletes only `compiled/v*/SpaceAGORA` and `compiled/v*/SpaceAGORAGRAMSuiteExt`.
- Why it matters: a Julia cache file holds the compiled code, and, as far as I know, the source text of the package's files (what `Base.read_dependency_src` reads back). I did not check that against the files. Caches on this public repository's default branch can be restored by any pull request workflow, including one from a fork that edits the workflow. The setup action's own comment says the dev tree "must never enter a cache or an artifact of this public repository".
- Scope: the dev source tree itself is never cached; `data/GRAMSuite.jl` lives in the checkout. `main`'s `julia-actions/cache@v2` steps already cached the same compiled image after the same dev fetch, so this is carried over, not introduced. The rework is the moment to close it.
- Fix (02799024c): the `depot` job now deletes `~/.julia/compiled/v*/GRAMSuite*` before the save and fails if any GRAMSuite image remains; `copilot-setup-steps.yml`, which also fetches the dev tree, now runs `julia-actions/cache` with `cache-compiled: "false"`. No cache entry scoped to the default branch existed when this was checked (`gh cache list`, 2026-09-28); all entries were scoped to pull-request refs, which other pull requests cannot restore.
- Other exposure paths checked, no finding:
  - artifacts hold only shard TOML reports, `src/*.cov` tarballs and telemetry CSVs;
  - the dev token is passed only to per-call Git credential helpers, never in URLs or persistent config;
  - the opt-in access trace (`SPACEAGORA_CI_GRAM_TRACE=1`) logs private file paths but no contents;
  - the docs workflow no longer runs `julia-actions/cache`.
