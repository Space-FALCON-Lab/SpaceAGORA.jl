# Review record: PR 409: fixed rho-adaptation interval for the RPO LQ-MPC solver

## Scope

Review of the SpaceAGORA `osqp-fixed-rho-interval` branch against main (14174a682,
v0.3.0). On main commit 25c2c3e05 a Julia CI coverage shard failed at
`test/unit/gnc/rpo_examples_planner_contract_tests.jl:170`
(`sol2.t == sol.t && sol2.u == sol.u`): the RPO CubeSat MPC example flown on the HYPR
planner path and again through `RetainedPathRPOPlanner` installed identical references
but flew different trajectories. The same shard passed on the next main commit.

Cause. The RPO LQ-MPC controller's OSQP workspace (`_rpo_lqmpc_workspace`) left
`adaptive_rho_interval` at OSQP's default, 0 ("automatic"). In OSQP 0.6.2 (the
`OSQP_jll` build used here, compiled with profiling), the first solve of a workspace
then compares the elapsed solve time with `adaptive_rho_fraction` times the measured
setup time at every iteration, and once it is exceeded writes the interval (the
current iteration rounded to a multiple of `check_termination`) into the workspace's
settings for all later solves. The iteration of the first rho update and the interval
therefore depend on wall-clock timing. Each run rebuilds the workspace
(`initialize_control!`), so each flight draws its own schedule, and a slower setup in
one of them (coverage instrumentation, a loaded runner) changes its iterates and
commands.

Change. `adaptive_rho_interval=25` in `_rpo_lqmpc_workspace`: rho is still adapted,
every 25 iterations, the solver's termination-check interval. No other setting of
this workspace depends on time (`time_limit` is unset; 0 disables it). The batch
example's reproducibility table lists the new setting, and three tests are
strengthened (below).

Authorship disclosure: this record was drafted by the author of the PR; it does not
replace an independent review.

Independent review: the coordinator reviewed the change under Giusy's delegation on
2026-10-18. The one source line sets a fixed `adaptive_rho_interval` in the workspace's
setup, so the rho schedule no longer comes from the measured setup time. Adaptive rho
stays on, and `time_limit` stays unset (disabled), so no remaining setting depends on
the clock. The new read-back test reads the setting back from the native workspace,
because OSQP.jl ignores unknown setting names, and it fails on main. The two restored
tests now compare exactly where they had been loosened for this variation.

## Findings

No P1 or P2 findings. Points a reviewer should check:

- Low, behaviour: RPO MPC results can change bitwise relative to main wherever main's
  automatic schedule was not "every 25 iterations from the first iteration". On this
  machine main's usual outcome already matched it: the example pair, a solver-level
  closed loop and the comparison batch give the same bits as main's typical run, and no
  test pins RPO MPC numbers. Runs on main that drew a different schedule (the
  intermittent ones) are the ones that change.
- Low: the value 25 equals OSQP's default `check_termination`, which this workspace does
  not set; rho updates and termination checks then fall on the same iterations, as
  OSQP's automatic mode also arranges.
- Low: OSQP.jl ignores unknown setting names when it builds the settings struct, so a
  misspelt key would be silent; the new unit test reads the native workspace back.
- Outside this change, by design: the RPO comparison planners (CHOMP, STOMP, RRT) and
  HYPR accept wall-clock planning budgets (`runtime_limit_s`, `max_runtime_s`;
  the comparison batch defaults to a finite budget with a large iteration cap).
  Plans under a binding budget depend on machine speed. The tests use infinite or
  non-binding budgets.

## P1 Assessment

No P1 findings. The change fixes one solver setting of one workspace constructor;
the problem data, tolerances, warm start and iteration limit are unchanged, and adaptive
rho stays on.

Unresolved P1: No

## Residual Risk

- RPO MPC trajectories may differ bitwise from results recorded on main before this
  change, in runs where main's timing-dependent schedule differed from a fixed interval
  of 25. Each QP solution meets the same solver tolerances either way.
- Results are now repeatable for a given build and machine. Across machines or
  instrumented builds, floating-point code generation can still differ (a coverage
  build gave other trajectory bits than a plain build here, from identical QP
  solutions), so tests should keep comparing runs within one process.
- Not changed: wall-clock planning budgets in the comparison planners and HYPR.
- OSQP 1.x changes the solver API and defaults; the interval should be rechecked with
  any OSQP upgrade (the new unit test reads it back).

Unresolved P1: No
