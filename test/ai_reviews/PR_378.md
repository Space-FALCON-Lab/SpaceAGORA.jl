# Review record: PR 378: check_sensor, and the built-in sensors through it (contributor kit K2)

## Scope

Review of the SpaceAGORA `conformance-sensors` branch (head `476cf9b4a`, one commit)
against main `427d9bbea` (the merge of #368, which added `SpaceAGORA.Conformance`).
This is K2 of the contributor kit approved on 2026-10-16.

The PR adds `check_sensor(sensor; fixture, seeds)` and `test_sensor` to
`SpaceAGORA.Conformance`. The checks use the engine's own sensor machinery: the
fixture mounts the sensor with `add_sensor!`, the engine samples it in its sensor
callbacks (which reset the run state and call `initialize_sensor!`), and a recording
callback reads each new measurement and, at the start, quarters and end of the run,
the truth (`_sensor_truth`) and mounting context (`actuator_context`) the engine passes
to `sensor_measure`. Run-level checks compare the sensor's measurement history (times
and values), bit for bit, the way K1 compares saved states. Nine checks:
`run_state_fields`, `requirements_supported`, `measurement_shape`, `repeatable_run`,
`deepcopy_equivalent`, `global_rng_independent`, `concurrent_equals_sequential`,
`seed_repeatable` and `custom_state_reset`. `conformance_fixture` gains `sensors=`,
which mounts the sensors on the first spacecraft's root link. The three built-in
sensor kinds run through the check, and every check id has negative controls.

Authorship disclosure: this record was drafted by the author of the PR. It does not
replace an independent review. Giusy accepted this record as reviewer on 2026-10-17.

## Findings

No P1 findings.

Points a reviewer should check:

- Medium, naming: the design lists `rng_only` among the sensor checks and
  `global_rng_independent` for every kind, with the same meaning. The report uses
  `global_rng_independent` for sensors too, so one id means one thing across kinds.
- Medium, overlap with #371 (navigation sensors): #371 adds `GNSSReceiver`, `SunSensor`
  and `Accelerometer` and lets sensors ask for the Sun's direction. The coverage rule
  fails until each new kind has an instance or an exemption, so whichever of the two
  merges second adds them to `sensor_instances()`. `requirements_supported` asks the
  engine (`add_sensor!` on a copy of the sensor), so it follows #371's rule without a
  change. #371 currently conflicts with main itself (`sensors.jl`, `registry.jl`,
  `SpaceAGORA.jl`, the API symbols), so the merge with K2 could not be run yet.
- Low, by design: `seed_repeatable` calls a sensor noisy when two calls of
  `sensor_measure` on one engine-built truth, with streams of two seeds, differ; only
  then must runs with the two seeds differ. A sensor configured without noise, or one
  that draws but discards its draws, is not required to change.
- Low, by design: `custom_state_reset` runs one deep copy of the fixture twice with
  `isolate_state=false`, so the caller's sensor is untouched by it;
  `deepcopy_equivalent` runs the caller's sensor itself, after all other runs.
- Low, overlap with `requirements_supported`: a record `add_sensor!` refuses for
  another reason (no `latest_time_s`, immutable) fails that check as well as
  `run_state_fields`.
