# Independent review of PR #580

## Scope

Reviewed commit `73f29a06bc1a460e3eeea81dd6f225d77e6fb742` against `origin/main`, including the public interfaces, scoped restart path, process isolation, SPICE reconstruction, tests, and documentation. This is a bounded experimental service for forecasts captured at the first pre-command operation of a supported controller tick. It does not integrate the MPC search into a live campaign or establish mission accuracy.

The review included inspection of the implementation and local verification logs; it was not an independent rerun of the full suite. The reproducible scope and limitations are recorded in `docs/quality/control_forecast_verification.md`.

Also reviewed the new fixture and unit tests, test registration, public API inventory, documentation navigation, user guide, extensibility note, and verification record.

## Findings

No unresolved findings in the documented supported path. The following P2 findings from the implementation review were addressed before the reviewed commit:

- `control_forecasts.jl`, snapshot data guard: remote references and custom array storage could retain shared external state. Remote references/channels are rejected, and supported arrays are limited to the explicit owned-storage types.
- `control_forecasts.jl`, worker initialization: an arbitrary worker kernel pool and stale ephemeris reuse caches could change forces. File contents are verified before pool mutation; replay resets managed furnishing state, preserves kernel order and duplicate loads, and clears the engine reuse cache. Meta-kernels and programmatically assigned pool state remain unsupported.
- `control_forecasts.jl`, execution lifecycle: simultaneous forecasts could interleave process-global SPICE state, and nested worker creation could bypass a same-process check. The complete evaluation is locked, nested capture and worker creation are rejected, and a dedicated process is required.
- `control_forecasts.jl`, input contract: unsupported hardware/state and scoped engine overrides could escape the preservation contract. The supported scope is explicitly checked, the resolved solver and relevant environment are preserved, and overflowing/nonfinite forecast end times are rejected.

The pending-tick treatment is necessary: the run clock advances its periodic index before invoking the controller. Capturing an ordinary checkpoint at this boundary would skip the current command. The forecast snapshot explicitly restores that tick as pending.

## Residual Risk

The caller must capture before applying its current command and supply trusted controller code with complete model-state hooks. The data guard is not a security sandbox and cannot prove that arbitrary user methods avoid global state. A dedicated worker must not concurrently run unrelated simulations. The supported model, geometry, hardware, atmosphere, clock, and kernel restrictions are deliberate limits, not evidence of broader compatibility.

Both inspected full documentation builds (`forecast-docs-build-v1.log` and `forecast-docs-build-v2.log`) reached document and cross-reference checking but stopped before rendering on HTTP 429 responses from existing GitHub links. Neither is a successful full build; the normal link check remains enabled and a successful build is still required.

Both full-force cases place the incoming Cartesian state at the scenario start epoch solely to test restart equivalence. The completed longer case extends this bounded engine comparison through an atmospheric pass and the next physical apoapsis, with interpolated crossing agreement. It does not establish targeting accuracy, absolute event accuracy, campaign performance, handover, or operational search cost. The forecasts replay a fixed plan; they do not run the optional apoapsis search. Runtime MPC wiring, broader configuration qualification, and mission-level acceptance remain separate work.
