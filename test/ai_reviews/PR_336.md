# PR review: robot-arm binding gives each spacecraft its own controller state

## Scope

Review of PR 336 (branch `robot-arm-bind-fresh-state`, head `4374bdc32`) against `main` at `58b8dbc40`: `git diff main...robot-arm-bind-fresh-state`. Two code commits (`05e29dedc`, and `4374bdc32` after review) plus this record's commit. `bind_spacecraft(::RobotArmControlEffector, i)` gives the bound copy a deep copy of the controller and of the held command. The `bind_spacecraft` docstring now states which members a bound copy owns.

Authorship disclosure: the author of the PR drafted this record. It lists what the author checked and what the independent reviewer must verify; it does not replace that review.

- `src/models/gnc/control/control_hooks.jl`: the `RobotArmControlEffector` method of `SimulationLifecycle.bind_spacecraft` sets `b.controller = deepcopy(m.controller)` and `b.held = deepcopy(m.held)` on the shallow copy (the first commit set `b.held = RobotArmHeldActuation()`; see Findings).
- `src/models/gnc/interfaces/simulation_lifecycle.jl`: `bind_spacecraft` docstring. A member that holds one spacecraft's run state needs its own copy; members indexed by spacecraft (such as `ApolloDescentState`) stay shared.

Outside `src/`: `test/unit/spacecraft_gnc_tests.jl` (new binding tests, and one existing assertion inverted); `test/ai_reviews/PR_336.md` (this record).

## Findings

Author's notes for the reviewer (no P1 known to the author; the one P2 raised in review is resolved):

- Resolved, P2 from a review comment on the PR: the first commit gave each bound copy a fresh `RobotArmHeldActuation()`, which dropped a held command configured on the template. With no plan, `calcControlEffect!` returns before writing `held` (`robot_arm_control.jl:185`), so such a copy commanded zero for the whole run. `4374bdc32` deep-copies the template's held command instead; a new test covers the case and fails on `0c61c3de9`.

- Low, scope: on `main` the shared state changed no output. `robot_arm_joint_mpc_control` writes `U_prev` (`robot_arm_control.jl:127-128`) and nothing reads it (the solve is `ctrl.H \ rhs`; the only other `U_prev` access in `src/` is the RPO controller reset in `planner_lifecycle.jl:127`). `calcControlEffect!` assigns a new `RobotArmHeldActuation` to `held` on every tick (`robot_arm_control.jl:196`) and never changes it in place. The fix removes a latent coupling.
- Low, behaviour change by design: the per-spacecraft GNC testset pinned `bound.held === arm.held` ("retain nested mutable members"). That assertion is inverted.
- Note: the copy's controller and held command start from the template's current values, including any `U_prev` or held command left by an earlier run with `isolate_state=false`. That matches what the shared object held before; resetting the warm start at run start is a separate question for the GNC runtime work.
- Note: `controller` is typed `Any`; `deepcopy` also handles `nothing` (the default) and user-defined controllers.

Reviewer to verify:

- Only effectors declared on a spacecraft pass through `bind_spacecraft` (`_flatten_spacecraft_gnc`, `execution.jl:405-416`); configuration-level robot-arm effectors, which every tracked example and test except the binding tests uses, are unchanged.
- The `plan` stays shared and is not mutated during a run (`RobotArmPlan` is an immutable struct; the effector only samples it).
- The new binding test fails on `main` (the first controller-identity assertion), and the inverted assertion fails on `main`.
- The docstring sentence agrees with the other built-in methods: the momentum manager gives the copy its own `mounted_levels`, and the Apollo models share `state` and `actuators`, which are indexed by spacecraft.

## P1 Assessment

No P1 findings known to the author. The control law reads neither shared member, and each copy starts from the template's values, so torques and every saved output are unchanged for existing configurations; the only observable change is object identity of `controller` and `held` in bound copies.
