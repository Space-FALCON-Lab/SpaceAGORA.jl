## Findings

Author's notes for the reviewer (no P1 known to the author):

- **Design, medium: what "reset" means for a value a user can configure.**
  Several built-in models keep, in one field, both a value the user may configure
  and the state the run then writes: the robot arm's, RPO controller's and momentum
  manager's held commands and accumulator, the deprecated RPO guidance's goal and
  plan buffer, and the plan buffer. Each records its value at its first
  `initialize_*!` and restores it at every later one: two runs start equal, the
  read-back after a run is unchanged, and a held command configured with no plan
  stays the command for the whole run (the PR 3 review point, #336). Edits made to
  those fields between two `isolate_state=false` runs on one object are replaced.
  Pure run state (Apollo entries, command states, burn windows and flags, warm
  starts, logs, mounted levels) starts as a new model holds it.
- **Design, medium: the burn scheduler restores only what it wrote.** Its `Δv`,
  `direction`, `start_burn_time` and `stop_burn_time` are its configuration, and
  the scheduler also writes them during a run (sign normalization, guidance
  commands, planned and cleared windows). The scheduler records its last write per
  spacecraft; at the next run's start an entry still equal to that write returns
  to its value at the previous run's start, and any entry changed since is the new
  configuration. So a sweep that edits `Δv` between `isolate_state=false` runs keeps
  working.
- **Design, medium: the plan buffer must start with a plan.** The engine's coupled
  compliant arm sizes the arm's state from the controller's plan when the run is
  built, and drives the arm toward that plan at each right-hand-side evaluation.
  A buffer-fed controller therefore needs the plan the arm starts from;
  `RobotArmPlanBuffer(model, base_pose, q_start)` holds the arm still. The
  controller's pre-run check refuses an empty buffer. The engine reads the arm's
  plan through the buffer, so the arm follows each installed plan from its install
  time. `check_link` refuses a buffer that starts with a plan for another arm or
  base pose than the planner's settings, because the state is sized from it.
- **Design, low: requests start from the measured joints.** The coupled arm state
  always exists for a buffer-fed controller, so the request's start joints are the
  arm's measured joints and the settings take none. Under gravity the measured
  joints drift slightly while the arm holds; the installed plan starts exactly at
  the request's start (validated to 1e-9 rad).
- **Design, low: the binding produces its configured link.** `AlgorithmGuidance`
  now declares `Produces(link)` for a configured link, for every family. A link
  type without methods keeps the defaults (any cardinality, no check, no
  initialization), so the burn-plan family (no configured link) and other links
  behave as before; the binding's own one-binding-per-target refusal still runs
  first.
- **Low: the RPO controller's solver workspace is rebuilt at each run's start.**
  `deepcopy` already rebuilds it for `isolate_state=true`, so a first run is
  unchanged (parity below); a reused controller no longer starts from the previous
  run's dual iterates.
- **Low: the deprecated `RPOGuidanceModel` resets.** G-8 covers every built-in
  model. Its pre-run check reads the buffer before the reset, so on a reused
  object whose first run planned, the check that HYPR is loaded is skipped; the
  first run needed HYPR anyway.
- **Low: one controller per plan buffer.** Bound copies of a buffer-fed controller
  share the buffer, so a template declared on two spacecraft is refused by the
  link's cardinality, as two bindings on one link are by the binding.
- **Low: clearance is sampled at the reference's samples** (design 4.3: "sampled
  clearance"), link by link with the existing clearance function.
- **Note: the kit's new checks.** `initialize_resets` for guidance and control is
  required from 0.3.0, the kit's first release (K-4: checks of the first release
  are required). Control reports gain it after the four run-level checks, guidance
  reports before `bind_fresh_state`; code that reads check ids by position sees the
  new order.
- **Note: root exports.** `BaseThrusterModel` and `PropulsiveBurnPlan` were
  reachable only as `SpaceAGORA.SimulationModel.*`; they are now root exports with
  their docstrings on the root bindings. `PropulsiveManeuverCommand`, the thruster
  guidance's command, stays unexported: neither family uses it.
- **Note: registry.** The eight lifecycle hooks are rows of a new "GNC lifecycle"
  group with `:page` gaps (no page names them yet; the docs bundle adds the GNC
  page). The family's names are in a section that holds no hook, as for the
  burn-plan family.

Reviewer to verify:

- That `algorithm_lifecycle.jl` stays free of family-specific code (the
  acceptance rule): its only change is the generic `gnc_links` method.
- The bitwise argument for first runs: every reset either restores the value the
  first `initialize_*!` recorded, or sets the value a new model has; the engine
  lookup is unchanged for effectors without a plan buffer.
- That the reset rules match G-8 for each model listed above, and that no
  built-in model with run state is missed (the coverage test enumerates the types).
