# AI Review — PR 64: tilted-dipole sign fix + IGRF field source for MagneticTorqueRodModel

## Scope
Two related magnetic-environment changes found while wiring an IGRF option for the CYGNSS rotational campaign (FM4 carries no magnetometer telemetry, so its torque budget needs a modeled field):

1. **Sign bug (correctness): `get_magnetic_field_dipole` returned the antiparallel field.** `M_HAT_ECEF` points at the north magnetic pole, but Earth's dipole *moment* points toward the geomagnetic south; with the formula's leading minus sign the returned field was ~170 deg from IGRF at LEO. Physical pins that the fix satisfies and the old code inverted: equatorial field = +B0 along the pole axis (north); field above the north pole = −2·B0 (down).
2. **IGRF field source (feature, opt-in): `MagneticTorqueRodModel(field_model=:igrf, igrf_year=...)`** evaluates IGRF at the spacecraft's geodetic position in both the `wrench` path (geodetic coordinates already on `PlanetFrameSample`) and the legacy `calcForceTorque` path (via `rtolatlong`). One epoch per model by design — secular drift over a sim is negligible and it keeps calendar conversions out of the integrator loop.

## Changed Files
- `src/dynamics/coupled/perturbations.jl` — sign fix in `get_magnetic_field_dipole` (with derivation comment); `MagneticTorqueRodModel` gains `field_model::Symbol=:dipole` / `igrf_year::Float64` with a validating kwarg constructor (zero-arg construction unchanged); new `_magnetic_field_inertial` helper owning the field-source dispatch and the nT→T conversion for the IGRF branch; both call sites routed through it; `get_magnetic_field` docstring corrected (it computes IGRF, not WMM, and returns the inertial frame in nT — documented as NOT interchangeable with the Tesla-returning dipole function).
- `src/dynamics/coupled/force_torque_models/perturbation_effectors.jl` — import `rtolatlong` via `AerodynamicEffectors` (which owns a `reference_system.jl` include) instead of adding another include copy.

## Findings
- P1 (fixed): dipole field sign. Blast radius: any simulation with a nonzero `Magnet` dipole moment or the study's telemetry magnetorquer effector had every magnetic torque sign-flipped. No in-tree scenario, example, or test configures magnets (grep audit), so default physics and all CI-gated results are bit-identical. `benchmarks/studies/cygnss_attitude_torque_reconstruction/common.jl` reuses `get_magnetic_field_dipole` directly and inherited the flip — plausibly why measured-dipole magnetic replay degraded attitude accuracy in that study; its results deserve a rerun (flagged to the PI, not part of this PR).
- P2 (addressed): IGRF units — the library returns nT while the dipole path returns Tesla; the helper converts so both branches share one unit contract, and the docstrings now state the difference explicitly.

## P1 Assessment
The sign fix is validated three independent ways: analytic pins (equator/pole direction and magnitude), cross-validation against IGRF (<35 deg alignment at four LEO points spanning both hemispheres — was ~170 deg), and consistency with the private-repo FM4 torque-budget scripts whose correctly-signed dipole and IGRF fields produce consistent residual-dipole estimates.
Unresolved P1: No

## Tests Added/Updated
- `test/probes/coverage_parallel_telemetry_probes.jl` — "Magnetic field: dipole sign fix + IGRF source option": constructor contract (defaults, `:igrf` year requirement, invalid source rejection); the two analytic sign pins; IGRF-vs-dipole magnitude band and alignment at four LEO points; `wrench` plumbing with a real `Magnet` on a `make_three_body_spacecraft` (torque = m×B for both field sources, zero force, τ⊥m).

## Residual Risk
- The legacy `calcForceTorque` `:igrf` branch is exercised indirectly (same helper as `wrench`) but not end-to-end in the probes.
- `igrf_year` is user-supplied; a mismatched epoch degrades gracefully (secular drift ~0.1%/yr).
- Downstream users of the (dead-code) `get_magnetic_field` should note its nT/inertial contract is now documented; behavior unchanged.
