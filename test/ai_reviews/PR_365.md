# PR review: the planner path's geometry provider, hold fallback and HYPR retiming

## Scope

Review of PR 365, the `rpo-planner-contract-extensions` branch (head `bc51e5115`) against
`main` at `923fb06d7`: `git diff main...rpo-planner-contract-extensions`. One commit.

GNC PR 19b (G-11 = b, G-14 = a): the three contract extensions that make
`make_rpo_configuration` with `PlannerGuidance` a replacement for the deprecated
`RPOGuidanceModel`: geometry that changes during a run (a provider with
revisions), a hold installed when a request is rejected (the RPO family's
`:install_fallback` policy), and `retime_rpo!` for `HYPRRPOPlanner`. All three are
opt-in. They build on #347's request driver: the hold is `on_rejection` plus
`fallback_product`, retiming goes through `is_revision_request` and
`propose_revision!`. No parallel request path. The examples move to the planner
path in PR 19c.

that review.

## Findings

Author's notes for the reviewer (no P1 known to the author):

- **Medium, open decision: validation often refuses HYPR retimes under an
  acceleration limit.** `retime_rpo!` times the active reference's polyline with
  HYPR's tangential retimer at the request limits reduced by the 1% headroom, as a
  new plan does. While turning at the full tangential limit, the vector
  acceleration the common validator measures can exceed the request limit. Seen
  locally: in legacy mode from a start 1 cm or more off the reference (adapter
  fixture, limit 0.1 m/s²), and in manuscript mode in the 2 s pilot run, about 5%
  over the limit. The validator refuses (`:failed/:reference_rejected`): with
  `on_rejection=:install_fallback` the chaser holds, with `:fail` the run stops.
  Nothing is relaxed. The contract page already says HYPR's tangential limit can
  exceed the vector limit and that a new reserve must be a prospective setting.
  A retime-specific reserve (for example a tangential limit of a/√2, which bounds
  the vector to about the limit) is a policy choice left open; 19c needs either
  that decision or the fallback. Documented in both pages and pinned by tests.
- **Design, medium: the binding configures the family (`bound_family`).** The
  rejection policy belongs to the simulation, not to the planner, and the family
  is declared by the algorithm. The driver therefore asks the binding
  (`bound_family`, default unchanged) and refuses another family type. This is an
  addition; no existing contract signature changes. `RPOReferenceFamily()` still
  constructs the default, and default instances compare `===`.
  `family_contract_version` stays 1.0.0 because the request, product and
  validation are unchanged; the reviewer may prefer 1.1.0 for the new policy.
- **Design, low: the revision trigger keeps a reference that still clears.** When
  the provider's revision changes, the remaining polyline of the installed
  reference is checked against the new snapshot with the trusted `clearance_at`,
  the request clearance and the validation sample spacing and cap (over the cap
  counts as blocked). Clear: kept and recorded. Blocked: `:replan`. A hold is
  always replanned. The legacy model differs: it brakes before every replan and
  retimes below a larger clearance margin. Both policies are documented.
- **Design, low: hold triggers.** One retry when the chaser settles on a hold;
  renewal by a `:replan` request when the hold would no longer be current at the
  next reference step; a revision change replans it. A rejected retry or renewal
  waits for the next renewal, revision or event, so a persistent refusal costs one
  request about every `plan_validity_s` less the preview. Tracking-error replans
  are suspended while holding. Renewal assumes guidance ticks every reference step
  (as `make_rpo_configuration` configures); a slower guidance rate can let a hold
  expire between ticks, which fails the run with `:expired_reference` as before.
- **Low: the hold is not validated.** It is the family's fallback, installed after
  the rejection is recorded. A hold inside a newly appeared obstacle is still a
  stop at the current position; the next revision change replans it.
- **Low: provider failures.** In a tick they fail the run as
  `:geometry_provider_exception` (or `:invalid_geometry_revision` for a non-string
  or empty revision); inside a request the driver reports them as the binding's
  `:planner_exception`, like any exception there.
- **Low: run reports keep their fields.** The policy and provider are not added to
  `rpo_run_report`, so reports of runs without the options stay identical. Their
  effect is in the records (`event=:trigger`, `:fallback_installed`) and in each
  request's geometry and revision.
- **Note: the legacy route rule is duplicated on purpose.** Extracting it from
  `rpo_retime_existing_plan` into a shared function changed the last bit of the
  projection point (a different compiled context; StaticArrays' `dot` may fuse
  multiply-adds). The adapter therefore keeps its own copy (`retiming_route`), and
  the legacy function is untouched so the legacy model's runs stay bitwise. The
  copy goes when the model is removed (PR 21).
- **Note: #353's warning text changed.** It now names the replacements for the
  spheres, hold and retiming, and says the model will be removed in a later
  release (G-14 = a). Still a plain `@warn ... maxlog=1`; the compatibility test
  still finds the three names it checks.
- **Note: the HYPR companion is untouched.** The retime calls only functions core
  declares and HYPR already implements (`rpo_sample_path_with_params`,
  `rpo_retime_sampling_ds_m`, the configured `rpo_retime_profile`,
  `rpo_reference_from_path`) plus core kernels. The HYPR files holding them are
  unchanged between the pinned revision and the F-H candidate (HYPR 0.2.0).

Reviewer to verify:

- **Defaults are today's behaviour:** with no provider, the `:fail` policy and an
  infinite retime threshold, `calcGuidanceEffect!` takes the same branches, pushes
  the same records and draws nothing more; `bound_family` returns the declared
  family.
- **No parallel path:** every request, the hold and the retime go through
  `run_algorithm_request!`; nothing installs into the plan buffer elsewhere.
- **Atomicity is unchanged:** nothing new runs between validation and `install!`.
- **The provider is called only from guidance ticks and request building**, never
  from the right-hand side.
- **`remaining_clearance` matches the validator's sampling** (spacing, cap,
  endpoints) and fails toward replanning (NaN and the cap count as blocked).

## Residual Risk

- Retiming under an acceleration limit is often refused until the reserve decision
  (Findings); with the fallback the run holds instead of retiming.
- A reference kept after a revision change keeps its original geometry revision;
  only the trigger record shows that it was checked against the newer geometry.
- The hold is a stop at the current position, not a safety certificate.

## Update after review (cceac4929)

- **Resolved: interval replans during a hold.** The automated review found that,
  with `on_rejection=:install_fallback` and a finite `replan_interval_s`, interval
  replans still ran during a hold. Each refusal installed a new hold and allowed
  another settled retry, so a planner that kept refusing was asked at every
  interval. The "Design, low: hold triggers" note said one request about every
  `plan_validity_s`; that holds only after this fix. The interval and
  tracking-error conditions in `calcGuidanceEffect!`
  (`src/models/gnc/planning/rpo/planner_lifecycle.jl`) are now gated on no
  active hold. The `make_rpo_configuration` docstring
  (`src/models/gnc/planning/rpo/configuration.jl`) and the pilot guide say so.
  Impact before the fix: planner cost; the hold stayed installed.
- **Test:** "Hold fallback" in `test/unit/gnc/rpo_planner_extensions_tests.jl`
  adds a one-tick interval with a refusing planner: 3 requests in 1 s, one settled
  trigger, two holds. Without the fix it reports 10 requests.

## Update after review (aa63168ea)

- **Resolved: overwritten default constructor.** `RPOReplanningSpheres`
  (`src/models/gnc/planning/rpo/configuration.jl`) had one typed field, so Julia
  gave it an untyped default constructor, `RPOReplanningSpheres(::Any)`. The keyword
  form `RPOReplanningSpheres(spheres; ...)` replaced it. Precompilation refuses
  method overwriting, so precompiling the package failed (coverage shard,
  `test/unit/parallel/precompile_state_tests.jl`). Calls with a configuration were
  unaffected: Julia's typed default constructor handled them. The configuration
  form is now the only inner constructor, and the keyword form is a separate method.
  The other new types of this PR cannot hit this: `RPOReferenceFamily` has only a
  keyword inner constructor, `TriggerState` no outer constructor. A package load
  with `--warn-overwrite=yes` reports no overwrite.
- **Test:** "Replanning spheres: revisions and snapshots" in
  `test/unit/gnc/rpo_planner_extensions_tests.jl` checks both constructor forms. It
  documents them; the regression itself is caught by precompilation, which the
  precompile-state test performs in a fresh process.
- **Evidence on aa63168ea:** the precompile-state test with `--code-coverage=user`
  and a real precompile, 5/5 and 8/8; extensions 88/88, adapter 163/163, lifecycle
  155/155, compatibility 60/60; 33/33 PR gates.
