# Review record: PR 413: Tick periodic GNC models at checkpoint segment boundaries

## Scope

Review of the SpaceAGORA `checkpoint-boundary-ticks` branch against main
(c7db8b6fb, v0.3.1): 0.4.0 PR 3a, the periodic tick that a checkpointed run
skipped at each segment boundary. The fix (3faa50ac2), a CI fix (d66e9e82e) that gives the new callback's affect the
shape of DiffEqCallbacks' `PeriodicCallbackAffect`, whose `affect!` field suite 02
and the threaded coverage probe call directly, and this record (with a test-comment
correction).

A checkpointed run solves consecutive segments, and each one initialized its
callbacks again. `PeriodicCallback` restarted its tick grid at each segment's
start and never ticked at a segment's final time, so a navigation, guidance or
control tick on a boundary was lost, a boundary off the grid shifted every later
tick, and a resumed run restarted the grid at the resume time. #401 and #405
scheduled their test ticks off the boundaries because of it. This PR re-implements
on current main (after the H4 tick renames, #401 and #405) the fix written on
2026-10-15 as the local branch `checkpoint-periodic-ticks` (c79f98aa0), and adds
the case that branch left open: a run resumed from the checkpoint written at the
end of a finished run, to extend it.

- One periodic callback (`SimulationCallbacks._run_clock_periodic_callback`, new
  file `callbacks/periodic_tick_callbacks.jl`) for navigation, guidance and control
  effectors and the mounted burn tick.
- In a checkpointed or resumed run the engine sets a run clock in the shared
  buffers (origin 0, horizon the mission end). The callback then ticks on the run's
  grid, including at a segment's final time before the run's end: after the step
  to that time, before the rows saved there and before the checkpoint written
  there.
- A run does not tick at its own end, so a checkpoint written there now records the
  ticks due then as pending (`runtime_state.periodic_ticks = (version=1, pending_s=t)`).
  A run resumed from it takes them when its first solve starts (as
  `PeriodicCallback(...; initial_affect=true)` would), before the rows saved there.
  A checkpoint written at a segment boundary has no entry.
- Control models learn the grid's origin through `gnc_clock_started!` (at the run's
  start and at each solve's start): 0 in a checkpointed or resumed run, the solve's
  start otherwise (unchanged).
- Without checkpoints or a resume the run clock is unset (NaN) and the callback is
  `PeriodicCallback(f, dt)`: the same tick times, condition (including the
  `maxiters` guard), stops, `save_positions` and initialization.

Authorship disclosure: this record was drafted by the author of the PR. The plan
assigns behaviour PRs an independent reviewer (the PI, or the second reviewer when
available); this record does not replace that review.

Independent review: the coordinator reviewed the change under Giusy's delegation on
2026-10-19. Without a run clock (a run in one solve) the new callback ticks as
`PeriodicCallback` did: from the solve's start, never at its final time. The identical
fingerprints show it. A checkpointed or resumed run keeps one grid from 0 to the
mission end, ticks at segment boundaries, and reports that origin to
`gnc_clock_started!`. A checkpoint written at the run's end records the ticks due there,
so a resume that extends the run takes them first; a mismatched entry is refused. Each
task keeps its own tick clock, so concurrent solves of one callback do not share a
phase. Residual, low: each callback's clock lives in task-local storage under a fresh
key per run and is never removed, so a task that runs many simulations in a row keeps a
few small entries per run.

## Findings

No P1 or P2 findings.

Points a reviewer should check:

- By design: a resumed run's grid starts at 0 (the run's start), as the sensors' sampling grid does since #401. Resuming a checkpoint written by 0.3.x, whose segments restarted the grid, continues on the run's grid from the resume time on; such a checkpoint has no pending entry, so the resumed run takes no tick at its start.
- By design: a checkpoint written at the run's end now always carries `runtime_state` (the pending entry), where it carried none before for a run without interlinks, batteries, faults, sensors, hinges, gimbals or model state. Readers that require `runtime_state === nothing` for such a file would see the difference; none in the repository does.
- Low: the pending entry is written for every end-of-run checkpoint, whether or not the run has periodic models; it is a time and a version.
- Low: a run that stops early (an event's `terminate!` or a failed segment) writes its checkpoint at the stop time, before its end, without a pending entry; a tick due exactly at that time is not taken on a resume.
- Low: the callback reads the stale `integrator.sol.prob.tspan` only without the run clock, as `PeriodicCallback` does; under the run clock the run's end replaces it (a cached integrator moved by `reinit!` keeps the first segment's `tspan`).
- Pre-existing, unchanged: the multirate solver's sub-solves pass `reinit_callbacks=false`, so periodic ticks are lost there with or without checkpoints; `SavingCallback` restarts its `saveat` grid at each segment.
- GNC PR 20 (another 0.4.0 PR) changes the tick callbacks' `skip_inactive` default; this PR leaves `_gnc_tick!` and `gnc_scope.jl` alone, so whichever merges second merges main in.

CI on 3faa50ac2: suite 02's callback test calls `navigation_cbs[1].affect!.affect!(integrator)` (as does `test/probes/coverage_threaded_probes.jl`), which reads `PeriodicCallbackAffect`'s field; the closure the first commit used has none. Fixed in d66e9e82e (a callable struct with that field). The other failures on 3faa50ac2 were the missing review record (ai-review-artifact-gate, and nightly-stress, whose other gates passed) and the jobs that aggregate suite 02's shard.

Update (review P2, thread 4310927423 on `resume_checkpoint.jl`): the finding held that a checkpoint written where a solve stopped early at a grid time, with no pending entry, would make a resume skip the tick due then. Checked against the installed OrdinaryDiffEqCore 4.18.0 (`handle_callbacks!`) and DiffEqBase 7.21.2 (`apply_discrete_callback!`): a step's continuous event is applied first and every discrete callback after it, terminated or not, so the tick due then runs before the checkpoint and no entry is needed. All four built-in terminations (impact, touchdown, orbit count, entry count) are vector continuous callbacks; the interlink scheduler never terminates; the mission-segment deadline terminates from a discrete callback, but `run_mission` refuses checkpoints. The check found a crash instead: such a tick then scheduled its next stop on the stops `terminate!` had emptied (`maximum` of an empty array), so the run threw before its command, as with `PeriodicCallback` on main. Fixed in 44300dbb1: no next stop after a termination, and a comment at `_periodic_tick_checkpoint_state`.
