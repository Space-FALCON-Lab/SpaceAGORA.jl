## Findings

No P1 or P2 findings.

Current behavior that the new testset pins, and this PR does not change:

- **When a solve throws, the two branches leave different rows.**
  - A single solve's partial output holds the rows saved up to the failure (from `saved_values`).
  - A checkpointed run's holds only the segments it finished: the failing segment's rows are in `saved_values` but are not appended before the rethrow.
- **When a solve ends without success,** a checkpointed run's partial output also holds the failing step's final state. `_append_checkpoint_saved_segment!` adds it, so the last row can fall between save times. A single solve's ends at the last regular save time.

Points a reviewer should check:

- **Statement order is kept.** The trace push, then the row collection, then `last_sol`, then the retcode check, in each branch as before.
- **`args` in the tuples.** `args` is boxed in `run_simulation` already, as on main. The tuples read it once, after its last assignment (the `isolate_state` copy). The solver call and the saves see the same object as before.
- **No name shadowing.** `solve_setup` does not shadow `solve`. `run_simulation` makes no `solve(` call.

## Residual Risk

- **Partial-output differences are pinned, not resolved.** In a checkpointed run, a throwing solve leaves no rows from its failing segment, while a failing retcode leaves them and the failing step's state. Single solves differ from both. Making them uniform would be a behavior change, outside C5.
- **`return_solver_metadata` on a checkpointed run is not in the testset.** It returns one trace entry per segment (checked by hand on the branch: three entries for three segments). The `push!` moved into the helper and still runs once per solve. Separately, `run_simulation`'s docstring says checkpoint writing "cannot be combined with `return_solver_metadata=true`", but nothing refuses the combination. That doc/code mismatch is older than this PR and is reported separately.
- **The mutation checks evaluate variants in one process.** They show the testset detects each change; they are not separate CI runs.
- **The `Core.Box` count is syntactic.** It shows no new boxed variable in `run_simulation`'s lowering. It does not measure allocations or runtime, which this PR does not claim to change.
