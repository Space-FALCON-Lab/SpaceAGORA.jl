# Review record: PR 437: burn edges keep an inactive spacecraft's command released

## Scope

Review of the SpaceAGORA `burn-edge-inactive` branch against main (`4f727266b`): the
fix for finding 5 (P2) of the interface program's outside review of 2026-10-20,
"a later burn edge rearms an inactive spacecraft's released mounted command".

Since 0.4.0 (#411) a model's periodic tick is replaced by `release_command!` while
its spacecraft is inactive (`skip_inactive`, true by default), and the burn
scheduler's mounted tick follows that rule. The scheduler also writes its mounted
engine level outside that tick, in `refresh_burn!`, which two callback paths call
for every spacecraft:

- the burn-edge callback, at each end of a burn window and when a burn-plan
  family installs a plan;
- each scheduling pass (`_schedule_thruster_control!`): the initialization
  callback at every solve's start, and the rescheduling when a spacecraft leaves
  the atmosphere.

Neither path checked inactivity. A spacecraft deactivated before its ignition got
its engine back on at the ignition edge until the next tick released it again.
The right-hand side already froze the inactive spacecraft, so no trajectory
changed; the commanded level and the reported state were wrong.

Change: both paths keep the burn's bookkeeping (window, burn flag, solver stops,
trace) and then apply the model's release again when the command is released at
that time, by the rule the tick uses: the spacecraft is in the model's scope and
inactive, and the model declares `skip_inactive` (new internal `_released`). For
the burn scheduler the release turns the mounted engine and wheels off and keeps
the schedule; in `:ideal` actuation it does nothing. A spacecraft made active again
fires from the scheduler's next scheduling pass, burn edge or tick, while its window
is open.

Other built-in callbacks checked for command writes outside `_gnc_tick!`:

- through `_gnc_tick!` already: the periodic control, guidance and navigation
  callbacks, the burn scheduler's mounted tick and its guidance pass; the linked
  producers' `before_reference_control!` runs only when the consumer ticks some
  spacecraft (`_ticks_any`);
- applying a released command, by design: `_apply_mounted_tick!` after a release;
- consistent with a release: the touchdown event's `on_touchdown` (the Apollo
  controller records contact and turns its actuators off);
- writing model bookkeeping, not commands: `atmosphere_transition!` (EDG passage
  state; a frozen spacecraft does not cross the boundary);
- reading commands or writing physical state only: actuator fault switches, power
  shedding, CMG gimbal stops, sensor sampling, plume acceptance, interlink
  scheduling, external-propagation sync, state anchors, the EDG heat observer and
  thermal sampling;
- run start and checkpoint resume: the models' initializers and restores set run
  state for every spacecraft before the first tick (see Residual Risk). With this
  change the burn scheduler's initialization pass releases an inactive spacecraft
  at once.

- Both paths that write the burn scheduler's mounted level outside its tick go
  through `_refresh_burn_keeping_release!`: the scheduling pass
  (`_schedule_thruster_control!`, at the run's start and at an atmosphere exit) and
  the burn-edge callback. It calls `refresh_burn!` unchanged, so the window, burn
  flag, stops and trace still update. It then calls `release_command!` when
  `_released` holds.
- `_released` uses the rule `_gnc_tick!` uses: in the model's scope, inactive, and
  `skip_inactive`.
- On a reactivated spacecraft, `_released` is false, so the next edge or tick fires
  as scheduled.

## Findings

No P1 or P2 findings. Points a reviewer should check:

- Low: the burn's bookkeeping goes on for an inactive spacecraft, as the finding
  allows: `burning`, the recorded window and the trace still switch at its window's
  ends, and `held_command` reports them. In `:ideal` actuation the saved thruster
  level is read from that schedule, so an inactive spacecraft's saved level follows
  its window; the right-hand side ignores it.
- Low: on reactivation the engine fires from the scheduler's next scheduling pass,
  burn edge or tick, not at the reactivation instant; those are the only times the
  mounted level is written (wording corrected after Codex's review of 2026-10-20).
- Low: `refresh_burn!` itself still writes the scheduled level; the rule lives in
  the engine's callers, beside `_gnc_tick!`. A direct caller of `refresh_burn!`
  outside the engine does not get it.

## P1 Assessment

No P1 findings. The change adds a release after the scheduler's bookkeeping on the
two callback paths, only when the command is released at that time; for an active
spacecraft both paths do exactly what they did, and an inactive spacecraft's state
was already frozen.

Unresolved P1: No

## Residual Risk

- At a checkpoint resume with a spacecraft already inactive, a model other than the
  burn scheduler holds its restored or run-start command for that spacecraft until
  its first tick releases it. The right-hand side ignores that spacecraft meanwhile.
- A model whose `release_command!` keeps its default (no-op) holds its last command
  after a deactivation; the release rule cannot zero a command the model does not
  release.
