  0.7.0; it merges after the v0.6.1 tag.

What it does:
- Each interlink history sample records the score that selected each active
  link (`scores`). With `InterlinkModel(; record_terms=true)` and a
  `WeightedPolicy`, it also records each top-level term's own score (`terms`).
- `link_schedule(model; policy)` and `link_schedule(results)` turn the history
  into a table: one row per window over which a link was selected or (with
  recorded availability) could close, with the link, its endpoints, the span
  and the scores.
- A run with interlinks that writes results writes the table as
  `simulation_results_link_schedule.csv` and `.feather`, and lists both in the
  manifest with an `[interlinks]` entry.

Rule: the scheduling, the states, every results column and the checkpoint
payload are unchanged. The only new outputs are the two files, the manifest
entries that list them, and `SimulationResults.files`.

## Findings

No P1 or P2 findings in the author's own review. Two problems were found and
fixed while building, and one by a surviving mutant. One merge needs care. Points a reviewer should check:

- **F1, fixed: the eccentricity policy's scoring method.** The first unit run
  failed for `EccentricityRatePolicy`, whose `_score_and_check!` method did not
  take the new `terms` keyword. It takes it now and ignores it, since that policy
  is never a mix.
- **F2, fixed: kind names.** The table names a link's kind with its type
  parameters (`DataLink{FixedRateBudget}`), as D-I6-5 says, so two budgets of
  one kind stay apart. A test and the docstring that expected the bare name
  were corrected.
- **F3, fixed: the mix's bit check was blind to reordering.** The test mix's
  weights and scales were powers of two (1, 2 and -0.25), so a mutant that
  changed the order of the mix's arithmetic only while recording terms kept its
  bits and survived. The test mix now uses 0.7/0.3 and -0.35/1.7, and the
  mutant is caught (Tests).
- **F4, open, for the merge order: C-5a's long layout.** C-5a
  (`results-long-layout`, not yet opened) and C-4b, stacked on it, conflict
  with this branch in `src/SpaceAGORA.jl`, `io_outputs.jl`, `persistence.jl`,
  `simulation_engine.jl` (adjacent exports and wrappers, keep both) and
  `execution.jl`. One part is more than text:
  - C-5a's long layout returns from `_save_simulation_results_if_enabled!`
    before this branch writes the schedule;
  - its return tuple has no `schedule_files`, which the `return_results`
    block reads.

  Whichever PR merges second should write the schedule in the long branch too,
  list it in the long manifest, and return `schedule_files` from both
  branches. A keep-both resolution of the text alone would fail for an
  interlinked long run with `return_results=true`.
- **The scores are read, not recomputed (D-I6-4).** `schedule_interlinks!`
  always scores before it selects (`score_candidates!` creates the workspace),
  and `select_interlinks!` reads the same `work.score`. So the recorded score of
  each link is the one the matching used, whatever the matching backend.
- **The terms share the mix's loop.** `_weighted_score` is the mix's own sum.
  The buffer only adds a store per term and edge, so a mix's scores keep their
  bits with recording on or off (tested), and the selection with them.
- **The manifest.**
  - An interlinked run's manifest gains `files.link_schedule_csv`,
    `files.link_schedule_feather` and `[interlinks]`. The bundle schema stays
    "1".
  - A run without interlinks writes the same manifest as main, apart from its
    write time (Tests).
  - Readers look up their own keys. The only reader of the results manifest's
    `files` in core is the viewer payload's hash check, which reads
    `files.feather`.
- **Thinning and resume.** The schedule is built from the history, not from the
  saved rows, so `SPACEAGORA_RESULTS_FINAL_ONLY` and the thinning stride leave it
  whole (tested). After a resume it covers the resumed interval only, as
  `contact_windows` does; the docs say so.
- **Low: memory per sample.** Each history sample holds two more small arrays.
  When terms are not recorded, the term matrix is empty but still allocated.
  The active and available lists still set the history's size. Keeping no
  history belongs to C-5 (D-I6-6).
