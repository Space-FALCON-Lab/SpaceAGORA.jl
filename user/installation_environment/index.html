Installation and Environment

Use this page when you need to set up a machine for local development, examples, or docs builds.

This page is for users and contributors who need to understand the repository environments before running anything heavier than a quick smoke path.

Shortest successful command:

julia --project=. -e "using Pkg; Pkg.instantiate()"

What to read next:

  • Quickstart
  • Assets & Modes
  • Distributed and HPC

Julia version

The root Project.toml pins julia = "1.12". Install that Julia release before instantiating either project.

The repository environments

Root project (--project=.)

The root project at the repository root is the canonical execution environment used by examples, tests, benchmarks, and most local commands in this repository.

Use it for:

  • example scripts
  • local verification runs
  • benchmark launchers
  • CLI commands

examples/odyssey_surrogate_env/

The Odyssey surrogate example has its own environment. It adds the public GRAMSuite Julia wrapper, which provides the native-free grid atmosphere, and uses the current SpaceAGORA checkout. Its setup script instantiates it, and the resolved manifest stays local:

julia --project=examples/odyssey_surrogate_env examples/odyssey_surrogate_env/setup.jl
julia --project=examples/odyssey_surrogate_env examples/odyssey_surrogate.jl

See the Odyssey walkthrough.

Optional MuJoCo companion

SpaceAGORAMuJoCo.jl provides standalone proximity scenes and externally propagated spacecraft inside run_simulation. Its repository owns the package, native binding, tests and Basilisk comparison harness. Julia 1.12 is required; native scenes currently support Linux x86_64 and use the pinned MuJoCo 3.11.0 artifact.

Build an independent environment from the companion checkout:

git clone https://github.com/Space-FALCON-Lab/SpaceAGORAMuJoCo.jl.git
cd SpaceAGORAMuJoCo.jl
julia --startup-file=no scripts/setup_env.jl /path/to/mujoco-env
julia --startup-file=no --project=/path/to/mujoco-env

Then load the packages explicitly:

using SpaceAGORA, SpaceAGORAMuJoCo

The companion's setup installs the exact core revision recorded in its Project.toml and creates its own manifest. It does not use a parent checkout, copy a core manifest, or call a HYPR installer. The package version-family constraint alone is not a compatibility guarantee; the source pair and ExternalPropagationServices contract version must agree. Loading core alone does not load this adapter or download MuJoCo.

For development, SPACEAGORA_CORE_PATH selects a local SpaceAGORA checkout instead of that source pin. Core CI uses this override with an immutable companion revision so changes to core are tested against the actual candidate. See the companion's installation guide for overrides. Start with Orbital Scenes with MuJoCo for the frame conventions, ownership rules and complete examples. The supported connection is documented in External propagation services and the shared optional adapter standard.

docs/

The docs build uses its own project:

julia --project=. -e "using Pkg; Pkg.instantiate()"
julia --project=. docs/make.jl

Your own project

Keep your script and generated results in a project outside the SpaceAGORA checkout. First select a recorded commit in your existing checkout and use absolute paths. The setup below explicitly installs that checkout into the new project, resolves its dependencies without copying a repository manifest, and declares the packages imported by the custom-force walkthrough. It does not add private modules to Julia's load path.

Save this as setup_user_project.jl outside the checkout:

using Pkg
length(ARGS) == 2 || error("Usage: setup_user_project.jl CHECKOUT NEW_PROJECT")
checkout, project = abspath.(ARGS)
isdir(project) && !isempty(readdir(project)) &&
    error("Choose a new empty project directory")
mkpath(project)
Pkg.activate(project)
Pkg.develop(PackageSpec(path=checkout); preserve=Pkg.PRESERVE_ALL)
Pkg.add([PackageSpec(name="StaticArrays"), PackageSpec(name="CSV"),
         PackageSpec(name="DataFrames")]; preserve=Pkg.PRESERVE_ALL)
Pkg.instantiate()

Run setup, then save my_effector.jl from the walkthrough in the new project:

julia --startup-file=no setup_user_project.jl /absolute/SpaceAGORA.jl /absolute/my-project
JULIA_LOAD_PATH="@:@stdlib" julia --startup-file=no --project=/absolute/my-project /absolute/my-project/my_effector.jl

The load-path setting prevents unrelated packages in your default global project from hiding a missing direct dependency. On Windows, Julia uses ; as the load path separator, so set JULIA_LOAD_PATH to @;@stdlib before launching Julia. The script writes results beside itself, independently of the terminal's working directory. Inspect SimulationResults and the three written files as described on Simulation Outputs.

Setup uses your existing Julia depot and can download missing packages. An explicit cached/offline check may instead set JULIA_PKG_OFFLINE=true and JULIA_PKG_PRECOMPILE_AUTO=0; a missing cached dependency then remains a setup failure, not permission to substitute another version. Success with a populated depot is not a clean-depot installation result. Do not modify the source checkout while a separate project is using its development path; record the checkout commit and both generated environment files with any result you keep.

The optional planner companion has its own documented installation. Installing the core project alone does not install or qualify HYPR, native GRAM, SPICE data, or a full mission workflow.

Local output paths

Generated reports and builds stay local. Common ignored output roots are:

  • output/
  • odyssey_surrogate_results/ and odyssey_surrogate_<cap>/, the Odyssey surrogate example's defaults when run from the repository root
  • docs/build/
  • docs/site/
  • docs/src/generated/

You can regenerate common local artifacts with:

julia --project=. scripts/regenerate_ignored_outputs.jl runtime-analysis quick
julia --project=. scripts/regenerate_ignored_outputs.jl telemetry quick
julia --project=. scripts/regenerate_ignored_outputs.jl docs

When you need more than setup

Environment setup only tells you that the Julia side is ready. If you need to know whether the machine also has the right data and licensed assets, go to Assets & Modes.
