## Findings

### P1 (must fix before merge)

**P1-1 (fixed in dc77bc4ea, tested in 50f1a7d4a): the pre-solve reseed re-arms Earth-GRAM's one-time CSPICE initialization on pool and per-satellite instances, reopening the `SPICE(BADSUBSCRIPT)` abort.**

- The mechanism. `EarthAtmosphere::setSeed` is `{ initializing = true; randomNumberGenerator.setSeed(seed); }` (`GRAM Suite 2.0/Earth/include/EarthAtmosphere.h:81`). The next `update()` takes the `if (initializing)` branch (`EarthAtmosphere.cpp:469-476`), which calls `time.getDayOfYear()` and `time.getStartTime(...)`. By the repository's own analysis (`_warm_gram_pool_model!` docstring, `model_selection.jl:170-189`, and the comment at `setup.jl:1697-1722`), that branch reaches CSPICE's `timout_c`, and several fresh instances taking it concurrently corrupt CSPICE's trace stack and abort the process. The fix for that crash was to drive the first update of every pool and per-satellite instance serially at construction. `_reset_density_model_histories!` (`setup.jl:1737`) calls `set_seed!` on exactly those instances, unconditionally, so each is back in its pre-warm state when the solve starts.
- Scenario A (automatic, no opt-in variable). Native Earth GRAM, 1024 or more spacecraft reaching native GRAM, the V2 policy (`SolverConfig(parallel=true)` or R6/R7), 16 or more threads, and either `EnvironmentModel.wind = false` or `SPACEAGORA_GRAM_WIND_MODE=nominal`. The callback-width calibration (`rhs_calibration.jl:2146-2185`, on by default under V2) calls the density callback's `affect!` before the solve; the batch route builds and warms the isolated pool (`_ensure_gram_isolated_pool!`, `model_selection.jl:140-165`). The reset then reseeds those models. Pool width is capped at 4 (`_gram_isolated_pool_max_workers`), so every calibrated width of 4 or more maps to the same 4 workers and the pool is not rebuilt; the solve's first pooled callback runs four first updates concurrently under four separate locks. This PR also widens the exposure: before it, every callback query passed `wind=true`, so under the pinned wrapper's default perturbed mode the automatic pool always declined; `wind = false` runs now reach it.
- Scenario B (opt-in). `SPACEAGORA_GRAM_PER_SAT_INSTANCES=1` with `SPACEAGORA_GRAM_LOCK_SCOPE=model`, the combination the `setup.jl` comment identifies as having crashed under threads. The per-satellite instances are always built and warmed before the reset, and in a history-free run (wind off or nominal) the density callback and RHS may take their first update from worker threads.
- Not affected: the default single-instance configuration (the global lock serializes every call), and history-dependent runs under `auto` (the pool declines, and the frozen serial callback makes the first updates in index order on one thread).
- This is inferred from the code and the documented earlier crash; it was not reproduced.
- Fix, either of:
  - reseed only what needs it: call the reset only when `_run_density_history_dependent(p.args)` holds (density-only and nominal-wind runs gain nothing from it) and, for an explicit pool `on`, re-drive `_warm_gram_pool_model!` on each reseeded pool and per-satellite instance serially inside `_reset_density_model_histories!`; or
  - always re-warm after reseeding. A fresh instance is also warmed at construction, so reseed followed by the same warm query reproduces a fresh warmed instance, and the "reseeded equals fresh" property the tests assert is kept.

  Add a test that reseeds a warmed pool and asserts the pool is re-warmed (or not reseeded) before its next concurrent use.
- Resolution (dc77bc4ea): both fixes. `_reset_density_model_histories!` returns early unless `_run_density_history_dependent(p.args)` holds, reseeds only models that are themselves history-dependent, and re-warms every reseeded native model (configured, per-satellite, pool) with `_rewarm_reseeded_gram_model!` (the same warm query as `_warm_gram_pool_model!`, under the process-wide GRAM lock), serially, before the solve. It also clears the track and look-ahead caches.
- Evidence: the crash was reproduced. Eight warmed pool instances reseeded with `reset_density_model_history!` alone and then updated concurrently aborted every time: `SPICE(BADSUBSCRIPT) ... procedure "trcpkg"` at 4 threads (2 of 2 attempts, 10 rounds each) and a heap-corruption abort at 8 threads. The same loop through `_reset_density_model_histories!` survived 200 rounds at 8 threads. Tests (50f1a7d4a): after the reset, every model's next queries equal a fresh model's after the warm query and differ from a fresh model's first queries; a child updates eight reset pool instances concurrently at 4 threads for 10 rounds and matches a serial round; a counting model checks that wind-off and history-free runs are not reseeded.

### P2 (should fix)

**P2-1 (fixed in ce399982f): surrogates are treated as history-dependent, so the `auto` freeze and the serial callback now apply to every surrogate run with winds on.**

- Where: `density_models.jl:520`, `density_model_history_dependent(::GRAMAtmosphereModelSurrogate)` forwards to the native base model, and `_run_density_history_dependent` (`config.jl`) uses it.
- Why it is too broad: the default surrogate has no point-fallback altitude for Earth, Mars or Venus (`gram_default_point_fallback_below_m` returns `nothing` except for Titan), and in-grid queries are table lookups with no native call. Native GRAM is reached only for an out-of-grid point, a warn-once path.
- Effect: a surrogate run with `wind = true` under the default wind mode now reads density and wind once per accepted step instead of at every stage, a numerical change, and its density callback loses threading even though `density_model_threadsafe(::GRAMAtmosphereModelSurrogate) = true`. The surrogate is the lock-free constellation path, so this is also a throughput regression. The PR description says the change applies to "native GRAM with perturbed winds" and that other models are unchanged, which is not what the code does.
- Fix: make a surrogate history-dependent only when it has a configured `point_fallback_below_m` (or treat the out-of-grid fallback as an accepted exception and document it), and state the rule in the guide.
- Resolution (ce399982f, guide in 4d16dc45a): a surrogate is history-dependent only with a configured `point_fallback_below_m` and a history-dependent base. The out-of-grid fallback is documented as an accepted exception. Tested (50f1a7d4a): a pure-grid surrogate over a history-dependent core is neither frozen nor serialized and its callback threads.

**P2-2 (fixed in 4d16dc45a, documentation): the `auto` freeze overrides the vacuum-predicted cache, and the guide says it does not.**

- Where: `_sample_atmosphere_from_planet_frame` checks the freeze before calling `_density_state_from_kinematics!` (`effector_sampling.jl:85`), so under freeze the RHS never interpolates the look-ahead spline. The guide keeps the sentence "It has no effect on the vacuum-predicted-cache path" (`docs/src/user/parallel_execution.md:249`).
- Effect: with `SPACEAGORA_VACUUM_GRAM_CACHE=1` (the path the guide calls the supported way to run real GRAM at constellation scale), perturbed winds and winds on, per-stage spline interpolation silently becomes a per-step zero-order hold. This was already true under an explicit `=1`, but it is now the default for that configuration.
- The freeze is defensible there: cache rebuilds issued from threaded RHS stages would advance the walk in scheduling order. But the behavior and the doc disagree.
- Fix: correct the sentence and state which path wins, or restrict the freeze under the vacuum cache to rebuilds (confine rebuilds to the serial callback and keep per-stage interpolation).
- Resolution (4d16dc45a): the documentation was corrected, not the code. The vacuum cache is rebuilt from whichever caller finds it stale, including RHS stages that run threaded, and each rebuild is a burst of native queries, so the cache path does not give ordered queries by itself. Keeping per-stage interpolation would need rebuilds confined to the serial callback, a larger change. The guide now says a freeze takes precedence over the cache and why.

**P2-3 (accepted, evidence in 4d16dc45a): `auto` changes the default numerical model of every native-GRAM run in the pinned wrapper's default wind mode.**

- With winds on and perturbed mode (the wrapper default), density, temperature and wind are now held for each accepted step. The PR measures one case (2.65 m and 1.4 cm/s after 300 s at a 130 km perigee) and a large speedup. The step-size controller no longer sees the within-step variation of drag, so the error is governed by `dt_max_atmosphere`, not by the tolerances.
- Accepting it is reasonable: the per-stage alternative is both nondeterministic and, per the guide's own measurement, pathologically slow.
- Missing: a bound on a longer, drag-dominated case (a multi-pass aerobraking arc or an entry) against `=0` at one thread. The release notes should say that GRAM-backed results produced before this change are not reproducible bit for bit with the default settings.
- Evidence (4d16dc45a, in the guide): one spacecraft, Earth, 118 km by 2000 km, three orbits (three drag passes, apoapsis down about 47 km), native GRAM, one thread. `auto` against `0` with the same seed: apoapsis 75 m and 105 m (seeds 1001, 1002), periapsis under 2 m, heat load 0.35% and 0.48%, final position 0.8 km and 1.3 km. The pure hold error (nominal winds, `1` against `0`): 87 m and 0.19%. The seed-to-seed spread under per-stage sampling: 214 m, 0.74%, 1.8 km. Wall time 0.36-0.60 s frozen against 2.7 s per stage. The guide states that pre-change perturbed-wind results are not reproduced bit for bit.

### P3 (minor, accepted, or out of scope)

Determinism claim and guards:
- P3 (accepted; the guide now says the dynamics' queries): the claim that the per-step callback is the only place the solve queries native GRAM does not hold with E-EDG. `_edg_environment_state` (`targeting_control.jl:72`) queries the configured model directly (not the frozen sample, not the per-satellite instance), and the heat-load predictor queries it up to 2000 times per call at latitude and longitude 0 (`heat_load_control.jl:111-121`, which also requests winds it discards). These calls are ordered, because `AerobrakingEnergyDepletionControlModel` is not `control_model_threadsafe`, so determinism holds. But they advance and displace the same walk the dynamics use (pre-existing).
- P3 (fixed in e2e6f2c2e: the comment now says the control callback has no guard): the `runtime_types.jl:675` comment says control callbacks also serialize for a history-dependent run. `_control_callback_thread_decision` (`config.jl:495`) has no such guard. With `SPACEAGORA_CONTROL_ASSUME_THREADSAFE` set, E-EDG queries would follow thread scheduling. Either add the guard or correct the comment.
- P3 (fixed in dc77bc4ea: the reset clears both): the reset does not clear the GRAM track caches or look-ahead caches (`gram_density_cache`, `vacuum_gram_caches`). With either cache enabled (both are off by default), a pre-solve probe that fills a cache at t0 makes the solve start from pre-reset winds. The probe runs only when calibration runs, which depends on the thread budget and the calibration store. Clearing both in `_reset_density_model_histories!` closes this.
- P3 (accepted): `_rhs_density_service_candidate` (`gram_process_batch.jl:228`) does not check the freeze. With the process pool `on`, or a forced `=1` with nominal winds, the service fill overwrites the frozen buffers at every RHS evaluation. This is pre-existing and needs an explicit opt-in.
- P3 (accepted): `_density_callback_thread_decision(p.args, num_sats)` in the RHS prefill (`dynamics_rhs.jl:1911`) passes no `p`, so its snapshot never sees the history guard. It is harmless because a frozen RHS reads buffers, but the guard is not uniformly applied.

Warm-up and pin:
- P3 (fixed in e2e6f2c2e; warm-up kept): the extension comment (`ext/SpaceAGORAGRAMSuiteExt.jl:349`) still says the durable fix "belongs in GRAM". The new pin has it (#5 adds `initializeData()` to `MAP::getWindStandardDeviations`). The warm-up is still worth keeping, and the comment should say why:
  - users of the public wrapper build native GRAM from unpatched sources;
  - GRAM's lazy statics use an unsynchronized `initialized` flag, and loading them once under the setup lock keeps concurrent first updates on separate instances (pool workers, `LOCK_SCOPE=model`) from racing on them.
- P3 (accepted): a warm-up failure is logged at `@debug` only and retried on every construction and reset. If it can never succeed on a host, the first-run defect silently persists on unpatched native builds. A one-time `@warn` after the SPICE-deferral case is ruled out would surface it. Processes that never use Earth are unaffected (the planet check comes first).
- P3 (accepted): #6 (`getCorrelationCoefficients` loads its tables) is not warmed and not needed: nothing in SpaceAGORA calls the CorrMonte path.
- Checked: the upstream compare touches only `Earth/include/EarthAtmosphere.h`, `Earth/source/EarthAtmosphere.cpp`, `EarthAtmosphereData.cpp` and `MAP.cpp`. The `native` sparse profile includes all of `GRAM Suite 2.0/Earth/`. The setup action rebuilds native GRAM from the checked-out pin with `--clean`. The coverage shards set `SPACEAGORA_REQUIRE_NATIVE_GRAM_PROBES=1`, so the native tests cannot skip there.

Reseed semantics:
- P3 (accepted, pre-existing): every copy of a recipe-backed model is reconstructed with the same seed (1001 by default). Campaign members, `isolate_state` copies and per-satellite instances therefore all draw the same random sequence, and a constellation ensemble is not equivalent to the monolithic constellation run under perturbed winds (one shared walk against N seeded walks). The reset makes this explicit: repeated runs with `isolate_state=false` no longer give different realizations. Users who want dispersed perturbations must vary `seed`. Worth one sentence in the guide.
- P3 (accepted): bit-identity of a reseeded atmosphere with a fresh one is measured for Earth and Mars only. Earth's `setSeed` override does not call the base `PerturbedAtmosphere::setSeed`, so it relies on `initializePerturbations` re-initializing everything on the next update. Other bodies are unmeasured.
- P3 (accepted): a raw-core wrapper with no recipe is not reset (documented; the test asserts it).

Wind flag:
- P3 (accepted): the legacy T-EDG predictors and aerobraking control paths (`eom_predictor.jl`, `trajectory_predictor.jl`, `control_commands.jl`, `constraint_tracking.jl`) take their wind switch from `ip.wm` and query GRAM through the Python bridge, not from `EnvironmentModel.wind`. The commit title's "every atmosphere path" should be read as every native-Julia path.
- P3 (expected behavior change): telemetry scenarios default to `include_wind=false`. Before this PR, the callback and RHS still requested winds and fed them to the aerodynamics, so GRAM-backed telemetry cases (Odyssey, VEX) move with this fix. The telemetry regression jobs were still pending when this was written.

Tests:
- P3 (fixed in 50f1a7d4a: eight spacecraft with the threaded callback, prefill and RHS loop forced on; the negative control uses a pure-Julia history-dependent model, because per-stage perturbed GRAM with several spacecraft does not finish in test time, and it differs between 1 and 4 threads without the freeze): the 1-versus-4-thread child test uses four spacecraft. At four threads, the `:density_callback` source's 16-thread floor keeps the callback and the RHS atmosphere prefill serial anyway, so the test would likely pass with the freeze disabled too. It demonstrates the first-atmosphere fix and repeatability, not thread-order independence. A negative control (the same children with `SPACEAGORA_DENSITY_FREEZE_PER_STEP=0` and threading forced) would show that the test can fail.
- P3 (fixed in 50f1a7d4a: output goes to a log printed on failure): the children's output goes to `devnull` (`gram_wind_determinism_tests.jl:227`), so a CI failure reports only `ok == false`. Capture stderr to a file and print it on failure. Under `--code-coverage=user`, `Base.julia_cmd()` carries the coverage flag into both children, which then load SpaceAGORA without package images: slow, but not flaky. Nothing in these tests depends on timing.
- P3 (nit, accepted): `_rhs_density_service_candidate` now parses `SPACEAGORA_GRAM_PROCESS_POOL` a second time on every RHS evaluation.

### Checked, no finding

Reseed and warm-up:
- Placement: the reset runs after the contention probe, the RHS sweep, the callback-width calibration and the width-trial installation. The only native queries between it and the first step are the density callback's `initialize` affect, which OrdinaryDiffEq runs before the initial `dt` estimate.
- `isolate_state=true` reconstructs from the recipe; `isolate_state=false` reseeds the shared instance. Both are tested.
- Checkpointed solves: each segment's callback `initialize` adds one query at the segment start. It is deterministic.
- Thread safety of the reset itself: it runs on the calling task before the solve, the static-table set is guarded by the setup lock, and `tracked_lock` sites are views of one shared native lock, so the setup-then-call nesting cannot invert.
- `_gram_core_seed` falls back to 1001, the wrapper's default, and reseeding does not undo the constructor's step-size or perturbation-scale settings.

Freeze `auto`:
- Activation: only for a history-dependent model with `wind = true`. `off` and `0` restore per-stage sampling; a typo throws `ArgumentError` at run setup.
- The callback's history guard precedes both the pinned width and an explicit `on`. The pool's `lock_free` width query is exempt, and the pool declines under `auto`.
- Batch-route selection depends on the number of spacecraft, not on threads.
- The uniform-light batch is off under freeze.
- The density callback is installed whenever there is an atmosphere and spacecraft have links. `gravity_backbone_split` rejects atmosphere effectors, so no frozen run lacks the refreshing callback.

`wind = false`:
- Every native-Julia consumer is masked:
  - aerodynamic wrench and mesh surrogate (through the sample);
  - per-link query;
  - thermal callback;
  - E-EDG state and prediction;
  - the saved `wind` field (from the buffers);
  - the isolated-pool, locked-batch, uniform-light and process-service writes;
  - track-cache and look-ahead values (through the masking wrapper).
- With winds on, `_environment_wind(true, w) === w`, and every changed call site passes `true` as before, so nothing changes except the freeze of P2-3.
- A parameter object whose environment has no `wind` keeps requesting winds.

Pools:
- One predicate is shared by both pools and by the RHS service pre-check, with identical semantics to the isolated pool's previous inline rule: `auto` declines requested history-dependent winds, `on` never declines on this ground, and density-only and nominal batches stay eligible.

E-EDG sign:
- GRAM's `ewWind`/`nsWind` are the air's velocity (positive east and north). The aerodynamic wrench, the mesh surrogate, the thermal callback and all T-EDG and aerobraking control predictors already use `vel_pp - wind_pp` with the same east/north/up rotation. The new test checks the E-EDG environments against the wrench's drag direction. The heat-load predictor discards the wind, so the sign does not reach it.
