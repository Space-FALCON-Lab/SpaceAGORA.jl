# Review record: PR 380: planning-algorithm and algorithm-family checks (contributor kit K4)

## Scope

Review of the SpaceAGORA `conformance-algorithms` branch (head `e0440d7fd`, one commit)
against `conformance-gnc-models` `afb45efa1` (K3), which is on K2 `476cf9b4a` and main
`427d9bbea`. This is K4 of the contributor kit approved on 2026-10-16.

The PR adds `check_algorithm(algorithm, requests; trusted, run_context, simulation)`,
`check_algorithm_family(family, algorithm, requests; link, trusted, run_context)`,
`test_algorithm` and `test_algorithm_family` to `SpaceAGORA.Conformance`, with the RPO
family's conformance pieces: `rpo_conformance_requests`, `rpo_trusted_queries`,
`rpo_conformance_simulation` and an internal conformance link. The checks use the
general GNC algorithm contract itself: `algorithm_family`, `initialize_algorithm`,
`validate_capabilities`, `propose!`/`propose_revision!`, `validate_proposal`,
`proposed_product`, `is_current`, `install!`, `on_rejection`, `fallback_product`, and
the shared request driver `run_algorithm_request!` with the kit's test binding. The
check ids:

- algorithm: `family_resolves`, `family_trusted`, `result_contract`,
  `stream_untouched_if_declared`, `deterministic_given_stream`, `request_not_mutated`,
  `initialize_independent`, `refuses_explicitly`, `driver_round_trip`, `simulation_run`;
- algorithm family: `family_resolves`, `family_obligations`, `driver_round_trip`.

`algorithms.jl` loads with `GNCAlgorithms`, `reports.jl`, `walker.jl` and standard
libraries alone, as the design requires, and the standalone contract tests include
it. The direct planner, a hold planner and (with SpaceAGORAHYPR loaded) the HYPR
planner run through `check_algorithm`; the RPO family runs through
`check_algorithm_family` under both of its policies.

## Findings

No P1 findings.

Points a reviewer should check:

- Medium, narrowed from the design (three places, each stated in the PR):
  `fallback_product` is required under `:install_fallback` only, because the RPO
  family defines it for both of its policies; `result_contract` does not check that a
  result copies its product and diagnostics, because the driver deep-copies every
  result before validation; `refuses_explicitly` covers revision requests, the
  contract's explicit rule, because the driver never asks an algorithm about a request
  its capability check refuses.
- Medium, `family_trusted`: core-owned means the family type is defined in the module
  tree that holds `GNCAlgorithms` (SpaceAGORA, its family modules and its service
  facades). In the standalone contract tests that tree is the test module.
- Medium, `driver_round_trip` compares the driver's run with the family's verdict on
  proposals made from deep copies of the binding's state and stream. An algorithm whose
  answer depends on its state's identity rather than its value fails it, as the
  negative control shows; a nondeterministic one fails it as well as
  `deterministic_given_stream`.
- Low, `simulation` is a function of the algorithm that returns the binding's run
  records. For RPO, `rpo_conformance_simulation` also runs the configuration twice in
  sequence and twice concurrently (with two or more threads) and throws when the runs
  differ; that is how the lifecycle test's rerun assertions now run.
- Low, family-facade detection: a family whose defining module has a `CONTRACT_VERSION`
  binding is treated as facade-served and must state `family_contract_version`.
- Low, later work: GNC PR 15 (`comparison-planner-objects`) adds seven
  `AbstractRPOPlanner` types, and GNC PR 16 (`burn-plan-family`) adds `BurnPlanFamily`
  and the generic `AlgorithmGuidance`. The coverage rules fail until each new type has
  an instance or an exemption, so whichever of each pair merges second adds them; PR 16
  also supplies the burn-plan requests, trusted queries, conformance link and a
  simulation through `AlgorithmGuidance`.
