## Findings

Author's notes for the reviewer (no P1 known to the author):

- **Design, medium: the binding ticks before control.**
  - `AlgorithmGuidance`'s periodic callback is placed before the control callbacks,
    through the same internal ordering function EDG targeting uses. The family's
    consumer therefore takes up a product at the tick it is installed.
  - `PlannerGuidance` keeps its later position, so RPO runs are unchanged.
  - PR 18 must decide whether EDG modes other than targeting accept this order when
    they move onto the binding, or whether the order becomes a family declaration.
  - The method extends an internal engine function from another module. A public
    declaration would belong with GNC PR 6's `GNCRuntime`.
- **Design, medium: the scheduler takes up plans installed between its passes.**
  - The burn-edge callback's condition now also checks, at every step end, whether
    the effective window differs from the one `refresh_burn!` last recorded.
  - The scheduler records every burn it plans in the same pass, so without a
    binding the check never fires. The parity scenarios confirm the results are
    unchanged.
  - Behaviour change outside the binding: a script that changes
    `start_burn_time`/`stop_burn_time` or the plan buffer during a run (an extra
    callback) now has the change taken up at the next step end, with stops at the
    new ends. Before, it waited for the scheduler's next planning pass.
  - The check costs one window computation per spacecraft per step; no allocation.
- **Design, low: who plans a spacecraft's burns.**
  - The family's preflight refuses a configuration where the scheduler would also
    plan for that spacecraft: a nonzero `Δv`, its own window, or one of the two
    built-in thruster guidance models.
  - A user guidance model that writes `maneuver_commands` is not detected. The
    scheduler would then plan its own burn over the installed plan.
- **Low: the request's thrust and specific impulse are the scheduler's configured
  values** (`thrust[i]`, `Isp[i]`), not those of a plan still in the buffer. The
  scheduler's own sizing uses `_effective_thrust_isp`, which prefers an active
  plan's. Both are equal for plans the family installs.
- **Low: a window starting before the request is refused**
  (`:window_before_request`).
  - The scheduler still schedules such a window for its own burns when the next
    apoapsis is closer than half the burn. That burn then starts at once and is
    shorter than planned. Unchanged here.
  - `ApoapsisBurnPlanner` proposes the same window, and the family refuses it with
    a record. A planner that shifts such a burn is a later choice.
- **Low: validation tolerances.**
  - Propellant and impulse must agree with the trusted check to a relative 1e-9.
  - The window must last the check's duration to a relative 1e-9 plus four ulps of
    its ends: the scheduler times a burn with the constant-thrust formula, while the
    check divides the impulse by the thrust, and the window ends round around the
    apoapsis time.
  - The thrust and specific impulse must match exactly.
- **Low: zero Δv leaves no record.** `AerobrakingCampaignPropulsiveManeuverGuidanceModel`
  sends a zero command on every orbit without a maneuver. Recording those as
  refusals would fill the records.
- **Low: records grow with requests.**
  - Each request keeps a copied `BurnPlanRequest`, small and fixed-size.
  - With a finite `replan_interval_s`, a planner that declines every time adds one
    rejection record per interval.
- **Low: the trace CSV logs a family plan's `burn_start` and `burn_end`, not a
  `schedule_set`**; the binding's records hold the installation.
- **Note: `_validated_burn_plan` is unchanged** in signature and results (suite
  05 calls it directly). Its body now goes through `_burn_plan_sizing`.
  - The checks are the same, one at a time, so the first failing one names the
    reason.
  - The affordability test keeps its exact form,
    `!(required > available + 1e-9)`, so a NaN available propellant is still
    accepted as before.
- **Note: `initialize_control!(::BaseThrusterModel)` empties only the new
  records.** G-8's full reset of the scheduler's run state is GNC PR 12.
- **Note: `bound_family` (#365).** The driver resolves the family through
  `bound_family(binding)`, whose default is `algorithm_family(bound_algorithm(binding))`.
  `AlgorithmGuidance` configures no family instance, so this is the family its
  `build_algorithm_request` and preflight resolve with `algorithm_family`. Calling
  `bound_family` there too is a small follow-up.
- **Note: registry rows.** `family_request`, `family_link`, `preflight_family`
  need rows and `algorithm_run_report` a `NOT_HOOKS` reason in H8a's registry
  (#361). #361 merges first; this PR then adds them as a separate commit on
  `docs/extension_hooks.jl` (prepared, 22 lines). The "Burn-plan family" section
  holds no hook, so `HOOK_SECTIONS` does not change.

## Update after review (33a9319c7)

- **Resolved: results for another request.** The automated review found that
  `validate_burn_plan` (`src/models/gnc/control/burn_planning.jl`) never compared
  the result's `request_id` with the request's. A stale or cached `AlgorithmResult`
  could be accepted for a later request and installed. It still had to pass every
  other check against the later request's snapshot, so the installed plan was valid
  for the current state; the installation, though, was recorded against a request it
  was not proposed for. The validator now refuses such a result first, with
  `:request_mismatch` and metrics `(result_request_id, request_id)`, as
  `validate_rpo_result` does. The docstring lists the reason.
- **Tests:** in `test/unit/gnc/burn_plan_family_tests.jl`, "Trusted validation
  reasons" checks the reason, its metrics and that the id check comes before the
  status; the new testset "Negative control: a result for another request is
  refused" runs a planner that returns its first result for every later request: the
  later request is refused and recorded, the first plan stays installed, and the run
  equals one without the later request. With the check removed in memory, both fail
  (6 failures, 1 error).
- **Evidence on 33a9319c7:** the new file 128/128 (`--depwarn=error`); 33/33 PR
  gates; review-record and P1 gates; strict docs build. The parity scenarios and the
  suites were not rerun: only the burn-plan family's path calls the validator.
