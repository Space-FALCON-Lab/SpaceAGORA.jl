Writing a GNC Algorithm

Choose the route that matches what you are adding. A controller or estimator updates a value at each tick. A planner proposes a product that an existing family checks before it is used. Defining those family rules, or adding a service boundary for a companion package, is work in SpaceAGORA itself.

What you want to addStart here
A controller that holds a command, or an estimator that holds an estimateFeedback controllers and estimators
A planner for an existing family: RPO, burn plans, joint references or EDGPlanning algorithms
A new family, its trusted validation, or a companion service boundaryContributor kit integrations

To keep your work in a separate repository, use Building Your Own Research Repository. It explains which starter to choose, how to pin SpaceAGORA and how to run the shared checks. Read Your First Script and the Extension Conventions before either algorithm guide. The Extension Hook Reference lists the signatures and defaults.

Which profile?

Use the feedback profile when a tick computes a command or estimate from the current state. Use the planning profile when an algorithm proposes a trajectory, burn plan, joint path or decision that can be validated before use. A planner and controller can use both, sharing a link as the RPO pilot does.

The two profiles share one vocabulary:

StepFeedback profilePlanning profile
Inputstate at the tick, or a measurementan owned request snapshot built by trusted code
Outputa command or an estimatea product proposed in a result
Checkyour own limits, in the tickvalidation by the family, which can reject
Keephold until the next tickinstall into a link and use while current

The family side

These functions belong to trusted core code. An algorithm for an existing family implements the planning hooks instead. The GNC Algorithm Contract API gives the signatures of the core hooks:

  • The family checks capabilities and proposals with validate_capabilities and validate_proposal, installs accepted products with install!, checks is_current, and selects on_rejection and fallback_product. It declares family_contract_version and algorithm_result_type, identifies revisions with is_revision_request, reads proposed_product, and produces installed_record and rejected_record entries for the run report.
  • The family's simulation integration supplies the owned family_request, resolves its install target through family_link, and checks the configuration with preflight_family before a run.
  • The binding supplies its algorithm_runtime, bound_algorithm, bound_family and bound_link, builds an owned request with build_algorithm_request, provides independent trusted_queries, and handles a stopped request with fail_algorithm_request!.

For a new family, follow Adding a GNC algorithm family. For a new family or companion service boundary, use the Contributor kit integrations checklist. Both start with a core pull request; the existing-family algorithm stays in your own repository.

House rules for both profiles

  • Draw randomness only from the rng you are given, never from Julia's global stream: planning functions take an explicit stream and have no default one, and the conformance checks rerun your model with the global stream reseeded.
  • Keep run state in the model (feedback) or in the state initialize_algorithm returns (planning), never in globals, and reset a model's run state in its initialize_*! hook.
  • Keep a user's change between two runs. A value a user may configure that the run also writes, such as a held command or a plan buffer's plan, goes back at the next run's start only while it still equals the model's last write: record a copy of each write in the model, and in initialize_*! return an entry still equal to it to its value at the previous run's start, and keep an entry changed since as the user's new configuration. Every built-in model follows this rule, the burn scheduler's schedule included, so a held command configured with no plan is the command for the whole run, in every run.
  • Survive deepcopy. run_simulation runs a copy of the configuration unless isolate_state=false, and a link shared by two models stays shared in the copy.
  • bind_spacecraft gives fresh run state to each spacecraft's copy.
  • Keep the output hooks pure: no law, no warnings, no I/O and no heavy allocation. They run at every evaluation of the equations of motion.

Test your algorithm

Run the engine's conformance checks on a representative configuration. The feedback guide shows the controller and estimator checks; the planning guide shows each planner's requests and simulation fixture. Run with two or more threads to compare concurrent and sequential runs. A pass checks interface behaviour; scientific validation remains yours.

Templates

  • templates/control_hook_template.jl: a feedback controller, including its declarations, held command and checkpoint hooks.
  • templates/gnc_planner_template.jl: an RPO planner using the public names, with the steps for another existing family.

Deprecated paths

  • RPOGuidanceModel was removed in SpaceAGORA 0.5.0. Use make_rpo_configuration(planner=HYPRRPOPlanner(...)); see Moving from RPOGuidanceModel.
  • Selecting an RPO planner by a Symbol, such as :rrt_star, was removed in SpaceAGORA 0.5.0. Pass a planner object, such as RRTStarPlanner().
  • The old hook names (calcControlEffect!, calcControlForceTorque, calcControlMassFlowRate, calcGuidanceEffect!, calcNavigationEffect! and the rest) were removed in SpaceAGORA 0.5.0; see Migrating Extension Hooks.
