# Review record: PR 466: directed interlink matching

## Scope

Review of the SpaceAGORA `directed-matching-keys` branch against main
(65f7a33aa, with #451, #455 and #456).

The fix was found while building I-4 (data links), where two-way data links
are common. It was split out on the coordinator's request as a 0.5.1 fix for
#444's directed links. I-4's branch carries the same change.

What it does:
- The optional NetworkX matching path selects each matched link's own key.
- Of parallel candidates (directed links both ways between the same two terminals), only the higher-scoring is matched.

Rule: runs with undirected links only are bitwise unchanged.

One commit: 5ee585048.

Authorship disclosure: this record was drafted by the author of the PR. The
plan assigns behaviour PRs an independent reviewer (the PI, or the second
reviewer when available); this record does not replace that review.

Independent review: the coordinator reviewed PR 466 at `5ee585048` under Giusy's
delegation on 2026-10-21. It was a read-only review of the diff, without rerunning
the tests.

- **The extension** maps each NetworkX vertex pair to its one candidate edge
  (`between`) and selects that edge's own key. A directed link therefore keeps
  transmitter first. For an undirected link the key is its stored lower-first
  key, as before.
- **Parallel candidates.** `_drop_parallel_candidates!` keeps one candidate per
  vertex pair: the highest exact score, and on a tie the first in the candidate
  list. The list is built in canonical endpoint order (`sortperm` in Step 1), so
  the docstring's tie rule holds. Candidates and exact scores are pruned
  together.
- **Runs without parallel links.** These return before any change (`all(keep)`),
  which agrees with the bitwise-identical runs.
- **Scope.** The parallel-candidate rule is a fault on main in its own right: the
  backend's simple `Graph` keeps the last-registered weight. The extension relies
  on the rule, so the two belong together.
- No commit carries a trailer.

## Findings

No P1 or P2 findings.

The defect fixed, on main since #444:
- **Directed links in a cyclic component**, with PythonCall loaded:
  - `select_cyclic!` pushed `minmax(vertices[a], vertices[b])` for each matched pair.
  - A directed link is keyed transmitter first, so when its transmitter is the higher endpoint, `select_interlinks!`'s `edge_index_lookup[key]` threw a `KeyError`.
  - When the reverse link was also registered, the lookup succeeded on the wrong link, which was then activated.
  - This applies to any directed kind, I-3's power beams included, in a component the tree matching cannot solve.
- **Parallel candidates**:
  - NetworkX's simple `Graph` keeps one edge per vertex pair, so `add_edge` for the second direction replaced the first one's weight. The matching could then select the lower-scoring direction.
  - The Julia DFS counted the pair as two edges between two vertices, a cycle, so a two-way pair alone needed the optional backend.

Points a reviewer should check:

- **Bitwise identity.**
  - Undirected links register once per pair, so `_drop_parallel_candidates!` drops nothing in runs that have only undirected links.
  - The NetworkX path's selected keys are unchanged for undirected links, which are keyed lower endpoint first.
  - The laser examples and the power-link runs below confirm it.
- **Low: one `Dict` per selection.** `_drop_parallel_candidates!` allocates a small `Dict` at every selection with two or more candidates. That is at most once per accepted step, beside the BigInt weights the selection already builds.
- **Low, by design: ties.** Of two parallel candidates with equal scores, the first in endpoint order is kept: the one whose transmitter has the lower `(spacecraft, terminal)` key. The choice does not depend on the registration order.
