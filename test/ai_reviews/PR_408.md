# Review record: PR 408: Keep a user's edits between two runs on one model

## Scope

Review of PR 408, the `keep-edits-between-runs` branch against `main` at
`f31cb6bbb`: `git diff main...keep-edits-between-runs`. The change is one commit,
`cd0ac37a9`; this record follows it in a second commit.

Giusy's decision of 2026-10-18, a follow-up to #394 after the 0.3.0 release:
every built-in model keeps a user's edits made between two runs on the same
object, as the burn scheduler does. #394 recorded each value a user may configure
and the run also writes at the model's first `initialize_*!` and restored it at
every later one, so an edit between two `isolate_state=false` runs was replaced.
This PR moves those models to the burn scheduler's rule: the model records its
last write; at the next run's start an entry still equal to that write returns to
its value at the previous run's start, and an entry changed since is the user's
new configuration, kept and the start of later runs. #394's guarantees stay: two
runs on one unedited object start equal, the kit's `initialize_resets` passes,
and first runs follow the same path as on `main`.

Authorship disclosure: this record was drafted by the author of the PR. It lists
what the author checked and what the independent reviewer must verify; it does not
replace that review. One design point is for Giusy to confirm: the deprecated RPO
guidance's plan buffer counts as one entry (see Findings).

Independent review: the coordinator reviewed the change under Giusy's delegation on
2026-10-18. `SimulationLifecycle._run_start_entries` applies the burn scheduler's rule
entry by entry: an entry still equal to the model's last write in the previous run
returns to a copy of its value at that run's start, and an entry changed since is
kept. Before a first run, or when the model wrote nothing, every entry is kept. The
restored or kept state then becomes the next run's baseline, so two runs of an
unedited configuration still start equal. Each model records its writes where it
makes them (at its tick, or at a plan install). Residual, as for the burn scheduler: a
user edit that sets an entry to exactly the value the model last wrote cannot be told
from no edit, so that entry returns to its run-start value.

## Findings

Author's notes for the reviewer (no P1 known to the author):

- **Design, medium: equality decides what counts as an edit.** An entry still
  equal to the model's last write, by contents, returns to its run-start value.
  So a user who sets a value equal to that write cannot be told apart from no
  edit, and the value returns. The burn scheduler has the same property. A copy
  of each write is recorded, so an edit made in place (for example a changed
  element of the held joint torques, or of a plan's time grid) is detected.
- **Design, medium, for Giusy: the deprecated RPO guidance's plan buffer is one
  entry.** Its plan, validity and time are written together. Field by field, a
  plan a user set would come back marked invalid and be replanned at the first
  tick. Any change to the buffer keeps all three. Its other run fields (goal,
  replanning record, counters, phase, pending replan) are entries of their own.
- **Design, low: the momentum manager's accumulator follows `initialized`.**
  The fields are entries of their own. A run that starts uninitialized sets
  `h_wheels` to `h_wheels_0` at its first tick (without integrated wheels), so an
  edit of `h_wheels` alone is replaced at that tick. `h_wheels_0` is the
  configuration for the starting momentum, as before. The docstring says so.
- **Design, low: the robot-arm buffer's plan and time are separate entries.** A
  user who sets only the plan after an install gets the time the previous run
  started from, not the install time. Each run's start is a finite time, so no
  invalid combination arises.
- **Low: a planner-linked RPO controller.** The planner's plan-buffer link sets
  the controller's held command to zero before `initialize_control!`. The rule
  treats that as a change and keeps it, which is the start the controller had
  on `main`. The planner guidance refuses `isolate_state=false` anyway.
- **Low: what each tick records.** The arm and RPO controllers copy their held
  command at each tick (a small struct; the arm's holds one vector). The manager
  records its plain-value state. The RPO guidance copies its replanning events
  vector (shallow) after each tick and copies a plan or pending replan only when
  the object changes. The arm buffer copies a plan at each install. At a run's
  start, a restored plan is deep-copied. The output hooks are unchanged.
- **Low: the engine's start query has no side effect.** `_buffer_run_start` builds
  the start without writing the buffer. It is called while the initial
  conditions are built and again in `link_initialize!`, and both calls give the
  same result.

## Residual Risk

- A user's value equal to the model's last write is not seen as an edit (see
  Findings), as for the burn scheduler.
- Fields that belong together are entries of their own, except the RPO
  guidance's plan buffer. The docstrings say which value to set (for example
  `h_wheels_0` for the manager's starting momentum).
- User models are not changed. The house rule in the GNC algorithm guide
  describes the pattern. The kit's `initialize_resets` checks equal starts, not
  that edits are kept.
- The deprecated RPO guidance's real runs need the HYPR companion. Its rule is
  tested here with recorded writes, and the HYPR files that run it pass locally
  with the companion loaded.
- Not run locally: the EDG companion suite (no model it covers changes) and the
  full integration suites; CI runs them.

Giusy decided on 2026-10-18 that the deprecated RPO guidance's plan buffer (plan, validity
and time) counts as one entry, as built.
