What it does:

- A `:data_throughput` policy.

Rule: runs without a data link are bitwise unchanged.

- **The budget.** `ShannonBudget` uses Friis for the received power,
  `P_t G_t G_r (λ / 4πd)²` with `λ = c / f`, thermal noise `k_B T B`, and
  `η B log₂(1 + P_r/N)`, capped at the budget's and each radio's
  `max_rate_bps`. Availability needs a separation in `(0, range_m]`, so the rate
  is never evaluated at `d = 0`. A virtual terminal is refused for a budget that
  reads hardware.
- **The counters.** `_apply_data_rhs!` returns at once without the data states,
  which a run has only with a `DataLink` (`has_data_links` in
  `build_initial_conditions`). It writes zero rates for inactive spacecraft.
- **History.** `InterLinkHistory` gains `available`. The two-argument
  constructor stays, and the history is not part of a checkpoint
  (`resume_checkpoint.jl` is untouched). `contact_windows` sorts by start, then
  key, so its order does not depend on the dictionary.
- **#466.** The branch carries #466's commits, merged in, not rebased. Once #466
  merges, its files drop out of this diff.
- **History memory.** This review added a residual risk: every interlink run's
  history stored the available links at each step. `46dd35cc6` addresses it and
  was reviewed the same way. `records_available` gates the record; the
  default (`nothing`) records only in a run with a `DataLink`, and
  `record_available=true` or `false` overrides it. The new field is set only by
  the keyword constructor and is not part of a checkpoint's identity, since the
  history is not checkpointed. Runs without data links keep the history they had
  before I-4.

## Findings

No P1 or P2 findings.

Points a reviewer should check:

- **Bitwise identity.** Every new path is gated:
  - the data states and columns exist only with a `DataLink` (`has_data_links`);
  - `_apply_data_rhs!` returns at once without the states;
  - `terminal_shed_tier(::LaserTerminal) = 1` gives the laser path the same tier, sums and order as before, and a `PowerReceiver` (tier 0) asks for nothing;
  - the level column's shedding equals `shed_levels` for link-driven laser terminals (both zero them from tier 1);
  - `_drop_parallel_candidates!` drops nothing without parallel candidates, which undirected links cannot form;
  - the NetworkX path returns the same keys for undirected links.

  Since 46dd35cc6, the `available` field stays empty in runs without a data link unless asked for, so their history holds what it did before. No existing output reads it. The fingerprints below confirm it.
- **2026-10-21, coordinator review: the history's memory (addressed in 46dd35cc6).** The review added a residual risk: every interlink run's history stored the available links at each accepted step, data links or not, so a large constellation over a long run kept more history in memory.
  - `InterlinkModel(; record_available=nothing)` now decides. The default records them only in a run with a `DataLink`, where contact time is part of the result; `true` records them in any run, and `false` in none.
  - Runs without data links keep the history they had before I-4.
  - `contact_windows(history; active=true)` works either way.
  - The setting is not part of a checkpoint's identity, since the history is not checkpointed.
- **The matching fix comes from PR 466.** Two-way data links need it: two directed links both ways between the same radios are parallel candidates, and the optional NetworkX path had keyed directed links lower endpoint first. It was found here and split out for 0.5.1; its record has the defect, the tests and the negative controls. This branch carries PR 466's commit, 5ee585048, merged in, so once PR 466 merges, a merge of main brings nothing new for those files.
- **Low, by design: the counters take part in the step control.** In a run with a data link, `data_sent_bits` and `data_received_bits` are states, so the error estimate includes them. Its accepted steps, and so its schedule's resolution, can differ from the same geometry under another policy; in the contact-window test, by less than one step. Runs without a data link are unchanged.
- **Low, by design: a budget is part of the link's checkpoint identity by value.** The link identity records its fields as they are, so a budget is compared and serialized as a value. A budget kind should be an immutable struct, as `AbstractDataBudget`'s docstring says. A mutable one would never compare equal, so its run would refuse to resume.
- **Low, by design: a shed radio closes all its links**, receiving ones included. A receiving radio draws nothing, but shedding turns the radio off.
- **Low, by design: the radio mounts as a user-defined kind**, through `add_actuator!` (`link.custom_actuators`), as I-3's `PowerReceiver` does.
- **Low: one policy per run.** `:data_throughput` scores only data links. A run mixing momentum, power and data links waits for I-5. Full duplex on one radio does too.
- **Overlaps.** All four were listed in the design's overlaps (§10), which went to the coordinator with the decisions:
  - `interlink_scheduler.jl`: one line and an import;
  - `save_fields.jl`: the data columns and the level column's shedding. No `data_callbacks.jl` was added;
  - `registry.jl`: imports;
  - `dynamics_rhs.jl`: the state shape and `_apply_data_rhs!`, beside `_apply_power_rhs!`.

  `control_callbacks.jl`, `callbacks/assembly.jl`, the callback list, `setup.jl`, `execution.jl`, `resume_checkpoint.jl` and `simulation_model.jl` are untouched.

## Residual Risk

- Onboard storage and queues are I-8 and ground stations I-9. Pointing,
  antenna patterns, Doppler, atmospheric and polarization losses, interference
  and acquisition time are not modelled until I-7.
- Runs that mix momentum, power and data links can't score them together
  until I-5, and one radio carries one link at a time until then.
- Contact windows have the scheduler's accepted-step resolution, and a resumed
  history splits a window at the resume.
- In a run with a data link, the bit counters are states, so they take part in
  the solver's step control. Its accepted steps, and so the schedule's
  resolution, can differ slightly from the same geometry under another
  policy: by less than one step in the contact-window test. Runs without a
  data link are unchanged.
- A run with a data link, or one that sets `record_available=true`, keeps the
  available links of each accepted step in `model.history`. A large
  constellation with many candidate links over a long run keeps a
  correspondingly larger history in memory; set `record_available=false` when
  contact windows are not needed. Other runs record none (46dd35cc6). The saved
  states and the schedule are unchanged either way.
