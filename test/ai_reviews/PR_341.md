# PR review: untyped control-hook fallbacks

## Scope

Review of PR 341 (branch `control-hook-fallbacks`, head `ac433f39d`) against `main` at 3aec32d8f:
`git diff main control-hook-fallbacks`. One commit, ac433f39d.

- `calcControlMassFlowRate` and `calcReactionWheelTorque` each lose two typed
  fallbacks and gain one fully untyped fallback with the same return value
  (`0.0` and `nothing`).
- `calcControlForceTorque` gains a generic declaration with a docstring. The
  root `@doc` bindings of `calcControlForceTorque` and `calcControlMassFlowRate`
  switch from a method's docstring to the generic one.
- Docstrings and the two templates name the index `spacecraft_index`. The
  control template drops its `p::ODEParams` annotation.

## Findings

Author's notes for the reviewer (no P1 or P2 known to the author):

- Low: two places still name the index `i`: `docs/src/extensibility.md:145-146`
  and the `AbstractControlEffectorModel` docstring
  (`src/foundation/core/types/abstract_types.jl:21`). Both files are edited by
  the open #339, so they were left for a follow-up.
- Low: on `main`, a fallback call with `u` not an `AbstractVector`, `p` not an
  `ODEParams`, a non-`Int64` index or a non-`Float64` time raised a
  `MethodError`. Now it returns `0.0` or `nothing`. No caller in `src/` or
  `ext/` relies on that error: there is no `hasmethod`, `applicable` or `which`
  on these two hooks. The engine always passes those types.
- Low: the new ambiguity check covers every method of the four hooks loaded in
  the test process, including other test files' methods. A future test file
  that defines an ambiguous pair would fail this testset rather than its own.
  That is deliberate: any such pair would break dispatch.
- Note: the package's own methods keep their `p::ODEParams, i::Int64,
  t::Float64` annotations (`BaseThrusterModel`, Apollo descent, robot arm, RPO
  MPC, energy depletion, solar panel). They are more specific than the untyped
  fallback, so dispatch picks them as before. Renaming their arguments belongs
  to the later hook renames.
- Note: the old mass-flow fallbacks declared `::Float64` as the return type; the
  new one returns the literal `0.0` without that declaration.

Reviewer to verify:

- Dispatch for every package effector type is unchanged.
  - Types with their own method still select it.
  - The others select the untyped fallback, which returns the same value the
    typed one did.
  - `Base.return_types(SpaceAGORA.calcControlMassFlowRate, (Any, Any, Any, Any, Any))`
    is `[Float64]`.
- The torque wording in the generic `calcControlForceTorque` docstring: "in
  the bus frame, about the root body's centre of mass".
  - It follows `aerodynamic_mesh_surrogate.jl:807` and the articulated
    right-hand side. There, `dynamics_rhs.jl:3144-3147` treats effector torques
    as about the bus origin (the root link's centre of mass) and moves them to
    the composite centre of mass.
  - In the rigid-body route the torque enters the attitude equation unchanged,
    and only when `orientation_sim` is on (`dynamics_rhs.jl`, the
    `p.args.mission_configuration.orientation_sim` branch after
    `assign_full_translational_rhs!`).
  - Confirm that the wording is right, or propose better wording.
- The force wording ("in the inertial frame, in N"):
  - control forces are summed with the dynamic effectors' inertial forces
    before `assign_full_translational_rhs!`;
  - `_mounted_control_effect` rotates the mounted force to inertial
    (`rot(q)' * force_body`).
- `Base.Docs.@ref(f)` with no signature returns the docstring attached to
  `function f end`. The root names therefore show the generic docstrings, as the
  new testset checks.
- No other docs page binds these hooks by signature. `docs/public_api_symbols.jl`
  lists them by name only.

## Residual Risk

- An external package that defined its own method on
  `(::AbstractControlEffectorModel, u::AbstractVector, p::ODEParams, i::Int64, t::Float64)`

  adds a more specific method instead. Calls with those types reach it as
  before. No companion defines these hooks: EDG, HYPR, MuJoCo and Visualizer
  `main` were searched.
