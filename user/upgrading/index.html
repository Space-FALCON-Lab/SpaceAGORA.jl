Upgrading

Use this page when you move a checkout, or a project that uses SpaceAGORA, to a newer release. Each section lists what you must change for that release.

Renamed and retired extension hooks have their own page, Migrating Extension Hooks, and Public API and Compatibility describes the deprecation rules.

0.6.0

The examples run in the examples environment

Plots and Roots are no longer dependencies of SpaceAGORA. The examples, the plotting scripts and the benchmark studies now run in the examples environment, examples/Project.toml, which takes SpaceAGORA from the checkout and adds the packages they use. SpaceAGORA's own functions are unchanged.

After updating a checkout, install it and prepare the examples environment. Terminal, from the repository root:

julia --project=. -e "using Pkg; Pkg.instantiate(julia_version_strict=true)"
julia --startup-file=no examples/setup.jl

Then:

  • Run the examples with --project=examples, for example julia --project=examples examples/AGORA_Basic_Quickstart.jl. An example that includes examples/common.jl and is started with --project=. continues in the examples environment once it is prepared, and otherwise stops with the setup command. The others, such as the cloth-panel and solar-panel demos, need --project=examples.
  • The command-line tool still runs with --project=.. Its run, telemetry and benchmark commands start their scripts in the examples environment, and stop with the setup command until it is prepared.
  • Scripts of your own that you ran with --project=. and that use Plots or Roots: run them with --project=examples, or move them to a project of your own that declares those packages (Pkg.add("Plots")).
  • Run examples/setup.jl again after a pull that changes the root Manifest.toml, so the examples follow the versions it records.
  • Contributors: the tests start example and CLI children in the examples environment, so prepare it beside the test environment (julia --startup-file=no test/setup.jl).

Installation & Environment describes the environment.

The RPO Plotly figures need using PlotlyJS

PlotlyJS is no longer a dependency of SpaceAGORA. The RPO Plotly figures come from a PlotlyJS package extension, which loads when PlotlyJS does: rpo_path_plot, rpo_tracking_plot, and the planner-comparison plots and their HTML reports. SpaceAGORA 0.5.1 announced the change the first time a script made one of these figures.

  • In a project of your own, add PlotlyJS and load it before making a figure. Julia REPL, in that project:

    using Pkg
Pkg.add("PlotlyJS")
using SpaceAGORA, PlotlyJS

    The order of the two packages does not matter. The examples environment already provides PlotlyJS, and the RPO examples load it.

  • Without PlotlyJS loaded, the figure functions throw PlotlyJSUnavailableError, whose message gives both steps. So does a planner comparison asked for figures: rpo_run_planner_comparison_batch refuses before it plans anything, and rpo_write_planner_comparison_outputs before it writes anything.

  • To write a planner comparison's CSV without figures and without PlotlyJS, set both write_plotly_outputs=false and write_failed_path_outputs=false in RPOPlannerComparisonConfig, or pass them to rpo_write_planner_comparison_outputs.

  • The qualified module bindings GuidanceHooks.PlotlyJS and GuidanceHooks.RPOComparisonReports.PlotlyJS are gone: use PlotlyJS itself.

  • The full sysimage (build/build_sysimage.jl) no longer includes PlotlyJS.

Runs with guidance, navigation or control models do not resume 0.5.1 checkpoints

A checkpoint now records which spacecraft each guidance, navigation and control model acts on, and a resumed run refuses one whose models act on other spacecraft, or are another number in a group. A checkpoint written by SpaceAGORA 0.5.1 or earlier holds no such record, so a run with any guidance, navigation or control model refuses it with an ArgumentError before anything is restored.

  • Finish such a run with SpaceAGORA 0.5.1, or run it again from the start after updating.
  • A run without those models resumes from a 0.5.1 checkpoint as before. Since that checkpoint holds no results rows, the resume warns that the earlier rows cannot be included, and writes its results to resumed_at_<t>s inside results_directory, leaving the earlier files as they were.

Simulation Outputs lists what a checkpoint records and what a resumed run refuses.

Machine calibration constants are measured again

The machine calibration no longer reads past its tables, and the cost constants it saves move to schema 5. Constants saved by SpaceAGORA 0.5.1 or earlier are no longer read:

  • A SolverConfig(parallel=true) run measures them again by itself, once in each working directory, as on a machine without constants.

  • On a machine that uses the predictive campaign planner any other way (profile R7, or SPACEAGORA_CAMPAIGN_PLANNER=predictive set by hand), rerun the calibration after updating, with the thread count you run with. Until then that planner runs without machine constants. Terminal, from the repository root:

    julia --project=. --threads=<T> scripts/calibration/calibrate_machine.jl

Parallel Execution says where the constants are kept.

Interlink scheduling policies are types

The scheduling policies chosen by a symbol are removed, without a deprecation period. Give the run a policy value instead, with SimulationConfiguration(scheduling_policy_model=policy). The default is still SemimajorAxisRatePolicy(), the old :gve_sma, so a run that never set a policy is unchanged.

  • A call with a symbol throws an ArgumentError that names its typed replacement, also under julia --depwarn=error: for example SemimajorAxisRatePolicy(targets=[31, 32]) for SchedulingPolicyModel(:gve_sma; target_indices=[31, 32]). Interlinks lists every replacement.
  • The keywords and properties target_index and target_indices are removed with them, and so are the 0.5.0 names target_idx and target_idxs, which 0.5.0 had kept until 1.0. Reading or setting scheduler.policy or a target property throws, naming .objective or .objective.targets.
  • Interlink checkpoints written by 0.4 and 0.5 resume under the typed policy that schedules the same, and a run moved to the typed policies gives the same results.
  • A policy of your own subtypes AbstractSchedulingPolicy and implements candidate_score (A custom policy). 0.6.0 also adds energy balancing and weighted mixes of policies.

The interlink states are interlink_dv and interlink_delta_sma

In a run with interlinks, the two states every spacecraft carries are renamed, since they hold the effect of every link kind: laser_dv is now interlink_dv, and laser_delta_sma is now interlink_delta_sma.

  • A script that reads u.sc[i].laser_dv or u.sc[i].laser_delta_sma, from a solution, an integrator or a save-field getter, stops with the state's own lookup error, which does not name the replacement: the name of a state cannot warn. Read interlink_dv and interlink_delta_sma instead.

  • The results gain scN_interlink_dv_1 .. scN_interlink_dv_3 and scN_interlink_delta_sma. The scN_laser_* columns and the :laser_dv and :laser_delta_sma save fields stay beside them, with the same values, until 1.0. A column cannot warn either, so search your analysis code for the old names. Terminal, in its folder:

    grep -rnE "laser_dv|laser_delta_sma" .

  • In a run with interlinks, every column after the quaternion block moves four places per spacecraft. Code that selects those columns by position needs updating.

  • Checkpoints keep the old names inside: interlink checkpoints written by 0.5 resume, and 0.5.1 resumes one written by 0.6.0.

Output Columns lists the columns.

The companion packages are 0.5.0

SpaceAGORA 0.6.0 provides HYPRServices and EDGServices at contract 3.0.0, and pins HYPR 0.5.0, SpaceAGORAEDG 0.5.0 and SpaceAGORAMuJoCo 0.5.0. The 0.4.0 companions do not install with 0.6.0, and HYPR 0.5.0 and SpaceAGORAEDG 0.5.0 refuse SpaceAGORA 0.5.1. ExternalPropagationServices stays at contract 2.0.0.

  • Set up each companion you use again after updating, from a Git clone of SpaceAGORA. Terminal, from the repository root (likewise with mujoco or edg):

    julia --startup-file=no scripts/optional_packages.jl setup hypr /path/to/hypr-env

    Installation & Environment describes the commands.

  • 75 RPO and robot-arm helpers that only HYPR's extension called are HYPR's own functions now, among them rpo_path_cost, rpo_retime_path and rpo_retimed_reference. Code that reached one through HYPRServices or SpaceAGORA's internal modules uses SpaceAGORAHYPR.RPO.<name> or SpaceAGORAHYPR.RobotArm.<name> (Versioned HYPR service contract).

  • _edg_planet_frame_lpi and _edg_sample_prediction_atmosphere leave EDGServices; SpaceAGORA keeps both calculations for its own prediction code (EDG package boundary).

  • RPOStationGeometry and RPOCubeSatGeometry are public SpaceAGORA names.
