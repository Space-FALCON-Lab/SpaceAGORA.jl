## Findings
- P1 (fixed in-branch, commit fa1c7f1f): the 3-way merge orphaned `sound_velocity` in `_aero_pure_wrench` (`src/dynamics/coupled/aerodynamic_wrench_models.jl`) — main had added wind-relative `mach`/`S` lines while the picked commit deleted their `sound_velocity` dependency; git merged both silently. Every aero wrench evaluation would have thrown a runtime `UndefVarError`, invisible to syntax parsing and precompile. Resolution: removed the dead spacecraft-level `mach`/`S`; the per-link `mach_body`/`S_body` computed inside the link loop supersede them.
- P1 (fixed in-branch, commit 6a6ae93d resolution): the picked per-link terms `q_body`/`mach_body`/`S_body` originally used the planet-relative speed (`vel_pp_mag`) because the source branch predates the wind-relative airspeed fix. Resolution: all per-link terms use `vel_pp_rw_mag` (v − w), matching main's convention pinned by the airspeed sign contract.
- P2 (fixed in-branch, commit 1c830a93): as committed on the source branch, the ODEParams-aware `wrench` methods activated per-link atmosphere sampling unconditionally, changing default simulation physics for multi-link spacecraft with orientation enabled. Resolution: gated behind `set_per_link_atmosphere!` (default off); the study's aero cases enable it explicitly.
- P3 (accepted): `_aero_link_atmosphere_query` deliberately bypasses the per-satellite GRAM trajectory-extrapolation cache (documented in-code); when the opt-in feature is enabled it costs one extra raw density query per non-root link per RHS evaluation. Off by default, so no impact on existing scenarios.
- P3 (accepted): `MagneticTorqueRodModel` (`src/dynamics/coupled/perturbations.jl`) is newly wired but only active when a configuration instantiates it; no existing scenario constructs it.
