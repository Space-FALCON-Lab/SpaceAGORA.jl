# Review record: PR 505: stream long results at each checkpoint

## Scope

Review of the SpaceAGORA `results-streaming` branch against main (0f03bbfce). It is stacked on C-4b (`constellation-merged-results`, head 734d80542), which is stacked on C-5a (`results-long-layout`, head ae3ce6998); it contains their commits. It also contains the resume fix's branch (`resume-keeps-earlier-rows`, d15d2e552), a separate PR on main for a 0.6.x patch, which should merge first. This is C-5c of the constellations program's large-outputs step, built to the accepted design decision D-C5-9, and on the protocol of the resumed-run fix (#491): rows appended at each checkpoint, the length recorded in the checkpoint, cut back on resume.

What changes:

- A run with `results_layout=:long`, checkpoints and written results (with the results bundle) streams its results.
  - **At each checkpoint**, the rows saved since the last one, except the last row, are appended to the spacecraft and run tables and to the CSVs. The tables are Arrow IPC streams beside the checkpoint.
  - **The last row** stays in memory and in the rows file beside the checkpoint.
  - **The checkpoint's entry** (version 2) records the streams' and CSVs' lengths.
- **When the run ends, or a solve fails,** the remaining rows join the streams, and the Feather files and the manifest are written from them, one record batch per checkpoint.
- **The returned tables** read the Feather files in place.
- **Thinning** counts rows over the whole run.
- **A resumed run** cuts the streams and CSVs back to its checkpoint and goes on appending. A resume that solves nothing leaves the files as they are, unless the run was killed while writing them; then it writes them from the streams. A resume that cannot include the streamed rows keeps the streams under other names, as the resume fix keeps the rows file.
- **Column types.** An Arrow stream has one schema. Each checkpoint's rows are checked against the stream's columns before they are appended: a column whose stream type holds the new rows' is converted, and any other change stops the run, naming the column.
- **Unchanged:** every other run (wide, without checkpoints, without written results, without the bundle) keeps its rows in memory and writes what it writes today.

- **Changed on purpose.** A long-layout run with checkpoints and written results now streams.
  - Its files hold the rows, values and column types, and the CSVs the bytes, that it wrote before.
  - Its Feather files have one record batch per checkpoint instead of one.
  - Its returned tables read those files in place, so their columns are read-only.
  - It writes two more files beside the checkpoint.
- **Design choices for review.**
  - **The streams sit beside the checkpoint, as Arrow IPC streams.** Arrow appends only to its stream format, while the results `.feather` files are Arrow IPC files that other readers open. So the run appends to streams, and writes the Feather files from them when it ends or fails, one batch at a time. The design's sketch appended to the Feather file itself.
  - **The last row is held back at each checkpoint.** A resumed run that takes ticks due at its checkpoint saves the row at that time again (#491's retake). With the last row held, that row is never in the streams yet, so the retake needs no rewrite, and the rows file beside the checkpoint keeps one row.
  - **The manifest during the run** has `streaming = true`, the saved times written so far and the time reached. When the run ends it is the long layout's manifest, as an unstreamed run writes it.
  - **A resume that solves nothing** (its checkpoint at or past the end) reads the first saved times the checkpoint records from the streams and does not cut them back. Cutting them back would cut the finished run's CSV. When the run was killed while writing its files (its manifest still says `streaming = true`, or a Feather file is missing), it cuts them back and writes the files from them.
  - **A resume in another layout** (or without written results, or without the bundle) cannot include rows kept in the streams. It warns and writes to `resumed_at_<t>s`, as #491 does for any resume without usable rows, and keeps the streams beside the checkpoint under other names.
  - **Convert, or refuse by name.** Promoting a stream's column after it is written would mean rewriting the stream. Converting the later batch covers the common case, a column that allows `missing` from its first checkpoint; any other change is refused at the checkpoint where it appears.
  - **Streaming needs the results bundle.** With `SPACEAGORA_SAVE_BUNDLE=0` there is no Feather file to read in place, so such a run keeps its rows in memory.
- **T9 on main** (before this change): a wide checkpointed run that crashed after its third checkpoint and was resumed holds the whole run. Its table, feather and CSV bytes equal the uninterrupted run's (#491). So there is no "Fixed" line here.

## Residual Risk

- **Columns whose type changes between checkpoints.** A batch whose column type the stream's holds is converted. Any other change (a field `missing` through the first checkpoint and a number after it, or an `Int` that later becomes a `Float64`) stops the run at that checkpoint, naming the column, and so does every resume of it, where an unstreamed run promotes the column. The outputs page says how to avoid it. Default fields have fixed types.
- **Kept files accumulate.** Each fallback resume keeps the rows file and the streams beside the checkpoint under other names, and nothing removes them.
- **The streams stay beside the checkpoint** after the run, like the rows file, for a later resume. They hold the run's written rows again, so the checkpoint directory grows by about the size of the Feather files.
- **A hard crash in the middle of an append** leaves a partial batch at the end of a stream. The resume cuts it away, since the checkpoint records the length before it.
- **Memory.** A streamed run holds one segment of saved rows. The solver's own state, and a solution kept with `return_solution=true`, are not streamed.
