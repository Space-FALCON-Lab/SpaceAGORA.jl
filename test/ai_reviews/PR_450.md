# Review record: PR 450: constellation ensembles refuse index-bound dynamic effectors

## Scope

Review of the SpaceAGORA `ensemble-index-bound-effectors` branch (`1c6ec648a`) against main
(`a6736b36c`, v0.5.0 `41cd1f2ef` plus the docs-only #445; no `src/` change since
the tag). The fix for item 2 of §14 of the C-2 effector-scope design
(`_Command_Center/SpaceAGORA_Constellations_C2_Effector_Scope_Design_2026-10-20.md`),
"index-bound effectors in ensembles".

`run_constellation_ensemble` runs each spacecraft as a one-spacecraft run with the
parent's whole dynamic effector tuple, so every member's spacecraft is at run
position 1. `_validate_ensemble_uncoupled` checked interlinks and the GNC tuples,
not the dynamic effectors. Reproduced on main with two spacecraft:

- `ReactionWheelMomentumModel(spacecraft_index=2)` turns spacecraft 2 in
  `run_simulation`, but ensemble member 2 is bitwise identical to a member without
  the wheel: the effector never acts.
- Bound to spacecraft 1, the same wheel leaves spacecraft 2 unchanged in
  `run_simulation` but acts on ensemble member 2.
- `RobotArmReactionEffector(spacecraft_index=2)` is accepted; the engine's
  robot-arm binding (`_robot_arm_effector_matches`) never matches a member's
  position 1.
- `PlumeSurfaceInteractionModel` with one thrust entry per spacecraft: every
  member fails its own plume check ("Plume thrust vector must match the
  simulation spacecraft count."). The ensemble returns those as failed samples
  instead of refusing at setup.

Choice: refuse at setup rather than remap. Remapping would silently change which
spacecraft an effector acts on, and the C-2 design adds explicit per-member scope
translation later (D-C2-9).

Change (`constellation_ensemble.jl` only):

- `_ensemble_effector_bindings` reads the run positions an effector is bound to by
  the fields the engine reads as spacecraft indices: `spacecraft_index` (through
  `SimulationEngine._effector_spacecraft_index`) and
  `SimulationEngine._CROSS_SATELLITE_INDEX_FIELDS` (`chaser_index`,
  `target_index`).
- `_validate_ensemble_dynamic_effectors` refuses, with an `ArgumentError` naming
  the tuple position, the effector type and the member (index and spacecraft id):
  - an index that names no member;
  - an index `k > 1` (it would never act in member `k`);
  - index 1 in an ensemble of more than one member (it would act on every member);
  - a plume whose thrust count is not 1 (its check would fail in member 1), or one
    with a single thrust entry in an ensemble of more than one member (it would act
    on every member).
- It runs inside `_validate_ensemble_uncoupled` after the interlink check and
  before the `allow_gnc_effectors` early return, so the GNC flag does not bypass
  it. A one-member ensemble bound to position 1 is accepted.
- Docstring: one paragraph on the refusal.

Rule: existing runs and ensembles are bitwise unchanged. `run_simulation` is not
touched. In the ensemble the check only reads effector fields; the member
configurations are built as before.

Authorship disclosure: this record was drafted by the author of the PR. It does not
replace the independent review.

Independent review: the coordinator reviewed PR 450 at `1c6ec648a` under Giusy's
delegation on 2026-10-20. It was a read-only review of the diff, without rerunning
the tests.

- **Which bindings are read.** `_ensemble_effector_bindings` takes the index from
  `SimulationEngine._effector_spacecraft_index`, the same accessor the engine uses,
  and from `SimulationEngine._CROSS_SATELLITE_INDEX_FIELDS`. So the refusal
  follows the engine's own notion of a bound effector rather than a second list.
- **The rules match the member model.** Every member runs one spacecraft at
  position 1 with the whole tuple, so an index outside the ensemble, an index
  above 1, and index 1 in an ensemble of several members are each refused with a
  distinct message. A plume is refused when its thrust count is not one, or when
  several members would all run it. A one-member ensemble bound to position 1 is
  accepted.
- **Placement.** The call sits inside `_validate_ensemble_uncoupled`, before the
  member configurations are built and before the `allow_gnc_effectors` return,
  so it applies with and without that flag. `run_simulation` is not touched.
- **Refuse, not remap.** No effector moves silently to another spacecraft. The
  planned per-spacecraft effector scope (C-2, D-C2-9) adds explicit per-member
  translation later, and its builder knows where this call sits.
- `git merge-tree` with main `6d77179ba` is clean, there is no trailer, and
  `## Changed Files` lists the one `src` file.

## Residual Risk

- An effector that selects its spacecraft inside `wrench` (by
  `x.spacecraft_index`) without a `spacecraft_index`, `chaser_index` or
  `target_index` field, or a wrapper around a bound effector, is not seen and is
  passed to every member as before. The C-2 effector scope (D-C2-9) makes the
  binding explicit.
- GNC effectors under `allow_gnc_effectors=true` are still passed to every member
  unchanged, so an index-bound GNC effector has the same problem. This is the
  documented opt-in and is not changed here.
- Ensembles that ran on main with such an effector now throw at setup. Those
  members either ignored the effector, applied it to the wrong spacecraft, or
  failed. A release-note line is proposed with the PR text.
- Follow-up: C-2 D-C2-9 replaces this refusal for scoped effectors with per-member
  translation.
