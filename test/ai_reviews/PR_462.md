## Findings

- **2026-10-21, coordinator review (P3, fixed before the first push).** The notice
  said only to add `using PlotlyJS` to scripts. A project that depends on
  SpaceAGORA has PlotlyJS only as SpaceAGORA's dependency, so that line fails there
  with "Package PlotlyJS not found". In 0.6.0 the extension loads only when PlotlyJS
  is in the active environment. The notice now gives both steps: add PlotlyJS to
  the environment (`Pkg.add("PlotlyJS")`) and `using PlotlyJS` to the scripts. The
  text test checks both, in-process and in the `--depwarn=error` child (10 of 10).

No other findings.

- **One notice per logger.** `maxlog` counts per `_id` in the logger, and every call site uses one `_id`, so a session shows the notice once in total. A new logger, such as a test's, counts again.
- **Nested calls.** The figure builders that call the station trace builders tell the notice more than once per figure; `maxlog` absorbs the repeats. The builders are not hot paths.
- **Standalone loads.** Suites 01 and 03 load the package source into sandbox modules, so `RPOVisualization`'s import resolves through the sandboxed `SimulationModel`; suite 01 passes.

## Residual Risk

- **Notice wording.** It names `rpo_path_plot`, `rpo_tracking_plot` and the planner-comparison plots and reports. C4-4c (0.6.0) must cover the same set with its extension and error messages.
- **Already-loaded PlotlyJS.** Scripts that already load PlotlyJS themselves see the notice once as well. Telling them apart is not reliable while SpaceAGORA itself loads PlotlyJS.
- **Strict log assertions.** A user test that asserts no info logs around a plot (`@test_logs` with no patterns) now sees one record. `@test_nowarn` and warning-level checks are unaffected.
