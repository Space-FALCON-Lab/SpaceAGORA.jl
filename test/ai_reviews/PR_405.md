# Review record: PR 405: run state models keep in checkpoint files

## Scope

(f31cb6bbb, merged in at 3775152d9; the hooks commit 11c252be1 was written on
25c2c3e05). The follow-up of #401 that its record and the checkpoint design
note (2026-10-18) leave open: two extension hooks, `checkpoint_state` and
`restore_checkpoint_state!`, through which guidance, navigation and control
models and sensor kinds carry their own run state across a resume. Built with
the design note's proposed defaults, which stay open for the PI (D-1 to D-5):
those names; GNC models and sensors (not dynamic effectors); restore after the
run-start initializers; built-in models adopt the hooks later; registry rows

Authorship disclosure: this record was drafted by the author of the PR. The
plan assigns behaviour PRs an independent reviewer (the PI, or the second
reviewer when available); this record does not replace that review.

Independent review: the coordinator reviewed the change under Giusy's delegation on
2026-10-18. The model snapshot is checked when the checkpoint is read, before anything
is restored: its version, the models' kinds at their positions, and a restore method for
each saved state. The restore then runs after the run-start initializers, so the saved
state replaces their reset. A checkpointed run refuses at setup a model whose
`checkpoint_state` returns data without a `restore_checkpoint_state!` method. Runs whose
models keep no state write the same checkpoint as before, as the identical fingerprints
show.

Design decided by Giusy on 2026-10-18, as built ("let's go with these"): the names
`checkpoint_state` / `restore_checkpoint_state!` (D-1); guidance, navigation and control
models and sensors take part (D-2); the restore follows the run-start initializers, and a
resumed run keeps #401's behaviour of not calling `initialize_sensor!` (D-3); built-in
models adopt the hooks in later PRs (D-4); a registry row per hook now, with the
conformance round-trip check as a follow-up (D-5).

## Findings

One P1 from the automated review, fixed in e7d1fbf66; no other P1 or P2
findings.

- Fixed from review (P1, thread 4307208294): with a model snapshot in the
  file, a position saved as `nothing` was skipped without checking the model
  there. When another model wrote the snapshot and a model of the same kind
  keeps state only on the resume (stateful parameters, or a version that added
  the hooks), the kind and position check passed, nothing was restored, and
  the run continued from the initializer's reset; only a checkpoint without a
  snapshot was refused. The restore now refuses every model that returns state
  from `checkpoint_state` and has none in the file, with or without a
  snapshot, before restoring anything, naming the kinds.

Points a reviewer should check:

- Low, by design: models are matched by kind (`nameof` of the type) and position, not by identity or parameters; a model of the same kind with other parameters at the same position takes the saved state.
- Low, by design: `checkpoint_state` is called at setup of every checkpointed run (the check of the restore method) and at every checkpoint for every model; the defaults return `nothing`.
- Low: a model that returns `nothing` at one checkpoint and data at another breaks the contract ("`nothing` for the whole run or data for the whole run"); the engine does not check it between checkpoints.
- Low: state shared between models (a GNC link, a member shared by spacecraft-bound copies) is saved and restored once per model that returns it; the file keeps the sharing within one checkpoint (one serialized payload), and repeated restores put back the same data.
- Open decision (the design note's D-3, sensors only): the note has `initialize_sensor!` run again on a resume before the restore; the build keeps #401's behaviour and skips it, since it would need the first sample's truth and could draw from the restored random stream, which would shift every later sample. With the hooks the result is the same (the restore replaces the reset); a sensor kind without them resumes with what the sensor object holds, where the note's order would reset it. The note's order is buildable (the resume's truth and a copy of the stream); left to the PI with D-1 to D-5.
- Low: on a refused resume (models differ, or state missing), the callbacks' state of #401 may already have been restored into the configuration's objects; the next fresh run resets it.

CI on 3775152d9 found that the first version of this test ticked its navigation
model every 1 s with 1 s checkpoint segments: every periodic tick fell on a
segment boundary, where it is skipped (the known checkpoint-tick gap), so both
runs ticked none and the continuation held trivially, and the `> 0` check
failed. Fixed in 78b09760c (ticks every 0.3 s).
