# Review record: PR 439: the conformance state comparison pairs dictionary keys

## Scope

Review of the `conformance-dict-keys` branch against main (`4f727266b`). It answers
finding 4 (P2) of the outside review of 2026-10-20. The fix is for 0.5.0, where
`checkpoint_round_trip` becomes required.

Defect. `_same_state` is the structural comparison behind the run-level conformance
checks. It decides whether two states are the same:

- whether a model's own state at the end of two runs is the same
  (`_model_run_difference` in `src/interfaces/analysis/conformance/models.jl`);
- whether a restored state matches, through the checkpoint round trip in
  `src/interfaces/analysis/conformance/checkpoints.jl`.

It matches mutable objects one to one in both directions, so aliasing counts as state.
Its dictionary branch, though, looked up `b[k]` with each key `k` of `a`. Keys were
never compared, and they never entered the alias maps. Two outcomes followed, both
reproduced on main and at v0.4.0 (`c4bd7b6ab`):

- False positive. A model's dictionary key and another field share one mutable object.
  A broken restore replaces that sharing with two equal objects, and the comparison
  still returned true. A `Dict` finds the restored key by equal hash, so the check
  passed although the next update through the field no longer shows through the key.
- False negative. A correct `deepcopy` of `(dict=IdDict(k => 3), key=k)` keeps both
  the lookup and the sharing. It compared unequal, because the copy's key is another
  object and an `IdDict` finds keys by identity. A `Dict` whose keys hash by identity
  (a mutable struct without its own `hash`) failed the same way.

Change. Dictionaries are compared by a new `_same_entries`, which pairs the keys of
`a` and `b` one to one. It compares each key like any other state, through the same
alias maps as the values, and then compares the paired values.

- Plain keys (bits values, symbols, strings) carry no identity of their own. In a
  `Dict` or an `IdDict`, each is found by lookup, as before, and is now compared with
  the stored key the lookup gives. A `Dict` finds `1.0` with `1` (`getkey` gives the
  stored `1.0`), and that is a different key.
- Other dictionary types do not say which key they hold, so a lookup could hide a
  stored `1.0` behind a query `1`. Examples are `WeakKeyDict` and package types. Their
  stored entries are all paired, plain keys included, as described next (fixed-head
  review, first finding). Each key is assumed to be held once, as in every Base
  dictionary but one.
- That one is `Base.ImmutableDict`. It is a chain of entries, newest first, in which a
  newer entry shadows an older one with an equal key. Its entries are compared in
  iteration order, entry by entry (`_same_chain`, second fixed-head review). They are
  not compared field by field, because the empty dictionary that ends each chain
  leaves its value field unset.
- A mutable key the alias maps have already matched elsewhere in the state pairs only
  with its recorded partner.
- Every other entry is paired with an unpaired entry of `b` of the same shape. The
  shape is a hash of the key's and the value's state that ignores identity
  (`_entry_shape`), so entries that cannot match are never tried. An entry with one
  candidate is compared with it. An entry with more is a choice point: candidates are
  tried on copies of the alias maps, the one its key looks up to first. The first that
  can match is taken, and only a match is committed to the maps.
- Look-alike entries can be paired more than one way, and an alias met later in the
  state can rule out the pairing chosen first (PR review, P2). The comparison therefore
  searches:
  - When a pass fails, it starts again from the beginning, with the next candidate at
    the last choice point that had another one.
  - The states are the same when a whole pass succeeds, so only a complete assignment
    is accepted.
  - A trial that had to guess inside (look-alike entries nested in a candidate) does
    not rule the candidate out. The candidate is compared again on the maps, with its
    own choices recorded.
  - States without look-alike entries need one pass.
  - After 1000 further passes (`_MAX_REPAIRINGS`) the comparison stops, warns, and
    reports the states as different.
- An `IdDict` is searched with `a`'s keys only for plain keys, where identity and value
  agree, so its copied mutable keys are found through the pairing. Equal-hash and identity-hashed keys of a `Dict` pair the same way
  whatever the iteration order.

Nothing else in the comparison changes. Arrays, structs, big numbers, strings and the
skipped runtime objects (tasks, locks, IO) are compared as before.

## Findings

- Outside review finding 4 (P2) is fixed: both outcomes are now reported correctly.
- P2: a correct copy was refused depending on the order of entries or fields. It was
  raised in the PR review thread (`walker.jl:133`) and as the second #439 finding of the
  fixed-head review of 2026-10-20 (at `8c4bc515c`).
  - The defect: each entry was paired with the first candidate that matched on its own,
    and the choice was never revisited. Take a cache keyed by two look-alike nodes (equal
    fields, equal values), plus the active node held by a field after the dictionary or
    by a later entry. A correct `deepcopy` holding its entries in the other order was
    refused, because the first pairing conflicted with that alias. With the field first,
    the same objects passed.
  - Fixed in `e17b8b7d1`: the comparison searches over the pairings of look-alike
    entries (see Scope). Each choice stays open until the rest of the whole comparison
    has run, and the states are accepted only when one complete pass succeeds.
  - `ac45dd07f` adds the review's cache cases as tests: the field after the
    dictionary, the field before it, and an alias inside it.
- P2: changed stored keys of a generic `AbstractDict` were accepted. This is the first
  #439 finding of the fixed-head review of 2026-10-20 (at `8c4bc515c`, `walker.jl:84`).
  - The defect: for dictionaries other than `Dict`, the lookup helper gave back the
    query key rather than the stored one. So `Base.ImmutableDict{Any,Int}(1, 7)` and
    `(1.0, 7)` compared equal in both directions, although a model iterating them sees
    keys of different types.
  - Fixed in `ac45dd07f`: lookup is used only for `Dict` (`getkey`) and `IdDict`
    (identity). Other dictionaries have all their stored entries paired, and a stored
    entry shadowed in an `ImmutableDict` is compared as well. From `a660d377e`, an
    `ImmutableDict` is compared as its chain (next finding).
- P2, 2026-10-20, fixed-head review at `e02b6dd7b` (`walker.jl:195-206`, with the
  generic path picked at `:179-189`): "#439 can accept a changed effective value in an
  ImmutableDict".
  - The defect: one state held the shadow chain `[1 => 8, 1 => 7]` and its restored
    copy held `[1 => 7, 1 => 8]`. They have the same type and the same stored entries,
    so the stored-entry pairing of `ac45dd07f` accepted them in both directions.
    Their lookups differ, though: `schedule[1]` is 8 in one and 7 in the other, so the
    next command changes. `8c4bc515c` refused the pair, so the false acceptance came
    with `ac45dd07f`.
  - Fixed in `a660d377e`: an `ImmutableDict` is compared as its chain, entry by entry
    in iteration order, newest first, so precedence is part of the compared state.
    Keys still compare exactly, values and aliases through the same maps.

Points a reviewer should check:

- Low, the search bound.
  - The worst case is 1001 passes.
  - Each pass is one comparison of the state. On top of that, at each choice point
    with `g` candidates, it makes at most `g` trials of one entry on copies of the
    alias maps.
  - Look-alike entries whose pairing an alias settles later can need several passes. A
    group of `m` look-alike entries can need up to `m!` assignments, so the bound is
    reached from seven such entries whose pairing depends on later aliases
    (`7!` is above it).
  - When the bound is reached, the comparison reports a difference, with a warning that
    names the cause. So a correct state with many look-alike entries and later aliases
    can be refused.
  - Plain keys of a `Dict` or an `IdDict`, and entries whose contents differ, never
    form choice points.
- Note, cost. A dictionary without look-alike entries costs one shape hash and one
  comparison per entry. The trials, and their copies of the alias maps, are made only
  at choice points. The trial copies of the earlier version, made for every non-plain
  key, are gone from that case.
- Note, the shape hash follows at most 32 values of a key and 32 of a value, and a
  nested dictionary only by its type and length.
  - Entries that differ beyond that share a shape, and their trials tell them apart.
  - Equal states always have equal shapes, so no correct candidate is skipped.
- Note, strings. `String` keys count as plain keys; equal strings are the same key to a
  `Dict`, and identity does not matter for an immutable string. Other `AbstractString`
  keys go through the pairing and still compare by value.
- Note, lookup. Lookup is used only where it gives the stored key:
  - `getkey` for a `Dict`;
  - identity for an `IdDict`, where the stored key is the query itself.

  Other dictionaries pay a shape hash per plain key and pair them like other entries.
  Plain keys rarely look alike, so this seldom makes a choice point.
- Note, order in an `ImmutableDict`. With the chain compared in order, the same
  entries in another order are a different state even when no key repeats, for example
  `[1 => 7, 2 => 9]` and `[2 => 9, 1 => 7]`. A model iterating its schedule sees the
  order. A restore that rebuilds the chain must keep it; a `deepcopy` does.
- Accepted earlier and unchanged: `BigFloat` values compare with `isequal`, so precision
  is not part of the compared state.

## P1 Assessment

No P1 findings. The change affects only the dictionary branch of one comparison
function that the conformance checks use, and the search around it. A state with no
dictionaries compares exactly as before, in one pass. A `Dict` or `IdDict` with plain
keys compares as before, except that a key the dictionary finds by `isequal` but that
differs from it (`1.0` for `1`) is now a difference. Other dictionary types now compare
their stored entries.

## Residual Risk

- The search is bounded at 1001 passes. A correct state whose look-alike entries need
  more is refused, with a warning (see Findings).
- When a later alias settles the pairing of look-alike entries, each pass re-compares
  the whole state.
- Dictionary types other than `Dict`, `IdDict` and `ImmutableDict` are paired by
  their iterated entries, each key assumed to be held once. A package type that keeps
  shadowed entries, as `ImmutableDict` does, would need the same ordered comparison.
- `BigFloat` precision is still not compared (accepted limitation).
