## Scope

Review of PR 342 (branch `gnc-algorithm-interfaces`, head `81ce08cc2`) against `main` at
`94ddd1083`: `git diff main...gnc-algorithm-interfaces`. One commit.

  algorithm contract.

## Findings

Author's notes for the reviewer (no P1 or P2 known to the author):

- **Low, API surface:** 24 new exported names. `install!`, `is_current` and
  `propose!` are generic words. A search found no SpaceAGORA name and no export of
  a commonly co-loaded package with these names. They could still collide with
  user code that defines the same names after `using SpaceAGORA`.
- **Low, naming:**
  - `family_contract_version` was chosen over the design's `contract_version`,
    because an internal visualizer-service function has that name;
  - `propose_revision!` is new relative to the design text.
- **Low, ambiguity:** the general fallbacks are untyped in every position. The RPO
  methods type the planner and request (and the reference for revisions) and leave
  `state` and `rng` untyped, so a contributor's method that types its own algorithm
  is strictly more specific than the fallback. `plan_rpo!` still requires
  `rng::AbstractRNG`, so `propose!` with a non-RNG stream raises `MethodError`
  there.
- **Note:** `install!` has no RPO method in this PR. PR 14 adds it when the
  lifecycle's installation moves behind it.

Reviewer to verify:

- **The standalone contract still loads without SpaceAGORA or HYPR:** both
  standalone RPO tests include `gnc_algorithms.jl` first and assert
  `!isdefined(@__MODULE__, :SpaceAGORA)`.
- **No behaviour change:** no simulation path calls a general name yet
  (`git grep -n "GNCAlgorithms\|propose!\|install!" src`). Adding a supertype to an
  abstract type and to concrete structs changes no field, constructor or dispatch
  of existing methods.
- **The forwards are faithful:** `validate_proposal` splats the trusted
  `NamedTuple` into `validate_rpo_result` keywords. `validate_capabilities` passes
  `checkpoint` through. `propose_revision!` calls `retime_rpo!` and never
  `plan_rpo!`.
- **`DirectRPOPlanner` is in fact deterministic:** `plan_rpo!(::Nothing, ...)`
  never uses `rng`, and the contract test checks the stream after a candidate.
- **The public API gate and the strict docs build accept the new page.**
