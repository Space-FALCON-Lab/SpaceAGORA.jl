## Findings

The initial source and focused regression review identified no unresolved
runtime P1/P2 within the cases it exercised. The later published-tree review
found the campaign-duplicate issue and redundant planning saves described below.
New requests run on the configured control clock after due guidance. Startup and atmosphere-exit callbacks retain boundary
bookkeeping without forcing guidance or accepting requests. Accepted windows
and consumed request identities survive checkpoint segments and resume.
Explicit installed plans remain authoritative and register off-grid boundaries
after guidance; their existing setup prerequisites remain documented.

Identical consecutive refusal records collapse to the first timestamp without
consuming or suppressing later retries. Legacy scheduler checkpoints are refused
before result streams are opened or changed because missing request-consumption
state cannot be inferred safely. Review corrections addressed external-plan
precedence, pending configured-request consumption and public documentation.

## Residual Risk

This intentionally changes request-acceptance timing. The configured control
period determines when a new request can be considered. Guidance identity is
Δv, direction and source orbit; callers need a new source orbit for a repeated
identical command. Checkpoints predating v0.7.0 for runs containing a
`BaseThrusterModel`, including runs without a configured burn, require the
version that wrote them or a new run. Explicit BurnPlanFamily installations have a separate contract.
Retained plans do not promise identical adaptive trajectories after arbitrary
changes to checkpoint placement.

## Post-release findings and repair

The separate review of the published v0.7.0 tree found that flight-apoapsis
scaling could change an already consumed campaign command after a short burn,
causing another burn on the same source orbit. It also found duplicate solver
saves at every maneuver-planning tick, including idle ticks. The owner resolved
the configured-delta-v policy question: one burn per explicit request, with
guidance issuing repeated requests.

[PR 532](https://github.com/Space-FALCON-Lab/SpaceAGORA.jl/pull/532) preserves the
accepted campaign request for its source orbit and suppresses the redundant
planning-tick saves while retaining control stops and accepted burn edges.
Its [review record](PR_532.md) describes the added integrated regression,
checkpoint compatibility evidence and qualification limits. This follow-up
changes neither the historical standalone failures nor the published v0.7.0 tree.

A repair cannot undo duplicate burns already accepted or executed by v0.7.0.
Affected flight-scaled campaigns should restart from initial conditions for a
history without those earlier duplicate requests. Valid old checkpoint state
is preserved rather than silently rewriting accepted burn plans.
An old checkpoint can also contain a request emitted before the repair but not
yet accepted. The accepted-request latch takes effect at the next guidance
update; reading the old format does not retroactively correct every request.
