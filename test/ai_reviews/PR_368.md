# Review record: PR 368: SpaceAGORA.Conformance, its Test extension, and the force/torque and facade checks

## Scope

Review of the SpaceAGORA `conformance-suite-base` branch (head `16da3c8f6`: the
change `b8760d061` and a merge of main) against main `dcb994a68` (the merge of #355). This is K1 of the
contributor kit approved on 2026-10-16 (decisions K-1 to K-8, all option (a)).

The PR adds `SpaceAGORA.Conformance`, a public submodule (declared `public`, like
`EDGServices`) whose checks run the engine's own machinery on an object and return
a plain report:

- `check_force_torque_model(model; fixture, samples)` runs eight checks:
  `hooks_present` (the engine's pre-run hook check, `_missing_model_hooks`, on the
  fixture's concrete argument types), `supported_sample_signature` (method-table
  inspection of the sampled force hooks), `repeatable_run`, `deepcopy_equivalent`,
  `global_rng_independent`, `concurrent_equals_sequential` (all four through
  `run_simulation`, comparing saved times and states bit for bit), and
  `output_hook_pure` and `environment_declared` (calls of `wrench` on samples that
  the engine's `build_state_sample` and `sample_environment` build during a fixture
  run; third bodies included, now that #357 samples them for any declaring model).
- `check_service_facade(facade; version)` runs `facade_shape`, the adapter
  standard's rules that `test/unit/adapter_contract_tests.jl` used to state inline.
- `conformance_fixture(...)` is the no-GRAM run of the preflight test, built from
  public constructors; `ConformanceReport`, `ConformanceCheck` and `passed` are the
  report types.
- `test_report`, `test_force_torque_model` and `test_service_facade` are declared in
  core and defined in `ext/SpaceAGORATestExt.jl`, on `Test` as a weak dependency,
  with an error hint as in Distributions.jl. With `SPACEAGORA_CONFORMANCE_REPORT_DIR`
  set, `test_report` also writes each report as a TOML file, the format the
  contributor CI workflow (K5) reads (design section 5, step 4).

Core runs every check on one instance of each concrete built-in force/torque model,
and every check id has negative controls. The adapter facade test calls
`test_service_facade`, the preflight test's type walker moved into the module, and
the module has its own API section and generated page.

replace an independent review. Giusy accepted this record as reviewer on 2026-10-16.

## Findings

No P1 findings.

Points a reviewer should check:

- Medium, design premise: `using SpaceAGORA` already loads `Test`. OSQP, a
  dependency the package loads (`src/models/gnc/control/control_hooks.jl`), depends
  on MathOptInterface, which loads `Test`. So the extension loads in every session,
  in either load order, and the error hint cannot be reached while that chain stays.
  The design note's summary ("`using SpaceAGORA` never loads `Test`") and its
  argument against a hard dependency do not hold today; the weak dependency still
  adds no dependency and stays correct if the chain goes. The hint is tested through
  `_test_extension_hint`.
- Medium, coverage depends on the SPICE kernels: `NBodyGravityModel` and the two
  solar radiation pressure models need SPICE ephemerides (the engine refuses them
  under `SimpleEphemeridesModel` before the run). They run on a SPICE variant of the
  fixture when `data/GRAMSuite.jl` holds the kernels, as in CI, and are listed as
  exempt, with that reason, when it does not. With the kernels all nineteen built-in
  types pass; the N-body instance covers a declared third-body sample.
- Low, by design: `deepcopy_equivalent` runs the caller's model itself with
  `isolate_state=false`, after all other runs, so a model with run state holds that
  run's state afterwards. The docstring says so, and the negative-controls file
  tests it.
- Low, by design: the two concurrent runs advance in step (a discrete callback
  waits after each step for the other run, with a 60 s limit, and leaves the state
  and the derivative untouched) so that they overlap. Without it, the fixture runs
  are short enough to finish one after the other on separate threads. The built-in
  models' concurrent runs equal their sequential runs bit for bit, which also shows
  that the callback does not change a solution.
- Low, scope: from section 3.2, `conformance_fixture` has no `sensors=` keyword yet
  (K2 adds it); `no_deprecated_hooks` is unblocked now that #349 has merged and goes
  to a later K PR. `output_hook_pure` counts log records at `Info` and above. A
  model that declares third bodies needs a fixture with SPICE ephemerides; on the
  built-in fixture its run is refused and the run-level checks report that.
- Low, interface: the report file (`SPACEAGORA_CONFORMANCE_REPORT_DIR`) follows the
  K5 session's proposal: one TOML file per report, `target`, `kind` and one
  `[[checks]]` table per check with `id`, `status`, `since` and `detail`. Nothing is
  written when the variable is unset.
- Low, cost: each built-in model type compiles its own solve, so
  `builtin_conformance_tests.jl` is one of the heavier unit files; it is not in
  `.github/ci-shards.toml` yet and runs at the default unit weight until the next
  weight refresh.

## Residual Risk

- The suites, the example smoke and the full unit tree were not run locally; CI runs
  them.
- The precompiled image of the extension was not built locally (the shared cache
  keeps ten slots); CI builds it in every job that loads SpaceAGORA and Test.
- Without the SPICE kernels the N-body and SRP models and the third-body control are
  not exercised.
- The concurrency check needs two or more threads and skips with one; CI runs four.
- GRAMSuite is not installed locally, so GRAM-backed checks were skipped.
