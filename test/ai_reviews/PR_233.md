# AI Review Artifact — PR #233

## Scope
Articulated spacecraft. `Joint` gains `:hinge`, `:slide` and `:ball` types with joint-space stiffness, damping, rest and initial coordinates. A spacecraft with any non-fixed joint is integrated as a tree in joint coordinates on a free-floating base; spacecraft whose joints are all `:fixed` are unchanged.

## Findings
- P3 (reviewed): the rigid path adds one cached boolean load per RHS call. Bit identity was checked base-vs-candidate on 25 examples with byte-identical result CSVs; all 30 exit 0 on both.
- P3 (reviewed): the articulated path filters the gravity effectors out of the tuple passed to `_accumulate_dynamic_effectors!`. `effector_decision` holds only threading flags and an allotment, nothing indexed per effector, so filtering is safe. The only side effect is the effector cost model seeing the shorter effector count in articulated runs.
- P3 (reviewed): each satellite's workspace is touched only while that satellite is evaluated, because the serial and `@batch` loops partition by satellite.
- P3 (documented limits):
  - mixed rigid and articulated runs are refused
  - third-body gravity acts at the root with total mass
  - a gravity-gradient torque effector uses `inertia_tensor`
  - the harmonics gravity hook allocates per call
  - the viewer still draws configured rigid poses
- P3 (process): the first remote verification failed for environment reasons. The push script's copy excludes tracked `data/` files and is not a git repository. Re-verified from an exact `git archive` of the commit.

- P2 (found and fixed during review): the articulated base torque from aero, SRP and control effectors was accumulated with lever arms measured from the bus origin but applied about the root composite COM, wrong by `root_com_bus x F_body` whenever `:fixed` child links carry mass. `_assign_articulated_rhs!` now moves the torque to the composite COM. A test fails without the fix and passes with it; hinge-only spacecraft (`root_com_bus == 0`) are bit-identical.
- P2 (fixed in the 2026-10-12 integration follow-up): merging PR #232 introduced a second `_gravity_only_acceleration_ii` with the same positional signature. Julia keyword arguments do not distinguish methods, so the definitions overwrote one another during loading. The redundant arm helper and summation are removed; both callers use the spacecraft-aware helper backed by `_ArticulatedGravity`. `_ArmLinkGravity` now carries and forwards `sat_idx`, including from the actual engine hook, so gravity effectors receive the owning spacecraft rather than always spacecraft 1. The `_ArticulatedGravity` type and fields used by later dynamics PRs are preserved.
- P2 (fixed in the subsequent 2026-10-12 physics review): a ball joint attached to a rotated, fixed-merged parent link interpreted its quaternion and rate in the composite-head frame. A parent rotated 90 degrees about Z with local-X joint rate produced inertial-X rotation instead of inertial-Y rotation. The tree now retains the constant parent-link-to-composite-body basis; ball pose, relative velocity, Jacobians and bias acceleration use it. Public joint coordinates, rates, quaternion derivatives, rest and gains remain in the documented `link1` frame. The Joint and configuration documentation now state this contract explicitly, and stale claims that the engine ignores these joints were removed.
