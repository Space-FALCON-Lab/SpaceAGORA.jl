# Checkpoint table cadence: review record

## Scope

Repair of the standard results-table output cadence across checkpoint segments and resumed runs, developed against main a664365499c08cd84b1421047cb2208bf2b46e5b and merged with the current main before merge. Out of scope: the TrajectoryRecorder cadence, the split and multirate output paths, and any force-model or propagator change.

## Changed Files

- src/orchestration/simulation/callbacks/event_callbacks.jl: `_segment_output_times` (canonical epochs indexed from the run origin), `_run_clock_saving_callback` (a fresh inner saver per solve segment, fed only that segment's epochs plus its endpoints) and the stable `_RunClockSavingAffect` handle through which the pre-event drain resolves the live inner saver. The saver falls back to the problem span when the segment end is unset or stale.
- src/orchestration/simulation/callbacks/density_callbacks/assembly.jl: saver discovery recognises the wrapper.
- docs/src/user/control_forecasts.md: states that forecast rows lie on the run's output grid counted from the snapshot's clock origin.
- test/unit/simulation/checkpoint_output_grid_tests.jl (new), test/unit/simulation/event_output_tests.jl, test/unit/simulation/checkpoint_periodic_tick_tests.jl and test/unit/runtests.jl.

## Findings

On main the table saver was a `SavingCallback` with a scalar `saveat`, which the callback library expands from the problem span at every initialization, so each checkpoint segment, and each reinitialised cached integrator, restarted the grid at its own start and nominal epochs were lost. Each epoch is now defined by its index from the run origin alone, so it depends neither on the segment nor on the mission end nor on a later mission extension. Segment endpoints that are not epochs are kept as explicit rows; a boundary that differs from an epoch only by rounding yields both rows, since the tick clock's rounding tolerance is deliberately not applied to output times. Ordinary runs keep their rows exactly when the cadence and the mission time have short decimal forms, which covers the integer cadences in use; otherwise the time column can differ in its last bit from the old span-based range. Control forecasts take the same grid, anchored at the snapshot's clock origin.

## P1 Assessment

No P1. The change is confined to when the table saver samples; the saved quantities, the pre-event drain, the retake of the restored row on resume and the segment accounting are unchanged and their existing tests pass.

## Tests Added/Updated

- checkpoint_output_grid_tests.jl: the epoch grid at exact and off-grid boundaries, at extreme magnitudes and for refused arguments; an affine trajectory solved fresh, across cached reinitialisations with a stale problem span and across a horizon extension, with every nominal epoch present and the saved states matching the exact solution.
- event_output_tests.jl: a battery depletion event inside a segment of a run whose checkpoints are not commensurate with the output cadence; every nominal epoch is present and the sample before the event is correct.
- checkpoint_periodic_tick_tests.jl: a run interrupted and resumed across off-grid checkpoints has the same table as the same run in one piece, with every nominal epoch.

## Residual Risk

The TrajectoryRecorder keeps the per-segment cadence of its scalar `saveat`. The Strang `:multirate` route shares this saver and no test reads its table; it is not qualified by this change. Early-terminated runs get no table row at the termination time, as before.
