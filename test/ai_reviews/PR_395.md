## Findings

Author's notes for the reviewer (no blocking finding known to the author):

- **Low, compatibility by design:** without its step-5 commit, the contract commit
  fails every core CI job that installs the gitlinked companion
  (`optional-edg-installation`, the unit runner and suite 00, the examples smoke and
  coverage): the gitlink then points at SpaceAGORAEDG 0.1.0 (contract 1.0.0), outside
  the new compat `"0.2"`. The step-5 commit pins the companion pull request's head;
  the final pin is its merge commit (hook design 4.8).
- **Low, behaviour of direct calls:** prediction kernels called through core's
  compatibility bindings without an EDG state now have no clock and raise an
  `ArgumentError`; before, they read the configuration. Every run path passes the
  state (the two decision services do), so runs are unaffected; the tests that call
  such kernels directly now pass a context with the state's clock (`_edg_clocked`).
  Conversely, a direct call with a configuration that the run's EDG control does not
  hold used to be refused and now predicts on the state's clock.
- **Resolved after review (4305214121), the clock before the solve starts:** the
  clock period was `NaN` from link initialization until the solver's callback
  reported it, while an `AlgorithmGuidance` makes its first request in its
  initializer, so a targeting run starting inside the passage aborted. The engine
  now also reports the clock when the run starts (see the update below).
- **Low, record growth:** the generic driver records every request, and an EDG
  request copies the EDG state, so a binding requesting at every guidance tick keeps a
  record per tick over a long campaign. The reference page says so; the EDG guidance
  model keeps no records.
- **Note, ordering:** the binding ticks before the same tick's control (as every
  `AlgorithmGuidance`), while the EDG guidance model in maximum-depletion mode ticks
  after it. The acceptance runs give identical results either way: in that mode the
  guidance only selects the mode the control would select itself.
- **Note, overlap:** GNC PR 1 (#394) adds its family at the same places in
  `docs/make.jl`, `docs/public_api_symbols.jl`, `src/SpaceAGORA.jl` and
  `test/fixtures/conformance_instances.jl`; the conflicts are adjacent insertions,
  resolved by keeping both families.

## Update after review (b79961181)

Two findings of the automated review on `6b91cc53a`, both in
`src/models/gnc/guidance/aerobraking/edg_guidance_family.jl`, verified and fixed
with tests that fail on that head.

- **4305214121 (P1): the EDG clock before the initial targeting request.**
  Reproduced: an `AlgorithmGuidance` targeting run started at periapsis, inside the
  drag passage, aborted at its first request with `AlgorithmGuidanceError`
  (`:algorithm_exception`, cause "EDG prediction requires its configured control
  effector"). Link initialization resets `control_clock_period_s` to `NaN`, and the
  binding requests in `initialize_guidance!`, before the solver's periodic callback
  calls `gnc_clock_started!`. Fix: the engine reports each periodic control effector's
  clock when the run starts, after link initialization and before the models' own
  initializers (`_report_gnc_clocks!`: `gnc_clock_started!` with the configured rate
  and the run's start time), and again at each solve's start, as before. The binding
  stays generic.

  **The clock rule, final:** `_edg_targeting_control_clock(p)` returns the period and
  origin the engine reported to the EDG state of the provider call: at the run's
  start (the configured rate and the start time) and at each solve's start (the
  callback's period and start time, the same values within one run). It raises an
  `ArgumentError` only for a call without an EDG state, or in a run without the EDG
  control model, whose clock is never reported. Core never searches the configuration
  for it.
- **4305214122 (P2): targeting plan fields before installation.**
  `validate_edg_guidance_decision` now also refuses `:invalid_switch_time` (a `NaN`
  switch time in any mode, or a non-finite one on an active targeting plan; `Inf`
  stays the no-switch sentinel) and `:inconsistent_targeting` (`targeting_active`
  without the `:targeting` mode, or the mode without it). The companion's decisions
  keep these invariants: its plan sets the mode, the flag and a finite switch together,
  and its fallbacks clear the flag with the mode.

Tests added: in `edg_guidance_family_tests.jl`, the validation set gains the `NaN`
