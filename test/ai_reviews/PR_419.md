# Review record: PR 419: Keep which spacecraft are active in every checkpoint

## Scope

Review of the SpaceAGORA `checkpoint-spacecraft-activity` branch against main
(c7db8b6fb, v0.3.1): a 0.4.0 checkpoint follow-up, the gap #414's record names
as pre-existing. Commits: the change and its tests (778147d56), and this record.

A checkpoint held the activity flags (`p.is_active`) only inside the interlink
entry. A run without interlinks therefore resumed with every spacecraft active. A
spacecraft lost to an impact or a touchdown before the checkpoint came back: its
state was integrated again from where it stopped, its guidance, navigation and
control models ticked for it again (with `skip_inactive`, the 0.4.0 default after
#411, they should be released instead), and the solver's atmospheric phase and
thread allotment counted it. On the new test's fixture, a touchdown spacecraft was
reported touching down a second time just after the resume time. That happens
because its state rests where the event was located, a hair above its clearance; a
state a hair below would make the resume refuse to start ("must start above
terrain plus touchdown clearance").

- Every checkpoint the engine writes now carries `runtime_state.activity =
  (version=1, is_active=...)`, one flag per spacecraft. `_write_checkpoint!` adds it
  whenever it is given the flags; the engine always gives them.
- On a resume, `_restore_activity_checkpoint_state!` reads the entry and checks it:
  version 1, one `Bool` per spacecraft, and agreement with the interlink entry's
  flags when the checkpoint has one. It then copies the flags into `p.is_active`.
  It runs before the interlink restore, the callbacks' and models' checks, and the
  run-start initializers. A refused entry restores nothing.
- The interlink entry keeps its own copy, unchanged (version 1): an interlink
  checkpoint written before this PR still resumes through it, and one written after
  it carries the same flags twice, checked to agree.
- A checkpoint without the entry, written by an earlier SpaceAGORA, resumes as
  before: every spacecraft active, except in an interlinked run, which restores its
  entry's flags. `docs/src/user/outputs.md` says so.

The impact and touchdown events on a resume, as asked. Neither can fire again for
a spacecraft restored inactive:

- Impact (`get_impact_callback`): a `VectorContinuousCallback` with the default
  initialization. Its condition is evaluated for every spacecraft, inactive ones
  included. An inactive spacecraft's state is not integrated, though, so its value
  does not change and no crossing is found. DiffEqBase takes the sign at each step's
  start, and a zero sign triggers no directional event. The downcrossing affect also
  returns at once for an inactive spacecraft.
- Touchdown (`get_touchdown_callback`): the condition is the constant 1.0 for an
  inactive spacecraft, its initialization checks the start clearance only for active
  spacecraft, and its affect returns at once for an inactive one.

The new test checks that the touchdown is not reported again, and that the lost
spacecraft's state is the same at the end of the resumed run as at its start.

Open PRs: #413 also changes `_write_checkpoint!` and the resume block of
`execution.jl`, and #414 adds a line to that block. The new lines sit apart from
theirs. `git merge-tree` merges the branch cleanly with each of #411 to #417. The
new test declares `skip_inactive` true, so it holds before and after #411. It
compares a resumed run with an uninterrupted run with the same checkpoints after
the checkpoint time, so it holds with and without #413's boundary ticks.

## Findings

No P1 or P2 findings.

Points a reviewer should check:

- By design: every checkpoint the engine writes now carries `runtime_state`. Before
  this PR, a run without interlinks, batteries, faults, sensors, hinges, gimbals or
  model state wrote none (#413 makes the same change for a checkpoint written at a
  run's end). A reader that requires `runtime_state === nothing` for such a file
  would see the difference; none in the repository does. The storage-layer tests
  call the storage writer without runtime state and are unchanged.
- By design: an interlink checkpoint holds the flags twice. Folding the interlink
  copy into the new entry would need interlink entry version 2 and a reader for
  both versions; keeping it costs one vector and one agreement check.
- Low: a checkpoint written by an earlier SpaceAGORA resumes as before, so a run
  resumed from one still brings a lost spacecraft back. On the fixture, the
  impacted spacecraft is propagated again from 50 km and its models tick for it,
  and the touchdown spacecraft is reported touching down again at the resume time.
  Whether a touchdown is reported again, or the resume is refused, depends on the
  sign of a near-zero condition at the stored state; the test checks only that
  such a resume starts with every spacecraft active.
- Low: `gravity_backbone_split` checkpoints carry the entry through the same write
  path; the new test runs `:tsit5` only. Suite 03's gravity-backbone resume passes
  (see below).
- Pre-existing, unchanged: the orbit-count callback's state is not in a checkpoint
  (#414's record).

## P1 Assessment

No P1 findings. A run that does not resume never reads the entry, and a
checkpointed run only writes it; neither changes what is integrated. The
uninterrupted checkpointed runs of the new test are the same runs as on main, and
the resumed runs match them bit for bit.

## Tests Added/Updated
