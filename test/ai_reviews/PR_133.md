# AI Review Artifact - PR #133

## Scope
Adds an opt-in direct final-assembly path for flat constellation RHS runs. When `SPACEAGORA_RHS_FINAL_ASSEMBLY_DIRECT_LAYOUT=1` and the state layout is the standard contiguous translational layout, the RHS writes derivatives directly through the `ComponentArray` backing storage instead of assembling each satellite derivative through per-satellite component views. Unsupported layouts and coupled configurations fall back to the existing assembly path.

## Changed Files
- src/core/types/runtime_types.jl - adds `final_assembly_direct_layout` to the RHS plan environment snapshot and two shared-buffer refs that cache whether the current state/derivative layout supports direct final assembly and what stride it uses.
- src/simulation/engine/setup.jl - parses `SPACEAGORA_RHS_FINAL_ASSEMBLY_DIRECT_LAYOUT` and includes the flag in `_snapshot_rhs_plan_env_config`.
- src/simulation/engine/dynamics_rhs.jl - adds layout probing, cached stride/status handling, direct translational RHS writes for supported flat layouts, and guard conditions that decline the fast path for unsupported RHS kinds, orientation simulation, control effectors, robot-arm coupling, active atmosphere/heat-rate work, inactive satellites, or non-contiguous/non-standard state layouts.

## Findings
- P2: direct writes would be unsafe if the state layout changed or if a non-translational/coupled model needed derivative fields that the fast path does not own. The implementation probes parent/child `ComponentArray` data aliasing and exact field order, caches only a positive/negative layout result for that solve, and falls back to the existing per-satellite assignment path when any guard fails.
- P2: mass edge cases must match the existing force-to-acceleration behavior closely enough to avoid invalid derivatives. The fast path writes zero acceleration when mass is non-finite or effectively zero, matching the defensive behavior expected by the existing RHS assembly tests.
- P3: the feature is deliberately opt-in via `SPACEAGORA_RHS_FINAL_ASSEMBLY_DIRECT_LAYOUT`; the default production path is unchanged. This is appropriate because the speedup depends on a narrow state layout and flat-constellation RHS route.
- P3: because the optimization is below the solver API, the highest-risk regression is silent numerical drift rather than a type error. The unit test compares the direct path against the fallback path on the supported contiguous layout and verifies fallback for unsupported layouts/configurations.

## P1 Assessment
No P1 findings. Unresolved P1: No. The branch does not change default behavior; the direct final-assembly path is disabled unless the environment flag is explicitly set and all runtime guards pass.

## Residual Risk
Low. The fast path is opt-in, guarded by exact layout checks, and falls back to the existing implementation for the higher-risk cases. Residual performance risk is that the direct final assembly only helps the final derivative writeback portion of the flat RHS; it does not reduce solver allocation, force accumulation cost, or output retention cost. Residual compatibility risk is limited to out-of-tree callers that enable the environment flag with state layouts not represented by the current tests; those should be declined by the runtime probes and use the existing path.
