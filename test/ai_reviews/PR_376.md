## Findings

Author's notes for the reviewer (no P1 known to the author):

- **Design deviation, medium: the types live with the harness, in `GuidanceHooks`.**
  The design put them in a top-level module after `SimulationModel`. The comparison
  configuration, inside `GuidanceHooks`, must hold them as a field type and build
  them as its default, so the types are defined there and `GuidanceHooks` imports
  `AbstractRPOPlanner` and `RPOPlanningHeadroom` from the standard-library-only
  `RPOPlannerInterfaces` (loaded before `SimulationModel`). The contract methods are
  in the top-level `RPOComparisonPlanning` module, as the design and the HYPR adapter
  have it. All PR gates pass, including the architecture and GNC boundary gates.
- **Design, medium: objects carry their settings.** Each object owns its
  configuration and settings; the configuration's per-algorithm fields build the
  default list and resolve names. A configuration rebuilt from another's fields with
  new settings keeps the old objects' settings. This is documented on
  `RPOPlannerComparisonConfig`. The one such rebuild in the repository (the
  Reconstruction example) passes names directly, so it plans with the new settings.
  The harness still pins every object's cost to the 0.5 m safety distance.
- **Note, low: order of the pre-run checks.** Name resolution, its warning and the
  unknown-name refusal now happen before the HYPR check. A misspelled name on a
  core-only installation now raises `ArgumentError` rather than
  `HYPRUnavailableError`, and a name selection warns before the HYPR refusal (as the
  deprecated `RPOGuidanceModel`'s pre-run check does). Object and default selections
  reach the HYPR check unchanged.
- **Pre-existing, medium: the comparison's closed-loop tracking metrics vary run to
  run on unchanged `main`.** Two runs of the same batch on `main` differ in one
  case's LQ-MPC closed loop (`x_hist`, `u_hist` and the fuel, effort, clearance and
  final-error metrics derived from them), while the planned path, the timed
  reference and the random streams are identical. The likely cause is OSQP's default
  automatic adaptive-rho interval, which OSQP sets from the measured setup time. Not
  changed here. Consequence for this PR: the in-process batch tests compare planning
  outputs and timed references, not closed-loop metrics; the base-versus-head
  evidence below shows full equality, tracking included, whenever the base run itself
  repeats.
- **Known limit, low: polyline modes under an acceleration limit.** With an
  acceleration limit, the acceleration-limited retimer exceeds it at the corners of
  `RRTConnectPlanner` and `RRTStarPlanner` paths, and the unchanged validator refuses
  them (`:failed/:reference_rejected`, `:acceleration_limit`). The curve-based modes
  pass in the same fixture. Documented on the contract page and pinned by a test; no
  limit is relaxed.
- **Low: termination labels.** Swarm modes report HYPR's labels (`:time_budget`,
  `:completed` when stopped early, else `:iteration_limit`); search modes report
  `:completed`; CHOMP and STOMP report `:iteration_limit` when they used their
  iteration cap, else `:completed`. The contract path plans without a wall-clock
  limit.
- **Low: duplicated conversion.** The request mapping and reference timing in
  `plan_rpo!` repeat those of `HYPRRPOPlanner` (core `retime_rpo!` and the HYPR
  companion's plan route). Sharing them would change #365's adapter code, which the
  design keeps as is; a later consolidation can take all three.
- **Note: timing in the comparison records.** `planner_compute_time` and
  `planner_plan_time` are measured wall time and are excluded from the bitwise
  comparisons. Runtime-matched batches (`match_hypr_runtime=true`) budget the other
  planners with HYPR's measured time, so they are checked for ordering and keys only.
  All exact comparisons use fixed work: an infinite runtime limit, or a finite limit
  that never binds together with a capped `runtime_max_iters`.

Reviewer to verify:

- **Bitwise equivalence by construction:** each `_rpo_comparison_planner_path` method
  calls the same kernel with the same arguments as the removed `if` branch, the
  settings copies are field for field, and `rpo_pso_config(rpo_pso_config(c); safe_distance_m=s)`
  equals `rpo_pso_config(c; safe_distance_m=s)`.
- **The shim delegates to the objects, not the reverse,** and warns only at the two
  entries, never from the normalizer, labels, reports or a loop.
- **`plan_rpo!` never uses the comparison's 0.5 m** and never returns a search's
  direct-segment fallback as a candidate.
- **Nothing installs outside the RPO family's driver;** the objects have no run state
  (`initialize_planner` returns `nothing`).

## Residual Risk

- The Reconstruction example (`examples/Earth_RPO_HyPR_FinalISpaRo_Reconstruction.jl`)
  still calls the harness by name in its full run; it now warns once per planner and
  would refuse under `--depwarn=error`. The full run is not in the examples smoke
  (its smoke mode does not plan). Moving it to objects belongs with 19c's example
  work or a follow-up. The other RPO examples use the default objects or only the
  pure identifier and label helpers.
- The comparison's closed-loop metrics are not reproducible run to run on `main`
  (Findings); the parity evidence covers planning outputs exactly and closed-loop
  outputs only when the base run repeats itself.
- The contract path for the seven modes is new behaviour, tested on small fixtures;
  its performance against the request limits on realistic scenarios is not
  characterized here.
- The seven names become public API with a compatibility promise once a release
  carries them (G-2).
- `HYPRComparisonPlanner` and `HYPRRPOPlanner` are both HYPR planners with different
  purposes; the docstrings say which is which.
