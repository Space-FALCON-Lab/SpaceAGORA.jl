# Review record: PR 401: callback run state in checkpoints

## Scope

Review of the SpaceAGORA `checkpoint-callback-state` branch against main
(c4f65caf1). The last open item of the actuator layer's follow-ups: runs with
batteries, actuator faults or sensors resume from a checkpoint file instead of
refusing it, and hinges and gimbals resume at their angles. One commit.

Authorship disclosure: this record was drafted by the author of the PR. The
plan assigns behaviour PRs of the actuator layer an independent reviewer (the
PI, or the second reviewer when available); this record does not replace that
review.

Independent review: the coordinator reviewed the change under Giusy's delegation on
2026-10-18: each removed refusal is replaced by the snapshot restore, which checks the
whole snapshot (version, configuration, spacecraft count) before it changes anything; a
run that does not resume never sets the flag, so its callbacks reset as before; and a
fresh run's clock starts at 0 (`t_start = 0.0` in `run_simulation`), which the sensor
schedule's rebuilt grid relies on. The old-checkpoint refusal now comes after the
interlink restore instead of at callback construction; that restore only copies the
activity flags into the run's own parameters, so a refused resume leaves no state
behind.

## Changed Files

- `src/orchestration/simulation/engine/resume_checkpoint.jl`: `_callback_checkpoint_configuration` (each record with its position: a fault's actuator in the mounting order, a sensor's, hinge's or gimbal's link, a gimbal's thruster), `_callback_checkpoint_state` and `_restore_callback_checkpoint_state!` (read the snapshot first and validate it whole, then restore batteries, faults, sensors, hinges with their link attitude, and gimbals with their thrust rotation, and set the resume flag); `_write_checkpoint!` takes `callback_state` next to the interlink state.
- `src/orchestration/simulation/engine/execution.jl`: the checkpoint loop passes the callback state; the resume restores it after the interlink state.
- `src/orchestration/simulation/state/runtime_types.jl`: `SharedBuffers.callback_resume`, set by the restore.
- `src/orchestration/simulation/callbacks/power_callbacks.jl`: the refusal removed; the run-start reset of the battery flags skipped on a resume.
- `src/orchestration/simulation/callbacks/fault_callbacks.jl`: the refusal removed; the faults' activity kept on a resume (their mounting positions still resolved).
- `src/orchestration/simulation/callbacks/sensor_callbacks.jl`: the refusal removed; on a resume the sensors are not reset, `initialize_sensor!` is not called, and each period's schedule continues from the run's start at 0 after the last sample taken.

Outside `src/`: the outputs, power budget and extensibility pages, tests.

## Findings

Two P2 findings from the automated review, fixed; no other P1 or P2
findings.

- Fixed (P2): the restore returned early when the run had no batteries,
  faults, sensors, hinges or gimbals, before reading the snapshot, so a
  checkpoint holding such devices resumed into a configuration without them
  dropped them silently. The snapshot is now read first and, whenever
  present, validated, so a run without its devices refuses it (as the
  interlink restore refuses an interlink snapshot without `interlink_model`).
- Fixed (P2): the configuration did not identify where each record sits, so
  a fault moved to another actuator of the same kind matched and its saved
  activity and held level landed on the wrong actuator. Each fault now
  records its actuator's position in the mounting order (found as
  `resolve_faults!` finds it, by identity, since `f.index` is not resolved
  when the restore runs), each sensor, hinge and gimbal its link's position,
  and each gimbal also its thruster's position on that link.

Points a reviewer should check:

- Low, by design: a sensor kind's own state beyond the engine's fields
  (`rng`, `latest`, `latest_time_s`, a gyro's `bias`) is not in the file, so
  a kind with more state (what `initialize_sensor!` resets) resumes with that
  state fresh; the built-in kinds keep no more.
- Low, by design: control effectors' own state (held commands, ramps,
  planners) is not in the file, as before this change; the faults' onset
  levels, which come from those commands, are.
- Low: the sensor schedule rebuilds its next sample from the latest sample
  time over the period (a fresh run's clock starts at 0); a sample is due at
  the resume time only when the earlier run did not take it.
- Low, pre-existing and independent: with checkpoint segments the periodic
  control tick at each segment boundary is skipped (the separate
  `checkpoint-periodic-ticks` work); a resumed run skips the tick at its
  start the same way, so it matches a run checkpointed at the same interval,
  which is what the hinge and gimbal test compares against.
- Low: old checkpoints without the callback state are refused for runs with
  batteries, faults or sensors (which refused every resume before); runs
  with only hinges or gimbals resume from them as before, with a warning.

## P1 Assessment

No P1 findings. A run that does not resume never sets the flag, so its
callbacks take their run-start resets as before; checkpoints only gain a
runtime-state entry, and runs without batteries, faults, sensors, hinges or
gimbals write the same payload as before.
