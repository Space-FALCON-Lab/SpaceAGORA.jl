# Review record: PR 470: callbacks follow the run's solver mode

## Scope

Review of the SpaceAGORA `callback-solver-mode` branch against main
(`25d22f3f4`). It fixes the follow-up named in PR 453's record (Findings and
Residual Risk): `get_callbacks` took the gravity-backbone mode from the process
solver setting, not from the run's `SolverConfig`.

On main:

- `run_simulation` solves with `args.solver_config` when it is set, and otherwise
  with `_solver_config_from_env()` (`SPACEAGORA_SOLVER_MODE`, or an active
  `SimulationEngineConfig`'s overrides).
- `get_callbacks` (`callbacks/density_callbacks/assembly.jl`) set `backbone_mode`
  from `CallbackServices._solver_policy_mode()`, the process setting. Backbone mode
  leaves out the planet-frame update, the GRAM density perturbation, the density,
  thermal, entry-end and drag-state callbacks, the GNC phase (sensors, navigation,
  guidance, control, faults, power, CMGs), quaternion projection, result saving and
  the EDG passage-heat observer. The same function's initial-force output already
  preferred `args.solver_config`.
- When the two sources disagreed, the run got the callbacks of the other mode:
  - A backbone run chosen by `SolverConfig(solver_mode=:gravity_backbone_split)`
    under the default process mode (`tsit5`) got the first-order set. In vacuum,
    the only callbacks in that set beyond the backbone's are the planet-frame
    update and, when results are recorded, result saving. Since PR 453 a backbone
    run cannot have a density model, so no atmosphere callback reaches it. Its
    trajectory, saved times and results table were bitwise those of the same run
    chosen by `SPACEAGORA_SOLVER_MODE` (measured, see Tests).
  - A Tsit5 run chosen by `SolverConfig(solver_mode=:tsit5)` under
    `SPACEAGORA_SOLVER_MODE=gravity_backbone_split` got the backbone set. Its
    results table was empty, and a control effector never ticked (0 ticks against
    5 with the environment unset; 60 s, `control_rates` 10.0). With a density
    model it also lost the density and thermal callbacks.

Change:

- `_run_solver_config(args)` (`engine/solver_policy.jl`) states the rule once:
  `args.solver_config`, or `_solver_config_from_env()` when that is `nothing`.
  `run_simulation` uses it in place of its inline expression, which it equals.
- `get_callbacks` takes a `solver_mode::Symbol` keyword. Its default is
  `CallbackServices._run_solver_config(args).solver_mode`. The backbone decision
  and the initial-force output both read it.
- `run_simulation` passes the mode it solves with (`solver_mode=solver_mode`).
- The callback service declares `_run_solver_config` and no longer declares
  `_solver_policy_mode`. No callback reads the process solver mode any more; the
  service operation had no other user in `src`, `ext`, the tests, the docs or the
  open PRs (#462, #465, #468, #469). The engine's own `_solver_policy_mode` is
  unchanged.
- Docs: the callback-order section of `docs/contributing/architecture.md` says
  which mode decides the backbone set; `docs/src/user/solver_configuration.md` says
  the chosen mode decides both the integrator and the callbacks.

Independent review: the coordinator reviewed PR 470 at `b38c3cb33` under Giusy's

- **One source for the mode.** `_run_solver_config(args)` is `args.solver_config`
  when set, otherwise `_solver_config_from_env()`. That is the expression
  `run_simulation` used before, now shared. `run_simulation` passes its resolved
  `solver_mode` to `get_callbacks`, so the backbone decision and the
  initial-force output use the mode the run solves with.
- **The removed forwarder.** `CallbackServices._solver_policy_mode` was only a
  forwarder. Its config form was `cfg.solver_mode`, so dropping it changes
  nothing for runs with a `SolverConfig`. The engine's own `_solver_policy_mode`
  stays for its other caller.
- **The behaviour change is the fix.** Runs whose two mode sources agree are
  unchanged in callbacks, bits and tables. When they disagree, the callbacks now
  follow `SolverConfig`. The one visible effect on main was an empty results
  table for a Tsit5 run chosen by `SolverConfig` under a backbone environment;
  that table is now filled, with trajectory bits unchanged.
- **Merges.** It merges cleanly with main `25d22f3f4` and with #462, #465, #468
  and #469. Its `execution.jl` hunks are outside #465's. No commit carries a
  trailer.

## Findings

No P1 or P2 findings in the change. Points a reviewer should check:

- Deliberate behaviour change, the fix itself: a run whose `SolverConfig` and
  `SPACEAGORA_SOLVER_MODE` disagree now gets the callbacks of the `SolverConfig`'s
  mode.
  - A Tsit5 (or other first-order) run chosen by `SolverConfig` under a backbone
    environment now records its results, ticks its GNC models, updates the planet
    frame and, with a density model, installs the density and thermal callbacks.
    In the measured runs (one spacecraft, J2 gravity, no drag effector) the
    trajectory bits did not change, and the results table now equals the table of
    the same run with the environment unset. With GNC models, or with a drag
    effector whose phase tolerances differ, the trajectory changes too, because
    those callbacks now run.
  - A backbone run chosen by `SolverConfig` under the default environment now gets
    the backbone set: no planet-frame update, and no result saving (its table is
    built from the backbone's own solution, as before). Its trajectory, saved
    times and results table are bitwise unchanged.
- Low: the default resolution when `solver_config` is `nothing`. Main's
  `get_callbacks` used `_active_solver_config()`, which returns an active
  `SimulationEngineConfig`'s `solver` directly; the default now uses
  `_solver_config_from_env()`, which reads that configuration's override set, as
  `run_simulation` does. The two differ only when a `SimulationEngineConfig`'s
  `env_overrides` sets `SPACEAGORA_SOLVER_MODE` to another mode than its
  `solver.solver_mode`; `run_simulation` then solved with the override's mode, and
  the callbacks now follow it. Inside such a scope the default now also parses the
  override set, so a malformed solver override throws in `get_callbacks` as it
  already does in `run_simulation`. Only direct callers of `get_callbacks` use the
  default; `run_simulation` passes its own mode.
- Low: two other places resolve the same rule inline:
  `orchestration/mission/mission_segments.jl:252` and
  `interfaces/analysis/conformance/fixtures.jl:29`. They agree with
  `_run_solver_config` and are not changed.
- Low: the engine's convenience methods without a `SolverConfig` argument
  (`_build_typed_solver_problem` without a mode, `_solve_with_solver_policy(prob,
  args, ...)`, `_solve_with_explicit_solver(prob, args, ...)` and others) still read
  `_active_solver_config()`. `run_simulation` calls the forms that take its
  resolved mode or configuration, so they are not on its path.
- `git merge-tree` is clean with main and with each open PR head (#462, #465,
  #468, #469), and with #465 and #468 merged together. #465 and #468 also edit
  `engine/execution.jl`, in other hunks.

## P1 Assessment

No P1 findings. Runs whose `SolverConfig` and environment agree, and runs without
a `SolverConfig`, get the same callbacks as on main and are bitwise unchanged. The
runs that change are those whose `SolverConfig` named another mode than the
environment, which got the other mode's callbacks.

Unresolved P1: No

## Tests Added/Updated

- `test/unit/simulation/callback_solver_mode_tests.jl`, new testset "callbacks
  follow the run's solver mode". One spacecraft under J2 gravity in vacuum for
  60 s. A callback set is identified by the types of its affects, in order.
  - "the mode passed in decides": the keyword selects the backbone or the
    first-order set, and wins over the `SolverConfig` and the environment.
  - "chosen by SolverConfig only" (environment unset): the default set is the set
    of the `SolverConfig`'s mode, for the backbone and for Tsit5.
  - "chosen by SPACEAGORA_SOLVER_MODE only" (`solver_config=nothing`): the default
    set is the environment's mode, both ways.
  - "SolverConfig and SPACEAGORA_SOLVER_MODE disagree: SolverConfig wins": the
    backbone `SolverConfig` under `tsit5` gets the backbone set without the
    planet-frame update; the Tsit5 `SolverConfig` with a control effector and
    results under `gravity_backbone_split` gets the Tsit5 set with it.
  - "run_simulation installs the callbacks of the mode it solves with": a Tsit5
    run with a control effector, chosen by `SolverConfig` under a backbone
    environment, ticks its control as often as with the environment unset and
    returns an equal, non-empty results table. A backbone run chosen by
    `SolverConfig` under `tsit5` has the same times, states and results table as
    one chosen by `SPACEAGORA_SOLVER_MODE`.
- `test/unit/simulation/gravity_backbone_atmosphere_tests.jl`: comment only.

## Residual Risk

- A script that set `SPACEAGORA_SOLVER_MODE=gravity_backbone_split` while passing
  another mode's `SolverConfig` now gets that mode's callbacks: results, GNC ticks
  and atmosphere callbacks it was missing. Its output changes accordingly.
- A direct caller of `get_callbacks` whose configuration and environment disagree
  now gets the configuration's mode. No companion package found locally calls
  `get_callbacks` or the removed service operation.
