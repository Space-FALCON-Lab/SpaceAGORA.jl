Optional adapter standard

Use this page when you write or change a companion package: a separate package that adds an optional feature to SpaceAGORA, such as HYPR planning, MuJoCo propagation or EDG guidance. It tells you which boundary to use, what each boundary promises, and what to record about your tests.

A companion reaches SpaceAGORA through a service module, which these pages also call a facade. A service module is a module inside SpaceAGORA, such as SpaceAGORA.HYPRServices, that names the SpaceAGORA types and functions a companion may use and the functions it may add methods to. The companion owns its implementation and its dependencies. SpaceAGORA owns the shared configuration and result types, the simulation lifecycle, validation, and the services the module lists. Loading SpaceAGORA alone never loads a companion or its native library.

These rules apply to new adapters and to changes in existing ones. Each domain keeps its own protocol: an external propagator advances spacecraft state, a planner returns a reference that SpaceAGORA checks, and a guidance package computes its decisions. The domains share the rules on this page; there is no single callback or registry that all companions use.

Versions, source pins and evidence

When you record a SpaceAGORA and companion pair that works, write down three identifiers. Keep them separate, because each answers a different question:

  • Package version, in Project.toml: what Julia's package resolver uses to choose compatible releases.
  • Contract or format version: the version of the service module's rules, or of a file format, that the code checks when it loads.
  • Source revision: the exact SpaceAGORA and companion commits your check ran on.

A SpaceAGORA checkout selects companion source revisions through its git submodule pins (gitlinks) and packages/VisualizerSource.toml. A companion's default branch or release tag can point somewhere else. So record both commits you tested. A new package version, or an updated pin in the documentation, is not a new test run, and neither is reading a newer companion's source.

Name the checks you ran with each result, and how each one ran. Pure-Julia HYPR tests and analytic EDG runs test behavior, such as numerical results and run isolation, without native code. A native or scientific claim needs the case that exercises it: a real MuJoCo scene, a GRAM atmosphere or an EDG reference campaign.

Some companion tests and research scripts still use private SpaceAGORA paths. These paths are not supported, so do not use them in new code; maintainers find them, with the tests to run for each boundary, in docs/contributing/companion_boundaries.md in the contributor documentation.

Facade shape and compatibility

Every service module provides:

  • CONTRACT_VERSION::VersionNumber, the contract version, which is independent of package release versions;
  • require_version(expected), which returns nothing for the one supported version and throws the module's CompatibilityError for any other;
  • IMPLEMENTED_FUNCTIONS, the functions the adapter may add methods to;
  • CONSUMED_SERVICES, the SpaceAGORA types and operations the adapter may use.

Each entry in these lists is a Symbol for a name in the module, or a tuple of symbols for a path through nested namespaces. Any extra list must be named and documented: HYPR's CLOTH_SERVICES, for example, is relative to its Cloth namespace. The names are aliases, so each type and function keeps its original identity. Reach adapter-specific SpaceAGORA code only through the listed names; for ordinary configuration and simulation, use the documented root public API. Whole internal modules and the engine's raw storage are not part of the contract.

Check the contract version before you define adapter methods or load a native library, and check it again when the adapter initializes. If the version is refused, leave the adapter unavailable. After a failed package load, start a new Julia process: Julia may already have defined some of the package's methods, and they are not undone.

Contract versions must match exactly, even when a change only adds a name. A change to signatures, units, frames, result fields, mutability, ownership or failure behavior needs a new reviewed contract version. A package compatibility range only limits what the resolver may install; record which releases in the range you actually tested.

Package and installation rules

An adapter is either a standalone package that depends on SpaceAGORA, or a Julia extension that loads when a weak dependency is present. SpaceAGORA must not have a mandatory dependency on an optional adapter. Keep the implementation in its companion and activate its supported adapter by loading the required packages.

HYPR and SpaceAGORAMuJoCo are pinned at exact revisions as Git submodules under packages/robotics/, and SpaceAGORAEDG under packages/gnc/. These are source checkouts: they are not copies of the implementations, and they add no required dependency. The shared optional-package helper checks the pinned revision, the package UUID and version, and that the checkout is clean, before it passes the path to the existing installer. It sets up only the repository you select. Keep this setup step separate from activating the companion, from the runtime version checks and from scientific acceptance. A passing source check means the right source is installed; run a native simulation before you report one as passing.

Each repository declares its own runtime and test dependencies, owns its native artifacts, and provides an installation path that works outside a SpaceAGORA checkout. Do not rely on a parent Manifest.toml, sibling source paths or another adapter's setup script. For an unregistered or unreleased integration, record the exact source revisions of the pair you tested, and install the SpaceAGORA revision before the adapter. A package's [sources] entries do not carry over into other environments that use the package.

Ownership and scientific semantics

Document who owns the configuration, the mutable runtime, the state, the random-number streams, the native resources and the cleanup. Never let state that serves as a template become mutable state shared between runs or workers. Where they apply, state the units, coordinate frames, quaternion convention, index mapping, callback order and time synchronization. Use SpaceAGORA's services for shared calculations instead of copying them into the adapter.

Refuse unsupported modes with an explicit error. Do not quietly switch the integrator, drop a configured feature, relax an accuracy threshold, or report a failed native test as a skip. Run both SpaceAGORA's validation and your adapter's, since each checks different things, and test each execution mode you support: a configuration preflight checks the configuration only.

Saved-output consumers

SpaceAGORAVisualizer, a separate package, reads SpaceAGORA's saved files in a versioned format; it uses no simulation services. SpaceAGORA owns the scene metadata and the conversion of saved rows; the companion owns the HTML assembly, the browser code and third-party assets. Their renderer protocol and portable payload schema are both version 1. The extension checks the renderer protocol before it hands over the work, and the companion checks the payload schema before it renders. These integer format versions are separate from the VersionNumber contracts of the service modules above.

The integration uses ext/SpaceAGORAVisualizerExt.jl and a weak dependency. Loading SpaceAGORA alone leaves the renderer absent; loading both packages, in either order, enables HTML export. A missing renderer fails before a requested run or campaign creates outputs. Scene and JSON export work without it. The companion also opens saved JSON without SpaceAGORA.

scripts/setup_visualizer.jl installs the revision pinned in packages/VisualizerSource.toml into a separate environment. Installation and both load orders are supported. The companion does not read the engine's raw state, add dynamics of its own or change propagation settings. See the user guide for the supported commands.
