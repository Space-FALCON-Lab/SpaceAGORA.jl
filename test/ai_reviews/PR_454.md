# Review record: PR 454: the phases of a run's start, and who owns each run state

## Scope

Review of the SpaceAGORA `init-resume-phases` branch against `callback-phases` (#449; C2a head 0bbaff0d5, which includes main 6183d00d2). This is item C2b of the post-0.5.0 structure and readability cleanup plan ("C2. Make engine sequencing readable in two small PRs"). It lands after C2a.

The change is behavior-preserving:

- the start of `run_simulation` becomes three named private phases, called in the same order;
- the checkpoint-state file is regrouped in the order a resume uses it;
- the lifecycle hooks' run order is stated once;
- a maintainer section holds the run-state ownership table;
- one testset pins the resume order.

No run order, numerical result, public signature or checkpoint format changes.

The plan's Preserve list, and where each item stays:

- **The release's exact ordering:** the moved statements are byte-identical, in their old order (see the proof under Tests).
- **Engine and callback state and model state restored at different times:**
  - `_resume_engine_state!` restores activity, interlinks, callback records and pending ticks, and only checks the model snapshot;
  - `_start_run_models!` restores the models' state after the initializers.
- **Links initialize once:** `initialize_gnc_links!` stays the first statement of `_start_run_models!`, called once per run.
- **Model snapshots supersede run-start resets:** `restore_checkpoint_state!` still follows the initializers.
- **Resumed sensors avoid reinitialization:** `callback_resume` is still set in phase 1, before the sensor callbacks initialize.
- **Resumed RPO avoids a duplicate initial request:** `model_resume` is still set in phase 1, before the initializers.
- **Between-run user edits and isolation:** untouched (`_run_start_entries`, `isolate_state`).
- **#444:** its initialization scheduler placement in `execution.jl` and its `hardware_terminals` entry in `resume_checkpoint.jl` are unchanged; the residual proof and the regroup proof cover them.

## Findings

No P1 or P2 findings in the change.

Outside the change, recorded as current behavior and not altered: hinge and gimbal angles and the mounted thrusters' firing state (`κ`, `thrust`) have no run-start reset.

- With `isolate_state=false`, a repeated run continues from where the previous one left the hardware. Run three times, a `PanelHinge` with `max_rate_rad_s=0.1`, held at level 0.5 for 3 s, ends at 0.1, 0.2 and 0.3 rad.
- With the default `isolate_state=true`, each run starts from the configured values.
- Batteries, faults and sensors are reset.

The table states this. Whether hardware should follow the GNC models' "start equal" rule is a separate decision.

Points a reviewer should check:

- **Destructuring.** `run_simulation` takes the phase-1 results as `(; resumed, model_snapshot, pending_ticks, t_start, u_start) = _resume_engine_state!(...)`. The same five values as before are bound, once each.
- **Arguments.** Each phase receives the same values its statements read before: `args`, `p`, `solver_mode`, `initial_conditions`, `mission_end`, `run_clock`, `checkpoint_active`, and phase 1's results. The phase functions' parameter names equal the old local names, so the moved text is unchanged.
- **Load order.** The regrouped file has no top-level statements other than definitions. `CALLBACK_CHECKPOINT_STATE_VERSION` keeps its place before the functions that read it.
