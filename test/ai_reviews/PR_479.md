# Review record: PR 479: copy configuration structs through their constructors

## Scope

Review of the SpaceAGORA `configuration-copies` branch against main (2088b4408, after #468). This is C-4a of the constellations program's campaign-results step, "settings copied through the constructor". It is built to the accepted C-4 design decisions:

- D-C4-7: one helper for every hand copy of a configuration struct, with a field-table test as the guard;
- D-C4-8: the example smoke copy keeps every setting it does not mean to change.

What changes:

- `SimConfig._with_fields(x; changes...)` copies a struct through its own constructor, with the named fields changed and every other field passed on as it is.
- The ten copies in `src` that listed every field one by one now name only the fields they change, and so do the five RPO planner-settings copies. The three copies that already carried every field (two by name, the density-epoch environment copy through `fieldnames`) use the helper too.
- Every existing run is bitwise identical. The one behavior change is in the example smoke copy: it no longer resets `articulated_live_pose_loads`, `checkpoint_interval_s` and `checkpoint_directory` to their defaults. No example sets them.

- **The helper.** `_with_fields(x; changes...)` refuses any name that is not a
  field of `x` with an `ArgumentError`. It passes every other field on as the
  same object and rebuilds through the type's own constructor, so its checks
  run. It uses the type's wrapper, so a parametric type's parameters are
  inferred again, as `_with_configuration` did. `SpacecraftModel`, whose keyword
  constructor computes fields, is rebuilt in field order instead.
  `_with_configuration` is now this helper. It refuses an unknown override with
  the same error, where it used to fail inside the constructor.
- **The copy sites.** Each now names only the fields it changes:
  - the ensemble member settings (results and checkpoint folders);
  - `_without_gnc` (the three GNC containers);
  - the Monte Carlo sample stamps (index, finish time);
  - the scene and viewer exports, the scenario builders, the mission workflow and
    the checkpoint conformance helper.
- **The smoke copy (D-C4-8).** `_example_smoke_args` now keeps every mission and
  simulation setting except those it means to change. It sets
  `save_visualization_scene`, `checkpoint_enabled` and `resume_from_checkpoint`
  to `false` explicitly, where the old lossy copy reached them only through
  defaults. So physics settings such as `articulated_live_pose_loads` reach a
  smoke run; no example sets one today.
- **The outside review's P1 and P3s (`4fe2950af`).**
  - `test/probes/configuration_copy_probes.jl` now expects the copy rule's `ArgumentError`, and the smoke copy keeping its checkpoint settings, so required CI no longer stops that shard.
  - The five RPO planner-settings hand copies now go through `_with_fields` (bitwise against main).
  - The `_without_gnc` test uses a spacecraft that has GNC.
  - The `_with_fields` docstring states that a `SpacecraftModel` rebuilt in field order skips its keyword constructor's checks.

## Findings

Found by an outside review and fixed (the in-house review of fc283d84a, 2026-10-21):

- **P1: a copy probe asserted the old behavior.**
  - `test/probes/configuration_copy_probes.jl` expected a `MethodError` for an unknown override, and expected the smoke copy to reset `checkpoint_interval_s` and `checkpoint_directory` to 300.0 and "".
  - Hosted CI failed plain 10 and coverage 13 on it. The probe aborted those shards, so 25 unit items in plain 10 and 18 in coverage 13 were not attempted.
  - The probe now expects the `ArgumentError` and the carried values (17.0 and "custom-checkpoints"). It also checks that `articulated_live_pose_loads` is carried.
  - This record said "No P1 or P2 findings" and that the suites pass. That was wrong: suite 09's probe driver was not among the suites run.
- **P3: the `_with_fields` docstring said the constructor's checks run for every type.**
  - `SpacecraftModel` is rebuilt through its field-order constructor, which checks nothing; the checks are in its keyword constructor. A copy changing `battery_energy_index`, `n_terminal` or `tempurature_index` to an invalid value was accepted.
  - The docstring now says so, and to change only fields whose values are already valid. Today's only caller, `_without_gnc`, changes only the GNC containers.
  - Checks were not added to the field-order path: the old `_without_gnc` used the same constructor, and no caller changes a checked field.
- **P3: the `_without_gnc` check could not catch a copy that keeps GNC.** The field table's spacecraft had empty GNC containers. It now has one guidance, navigation and control entry each, so a copy that does not strip them fails.
- **P3: the contributor rule overstated the sweep.**
  - Five RPO planner-settings copies still listed every field one by one: `RPOPlannerComparisonConfig` (14 fields), `RPORRTConnectSettings` and `RPORRTStarSettings` (12 each), `RPOCHOMPSettings` (4) and `RPOSTOMPSettings` (6).
  - They now use `_with_fields`. So does the density-epoch copy of `EnvironmentModel`, which merged all its fields by `fieldnames`. The sentence in `configuration_ownership.md` holds as written.

- **Fixed: the example smoke copy dropped settings.**
  - It named seven of `SimulationSettings`' thirteen fields and reset the others to their defaults.
  - Among them was `articulated_live_pose_loads`, which changes the physics of articulated spacecraft. An example that set it would have smoke-tested different physics, or met the articulated gravity-gradient refusal.
  - No example sets it today, so no smoke run changes.
- **Unchanged on purpose.**
  - `_with_study_settings` and the telemetry runner build fresh output settings for their studies. They take at most one value (`results_directory`) from the scenario, so they are not copies of it.
  - The RRT* planner builds RRT-Connect shortcut settings from its own settings (`rrt.jl`). That builds one type from another, so it is not a copy; `connect_max_steps`, which RRT* settings lack, takes its default. It is left as it is.

Points a reviewer should check:

- **The same constructor runs as before.** Every rewritten copy called the type's keyword constructor with every field; for `SpacecraftModel`, the positional one. The RPO settings types are keyword structs, and `RPOPlannerComparisonConfig`'s keyword constructor takes all 14 fields, the planner list included. `_with_fields` calls the same constructor through `Base.typename(T).wrapper`, so type parameters are inferred again from the values, as `_with_configuration` did.
- **The only new refusal is an unknown field name.** It now throws an `ArgumentError` naming the type and its fields. Before, a misspelled override reached the keyword constructor and failed there with a different error.
- **Imports.** The included files that use the helper import it at their top, as `adaptive_routing.jl` and `constellation_ensemble.jl` already do for other names. Suite 01's include-order and name-ambiguity checks pass. `planner_objects.jl` imports it into `GuidanceHooks`, which `SimulationModel` loads after `SimConfig`.

## Residual Risk

- **The field table must be kept.** It guards only the types it lists. A copy of another configuration type written field by field would not be caught. The helper's docstring and the two contributor pages state the rule.
- **The smoke copy now carries `checkpoint_interval_s` and `checkpoint_directory`.** They are read only when checkpointing or resume is on, which the smoke copy turns off, so they have no effect.
- **The field-order rebuild of `SpacecraftModel` checks nothing.** A future copy that changes a checked field must check it itself; the docstring says so.
- **The mutation checks redefine one function in a running process.** They show the tests detect each change; they are not separate CI runs.
- **Examples that need native GRAM data were not run locally.** Their copy path is the one checked field by field above, and none of them sets a setting the smoke copy now carries.
