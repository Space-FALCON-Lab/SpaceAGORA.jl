# Review record: PR 508: keep the earlier rows file when a resume cannot continue it

## Scope

Review of the SpaceAGORA `resume-keeps-earlier-rows` branch against main (0f03bbfce). This is a follow-up on the resumed-run fix (#491), found by the review of the 0.7.0 results PRs; it can go into a 0.6.x patch.

A checkpointed run that records results keeps its saved rows beside its checkpoint (`simulation_checkpoint.results.bin`). A run killed hard (no exception, so no partial save) writes no results files, so that file holds the only copy of its rows. Two kinds of resume replaced it:

- **A resume that cannot include those rows** (other save fields, no record of them in the checkpoint, another run's file) warns that "the earlier ones are kept", then starts a new rows file at its first checkpoint, overwriting the earlier one.
- **A resumed run that saves no results** removes the file at its first checkpoint.

What changes:

- **Both rename the earlier file** to `simulation_checkpoint.results.before_resume_at_<t>s.bin` immediately before their first checkpoint replaces or removes it, numbered when that name is taken (`..._2.bin`). A recording resume warns with the actual kept filename at that point. A resume interrupted before its first checkpoint leaves the earlier checkpoint and rows together at their original paths.
- **Unchanged:** a resume that continues the rows file, or that solves nothing, renames nothing, and runs that are not resumes start their rows file as before.

Initial implementation: d15d2e552, on main 0f03bbfce. The 2026-10-23 follow-up starts from PR head `18ae9566b701212fcd1670e51ca229da06566f75` and corrects the premature rename found in independent review.

Authorship disclosure: the author of the PR drafted this record. It does not replace the independent review.

## Findings

The independent review found a P2 in the initial implementation: moving the file at startup stranded the old checkpoint's readable rows if the fallback resume was itself interrupted early. The follow-up defers the move to the first checkpoint write. Verification of that correction is recorded below; the original author's checks are historical evidence for the earlier head.

- **Changed on purpose.** In the two cases above, the earlier rows file is renamed instead of overwritten or removed, so the checkpoint folder gains a file.
- **Design choices for review.**
  - **Rename, not relocate the new file.** The resumed run's own rows file stays at the path its checkpoints record, so a later resume of it works as before. The earlier file moves to a name that says what it is.
  - **When.** Only a resume reaching its first new checkpoint renames, at the point where the old file would otherwise be overwritten or removed. A no-op resume and a first segment that fails leave it alone.
  - **Reading a kept file.** It has the rows file's format (Julia `Serialization`, see the docs). No public reader is added: the point is that the rows are not destroyed.

## Residual Risk

- **Kept files accumulate.** Each fallback resume adds one beside the checkpoint, and nothing removes them. They are about the size of the results CSV.
- **No reader.** The kept rows are in Julia's `Serialization` format, readable by the Julia version that wrote them through the internal row reader. Normal resume does not search the numbered kept files. Changing back to the original save fields does not recover them automatically; recovery needs the matching checkpoint identity and an explicitly reviewed recovery procedure.
- **The long layout's streamed rows** (0.7.0, C-5c) need the same care. That PR carries this rule to its streams.
