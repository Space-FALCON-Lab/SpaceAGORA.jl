# Review record: PR 504: merge a constellation ensemble's results on request

## Scope

Review of the SpaceAGORA `constellation-merged-results` branch against main (0f03bbfce). It is stacked on C-5a (`results-long-layout`, head ae3ce6998), whose commits it contains. This is C-4b of the constellations program's campaign-results step, built to the accepted design decisions D-C4-1 to D-C4-6, with D-C5-13 for the members table: the members are built with C-5a's long builder, so no `sc1_` prefix is stripped by name.

What changes:

- `run_constellation_ensemble(args; merge_results=true)` returns a `ConstellationEnsembleResult`.
  - `campaign` is the `MonteCarloResult` the call returns without the keyword.
  - `members` has one row per member and saved time, in the long layout's columns.
  - `constellation` has one row per member: identity, folder, status, rows and its last saved row.
  - `files` lists the merged files, written with `results=true`.
- Without the keyword nothing changes.
- Each member runs with `return_results=true` inside a scoped sink, and its final results save puts its long tables there, whichever layout it writes.
- Two refusals run before any member: the solver-metadata pair, and a run-wide save field with a per-spacecraft field's column prefix.

## Findings

No open P1 or P2 findings.

- **The in-house review (2026-10-23): Not clear.** It found one P1, one P2 and three P3s here. This round:
  - **P1-2, fixed.** In the long layout with `return_results=true`, a member's returned value holds the tables its final save put in the sink, and the merge changed them in place. Member 1's table became the members table, the others' `spacecraft` column was rewritten, and member 1's run table was left inconsistent. The merge now copies a member's tables first when its value holds them. The other cases build the tables for the merge alone, and are not copied.
  - **P2-1, fixed.** The merge kept every member's tables referenced through the campaign's samples until it returned, so it held the members' rows about twice. As each member is merged, its sample is replaced, in the campaign and its successful list, by one holding only the caller's value. The comment and the docstring now say what is held.
  - **P3-5, not done:** T14, the process route, still has no test (see below).
  - **P3-6, documented:** the docstring and the constellations page say to build `save_fields` from a member's configuration.
  - **P3-7, fixed:** an invalid `results_layout` is refused before any member runs.

- **Changed on purpose.** None for existing calls. `merge_results=true` is new.
- **Design choices for review.**
  - **Built with the long builder (D-C5-13).** The C-4 design stripped `sc1_` from each member's wide table by name, with a collision rule. Instead, a member's tables come from C-5a's builder through a scoped sink set around its run, so which table a field goes to follows its `per_satellite` flag. The sink is filled only at the final save of a run inside an ensemble merge. Every other run builds nothing more, and the member's own files and returned value do not change.
  - **Identity types** are the long layout's: `spacecraft` `Int32`, `spacecraft_id` `Int64`, `plane` and `slot` `Union{Missing, Int16}`. The C-4 draft said `Int`; C-5a's schema decided.
  - **Run-wide fields sit beside the per-spacecraft ones** in the members table, as the C-5 design says a member's run-wide fields belong to it. The C-4 collision rule (keep `sc1_` on a clash) is gone with the stripping. A run-wide save field with a per-spacecraft field's column prefix is refused before any member runs. A name that meets one only once flattened is refused when the tables merge, before any merged file is written.
  - **`member_tag`** is the folder the member used: the unpadded name when it resumed from a checkpoint written by SpaceAGORA 0.4 or earlier.
  - **Members are merged in position order** by walking the runner's samples, which the runners keep sorted by index. Each member's tables are appended as they are reached.
- **Pre-existing, documented:** save fields passed to an ensemble are built by the caller, and the default ones are sized for the configuration they were built from. A `save_fields` list built from the whole constellation fails in every one-spacecraft member. The docstring and the constellations page now say so, and the tests build the list from a member's configuration.
- **Not in this PR.**
  - The C-3d refusal of bound configuration-level GNC (T10's last case) comes with C-3d, which is not built yet. C-4b now lands before C-3d; both edit `constellation_ensemble.jl`, in different hunks.
  - T14 (the process route) is not added (review P3-5). The member closure lives in SpaceAGORA, so a process worker can run it, and the review's probe found the merge on that route equal to the serial one. No unit test starts a process pool for it; the threaded routes and the serial one are tested.

## Residual Risk

- **Memory.** The members table holds every saved row of every member. While merging, each member's rows are held once: in its outcome until appended, then in the members table. Each member also builds its long tables once at its final save, and the values it returns with `return_results=true` are kept. The docstring points large campaigns at `SPACEAGORA_RESULTS_THIN_STRIDE` and `SPACEAGORA_RESULTS_FINAL_ONLY`. A merge from disk, one member at a time, is C-5d.
- **The process route** is not exercised by a test (see Findings).
- **C-3d** adds a refusal to the same file; whichever lands second merges main.
- **The public API page** grows by one docstring, within its size limit.
