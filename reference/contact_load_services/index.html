Experimental contact-load services

SpaceAGORA.ContactLoadServices is a separate, exact-version v"0.2.0" contract for contact forces evaluated at the integrator's current trial state. It does not propagate any state. The optional MuJoCo companion implements the native contact solve; the core package has no native contact dependency.

Install an immutable provider configuration with ContactLoadServices.with_contact_model(args, model). Each run_simulation allocates its own provider runtime after preflight and closes it in finally, including when setup, a provider query or integration throws. Providers must clean up any partial allocation if contact_prepare fails; contact_close! must be idempotent. Configuration copies preserve contact_models without copying or sharing live native handles.

Supported first slice

One rigid spacecraft link with generic compliant attachments, or the existing compliant robot-arm route supplied by one RobotArmReactionEffector. All links participate with their own mass and full inertia. The arm requires a nonempty, fixed rest plan and no joint actuators. The joint coefficients must be finite, nonnegative and isotropic. Use serial :tsit5, attitude integration and a fixed time-bounded mission. Both maximum step caps must be positive and at most 2^-10 seconds; begin with 2^-12 and refine. Contact pins serial execution and disables execution calibration; concurrent queries on one runtime fail before touching shared scratch. Distinct runs own distinct scratch.

This experimental slice refuses other effectors, GNC, mounted devices, articulated backbones, mixed attachment/arm routes, variable rest schedules, actuators, external propagation, interlinks, checkpoint/resume, custom callbacks and reused solver caches. It is a bounded gravity-free experiment, not a qualified general collision interface. Provider-specific geometry and numerical settings are checked before native allocation.

Evaluation order and frames

  1. Assemble all smooth bus and attachment loads, including the compliant mount reaction, without yet assigning attachment acceleration.
  2. Pass an immutable tuple of ContactState values and the exact trial time to contact_evaluate!. Slot 1 is the bus; remaining slots follow attachment or arm state-column order.
  3. Validate one contact-only ContactWrench per body, including finite values, equal/opposite force and moment balance about a common origin.
  4. Add each wrench once to its body's COM load. Compute all accelerations, then subtract the final bus acceleration once from the relative attachment acceleration.

Arm positions and velocities are already inertial in the existing arm state; their derivatives do not subtract bus acceleration. Arm smooth-load assembly is separate from derivative assignment so contact is included before computing each link's acceleration. With a zero-contact provider, the existing arm trajectory is bit-identical. Generic attachments retain their relative translation layout.

This force-only interface does not by itself implement exact sticking. The expanded arm/geometry and exact-sticking qualification for Issue #4 is in progress; passing core load-injection tests is not physical qualification.

Positions and velocities are in inertial-parallel axes relative to an origin following the initial bus velocity. This removes the large initial orbital position and a common Galilean boost without subtracting nearly equal absolute positions to recover attachment separation. Quaternions are scalar-last active body-to-world rotations. Angular velocity is body-frame; smooth forces, smooth COM torques and returned contact COM torques are world-frame, in SI units. Smooth torques exclude gyroscopic pseudo-torques. ContactBody supplies finite positive physical mass and symmetric positive-definite body-frame COM inertia.

A provider must reset all trial scratch for every query, including repeated states, reversed times and rejected trial steps. It must not call a native time step, cache an old force, mutate observations or include smooth loads in its returned contact wrench. Hybrid providers may read their committed mode, but cannot change it during trial evaluations. It must reject native warnings, capacity exhaustion, nonfinite results and unconverged solves. Core's balance check is not a convergence test.

Provider inventory

Check require_version(v"0.2.0") before method definitions/native loading and again during package initialization. The common extension hooks are contact_preflight, contact_prepare, contact_evaluate! and contact_close!. The consumed types/helpers are AbstractContactModel, AbstractContactRuntime, ContactBody, ContactState, ContactWrench and with_contact_model. ContactRunState and engine internals are not provider APIs.

Hybrid models additionally subtype AbstractHybridContactModel and return an AbstractHybridContactRuntime. Their contact_event_value is positive inside the current mode; a downward zero crossing asks core to locate a transition. Core calls contact_accept! only at initialization, localized events and accepted steps. That hook recomputes from the supplied complete state, commits the mode, and returns one ContactVelocityCorrection per body. Core rejects nonfinite corrections, net linear/angular impulse, or an increase in kinetic energy. It records projection work separately from continuous contact work. Event trial forces may extend a mode's equations outside its admissible region for root localization; physical qualification must check accepted states and both sides of transitions. Providers cannot advance time or modify the integrator directly.

Core tests cover zero-contact trajectory identity, trial-state purity, one-time wrench injection, moment balance, unsupported configurations, serial ownership and cleanup. Native contact qualification and the remaining Issue #4 matrix belong to the companion; passing these core tests alone does not qualify a contact law or deployment scenario.

API reference

SpaceAGORA.ContactLoadServices.AbstractContactModel — Type

Immutable provider configuration; it must contain no native resource or run state.

source
SpaceAGORA.ContactLoadServices.AbstractContactRuntime — Type

One run's provider state. Reset trial scratch on every evaluate call; never integrate.

source
SpaceAGORA.ContactLoadServices.AbstractHybridContactModel — Type

Contact model whose discrete contact modes change only at accepted core transitions.

source
SpaceAGORA.ContactLoadServices.AbstractHybridContactRuntime — Type

Per-run hybrid contact state; trial evaluations must not commit mode changes.

source
SpaceAGORA.ContactLoadServices.ContactVelocityCorrection — Type

Numerical velocity projection at an accepted transition, in world linear and body angular coordinates. This is recorded separately from contact work.

source
SpaceAGORA.ContactLoadServices.ContactBody — Type

Physical body at its COM. Slot 1 is the rigid bus; remaining slots are the attachment or compliant-arm links in state-column order.

source
SpaceAGORA.ContactLoadServices.ContactState — Type

Read-only trial observation: SI, COM position/velocity in inertial-parallel axes, scalar-last active body-to-world quaternion, body angular velocity, and all smooth physical COM force/torque in world axes. A fixed or constant-velocity origin is used for positions/velocities. Smooth torques exclude gyroscopic pseudo-torques.

source
SpaceAGORA.ContactLoadServices.ContactWrench — Type

Contact-only force and torque about this body's COM, both in world axes (N, N m).

source
SpaceAGORA.ContactLoadServices.contact_preflight — Function

Validate provider geometry/settings before allocating native resources.

source
SpaceAGORA.ContactLoadServices.contact_prepare — Function

Allocate one runtime; clean up partial allocations if preparation throws.

source
SpaceAGORA.ContactLoadServices.contact_evaluate! — Function

Return one ContactWrench per body for this complete trial state/time. Reject nonfinite results, warnings, capacity exhaustion and unconverged solves; never reuse a previous force or advance native time. Inputs cannot be mutated.

source
SpaceAGORA.ContactLoadServices.contact_close! — Function

Release this run's native resources. Must be safe after a failed query and idempotent.

source
SpaceAGORA.ContactLoadServices.contact_event_value — Function

Positive inside the current contact mode; a downward zero crossing requests an accepted transition. Must be a pure query at the supplied complete state.

source
SpaceAGORA.ContactLoadServices.contact_accept! — Function

Commit contact-mode changes at an accepted core state and return one numerical velocity correction per body. Called at initialization, localized events and accepted steps; never during rejected stages. Corrections must conserve total linear/angular momentum and cannot add kinetic energy. Trials must not mutate the committed mode, and this hook must recompute from the supplied state.

source
SpaceAGORA.ContactLoadServices.with_contact_model — Function

Return a shallow configuration copy with the one experimental contact model installed.
