# Route-exploration harness and forced-plan hook review

## Scope

Independent review of PR 198 (`paper/route-exploration`, head `08df4b936`, with
`eeebfc624` beneath it), against `origin/main` at `9be384a20`. The branch forks
from `8ea61f28b` and is 196 commits behind main. Reviewed: the one source change,
the env-gated `SPACEAGORA_PREDICTIVE_FORCE_PLAN` override in the R7 campaign
planner; the P6s, P6ps, X1, X3, X4, X5a and X5b phases of the paper harness;
and the `force_*` and `rhs_*` arms of the parallelization-performance mode table.
Also checked: whether the branch merges cleanly into current main, and whether
main has since changed anything the override depends on.

The measured results themselves are out of scope. They are recorded in the paper
repository (`route_exploration_record_2026-10-02.md`). This review says only
whether the code that produced them is safe to land on main.

## Changed Files

- `src/simulation/campaigns/adaptive_routing.jl`: new `_predictive_forced_plan`;
  `_run_campaign_predictive` replaces the planned or leashed plan with the forced
  one when the variable is set, and traces the forced plan and every enumerated

- `benchmarks/studies/paper_parallelization_benchmarks/cli.jl`: phases P6s and P6ps

- `benchmarks/studies/parallelization_performance/modes.jl`: an `extra_env` field
  on `PPCModeSpec`, applied last in `ppc_mode_env_pairs`. Ten `force_<plan key>`
  arms and four `rhs_<mode>` arms, all derived from `predictive`.

No test or documentation file is changed.

After the review, `472180d2b` merges `origin/main` (no rebase; `eeebfc624` and
`08df4b936` are unchanged), and the fixes below add commits on top. Against
`origin/main` the only changed `src/**/*.jl` file is still
`src/simulation/campaigns/adaptive_routing.jl`; the fixes also touch
`test/gates/ci_ppb_workload_coverage_gate.jl`, `test/unit/runtests.jl`,
`test/unit/parallel/predictive_forced_plan_tests.jl` (new),
`docs/architecture/predictive_routing_r7.md` and the paper harness `cli.jl`.

## Findings

F1, high, blocks merge: the PR's own CI fails. `p1-findings-gate` and
`nightly-stress` both fail in `test/gates/ci_ppb_workload_coverage_gate.jl:69`:
292 checks pass and 1 fails. The precompile workload selects every phase whose
id matches `^P[0-9]`, so P6s and P6ps are treated as paper workload phases. Both
name native-GRAM cases (`gram_lookahead`, `gram_process`), which the workload
excludes. The gate allows exclusions only from phases `P6` and `P6p`. Two fixes
would work. One extends the gate's allowed set and header comment to P6s and P6ps,
which are paper rows according to the PR description. The other renames them out
of the `P` namespace, but the workload would then stop precompiling their
non-GRAM points. Each fix needs a one-line edit plus a comment update.

F2, medium: a forced run can leak into later unforced runs through the
persistent campaign corrections. When `pool_workers >= 2` and
`SPACEAGORA_CAMPAIGN_CORRECTIONS` is unset (the default, `:on`), the forced
campaign still calls `_predictive_fold_and_save!`. That records
`last_plan[shape_key]` as the forced key and folds the forced plan's observed
heap scale, round tail and worker sample time into the machine's corrections
file. The next unforced `predictive` campaign of the same shape is leashed from
the forced plan by `predictive_leash`, and is priced with terms the forced plan
fitted. This is the only way the hook reaches normal runs. Neither the hook nor
the `force_*` arms prevent it. X3 and X4 run `predictive` and the `force_*` arms
on the same shape in one process, so the harness relies on the operator exporting
`SPACEAGORA_CAMPAIGN_CORRECTIONS=off`. The paper record states that this was done
for the measured runs, so the recorded numbers are not affected. Suggested fix:
skip the fold and save when `forced !== nothing`. Alternatively, add
`"SPACEAGORA_CAMPAIGN_CORRECTIONS" => "off"` to the `force_*` arms' `extra_env`.

F3, low: a plan that is not enumerated is dispatched as given, with no
feasibility check. Any key that matches the regex is accepted, for example
`process@w0+l0`, `process@w999+l0`, `none@w5+l3`, or a process plan on a shape
whose candidacy allows no pool. `_predictive_dispatch` clamps the width to the
sample count, but not to the pool candidacy or the thread count. The X phases
hard-code `w32`, `b32` and `l15` keys. These match enumerated plans only when
`PPB_PAPER_BUDGET` is 32. That budget is sized from the host, so on any other
host these arms run off-list and oversubscribed. A measurement hook may
reasonably be this permissive, but the X phases should say they are TRX50-only,
or derive their keys from `PPB_PAPER_BUDGET`.

F4, low: the enumerated-plan lookup compares the raw string, not the canonical
key. A key that parses but is not canonical, such as `threads@w32+l0+b1`, is not
matched to the enumerated `threads@w32+l0`. It is repriced off-list with
`static_equivalent = false`, while the trace line compares canonical keys and
prints `enumerated=true`. Comparing parsed tuples in both places would make them
agree. None of the shipped `force_*` keys is affected.

F5, low, appears only after merge: main's `3609b0bcd` splits the inner-speedup
curve into `outer=true` and `outer=false` rows and passes `inner_curve_unsplit`
to `predictive_plan`. It also states that a plan is never priced from
measurements taken in the other runtime. The branch merges cleanly (trial
`git merge-tree` produces tree `cb8cd4007`). In the merged tree, though, the hook
still prices every plan it reprices off-list with `inner_curve`, which is now the
outer-split curve. That includes `none@w1+l0+bT`, which main would price only
from the unsplit rows. This affects the traced predicted makespan, not the plan
that runs, because a `none` plan is dispatched unguarded. The merged planner also
enumerates a different plan set from the one at `08df4b936`. So the paper's
statement that all 18 enumerable plans ran slower holds for the measured commit,
not for main after the merge. Suggested fix: pass `inner_curve_unsplit` for route
`:none` in the hook.

F6, note: a forced plan with local slots still runs under the guard, which may
close slots during the run. The source comment says the hook "runs that plan",
but strictly it runs that plan as the initial plan. The paper record documents
this and reports guard verdicts that closed nothing. The P6s comment cites
"P1's modes ... as P7 takes them", but P6s omits `policy_v2`, which P7 runs. The
new variable is not listed in `docs/architecture/predictive_routing_r7.md`
alongside the other planner variables.

Verified as correct:

- Unset, empty and whitespace-only values return `nothing` before any parsing.
  The only extra cost is one `ENV` lookup per campaign.
- An invalid key throws an `ArgumentError` that names the variable and the value,
  after planning and before any dispatch.
- `planning`, `predictive_plan` and `predictive_leash` are called exactly as
  before. The override only replaces `plan` after both have run.
- With nothing forced, the rewritten leash trace condition is equivalent to the
  old one.
- `extra_env` is empty for every pre-existing mode, so their environment pairs
  are unchanged. Arms run under `withenv`, which restores the variable after each
  arm.
- `ci_ppc_mode_profile_parity_gate.jl` is unaffected: `"predictive"` is still
  found by its anchor, and its own fields precede the generated arms.
- The `rhs_*` values are all accepted by `SPACEAGORA_RHS_EXECUTION_MODE`'s parser.
  Setting `calibrate="off"` stops the pre-solve sweep from overriding them.

## P1 Assessment

Unresolved P1: No correctness defect at P1 level in the source change. The
override is inert when unset, fails loudly on a malformed value, and leaves the
planner's decision logic untouched. Merging is nonetheless blocked by F1, a
required contract gate that fails on this head. F2 should be fixed before merge
as well, because it is the one way a forced run changes the behaviour of later
unforced runs. F3 to F6 can follow.

## Tests Added/Updated

None. The PR adds no test for `_predictive_forced_plan`, and the existing
planner suites do not exercise it. Existing CI passes except for the F1 gate:
all ten plain test shards, fifteen coverage shards, the threaded smoke and the
example suites.

Reviewer probe, run on the branch head and not committed: 133 of 133
assertions pass. The probe built a 256-sample, 32-thread, 32-worker plan space
with a linear inner curve, which gives 64 enumerated plans. With the variable
unset, empty or whitespace-only, the hook returns `nothing`. `bogus` and
`Process@w32+l4` throw `ArgumentError`. Every enumerated key, whether given bare
or padded with whitespace, returns the identical plan object. Repricing each of
the 64 keys through the off-list path reproduces the planner's makespan exactly.
The same run confirmed F3 and F4: `process@w0+l0` (infinite makespan, 0
consumers), `process@w999+l0` and `none@w5+l3` are all accepted, and
`threads@w32+l0+b1` is repriced off-list rather than matched.

Suggested minimum regression test (in `test/unit/parallel/predictive_planner_tests.jl`):
use `withenv`, with the variable unset and with it set to an enumerated key, a
malformed key, and an off-list key. Assert respectively `nothing`, identity with
the enumerated plan, `ArgumentError`, and a price equal to `_predictive_plan`'s.

## Residual Risk

The hook's behaviour is now part of `src/` with no unit coverage. A later change
to `predictive_plan_key`, `_predictive_parse_plan_key` or the candidate pricing
could break it without any test noticing. That would silently change what the
`force_*` arms measure.

The branch is deliberately not rebased, so that it keeps the measured commit
hashes. A merge commit therefore pairs `08df4b936`'s hook with main's two-curve
planner (F5). Any rerun of the X phases after the merge measures a different
plan space from the one the paper cites. Such reruns should be recorded against
the post-merge commit, not combined with the 2026-10-02 numbers.

P6s and P6ps add 4096-spacecraft points under `outer_threads` and
`outer_inner_static` to the paper precompile workload, which increases the
workload's build time. They also run 11 repeats of the 4096-spacecraft
native-GRAM traces, which is a long run on the reference machine. Neither is a
correctness risk.

### Findings addressed (author verification)

The items below have fresh author verification, not a separate independent
verdict.

- F1, addressed in `db9e88f0a`: the workload coverage gate allows native-GRAM
  exclusions from `P6`, `P6p`, `P6s` and `P6ps`, and its header comment names
  them. `4ea2e702d` exempts X5a and X5b from the P5f gate's check that no
  other phase declares full-budget modes. That failure was masked because the
  gate stopped at the F1 testset.
- F2, addressed in `51d27abd9`: a forced campaign skips
  `_predictive_fold_and_save!` on both the unguarded and the guarded path, with
  a comment giving the reason. A unit test runs a forced campaign on a shape
  with an affordable pool and corrections `on`, and checks that no file is
  written and the in-memory corrections fold nothing. Reverting the guard makes
  three of its assertions fail.
- F3, addressed in `51d27abd9`: a key that matches no enumerated plan is checked
  against the host (workers >= 1, at most the affordable pool on the process
  route, local slots within the planner's bound, `b <= T`, one worker on `none`,
  `W * b <= T` on `threads`). A violation throws an `ArgumentError` that names
  the variable and the bound. Every `force_*` key in X3, X4, X5a and X5b passes
  on a 32-thread, 32-worker budget, including `w32`, `b32` and `l15`.
- F4, addressed in `51d27abd9`: the enumerated lookup compares parsed keys, so
  `threads@w8+l0+b1` returns the enumerated `threads@w8+l0`.
- F5, addressed in `472180d2b` and `51d27abd9`: after the merge, an off-list
  `none` plan is priced from `inner_curve_unsplit` and the other routes from the
  split curve. Reruns of the X phases on the merged tree must not be combined
  with the 2026-10-02 numbers.
- F6, addressed in `db9e88f0a` and `51d27abd9`: the P6s comment says it omits
  `policy_v2`. The hook comment says that the forced plan is the initial plan
  and that the guard may close slots. `SPACEAGORA_PREDICTIVE_FORCE_PLAN` is
  documented in `docs/architecture/predictive_routing_r7.md` as a measurement
  tool whose campaigns skip the corrections.
- Tests: `test/unit/parallel/predictive_forced_plan_tests.jl` is registered in
  `test/unit/runtests.jl`. It passes 27 of 27 locally, and
  `predictive_planner_tests.jl`, `predictive_campaign_bookkeeping_tests.jl` and
  `inner_speedup_curve_outer_tests.jl` still pass on the merged tree.
  `test/contracts/pr_runtests.jl`, which includes the workload coverage and P1
  findings gates, and the AI review artifact gate pass locally.

### Additional findings addressed (2026-10-03 author verification)

This follow-up addresses five findings from the independent review of
`d919903e808590c99e77c5b5b8434769a4e0bcfc`. It appends fixes without changing
the historical measurement commits. These are implementation checks, not a new
independent scientific acceptance or a rerun of the paper campaigns.

- Forced plans now validate the workload's allowed routes before enumerated
  lookup or off-list pricing. Native-GRAM workloads cannot force a threads
  route. Process plans require at least two workers, matching dispatch's
  process-pool boundary; the formerly accepted one-worker process labels fail
  before dispatch.
- An explicit serial inner-thread budget applies around the serial dispatch,
  narrows any inherited ceiling, and restores the caller's environment. A
  serial plan without a declared ceiling retains the previous behavior.
- Serial baseline assignment preserves measured row counts. P6ps uses the
  matching thread/worker baseline, ordinary thread ladders retain their sole
  baseline, and X5a/X5b splits share the explicitly declared full-budget serial
  measurement. Ambiguous baselines remain missing. Optional experiment-level
  `budget_condition` partitions baseline candidates; per-arm cap metadata does
  not prevent a parallel row from matching its serial control.
- X1/X3/X4/X5a/X5b require explicit selection and retain their historical
  32-thread keys. Selection rejects incompatible budgets, preview mode, and
  insufficient thread/worker settings before any phase runs. Default and
  preview selections retain the non-exploration catalog.
- Bounded Julia 1.12.3 validation at four threads passed 1,333 assertions across
  the planner, campaign, corrections/bookkeeping, both inner-curve suites,
  forced-plan tests (39), baseline tests (22), selection tests (28), and paper
  workload coverage gate. The runtime checks use trivial closures; the harness
  checks use synthetic timing rows and catalog definitions. No native-GRAM
  simulation, full numerical campaign, or reference-host performance rerun was
  performed. New benchmark measurements must retain their new source identity.
- The final selector test passes 28 assertions without world-age warnings, and
  `test/contracts/pr_runtests.jl` passes, including all source gates and paper
  workload coverage. The sparse checkout restored only the 5,226-byte tracked
  assets manifest needed by the registry gate; reference data stayed excluded.
