What it removes:

- **The old index field names and keywords** (design 3.4, 6.4; #390 and #406):
  `MagneticMomentumManagerModel.sat_idx`, `RobotArmControlEffector.spacecraft_idx`,
  `RobotArmReactionEffector.spacecraft_idx`, and `chaser_idx`/`target_idx` of
  `RPOMPCControlModel` and `PlannerGuidance`. Gone: the keyword forwarding in the
  written-out constructors and the `getproperty`/`setproperty!` forwarding with
  its per-type helpers. An old keyword is now a `MethodError` (an unsupported
  keyword); an old property is a `FieldError`. The shared helpers in
  `HookDeprecation` (`_renamed_field_warning`, `_renamed_keyword`, `_NOT_PASSED`)
  stay for the deprecations below; they now say removal in 1.0 and take a type or
  a function as the owner of the old name.
  - `PlannerGuidance` and `RobotArmReactionEffector` go back to `Base.@kwdef`, as
    before #390/#406: every keyword and default is the one the written-out
    constructor had, and both index keywords of `PlannerGuidance` stay required.
  - The momentum manager, the arm controller and the RPO MPC controller keep their
    written-out keyword constructors, because `run_start`/`run_written` (#408) are
    fields but not keywords; each keeps its defaults (`spacecraft_index=1`,
    `chaser_index=1`, `target_index=2`).
- **`RPOGuidanceModel`** (design 6.3, G-11 = b; PRs 19b #365 and 19c #377 have
  merged, so G-14 no longer holds it back): the struct
  (`guidance/rpo/rpo_guidance_models.jl`), its hooks
  (`guidance/rpo/rpo_guidance_hooks.jl`: `build_rpo_plan`,
  `build_rpo_plan_from_start`, `_rpo_state_pos_vel`, `_rpo_replanning_config`,
  `_rpo_record_replanning_event!`, `_rpo_begin_replanning_hold!`,
  `_rpo_advance_replanning_hold!`, `maybe_update_rpo_replanning!`, its
  `update_guidance!` method), its scope, its run-start reset and write record
  (`_rpo_guidance_entries`, `_note_rpo_guidance_writes!`, its
  `initialize_guidance!`, #408), its plan-buffer `gnc_links` method, and its HYPR
  preflight (`preflight_guidance` in `rpo_planner_adapter.jl`, with the deprecation
  warning). The shared replanning kernels (`rpo_replanning_decision`,
  `rpo_retime_existing_plan`, `rpo_plan_from_path`, the replanning spheres) stay:
  `RPOReplanningSpheres`, the HYPR adapter and
  `examples/Earth_RPO_CubeSat_MPC_Replanning.jl` use them.
  - The replanning study `examples/Earth_RPO_HyPR_FinalISpaRo_Replanning.jl` ran on
    the model (D3 = a kept it as the recorded reproduction until PR 21) and is
    deleted. `docs/src/user/hypr_paper.md` records that the published dynamic
    reconstruction was produced with `RPOGuidanceModel`, reproducible from
    SpaceAGORA v0.4.0 (the last release with the model and the study) with that
    release's `Manifest.toml` and the HYPR revision pinned in its
    `packages/SpaceAGORAHYPR/HYPRSource.toml`, and keeps the commit the study was
    delivered at (`b165c0528`). `hypr_planning.md` and `rpo_planner_pilot.md` say
    the same in the past tense.
- **Selecting an RPO comparison planner by name** (design 6.4, PR 15 #376):
  `RPOPlannerComparisonConfig.planners` is a `Vector{AbstractRPOComparisonPlanner}`;
  `rpo_plan_comparison_path` takes a planner object; the shim
  `_rpo_comparison_planner(selection, cfg)`, `_rpo_comparison_selection_deprecation`
  and `_RPO_COMPARISON_PLANNER_TYPE_NAMES` are gone. A Symbol or string is a
  `MethodError` before HYPR is required. The identifier and label helpers
  (`normalize_rpo_comparison_planner_type`, `rpo_comparison_planner_label`) keep
  accepting names: the report rows and plots key on them.
  - `examples/Earth_RPO_HyPR_FinalISpaRo_Reconstruction.jl` still passed names from
    `HYPR_PLANNERS` to `rpo_plan_comparison_path`; it now passes
    `paper_planner_object(name, cfg)` (new in `examples/support/hypr_paper_comparison.jl`),
    which builds each object with the public constructors from the comparison
    configuration's settings fields, as `RPOPlannerComparisonConfig` builds its
    defaults. PR 15's bit-identity test showed a name and this object give
    bit-identical plans, so the example's results do not change.
- **`control_requires_periodic_callback`** (internal; design 6.4): removed;
  `_periodic_control_rates` in `external_propagation.jl` reads
  `tick_schedule(effector) === :periodic`, which is what the wrapper returned.
- **The engine's reads of the old index field names** (`8597c9507`): the
  duck-typed checks read only the new names. `_CROSS_SATELLITE_INDEX_FIELDS`
  (Jacobian coupling) is `(:chaser_index, :target_index)`, `_EXTERNAL_INDEX_FIELDS`
  (external propagation) `(:chaser_index, :spacecraft_index)`, and
  `_effector_spacecraft_index` (robot-arm plan coupling, articulated-panel check)
  and the viewer's `robot_arm_plan_for` read `spacecraft_index` only. A
  contributor model whose only index fields are `chaser_idx`/`target_idx` is no
  longer seen as coupling two spacecraft in the stiff solvers' Jacobian pattern;
  one with only `chaser_idx`, `spacecraft_idx` or `sat_idx` counts as acting on
  every spacecraft in the external-propagation check (a run with an external
  propagator refuses it); one with only `spacecraft_idx` is no longer bound to a
  spacecraft by the robot-arm and panel checks or the viewer. The migration page
  names these fields and behaviours.

What it deprecates, until 1.0 (`aa45f5b3f`): three older index names that were
never deprecated, renamed as #390 did, with the old name forwarding as a keyword
or property and one warning per owner and name (`:depwarn` group, an
`ErrorException` under `--depwarn=error`). An old keyword warns where it is
passed, before the run; an old property warns where it is read, which can be
inside a user callback during the run (and, under `--depwarn=error`, stop the run
there):

- `SchedulingPolicyModel`'s `target_idx` and `target_idxs` become
  `target_index` and `target_indices` (fields and keywords; the fields stay
  `const`). The keyword constructor resolves either spelling, refuses both, keeps
  the defaults (`1` and `nothing`; an explicit `nothing` still means "both
  endpoints"), the validation and the type checks (a `TypeError` for a wrong
  type, as the typed keywords gave). The interlink checkpoint snapshot keeps its
  stored keys `target_idx`/`target_idxs`, read from the new fields, so a
  checkpoint written before 0.5.0 still matches and resumes.
- `StateAnchor`'s field `sat_idx` becomes `spacecraft_index` (immutable; the old
  property forwards on reads). The positional constructor is unchanged.
- The `sat_idx` keyword of `get_periapsis_pulse_callback` becomes
  `spacecraft_index` (default 1). Its docstring was attached to the constant
  above it; it now documents the function.

Decisions (Giusy, 2026-10-19, through the coordinator), and how they are built:

1. **Drop the engine's reads of the old field names**, with the two
   contributor-model tests, and name the fields and behaviours in the PR text and
   the migration page: `8597c9507` (above).
2. **Julia's own errors plus the migration page**, no refusal stubs: an old
   keyword is a `MethodError`, an old property a `FieldError`, a planner name a
   `MethodError`; the migration page names each replacement.
3. **Deprecate the never-deprecated older names in 0.5.0 and remove them in
   1.0**, with forwarding, a warning, migration-page rows and tests
   including `--depwarn=error`: `aa45f5b3f`. The answer named
   `SchedulingPolicyModel.target_idx`; its sibling `target_idxs` is renamed too, to
   `target_indices` (design 3.4: several vehicles take `*_indices`). Engine locals,
   hook arguments and internal helpers keep `sat_idx` (design 3.4), and so do
   the interlink checkpoint's stored keys (above).
4. **Keep "reproducible from v0.4.0" with a visible TODO** until the rerun is
   done: `80348677b` adds a "TODO: rerun from v0.4.0 pending" warning box to
   `hypr_paper.md`. **TODO: the rerun from v0.4.0 is pending**; it follows the
   v0.4.0 tag, in the private studies setting, and is not part of this PR.
