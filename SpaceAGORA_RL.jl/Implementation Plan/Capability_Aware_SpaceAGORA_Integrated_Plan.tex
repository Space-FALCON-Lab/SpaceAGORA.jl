\begin{abstract}
This document converts the research outline \emph{Capability-Aware Learning
Architecture for Distributed Small Spacecraft Autonomy} into a package and
integration plan for \code{SpaceAGORA.jl} and \code{SpaceAGORA_RL.jl}.  The
proposal adds an Earth-observation task family without changing the ownership
of flight dynamics or actuator authority.  SpaceAGORA supplies physical truth,
public telemetry snapshots, typed activity commands, deterministic feasibility
checks, and bounded execution.  SpaceAGORA\_RL supplies the capability-aware
MDP, degradation experiments, policies, fleet allocation, explanations, and
evaluation.  Development proceeds from a small event surrogate and conventional
baselines to a live SpaceAGORA backend, generalization, distributed allocation,
and flatsat preparation.
\end{abstract}

\section{Objective and architectural decision}

The research objective is to close the loop
\[
\text{physical degradation}
\rightarrow \text{telemetry and estimation}
\rightarrow \text{operational capability}
\rightarrow \text{mission decisions}
\rightarrow \text{fleet reallocation}.
\]

The implementation should be a new Earth-observation (EO) task family in
\code{SpaceAGORA_RL.jl}.  It should reuse the package's existing MDP, backend,
action-mask, transition, learner, runtime, checkpoint, and parallel-rollout
interfaces.  It should not be embedded into the aerobraking MDP and should not
put learned decisions inside dynamics, guidance, or control code.

\begin{center}
\fcolorbox{agorablue}{lightblue}{%
\begin{minipage}{0.92\linewidth}
\centering
SpaceAGORA physical state and telemetry\\
$\downarrow$\\
Capability estimate with uncertainty\\
$\downarrow$\\
Capability-conditioned EO MDP and fleet allocator in SpaceAGORA\_RL\\
$\downarrow$\\
Typed mission activity command\\
$\downarrow$\\
Independent SpaceAGORA feasibility and safety gate\\
$\downarrow$\\
Conventional GNC, control, and physical execution
\end{minipage}}
\end{center}

The first implementation should be smaller than the complete research vision:
a deterministic event-driven EO surrogate, an oracle capability estimate,
three non-learning baselines, and one configuration-conditioned policy.  A
meta-learning implementation is deferred until held-out experiments establish
that static capability conditioning is insufficient.

\section{Assumptions and constraints}

\begin{enumerate}
  \item The requested destination is the existing nested package
        \code{SpaceAGORA.jl/SpaceAGORA_RL.jl}.
  \item EO is added alongside the implemented aerobraking and RPO task
        families; existing task behavior is not refactored as part of this work.
  \item SpaceAGORA remains the owner of physical propagation, vehicle state,
        GNC, actuator authority, and simulation execution.
  \item SpaceAGORA\_RL owns policy learning, degradation campaigns, fleet
        allocation experiments, and research metrics.
  \item Physical battery, payload, or data-system models that become useful
        outside RL belong in SpaceAGORA.  Inexpensive experimental surrogates
        may begin inside the EO task package.
  \item New EO integration calls only documented, root-level SpaceAGORA APIs.
        It does not add dependencies on private
        \code{SpaceAGORA.SimulationModel} internals.
  \item The learned executive proposes bounded mission activities.  A
        deterministic layer independent of the policy decides whether a command
        is accepted, rejected, or bounded.
  \item A coordinated constellation is one decision environment.
        \code{run_constellation_ensemble} explicitly handles uncoupled members,
        so it must not be used to split a coupled fleet-policy episode into
        independent spacecraft.  Parallel rollout workers each own a complete,
        isolated fleet episode.
\end{enumerate}

\section{Data and function contracts}

\subsection{Capability snapshot}

The planner-facing capability state is
\[
\hat{\mathbf{c}}_i(t)=
[\alpha_E,\alpha_G,\alpha_A,\alpha_P,\alpha_C,\alpha_S,\alpha_D],
\]
representing usable energy, generation, agility, payload, compute, storage,
and downlink capability.  A snapshot also contains spacecraft identifier,
timestamp, uncertainty, estimator/source identifier, freshness, and validity
flags.  Values must not silently imply certainty.

Physical truth, raw telemetry, estimator belief, capability estimate, and the
policy observation remain distinct records.  This separation prevents an
experimental policy from accidentally receiving latent degradation truth.

\subsection{EO tasks and activity commands}

An \code{EarthObservationTask} contains a task identifier, target geometry,
open/close time, mission value, allowed collection modes, required product
quality, raw data volume, processing demand, and optional latency or revisit
terms.

A \code{MissionActivityCommand} contains spacecraft/task identifiers, an
activity kind, bounded start and duration, requested collection mode, resource
reservation, and a policy/explanation correlation identifier.  Initial
activity kinds are
\[
\{\text{collect},\text{process},\text{downlink},\text{recharge},
\text{desaturate},\text{defer},\text{reassign}\}.
\]

A \code{CommandDisposition} records accepted or rejected status, a stable
reason code, the limiting constraint and margin, and any deterministic command
bounding.  Rejected commands must not mutate physical state.

\subsection{Public SpaceAGORA functions}

The proposed root-level surface is conceptually:

\begin{verbatim}
mission_snapshot(simulation, spacecraft_id, epoch_s)
evaluate_activity(snapshot, task, command)
execute_activity!(simulation, accepted_command)
\end{verbatim}

The engine may use internal types behind this API.  Learned, rule-based,
optimization, and operator commands all pass through the same deterministic
evaluation function.

\subsection{Learner-facing state and action catalog}

An \code{EODecisionState} contains mission time, resource state, pending
candidate tasks, capability estimate and belief, compact fleet summaries, and
communication freshness.  The observation is a fixed-length normalized vector
composed of resource margins, capability values and uncertainty, timing, the
top $K$ candidate tasks, and fleet/message summaries.

Neural-network outputs should not embed arbitrary task identifiers.  At each
decision the environment ranks the top $K$ candidates, creates a stable action
catalog from candidate slots and activity kinds, and masks invalid entries
with the existing \code{valid_action_mask} interface.

Hard constraints are enforced by both the action mask and SpaceAGORA command
gate.  They are not represented only as negative rewards.

\subsection{Reward and explanations}

The reward is decomposed and persisted:
\[
R_t=J_{\mathrm{delivered}}
-C_{\mathrm{resource}}
-C_{\mathrm{risk}}
-C_{\mathrm{degradation}}
-C_{\mathrm{uncertainty}}
-C_{\mathrm{coordination}}.
\]
Each term and every relevant constraint margin is written to the step log.

Every policy path emits one explanation record containing the selected action,
capability estimate and uncertainty, active constraints, predicted outcomes,
material alternatives, command disposition, and policy/checkpoint/config/seed
identifiers.  Explanation fidelity is then tested against recorded inputs and
the actual command gate, rather than inferred from network weights.

\section{Implementation phases}

\subsection{Phase 0: boundaries and fixtures}

\textbf{Deliverables.}
Typed capability, EO task, activity command, and disposition records; public
snapshot and feasibility fixtures; a hand-authored two-spacecraft/six-task
scenario; and versioned observation/action schemas.

\textbf{Verification.}
Constructors reject invalid ranges, serialization round-trips, identical
inputs have identical dispositions, and SpaceAGORA tests run without loading
SpaceAGORA\_RL.

\textbf{Exit gate.}
The RL task can be developed against fixtures without importing private
SpaceAGORA modules.

\subsection{Phase 1: single-vehicle event surrogate and baselines}

\textbf{Deliverables.}
An event-driven EO backend; energy, agility, payload-quality, storage, compute,
and downlink ledgers; degradation onset/severity; an oracle estimator; fixed
schedule, rule-based, and optimization-oracle baselines; and initial metrics.

\textbf{Verification.}
Seeded CPU episodes are repeatable, resources obey conservation and bounds,
infeasible actions are masked and rejected, nominal cases match baseline
expectations, and the oracle cannot lose to the identical feasible fixed
schedule because of implementation differences.

\textbf{Exit gate.}
One command evaluates the fixed, rule, optimization, learned, and oracle
policies on the same manifest-backed campaign.

\subsection{Phase 2: live SpaceAGORA adapter}

\textbf{Deliverables.}
A declared parent dependency; public orbit/access/attitude/resource snapshots;
typed command handoff; bounded collect, slew, desaturate, recharge, and
downlink execution; and cached exogenous access geometry.

\textbf{Verification.}
Surrogate and live backends share task/config/result interfaces, snapshot and
disposition fixtures agree at known states, accepted commands use only the
typed path, rejected commands do not mutate state, and a short live episode is
deterministic for fixed seeds and solver settings.

\textbf{Exit gate.}
A frozen policy runs unchanged against both backends.

\subsection{Phase 3: estimation and generalization}

\textbf{Deliverables.}
Oracle, delayed/noisy, and telemetry-derived estimators; battery, wheel, and
payload degradation sweeps; configuration-conditioned DDQN/A2C; held-out
configuration campaigns; calibration; and explanation-fidelity reports.

\textbf{Verification.}
Non-oracle observations exclude true capability, train/validation/test
degradation families are disjoint and recorded, manifests contain estimator
and schema versions, and every learned result is compared with rule,
optimization, and oracle baselines.

\textbf{Exit gate.}
Capability conditioning demonstrates repeatable value over an otherwise
identical policy that omits capability inputs.  Only then is a recurrent
context encoder or meta-RL adaptation module considered.

\subsection{Phase 4: distributed mission layer}

\textbf{Deliverables.}
A fleet environment, dynamic reassignment, a centralized allocation baseline,
timestamped decentralized messages, crosslink degradation, partial payload
loss, role reassignment, and fleet recovery metrics.

\textbf{Verification.}
Reassigned tasks are never double counted, reservations prevent exclusive-task
collisions, missing messages cannot bypass local safety, each rollout worker
owns an isolated complete fleet, and \code{run_constellation_ensemble} remains
limited to uncoupled physical studies.

\textbf{Exit gate.}
The fleet retains more value than independent local policies in at least one
preregistered partial-degradation regime without increasing hard violations.

\subsection{Phase 5: assurance and flatsat preparation}

\textbf{Deliverables.}
Deterministic replay, compute and memory measurements, command-gate fault
injection, operator rationale/counterfactual/reconstruction reports, and a
hardware shim preserving the snapshot and command schemas.

\textbf{Verification.}
Replay reproduces actions and dispositions, safety behavior is independent of
policy implementation, timeouts or malformed outputs resolve to documented
safe behavior, and reported uncertainty is calibrated.

\textbf{Exit gate.}
The software boundary is ready for embedded/flatsat work.  Hardware
procurement and flight qualification remain outside this package effort.

\section{Experiment and metric plan}

\begin{longtable}{P{0.29\linewidth}P{0.62\linewidth}}
\toprule
Campaign axis & Initial values \\
\midrule
\endhead
Backend & Event surrogate; SpaceAGORA live \\
Policy & Fixed; rule; optimization; DDQN/A2C; oracle \\
Estimator & Oracle; delayed/noisy; telemetry-derived \\
Degradation & None; battery; agility; payload; joint \\
Severity & Preregistered continuous bins \\
Fleet size & One, then two; expand only after correctness \\

\bottomrule
\end{longtable}

Required outcome measures are mission value retention, oracle regret,
adaptation latency, hard violations, minimum resource margins, capability
estimation error and calibration, held-out generalization, recovered value
after reassignment, revisit/gap, delivery latency, communication bytes,
decision time, memory, explanation fidelity, and replay completeness.
Aggregate results include seed counts and uncertainty intervals.

\section{Test strategy}

Fast pull-request tests cover:

\begin{itemize}
  \item contract construction, units, ranges, and serialization;
  \item observation shape/version and normalization bounds;
  \item action-catalog and mask invariants;
  \item deterministic surrogate transitions;
  \item reward-component arithmetic;
  \item command rejection and non-mutation;
  \item reservation and reassignment invariants; and
  \item one single-vehicle and one two-vehicle smoke episode.
\end{itemize}

Nightly or research campaigns cover Monte Carlo degradation sweeps, live
SpaceAGORA parity, held-out generalization, crosslink degradation, and
performance/memory regression.  Parent-package changes also satisfy the
existing architecture, canonical-path, naming, coverage, typed-configuration,
documentation, and artifact gates.

\toprule
Risk & Consequence & Control \\
\midrule
\endhead

Health/capability conflation & Planner depends on component details & Expose mission-level capability and uncertainty \\
Safety only in reward & Invalid commands remain possible & Masks plus independent deterministic gate \\
Variable task action space & Fixed-output learners do not fit & Top-$K$ slots and stable catalog \\
Latent-state leakage & Unrealistic evaluation & Separate truth, telemetry, estimate, observation \\
Fleet/worker confusion & False satellite independence & One fleet environment per worker \\
Private API coupling & Brittle integration & Declared dependency and root APIs \\
Opaque scalar reward & Tradeoffs cannot be audited & Persist reward components and margins \\
Premature meta-RL & Complexity without evidence & Require conditioning baseline first \\
Schema drift & Checkpoints silently misread state & Version schemas in manifests \\
\bottomrule
\end{longtable}

\section{Recommended first vertical slice}

\begin{enumerate}
  \item Add the four SpaceAGORA boundary records and deterministic fixture gate.
  \item Add an \code{EarthObservationMDP} with one spacecraft, six tasks, and
        event-driven energy/storage/downlink transitions.
  \item Model only battery-capacity degradation with an oracle estimator.
  \item Implement \emph{single image}, \emph{downlink}, \emph{recharge}, and
        \emph{defer} actions.
  \item Add fixed, rule-based, and optimization-oracle baselines.
  \item Train the existing DDQN implementation with capability included in the
        observation.
  \item Report mission value retention, regret, SOC margin, and adaptation
        latency.
  \item Run the frozen policy against a fixture-backed public SpaceAGORA
        adapter without private imports.
\end{enumerate}

This slice validates the package boundary and end-to-end experiment before
reaction-wheel degradation, image quality, meta-learning, or distributed
allocation are introduced.

\section{Definition of done}

The integrated framework is complete when:

\begin{itemize}
  \item dependencies are one-directional and declared;
  \item physical truth, telemetry, capability estimate, and policy observation
        are distinct typed records;
  \item learned and non-learned planners share task, command, gate, and metric
        paths;
  \item one frozen capability-conditioned policy runs on surrogate and live
        backends;
  \item single and joint degradation campaigns are repeatable and
        manifest-backed;
  \item fleet reassignment works under partial degradation and restricted
        crosslinks;
  \item hard constraints are enforced outside the policy;
  \item explanations are tied to recorded inputs, alternatives, outcomes, and
        command dispositions; and
  \item repository scripts regenerate all preregistered baselines, metrics,
        tables, and plots from the research outline.
\end{itemize}
