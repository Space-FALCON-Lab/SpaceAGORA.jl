# Review record: PR 438: Save mounted thrusters' firing state in checkpoints

## Scope

Review of the SpaceAGORA `thruster-firing-checkpoint` branch against main
(4f727266b): the outside review of 2026-10-20, finding 1 (P2), for 0.5.0.
Commits: the change and its tests (52bb21d89), this record (a12908581), and the
mounting-link correction (63558de38).

A mounted `Thruster` with `firing_dynamics=true` delivers its command through
its firing dynamics. At each control tick of the effector commanding it, the
engine (`_apply_mounted_thruster_firing!`) updates two fields on the thruster:

- its ramp factor `κ`;
- the average thrust `thrust` it delivers until the next tick.

Both live on the actuator record, not in any model. Neither checkpoint snapshot
saved them: neither the engine's callback snapshot nor the models' own state. A
resumed run restarted both at zero. It then delivered no thrust until its next
tick and ramped up again from zero, so it ended differently from an uninterrupted
run. Nothing refused the resume. The kit's `checkpoint_round_trip` reported
`advisory_fail` for such a fixture.

- The callback snapshot (version 2) records, per spacecraft, the mounted thrusters
  with firing dynamics in link order (`_record_firing`):
  - in its configuration, each one's place and firing parameters. The place
    (`_actuator_place`, since 63558de38) is its position in the mounting order
    (`mounted_actuators`), its link's position in `sc.links`, and its position
    among the actuators mounted on that link. The parameters are `max_thrust`,
    `cutoff_frequency`, `min_firing_time`, `level_on` and `level_off`;
  - in its state, `κ` and `thrust`.

  A resume restores them with the snapshot's other records, before the callbacks
  initialize and after every check, so a refused snapshot restores nothing.
- Another thruster configuration refuses the snapshot, as other devices do:
  - a thruster in another place: another position in the mounting order, another
    link, or another slot on its link;
  - a rating, ramp, minimum on-time or Schmitt level changed;
  - firing dynamics switched on or off.

  The configuration does not record a thruster's location or direction (see
  Findings).
- A fault's actuator is placed the same way since 63558de38. Before, a fault
  recorded only its actuator's position in the mounting order.
- A run with firing dynamics needs the snapshot. A checkpoint without one is
  refused, and the message names thrusters with firing dynamics.
- A version 1 snapshot (SpaceAGORA 0.4 and earlier):
  - still resumes a run without firing dynamics, compared with the configuration
    without thrusters;
  - is refused for a run with them, with a message saying the firing state is
    missing and the checkpoint was written by SpaceAGORA 0.4 or earlier.
- The fallback the brief allowed, refusing checkpoints for firing dynamics, was
  not needed.

The restored state is the one after the last tick before the checkpoint. A tick
on a segment boundary runs before the checkpoint written there (#413), and the
thruster holds that state until its next tick, as in an uninterrupted run.

Other actuator run state, checked:

- Reaction wheels: the wheels' momentum is integrated state (`h_wheels` in the
  state vector), so the checkpoint's state holds it. The assembly's
  `mounted_rates` are cleared and rebuilt at every right-hand-side evaluation. The
  assembly's `h_wheels`, `h_dot_wheels` and `tau_body_net` are not written during a
  run. Nothing missing.
- Control moment gyros and inner gimbals: the angles are integrated state
  (`cmg_angles`), and `cmg_rates` is rebuilt at every evaluation. A gyro's
  `gimbal_angle_rad` is only its initial angle. Nothing missing.
- Magnetorquers and laser terminals are immutable records. A torque rod's dipole
  comes from its level at each evaluation. A laser terminal's effect is in the
  integrated `laser_dv` and `laser_delta_sma`, and the interlink entry checks its
  configuration. Nothing missing.
- Hinges and thruster gimbals were already in the snapshot. A thruster's
  `gimbal_rotation` is recomputed from the restored gimbal angles.

The other records' places, checked for the same gap (63558de38):

- A hinge is recorded by its link's position, and a link carries at most one, so
  a hinge moved to another link refuses the snapshot.
- A gimbal is recorded by its link's position and by the slot, on that link, of
  the thruster it turns. A gimbal moved to another link or thruster refuses.
- A sensor is recorded by its kind, its link's position, its period and its seed.
- A fault recorded only its actuator's position in the mounting order: the same
  gap. It is now placed as a thruster is.
- A battery is one per spacecraft.
- A thruster's `stop_firing_time` is never written during a run.
- Not checked: user-defined `AbstractActuator` kinds. The actuator contract has no
  checkpoint hook, so any mutable state such a kind keeps is not saved. Nor the
  interlink scheduler's matching and graph flags, which every run resets at its
  start.

## Findings

No open P1 or P2 findings.

- P2, fixed in 63558de38. Found by the independent review of 2026-10-20, first
  finding.
  - The defect: at `52bb21d89` the configuration placed a thruster by its position
    in the mounting order alone. The sole firing-dynamics thruster moved from the
    root to another existing link keeps that position and its parameters, so the
    snapshot compared equal. `κ` and `thrust` were restored onto the remounted
    thruster, and the resumed run turned the vehicle where the checkpointed run
    did not.
  - The fix: the place now includes the link's position and the slot on that link.
  - Faults had the same gap and are placed the same way. Hinges, gimbals and
    sensors already recorded their link (see Scope).

Points a reviewer should check:

- By design: the snapshot's configuration includes each thruster's firing
  parameters, so changing a ramp, threshold or rating between the checkpointed
  run and the resumed one refuses the resume. Faults' values and sensors' periods
  already work this way.
- By design: every callback snapshot is now version 2, with an empty `thrusters`
  list per spacecraft when there are no firing dynamics. SpaceAGORA 0.4 refuses a
  version 2 snapshot ("version 1 is required"); resuming a newer checkpoint with
  an older SpaceAGORA was never supported.
- Low: a run with firing dynamics cannot resume a checkpoint written by SpaceAGORA
  0.4 or earlier. That checkpoint never held the state. The refusal says so, and
  the docs too.
- Low: user-defined actuator kinds that keep mutable run state have no way to
  checkpoint it (see Scope).
- Low: places are positions in lists. Two thrusters with firing dynamics and the
  same parameters, swapped in mounting order on one link, compare equal and take
  each other's state. So do the two gimbals of a two-axis gimbal on one thruster.
  The configuration records neither a thruster's location and direction nor a
  gimbal's axis; adding them would close this. Not changed here.
- Low: a version 1 snapshot (0.4) still places a fault by its position in the
  mounting order. A 0.4 checkpoint therefore resumes after its faulted actuator
  moved to another link at the same position: that checkpoint never recorded the
  link.
