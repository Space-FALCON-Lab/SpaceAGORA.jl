What it does:
- The states `laser_dv` and `laser_delta_sma`, which every spacecraft carries in
  a run with interlinks, become `interlink_dv` and `interlink_delta_sma`, at the
  same positions, with the same shapes and the same arithmetic.
- The results gain `sc{i}_interlink_dv_{1..3}` and `sc{i}_interlink_delta_sma`.
  The `sc{i}_laser_*` columns and the `:laser_dv` and `:laser_delta_sma` save
  fields stay beside them, with the same values, as aliases until 1.0.
- Checkpoints keep the old names inside; a resumed run reads either pair and
  refuses a state that mixes them.

Rule: every existing run's states are identical under the new names, and the
old columns are identical to the base's.

- **The rename.** The run's state shape (`execution.jl`) and the dynamics
  (`dynamics_rhs.jl`) use `interlink_dv` and `interlink_delta_sma`. The save fields
  come from one function, `interlink_save_fields`: the two new fields, then the
  `laser_*` aliases, each read from the new state, so the alias columns equal the
  new ones by construction. Without an interlink model there are no fields.

  (`_INTERLINK_STATE_NAMES`), so 0.5.1 can resume a 0.6.0 checkpoint. A resume
  reads either pair, refuses a state that mixes the two pairs or differs between
  spacecraft, and still refuses an interlink state that doesn't match the run.
- **What can't warn.** The state names and the alias columns can't emit a
  deprecation warning. The release note and the docs say so, give the search
  terms, and say that later columns move four places per spacecraft (D-I6-1,
  D-I6-2, accepted).
- **The vacuous checks.** The inventory found that `!hasproperty(..., :laser_dv)`
  passes even after a rename. `interlink_tests` now checks both states by their
  new names and the save-field order (new names, then aliases).

## Findings

No P1 or P2 findings in the author's own review. Points a reviewer should check:

- **The break (D-I6-1, decided).** Reading `u.sc[i].laser_dv` or
  `u.sc[i].laser_delta_sma` now fails with the state's own lookup error, which
  does not name the replacement. A `ComponentVector` takes its property names
  from its axis, so an alias would need a method on a ComponentArrays type
  (type piracy, on the state's hottest access path) or a second axis name for
  one range, and neither could warn. The 0.6.0 notes list it with #478's
  breaking change. No user outside core was found reading the two states or
  columns (Residual Risk).
- **The aliases cannot warn (D-I6-2, decided).** A column is read from a file
  or a table, with no SpaceAGORA code on the path. An interlinked run writes
  four more columns per spacecraft until 1.0; an explicit `save_fields` list
  without the two alias fields writes only the new ones.
- **The checkpoint encoding (D-I6-3, decided).** The writer renames the two
  components to their old names before serializing; the stored state then has
  the type and the bytes the base writes, and v0.5.1 resumes it (Tests). The
  renaming goes through the public constructor and is checked bit for bit; a
  difference would raise an internal error rather than write a changed state.
- **Resume.** A checkpoint with either pair resumes, and the old pair is given
  the run's names before the run starts; a state with parts of both pairs, or
  whose spacecraft differ in their naming, is refused with the existing
  message. A checkpoint with the new pair is not written by this branch; it is
  accepted so that a later change of the encoding stays readable.
- **Column positions.** The new columns take the laser columns' place and the
  aliases follow them, so every column that existed keeps its name, its values
  and its position relative to the others, and removing the aliases in 1.0
  moves nothing before them. In a run with interlinks, every column after the
  quaternion block moves four places per spacecraft. A search of the lab's
  other repositories found no reader that selects interlinked columns by
  position.
- **Low: test states as named tuples.** The checkpoint writer also renames a
  state given as named tuples, which only unit tests pass; it has no flat
  vector to check bit for bit.
- **2026-10-21, independent review at e5469265c: no P1 or P2, two P3s (fixed
  in 9e09e1dfe).**
  - *The refusal of a state whose spacecraft differ had no test.* Replacing
    `allequal(namings) ? first(namings) : :mixed` with `first(namings)`
    survived both interlink test files. A run's own state cannot reach that
    branch (ComponentArrays refuses spacecraft with different components), but
    a state given as named tuples can. `interlink_checkpoint_tests.jl` now
    builds one, the first spacecraft on the new names and the others on the old,
    and requires `:mixed` and the refusal; the replaced line fails two of its
    checks.
  - *The skip for `gravity_backbone_split`.* The resume's state check is
    skipped for that solver mode only because such a run never has interlinks
    (`_validate_interlinks!` refuses them before the resume) and its state has
    no `sc` components; `_checkpoint_state` and `_resumed_checkpoint_state`
    test `args.interlink_model` first. The call site now says so.
  - The review reran nine cross-version resumes, including v0.5.1 resuming a
    checkpoint of this branch, all equal to an unbroken run, and found six runs
    bitwise identical to the base.
- **Low: earlier results rows across builds.** Since #491, a resumed run
  includes the results rows saved before its checkpoint only when they were
  saved with the same save fields. A checkpoint written by a build without this
  PR's fields (for example #478's head) and resumed with this PR therefore
  starts its results at the resume, with #491's warning, and writes them to
  `resumed_at_<t>s`. Between releases this does not arise: 0.5.1 writes no rows,
  and 0.6.0 writes both the new fields and the aliases. A checkpointed,
  resumed interlinked run of this branch keeps all its rows (Tests).
- **Observation, not from this PR.** The RHS route check at
  `interlink_tests.jl:354` (unchanged from the base) expects `satellite_batch`
  and gets `flat_constellation_effector_queue` when Julia runs with one thread,
  so the file passes 246 of 247 at one thread. CI runs it with four threads,
  where all 247 pass.

## Residual Risk

- **Scripts that read the two states stop.** This is the decided break. A
  search of the lab's other repositories (code, constructed strings and
  retained serialized files), the HYPR package and the visualizer companion at
  its pinned revision found no reader of `laser_dv` or `laser_delta_sma`
  outside core. The unmerged `ORACLE_SpaceAGORA_Integration` branch has
  prototype examples that read the old states; a port of them needs the
  rename. Code the search was not given cannot be ruled out.
- **Readers by position.** Every column after the quaternion block moves four
  places per spacecraft in a run with interlinks; no reader by position was
  found.
- **Scripts that read the columns keep working until 1.0,** and nothing warns
  them; the docs and the 0.6.0 notes give the search command.
- **Wider tables.** Interlinked runs write four more columns per spacecraft
  until the aliases go.
- **Checkpoints and 0.5.1.** Since #476, a checkpoint also carries a
  `gnc_scopes` entry. v0.5.1 ignores it and resumes an interlinked checkpoint
  of this branch; a run with guidance, navigation or control models is #476's
  case, not this PR's.
- **A later encoding change.** Checkpoints keep the old names inside. A future
  release that writes the new names must keep the reader's acceptance of the
  old pair for checkpoints written before it.
- **Release.** This PR is for 0.6.0 and merges after #478.
