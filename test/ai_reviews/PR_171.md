# PR 171: adaptive parallel execution behind one SolverConfig flag

## Scope

Review of `policy-v2-consistency` against `main` (merge base via `git diff origin/main...HEAD`, head f680a034c, 222 commits, 157 files): the predictive campaign planner (R7), the `SolverConfig(parallel=true)` flag and its campaign keywords, automatic machine calibration, the performance changes the PR describes as byte-identical, the removal of the profile and outer-route bandit symbols from the root exports, and the paper benchmark harness.

All 32 changed `src/**/*.jl` files were read in full diff, together with `ext/SpaceAGORAGRAMSuiteExt.jl` and the surrounding code each change depends on (flat RHS route, calibration store, process pool, precompile workload, `machine_topology`). Tests were read for what they assert. Docs, scripts and benchmarks were reviewed more lightly: public-API consistency, the harness entry points, and callers of removed symbols.

Julia was not run for this review, because another job held the machine. Every finding below comes from reading the code. Where a claim depends on runtime behavior, the finding says how to confirm it.

## Findings

### P1 (must fix before merge)

**P1-1 (open): the new precompile warmups store this machine's topology in the package image.**

- Where:
  - `src/precompile_workload.jl:77-109`: `_warm_predictive_campaign` and `_warm_mixed_dispatch_campaign` call `run_monte_carlo(...; threads=:auto)` inside `@compile_workload`.
  - Both routes evaluate `ParallelProfiles._machine_parallel_class()`: the predictive route at `src/simulation/campaigns/adaptive_routing.jl:1120` and the bandit route through `_campaign_route_plan` at `adaptive_routing.jl:317`.
  - `_machine_parallel_class()` calls `usable_core_budget()`, which calls `machine_topology()`. That function fills the module-level `const _TOPOLOGY_CACHE = Ref(...)` (`src/parallel/routing/machine_topology.jl:31`, `:574-631`).
  - The route to process workers also reads `memory_budget_bytes()` from the same cache.
  - The reset block at `precompile_workload.jl:115-128` clears only the SPICE kernels, the predictive constants and the route-state flag. It does not clear `_TOPOLOGY_CACHE`, and nothing refreshes it at `__init__`.
  - The snapshot is serialized into the pkgimage, the same failure mode the file documents for `_FURNISHED_KERNELS`. On `main` the precompile workload never reached `machine_topology()`.
- What goes wrong: every process that loads the image uses the precompiling process's snapshot until someone calls `refresh_machine_topology!()`. The snapshot holds:
  - CPU count, physical cores and affinity mask;
  - cgroup CPU quota and memory limit;
  - total and usable memory.

  The `SPACEAGORA_CORE_BUDGET` and `SPACEAGORA_PHYSICAL_CORES` overrides are read only when the cache is filled, so setting them at run time no longer has any effect.
- Concrete scenarios:
  - Case 1: a container image precompiled during `docker build`, with no quota, and run with `--cpus=4 --memory=8g`. The planner and the memory caps see the build host's cores and memory. `effective_process_workers` then admits a process pool sized for the host, while `MemAvailable` inside the container is not cgroup-aware. The likely result is an OOM kill of the campaign.
  - Case 2: an HPC depot precompiled on a login node and used on a compute node with a different core count or Slurm cpuset.
  - Case 3: the benchmark harness's taskset runs, which rely on `SPACEAGORA_PHYSICAL_CORES` (the pinned-run note in the project records) and now silently get the precompile-time value.

  All three affect the flag's routing, and cases 2 and 3 affect the PR's own measured routing.
- Fix: add `ParallelProfiles._TOPOLOGY_CACHE[] = nothing`, or an equivalent reset helper, to the `@setup_workload` reset block next to `_reset_furnished_kernels!()`. Better, also clear it in `__init__`.
- To confirm: in a fresh process after precompilation, `SpaceAGORA.ParallelProfiles._TOPOLOGY_CACHE[]` should be non-`nothing` before any call is made.

### P2 (should fix)

**P2-1 (open): concurrent flagged `run_simulation` calls can leave the R7 environment behind.**

- Where: `src/simulation/engine/adapters/from_env.jl:440-462` and `src/simulation/engine/execution.jl:416-425`.
- `_with_parallel_flag` scopes the flag with `withenv` on the process-global `ENV`. `_parallel_flag_nested()` (`src/parallel/routing/env_mapping.jl:244`) treats a call as nested only on a `Distributed` worker or when `SPACEAGORA_OUTER_PARALLEL_ACTIVE` is set. The flag's own pairs set that variable to `"0"`.
- Scenario: two user threads call `run_simulation(args)` with `SolverConfig(parallel=true)` at the same time, for example under `Threads.@threads`, which is the pattern users reach for before `run_monte_carlo`.
  1. A saves "unset" and applies R7.
  2. B saves A's R7 values as its "previous" and applies R7.
  3. A exits and restores "unset".
  4. B exits and restores R7.
- Result: the process keeps the R7 profile's environment afterwards. That includes adaptive policy V2, persistent hints and state persistence, and `SPACEAGORA_CAMPAIGN_PLANNER=predictive`. Later `parallel=false` runs then run under it, which breaks both "nothing is left in the process environment" and "with `parallel=false` nothing changes".
- Before this PR, a per-configuration `SolverConfig` never wrote to `ENV`. The overlapping `setenv`/`getenv` calls from several threads are a further hazard.
- Fix options:
  - count active flag scopes under a lock and apply and restore only at depth 0; or
  - treat a second concurrent entry as nested; or
  - at minimum, document that `run_simulation(parallel=true)` must not be called concurrently.

**P2-2 (open, the known gap is real): plans that give each sample more than one thread do not get those threads on the flat and effector routes.**

- Where: `src/simulation/campaigns/predictive_planner.jl:663-707` and `src/simulation/campaigns/adaptive_routing.jl:780-797`, `:884-906`.
- The planner offers `threads@W` with `b = fld(T, W) > 1`, and mixed plans whose local slots run on `b` threads. Both dispatch with `SPACEAGORA_OUTER_PARALLEL_ACTIVE=1` and `SPACEAGORA_INNER_THREAD_BUDGET=b`: the threads branch sets it at `adaptive_routing.jl:780`, and `outer_split_env_pairs` sets it for local slots.
- Under that flag, the RHS heuristic serializes the routes the speedup curve was measured on:
  - `outer_serialized` clamps the single-harmonics flat route to allotment 1 (`src/simulation/engine/setup.jl:1418`, `:1471`), and does the same for the generic flat queue (`:1593`);
  - effector threading is forced off unless `SPACEAGORA_EFFECTOR_ALLOW_WITH_OUTER` is set;
  - under V2 the callbacks decline any split with more than 2 items per thread (`adaptive_decision.jl`).
- Only `satellite_batch` (Polyester, sized from the budget) and a calibrated plan pinned by a sweep under `outer=1` use the `b` threads.
- Meanwhile `rhs_inner_speedup_curve` (`src/simulation/engine/rhs_calibration.jl:507`) pools rows "whatever its budget or outer-split flag". That makes the curve mostly single-simulation (`outer=0`) measurements.
- Consequence: on harmonics constellations, the workload the curve exists for, a `b > 1` plan is priced at the curve's speedup but runs at about one thread per sample. The idle threads make such a plan slower than the static `threads@min(n,T)` it had to beat by the margin.
- The `:none` plan (`b = T`, one consumer, no outer flag) is unaffected. Results are unaffected; this is performance only.
- Fix options: let a declared budget above 1 lift `outer_serialized`, for example by treating `SPACEAGORA_INNER_THREAD_BUDGET > 1` from the planner as the allowance; or restrict the curve to `outer=1` rows for plans that run under an outer split.

**P2-3 (open): automatic calibration saves whatever conditions it ran under, and never redoes it.**

- Where: `src/parallel/cost/machine_calibration.jl:679-704`, `:583-636`.
- `ensure_machine_constants!` calibrates on the first flagged run, in whatever session that is, and a present file is never re-measured. Three problems follow:
  - The measurement uses `Threads.nthreads()`, in `_calibrate_usl`, `_calibrate_parallel_speedup` and `_calibrate_dispatch`, but `machine_fingerprint()` does not include the thread count. A first flagged run from a 1-thread session, which the flag explicitly supports with an `@info`, saves a speedup and USL ladder with a single point, and every later 64-thread session reuses it.
  - Several processes starting together on a fresh machine type in one working directory each calibrate while contending with each other. An example is a job array or parallel test runners, which share the path `pwd()/output/...`. Their inflated constants are saved permanently.
  - They also share the temporary name `path * ".tmp"`, so concurrent writers can interleave into one inode or fail `mv`. A failure is caught as `:failed`, and a corrupt file is re-measured. The contended constants are the real problem.
- The same shared `.tmp` pattern appears in `save_campaign_corrections` (`predictive_planner.jl:1451`).
- Fix: use a unique temporary name (pid plus random) and an advisory lock file. Record `nthreads` in the file, and recalibrate, or at least warn, when the current `nthreads` exceeds it.

**P2-4 (open): the `:auto_stiff` solver changes for any configuration with SRP, even with the flag off.**

- Where: `src/simulation/engine/solver_policy.jl:126-152`, commit ae99d0a3f.
- `SolarRadiationPressureModel` now qualifies for the explicit Tsit5 fast path. `:auto_stiff` runs whose stack is gravity plus SRP therefore stop using `AutoTsit5(Rodas5P)`. Where the stiffness detector fired, the 256-spacecraft case in `docs/architecture/third_body_cost.md`, the trajectory changes. It stays within tolerance, but it is no longer the same bits.
- The reported solver metadata also changes (`"Tsit5"` instead of `"AutoTsit5(Rodas5P)"`), and no Rosenbrock fallback remains.
- The change is defensible numerically, and `auto_stiff_gravity_tsit5=false` restores the old behavior. But it contradicts the PR body's "with it off routing and trajectories are unchanged", and it is missing from the byte-identical list.
- Fix: disclose it in the PR description and release notes. `test/unit/simulation/third_body_route_parity_tests.jl` pins the admission but no trajectory tolerance.

**P2-5 (open): `run_monte_carlo(...; parallel=true)` plans without knowing the workload, and may pick process workers on its own.**

- Where: `src/simulation/campaigns/adaptive_routing.jl:1371`, `src/simulation/campaigns/monte_carlo.jl:908-923`.
- The documented call `run_monte_carlo(1:100; parallel=true) do seed ... end` plans with `campaign_route_features(samples=0)`. That means one spacecraft, an unknown density family and a mission time of zero. The only way to describe the workload, `route_features=` built with the no-longer-exported `campaign_route_features`, is now documented as internal.
- Consequences:
  - the native-GRAM routing guards cannot apply;
  - the memory cap (`effective_process_workers`) cannot charge the per-spacecraft GRAM term;
  - no inner-speedup curve is found.
- At 16 samples or more the process route becomes a candidate, and on ties the planner prefers it (`_predictive_route_rank`). The flag can therefore switch a script to process workers without being asked.
- On those workers:
  - helper functions and state defined in the script's `Main` must still exist there (the harness has to preload them: `ensure_process_workers_with_sample_logic!` in `benchmarks/studies/gram_mars_fix_and_constellation_scaling/mc_multisat_thread_allocation_worker.jl:67`);
  - non-default SPICE kernels must be furnished there too (`docs/src/user/parallel_execution.md`, process section).

  Samples that fail this way show up as per-sample failures, not as a routing error. `docs/src/user/parallel_execution.md`'s "Nothing else needs configuring" does not mention it.
- Fix: derive features from the first sample's `SimulationConfiguration` when one can be observed; or keep a supported way to pass features; or exclude the process route under the flag unless workers are known to be prepared. Document the worker requirements next to the flag in any case.

**P2-6 (open): the memory model now admits roughly 45 times more native-GRAM workload per worker.**

- Where: `src/parallel/routing/machine_topology.jl:235-277`.
- The per-spacecraft native GRAM charge falls from 90 MB to 2 MB. The 2 MB comes from a 60 s arc, and the comment itself says the component that scales is the retained trajectory state, which grows with mission length and `return_solution`.
- Long missions that keep solutions, the Monte Carlo case, are outside the measured domain. Together with P2-5, where features default to one spacecraft, the cap can admit more workers than fit.
- The new default `--heap-size-hint` (`src/parallel/process/worker_pool.jl:131-146`) bounds the Julia heap, not the native memory.
- Fix: scale the term with mission length and save cadence, or charge measured RSS after the first sample. At minimum, state the domain in the user docs.

**P2-7 (open): exports are removed with no deprecation path, and some callers were missed.**

- Removing 17 profile and bandit symbols plus `campaign_route_features` and `campaign_outer_route_state` from the root (`src/SpaceAGORA.jl:20-24`, `docs/public_api_symbols.jl`) breaks `using SpaceAGORA; OuterRouteTuning(...)` with an `UndefVarError`. There are no `Base.@deprecate_binding` shims and no release note, although the version is pre-1.0 (0.1.0).
- Callers left behind:
  - `benchmarks/studies/gram_mars_fix_and_constellation_scaling/leo_ensemble_outer_backend_scaling_worker.jl:55-63` still calls `OuterRouteTuning(...)` and `OuterRouteState()` unqualified. It gets `using SpaceAGORA` through `examples/common.jl`, so it now fails. Its sibling `mc_multisat_thread_allocation_worker.jl` was fixed.
  - `docs/src/user/parallel_execution.md:564-573` still tells users to call `campaign_route_features`, `record_outer_route_feedback!`, `campaign_outer_route_state()`, `outer_route_stats_snapshot`, `reset_outer_route_state!` and `OuterRouteState` unqualified.
- Fix: add deprecated bindings for one release, qualify the script and the docs text.

### P3 (minor, accepted, or out of scope)

These are behavior changes with the flag off, each timing-only or claimed byte-identical:
- P3 (accepted): `outer_split_env_pairs` and `capped_inner_thread_budget` (`src/simulation/campaigns/monte_carlo.jl:801-835`) now cap a user-exported `SPACEAGORA_INNER_THREAD_BUDGET` that is wider than the share, including for `run_monte_carlo(threads=N)` with the flag off. The docstring documents and justifies it. Timing only.
- P3 (accepted, residual risk): the isolated GRAM pool changes from default `off` to `auto` above 1024 native items, with at most 4 workers (`src/simulation/callbacks/density_callbacks/config.jl:89-127`). Consequences:
  - It is active whenever `nthreads() > 1`, whatever the flag.
  - It adds up to four resident native GRAM images, about 106 MB each for Earth.
  - This path had the SPICE-corruption crash fixed on `router-eval-expanded-b6`.
  - Its bit-identity rests on `gram_isolated_pool_tests.jl`, which needs GRAM on the host.
  - The -30 m clamp added in `model_selection.jl` fixes a real abort on the pooled path (a surface-reaching run died there with GRAM's "Height below -31 meters" error while the locked path completed).
- P3 (accepted): the RHS heuristic changes (the 64-per-worker flat floor, flat at budget 1 to 3 for pre-pass-only stacks, the nested effector guard) and the density and thermal light-work guards also move routing with the flag off. They are claimed bit-identical and reasoned below.
- P3 (accepted): `thread_policy_decision` persistent-hint keys include `heavy_only`, and density and thermal now pass `heavy_only=true`. Their existing hint entries go cold once.

Other P3 items:
- P3 (out of scope, tracked): `run_simulation` now forces `GC.gc(true)` after every 8 unreferenced native atmospheres (`src/simulation/engine/execution.jl:921-928`, `ext/SpaceAGORAGRAMSuiteExt.jl`). The finalizer is pre-existing; this makes it run deterministically inside threaded campaigns. Whether GRAM's destructor is safe against concurrent calls on other instances is unverified.
- P3 (accepted): with the flag on, the working directory accumulates state under `output/parallel_policy_state/`: machine constants, persistent hints and route state (the R7 bundle sets `PERSISTENT_HINTS=1` and `STATE_PERSIST=1`), and corrections. That only happens with two concurrent campaigns in one process, which the `ENV`-scoped design does not support anyway.

### Checked, no finding

The flag:
- Flag off: `_parallel_flag_applies(false)` returns immediately. The `run_simulation` re-entry, the engine-config flag branch and the ensemble scope are all skipped. `threads=nothing` resolves to `1`, and `parallel=false` campaigns never touch `SPACEAGORA_CAMPAIGN_PLANNER`. The flag-off regressions found are the independent changes listed above, not the flag plumbing.
- Scoping: `withenv` plus `try`/`finally` restore both `ENV` and `_engine_active_overrides_ref` on exceptions. `_PARALLEL_FLAG_RESOLVED` is a `ScopedValue`, so the tasks a campaign spawns see "resolved" and do not re-apply the flag or recalibrate. Process workers see `myid() != 1`. Exception restoration is tested.
- Keyword semantics: `parallel=true` with any integer `threads`, including 1, throws `ArgumentError`. Members that disagree throw. `threads=:auto` without the flag keeps the bandit. A conflicting `ParallelConfig(profile=...)` with the flag throws.
- Calibration failure: a thrown calibration is logged, cached as `:failed` and not retried. The run proceeds without constants. `InterruptException` is rethrown.

The planner and dispatch:
- Planner edge cases:
  - `n = 0` returns early (`adaptive_routing.jl:1324`), and the makespan is 0.
  - `n = 1` gives only `:none`.
  - `T = 1` gives no threads or inner candidates, and `local_slots_max = 0`.
  - A pool of fewer than 2 gives no process plans.
  - Every division is guarded: makespan, round-tail observation, heap-scale observation, guard ratio.
  - `_predictive_dispatch` clamps width and slots to the batch.
- Guard races: consumers are closed only inside the guard's lock, after one atomic `decided` flip, and `close_dispatch_consumer!` refuses the last open consumer. So the dispatch always keeps a consumer and every sample runs exactly once (tested for both classes). Admission is checked before `take!`.
- The corrections file: a corrupt file, another schema, fingerprint or code token loads as fresh; the rules' inputs are validated; staleness drops parameters.
- The dispatch cache is off by default. Borrowed entries are released in `finally`, a busy cache falls back to a private pool, and `shutdown_process_pool!` clears it.

Numerical identity, by reading:
- The flat reduction sums slots in effector-tuple order from zero. The new aero pre-pass and the budget-1 pre-pass route write per-effector slots rather than totals, so the order matches the per-satellite chain.
- `_aero_prepass_satellite!` writes only its own satellite's slots and save-cache entries. Save-cache growth is lock-guarded, and `_aero_pure_wrench` is called rather than inlined, which preserves FMA contraction.
- The uniform-light density batch is skipped for any per-spacecraft cache state: freeze-per-step, the vacuum cache, the track cache, statistics, native GRAM, grid models, an inactive spacecraft, or mixed models. For the remaining analytic models its values equal what `_density_state_from_kinematics!` computes (a direct `getDensity`).
- `_spice_query_name` interning publishes copy-on-write under a lock, and readers load the table atomically; no reader can observe a rehash. The `map`-based third-body sample preserves body order.
- `@simd ivdep` on the harmonics batch loops was already on `main`; this PR corrects only the comment.
- `rhs_calibration.jl`: the change to the heuristic-vote exemption applies only under V2; flag-off (R5 and below) cached-verdict handling is unchanged.

## P1 Assessment

There is one P1, and it is open. P1-1: the new `@compile_workload` warmups store `machine_topology()`'s snapshot in the package image, so every process that loads the image uses the precompiling environment's core count, affinity, cgroup quota and memory limit for the flag's planner and memory caps. The `SPACEAGORA_CORE_BUDGET` and `SPACEAGORA_PHYSICAL_CORES` overrides then stop taking effect at run time. It is a one-line reset in the existing `@setup_workload` reset block. It does not change trajectories. It does invalidate the machine model the planner exists to use, and in containers with a runtime memory limit it can size a process pool past that limit.

The P2 findings do not block the merge on their own. P2-1, the environment left behind after concurrent calls, and P2-4, the SRP solver change with the flag off, both contradict statements in the PR body. They should be fixed or disclosed before the flag is announced.

## Residual Risk

- No Julia was run for this review. The bit-identity claims (flat versus satellite-batch at budgets 1 to 3, the aero and density batches, the GRAM pool) were checked by reading the order of operations, not by running the parity tests. So were the performance claims and P1-1's mechanism. The suggested confirmation for P1-1 is a one-line check in a fresh process.

They were tuned on two machines. The within-10% result in the PR body covers 11, 8 and 3 workloads at full budget only. Shapes outside that set, and partial budgets, rest on the margin rule.
- Concurrency of native GRAM destruction with in-flight calls on other instances, now forced by the collection hook, is untested.
- The removed exports may break downstream scripts outside this repository. Only in-repo callers were searched.
- The benchmark harness, the Python archive and table scripts, and the paper-workload package were reviewed for entry-point consistency only, not line by line.
