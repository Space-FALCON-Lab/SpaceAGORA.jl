## Findings

- **P1, fixed in this PR.** The study's pulse callback hung the measured-drag run on main.
  - Since #170, main's orbit-counter callback (the directional vector adapter) also locates the periapsis root of r·v, as an ignored downcrossing.
  - With the pulse callback on the same root, each callback's repeat guard covers only its own last event. The two re-detected the root in turn at t = 46187.058368211954 s indefinitely: the density log grew to 6.8 GB with no time advance.
  - In a short Earth propagation, the loser of the tie missed every pulse instead.
  - The pulse now fires at r·v = −1 m²/s, strictly before periapsis by r_p/(μe), about 23 ns at Venus Express. Its condition holds a positive constant once the pass is pulsed. An event that does not pulse calls `derivative_discontinuity!(integrator, false)`, like main's ignored crossings.
  - Under the old solver libraries, this change alone moves the measured-drag result by about the size of the run's known sensitivity: on `b7fc48189` + port, apoapsis MAE goes from 45.28553179052384 to 44.2467205441619 km.
- **Density conflict resolution.**
  - `tabulated_flight_density_pass_keyed` (the Tolson pass-keyed replay, `336130ad7`) is not ported. Nothing here needs it, and it would change Odyssey.
  - In `runtime.jl`, the per-pass branch sits in main's `_density_state_from_kinematics_unmasked!` and evaluates its fallback through the unmasked path. Main's wrapper then applies `_environment_wind` once, as for a plain GRAM model.
- **State anchors.** The `u_modified!` call is renamed `derivative_discontinuity!`, as #170 did for the anchor callback.
- **Defaults are unchanged.**
  - `comparison_axis` defaults to `:legacy`, the skipped events to 0 and −1, the thruster pulse to 0.0 (no callback built), and `pass_exponential_scale` to 1.0.
  - Without `SPACEAGORA_TELEMETRY_STATE_OUT` and `SPACEAGORA_PASS_DENSITY_LOG`, nothing is written.
  - In `common.jl`, the `all` alias is now spelled out as its previous five runs, so `--runs=all` is unchanged.
- **The paper's Venus Express numbers move on main. The cause is not this port.** Controls, each run locally with the reference rebuilt byte-identical to the study's:
  - `116a85f9d` (the study commit) reproduces the stored sf3 runs exactly.
  - The same commit with `guidance_schedule = "periodic"` equals this port on `eeebfc624` exactly, which equals the port on `b7fc48189` exactly. The study branch's windowed guidance default (`6bd11aea5`, not on main) is therefore the whole first step.
  - The port on `882dc0f6c` (#170) equals the port on main exactly, so #170 is the second step and nothing after it matters.
  - VenusGRAM from the published elements, apoapsis nMAE: 8.10258465670776% (study) → 7.73540818295944% (periodic guidance) → 7.51058372970378% (#170 and main).
  - Measured drag, apoapsis nMAE: 1.13921115692835% → 1.25142025135551% → 1.22271374445069% (pulse fix, old solver) → 1.72149417193718% (#170 and main).

## Residual Risk

- `PassKeyedExponentialAtmosphereModel` does not forward `density_model_history_dependent` or `density_model_threadsafe` to its fallback. A multi-spacecraft run of this model over a GRAM fallback with perturbed winds would be scheduled as history-independent and not thread-safe. The Venus Express runs are single-spacecraft with deterministic winds.
- The ORVM reference files are built from a 285 MB kernel that is not committed. The ORVM runs are not in CI, and CI's Venus gate still uses the digitized reference.
- The measured-drag result is sensitive to event-handling details at the kilometre level in apoapsis MAE, as the old-solver comparison above shows.
