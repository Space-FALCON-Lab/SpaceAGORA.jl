# Review record: PR 485: calibration kernels stay inside their tables

## Scope

Review of the SpaceAGORA `calibration-table-bounds` branch against main
`2088b4408`. Two commits. They fix out-of-bounds reads in the machine
calibration (`calibrate_machine`, which `ensure_machine_constants!` runs before
the first `SolverConfig(parallel=true)` run on a machine), and make constants
saved before the fix stale.

On main, `calib_batch_kernel!(ws, table, row, n_touch, simd_per_touch)` reads
`table[row, t]` for `t in 1:n_touch` inside `@inbounds`. Two ladders give it the
52×64 table from `calib_table(52, 64)` with more touches than 64:

- the arithmetic ladder of the USL fit (`_calibrate_usl`) asks for up to 4096
  touches;
- the parallel speedup curve (`_calibrate_parallel_speedup`) asks for 512, then
  `cld(512, w)` per worker.

The kernel then reads past the end of the 26 KiB table, up to about 1.6 MiB past
its start. Usually that memory is mapped and the reads return whatever is there;
sometimes it is not. The coverage job of PR 474 stopped with signal 11 in
`calibration_kernels.jl:62`, called from `_speedup_ladder` / `_calibrate_usl`
during `test/unit/parallel/parallel_flag_tests.jl`, inside suite 09's standalone
unit driver.

Audit of every call of the two table kernels on main
(`src/orchestration/parallel/cost/machine_calibration.jl`):

| Line | Ladder | Call | Table | Touches | In range |
|------|--------|------|-------|---------|----------|
| 349 | `_calibrate_coeff_touch` | `calib_touch_kernel!(tab, row, cols)` | `calib_table(rows, cols)` per knot | `cols` | yes, one walk |
| 369 | `_calibrate_simd_lane` | `calib_batch_kernel!(ws, tab, rows ÷ 2, n_touch, spt)` | 52×64 | 16 | yes |
| 277 | `_calibrate_usl` (arithmetic ladder) | `calib_batch_kernel!(…, tab, 26, cld(total_touch, w), 4)`, `total_touch = 4096` | 52×64 | 4096 serial and at `w = 1`, 2048, 1024, 512 at `w = 8`, … | no, below 64 workers |
| 414 | `_calibrate_parallel_speedup` (serial reading) | `calib_batch_kernel!(outs[1], tab, 26, total_touch, 4)`, `total_touch = 512` | 52×64 | 512 | no |
| 424 | `_calibrate_parallel_speedup` (per worker) | `calib_batch_kernel!(outs[wid], tab, 26, per, 4)`, `per = cld(512, w)` | 52×64 | 512 at `w = 1` … 86 at `w = 6` | no, below 8 workers |

The row (26, or `rows ÷ 2`) is inside the table at every call. The other
`@inbounds` reads of the calibration were checked by reading and stay inside
their buffers: the scalar kernel (`n = length(state) = 4096`), the allocation
and stream kernels (`n_elems = 4`, a buffer of at least 1024), the dispatch and
Polyester ladders (sinks of 8192 and 4096 for loops of at most that length) and
the reference kernels (`eachindex` and a stride inside `length(buf)`).

Change:

- `calib_batch_kernel!` (`calibration_kernels.jl`) walks the row again from the
  first column after the last, so the ladders keep the touch counts they mean to
  measure. The column index is a counter, `col = col == cols ? 1 : col + 1`,
  rather than `mod1(t, cols)`: the same file records that an integer division per
  item cost more than the work the scalar kernel was measuring. The workspace
  slice `d` still follows `t`, so the workspace walk is unchanged. Before the
  loop it checks the row and a non-empty table (`checkbounds(table, row, 1)`)
  and a non-empty workspace (`checkbounds(ws, 1, 1)`, which the return value
  reads).
- `calib_touch_kernel!` keeps its loop and checks `checkbounds(table, row,
  n_touch)` first when `n_touch > 0`. Its only caller walks each table once, so
  it refuses more touches than columns rather than wrapping.
- Docstrings of both kernels say so.
- `CALIBRATION_SCHEMA_VERSION` goes from 4 to 5 (`machine_calibration.jl`), with
  a note on why. `load_machine_constants` already returns `nothing` for another
  schema, so `ensure_machine_constants!` treats a schema-4 file as missing and
  measures again. `save_machine_constants` carries the file's `[campaign]` table
  across the rewrite, as for any re-measurement. A schema-4 file is never read
  as constants and never makes a run fail.

Why wrap rather than widen the tables: the arithmetic ladder is documented as
"cache-resident", and the 52×64 table is sized like a degree-50 coefficient
table. A table widened to 4096 columns is 1.7 MB, so the arithmetic baseline
would time memory traffic, and the allocation and bandwidth coefficients
subtract that baseline. Wrapping keeps the 26 KiB footprint and the stride of
each read (`rows * 8` bytes, one cache line per touch), and repeated walks are
what the harmonics kernel does: it walks its coefficient table once per
satellite.

Independent review: the coordinator reviewed PR 485 at `4f4276501` under Giusy's

- **The bug.** `_calibrate_usl` gave `calib_batch_kernel!` up to 4096 touches of
  a 52×64 table under `@inbounds`, and `_calibrate_parallel_speedup` gave it 512.
  The extra touches read past the table. Hosted CI hit it as a segfault at
  `calibration_kernels.jl:62` on a coverage shard of #474.
- **The fix.** The batch kernel walks its row again from the first column after
  the last, with a counter rather than `mod1`, as its comment says. So the touch
  count it means to measure is kept without widening the table out of its cache
  level. Both kernels `checkbounds` before their unchecked loops.
  `calib_touch_kernel!` documents and checks that one walk must fit. Every call
  site was audited against its table (the PR body's table).
- **Saved constants.** `CALIBRATION_SCHEMA_VERSION` goes from 4 to 5, so
  constants measured under the bug are measured again, once per machine on its
  first `parallel=true` run. The new test checks that a complete schema-4 file
  is measured again, not refused, and that its `[campaign]` table is kept.
- **What it does not touch.** No simulation result. The constants only route
  `parallel=true` work, and nothing in the engine's numerical path changes.
- **History.** Two commits on main 2088b4408, no trailers. They merge cleanly
  with main bfa32f6a4. The one local suite-09 failure,
  `parallel/precompile_state_tests.jl`, fails identically on main when run the
  same way locally, and passed in main's hosted CI. Hosted CI decides it here.

## Findings

No P1 or P2 findings in the change. Points a reviewer should check:

- Deliberate behaviour change, the fix itself: the calibration's arithmetic USL
  ladder and its parallel speedup curve now time reads of the 26 KiB table
  instead of reads striding through the memory after it. The constants they
  produce (`parallel_speedup`, `usl_alpha_base`, `usl_beta_arith`, and through
  `usl_beta_arith` also `usl_beta_alloc` and `usl_beta_bw`) will read
  differently from main's on the same machine. They are timings and were not
  compared. The predictive campaign planner reads `usl_alpha_base` and
  `usl_beta_alloc` (`campaigns/predictive_planner.jl`); the other constants feed
  the RHS-plan predictor, which has no caller outside `parallel/cost/`.
- Deliberate behaviour change, the schema bump: on a machine that saved
  constants before this change, the first `parallel=true` run in a working
  directory measures them again. That is the same one calibration a machine
  without constants runs, under the same lock, with the same "Measuring this
  machine's parallel cost constants once" message. Constants measured with more
  threads than the session, which would otherwise be kept, are measured again
  too, with the session's thread count.
- Simulation results: no simulation path calls either kernel (`git grep`: the
  five calls above are the only ones in `src`, `ext`, `scripts`, `packages` and
  `docs`, and no companion checked out locally calls them). The constants only
  steer the routing of `parallel=true` runs, and as timings they already differ
  from one calibration to the next.
- Low: `calib_batch_kernel!` and `calib_touch_kernel!` are exported. A caller
  that passed an out-of-range row, an empty table or workspace, or (touch kernel)
  more touches than columns now gets a `BoundsError` where main read outside the
  buffer. A batch-kernel caller with more touches than columns now gets the
  wrapped walk.
- Low: the wrap adds one compare per touch to the batch kernel. Each touch is
  followed by `simd_per_touch` passes over a workspace row of `B` lanes, so the
  compare is not what the kernel times.

## P1 Assessment

No P1 findings. The change removes reads outside the calibration tables and
retires the constants those reads produced. It changes no code a simulation
runs; only the calibration's own timings move.

Unresolved P1: No

    a child process with `--check-bounds=yes` and four threads includes the

## Residual Risk

- Every machine that saved constants before this change measures them once
  more, on its first `parallel=true` run in each working directory that holds a
  schema-4 file. A run that cannot measure (for example a calibration that
  throws) warns and plans without constants, as before.
- The constants file lives under the working directory. Checkouts before and
  after this change that share one working directory each read the other's file
  as stale, so each process re-measures and overwrites it on its first
  `parallel=true` run until both are on schema 5.
- The child in the new test stands in for the worker pool, the rate curve and
  `@batch`. If `machine_calibration.jl` or `robust_timing.jl` later needs
  another name when it is included (a macro, or a type in a method signature),
  the test fails with an `UndefVarError` until the stand-ins are extended; it
  does not pass silently. The child does not run the dispatch ladders, whose
  buffers were checked by reading.
- The record is written for PR 485; the number is filled in when it is committed.
