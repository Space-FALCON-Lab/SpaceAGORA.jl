## Wrong Julia version

**Symptom:** `julia --version` prints something other than
`julia version 1.12.x`. Depending on the command, the failure then looks like
one of these:

- Setting up the Odyssey example environment, or any `Pkg.add`, `Pkg.update`
  or `Pkg.resolve`, stops with an error saying that the `julia = ~1.12` compat
  entry does not include your Julia version (Julia 1.12 words it as `julia
  version requirement for package at ... not satisfied`; other releases word it
  differently).
- The documented root instantiate,
  `Pkg.instantiate(julia_version_strict=true)`, stops with `The active
  manifest file has dependencies that were resolved with a different julia
  version (1.12.3)`.
- A plain `Pkg.instantiate()` prints that sentence as a warning only, then
  fails later with messages such as `Could not locate the source code for the
  ... package. Are you trying to use a manifest generated by a different
  version of Julia?` or with a long list of precompilation errors.
- On Julia 1.11 or older, the strict command fails with `type Context has no
  field julia_version_strict`, because that package manager predates the
  option.

**Cause:** SpaceAGORA is tested and supported on Julia 1.12 only, and the
committed manifest was resolved with 1.12; the documented commands refuse
other releases rather than run an untested combination.

**Resolution:**
- Install a Julia 1.12 release: with juliaup, `juliaup add 1.12` and then
  `juliaup default 1.12`; otherwise the 1.12 installer from julialang.org.
- Make sure that release is the `julia` on your PATH and, in VS Code, the one
  selected by the Julia extension's executable-path setting.
- Rerun the instantiate command from the repository root. Each Julia release
  keeps its compiled caches in its own `~/.julia/compiled/v1.x` directory, so
  an earlier attempt on the wrong release needs no cleanup.

## Wrong working directory

**Symptom:** A documented command fails on a path it cannot find, for example
`ERROR: SystemError: opening file ".../examples/AGORA_Basic_Quickstart.jl":
No such file or directory`, or `using SpaceAGORA` fails with
`Package SpaceAGORA not found in current path`. On Windows, a terminal that
opened in `C:\Windows\System32` adds permission errors.

**Cause:** `--project=.` means "the project in the current directory", and
every relative path in the documentation is relative to the repository root,
the checkout directory that contains `Project.toml`, `src/` and `examples/`.
Run elsewhere, `julia --project=.` silently creates an empty environment
there: `Pkg.instantiate()` reports `No packages added to or removed from
.../Project.toml` and leaves a stray `Manifest.toml` behind.

**Resolution:**
- Change to the checkout before every terminal command (`cd` on all three
  platforms) and confirm with `ls Project.toml` on Linux/macOS or
  `dir Project.toml` on Windows.
- Delete any `Project.toml` or `Manifest.toml` that an earlier attempt
  created outside the checkout.
- In VS Code, open the checkout folder as the workspace so that its
  integrated terminal starts there; the editor itself is not a shell.
- In a Julia REPL, `Base.active_project()` must end in
  `SpaceAGORA.jl/Project.toml`; `pwd()` shows the directory Julia was started
  in, and `cd("/path/to/SpaceAGORA.jl")` changes it without leaving the
  session.

## Examples environment not prepared

**Symptom:** An example stops with `Prepare the examples environment first:
run julia --startup-file=no examples/setup.jl`, the command-line tool's `run`,
`telemetry` or `benchmark` command stops with `The examples environment is not
prepared`, or a plotting script fails with `Package Plots not found in current
path`.

**Cause:** From SpaceAGORA 0.6.0 the examples, plotting scripts and studies run
in the examples environment (`examples/Project.toml`), which adds Plots, Roots
and the other example packages to SpaceAGORA. The root project no longer
provides them, and the examples environment's manifest is generated, not
committed, so a fresh clone does not have it.

**Resolution:**
- Prepare it once from the repository root, after the root instantiate:
  `julia --startup-file=no examples/setup.jl`.
- Run examples and plotting scripts with `--project=examples`.
- Run the setup again after a pull that changes the root `Manifest.toml`, and
  when an example reports that the examples environment does not provide this
  checkout's SpaceAGORA.

## Shell command typed into the Julia REPL, or Julia code typed into the shell

**Symptom:** At the `julia>` prompt, `julia --project=examples examples/...` fails
with `ParseError: ... invalid operator`, `cd SpaceAGORA.jl` with
`extra tokens after end of expression`, `git clone ...` with
`UndefVarError: git not defined`, and a PowerShell line such as
`$env:GIT_LFS_SKIP_SMUDGE = "1"` with
`syntax: "$env" is not a valid function argument name`. At the shell prompt,
`using SpaceAGORA` or `include("...")` is reported as an unknown command
(`command not found: using`, or PowerShell's `is not recognized`) or as a
syntax error.

**Cause:** Two different programs read the line. The shell (PowerShell,
Command Prompt or a terminal) runs `julia`, `git` and `cd`; the Julia REPL
runs Julia code such as `using`, `include` and function calls.

**Resolution:**
- Blocks marked "Terminal" go to the shell prompt (`PS C:\...>` or `$`);
  blocks marked "Julia REPL" go to the `julia>` prompt.
- Start the REPL from the repository root with `julia --project=.` (or
  `julia --project=examples/odyssey_surrogate_env` for the Odyssey example);
  `exit()` or Ctrl-D returns to the shell.
- A line that starts with `]` is a package-manager command: typing `]` at the
  `julia>` prompt switches to the `pkg>` prompt, and Backspace returns.
- Running a script does not need the REPL at all:
  `julia --project=. path/to/script.jl` from the shell runs it and exits.

## Precompilation errors

**Symptom:** `Pkg.instantiate()` or the first `using SpaceAGORA` ends with
`ERROR: LoadError: Failed to precompile SpaceAGORA [afbfb69f-5c0b-4832-b760-43725dff8540] ...`
or `The following N direct dependencies failed to precompile:`, usually after
a long trace.

**Cause:** Most often the wrong Julia release (see above). Otherwise an
interrupted first instantiate, a partially downloaded dependency, or a
compiled cache left by a different checkout of the package.

**Resolution:**
1. Confirm that `julia --version` prints `1.12.x`.
2. From the repository root, rerun
   `julia --project=. -e "using Pkg; Pkg.instantiate(julia_version_strict=true); Pkg.precompile()"`.
3. If the same package fails again, delete
   `~/.julia/compiled/v1.12/SpaceAGORA` (Windows:
   `%USERPROFILE%\.julia\compiled\v1.12\SpaceAGORA`) and repeat step 2; a
   failing dependency has its own directory under the same parent.
4. When asking for help, quote the first line that names the failing package
   and the error it reports; the rest of the trace repeats it.

## First run is very slow

**Symptom:** The first `julia --project=. ...` invocation takes several minutes
before anything prints.

**Cause:** Julia compiles all package code on first load. SpaceAGORA pulls in
ODE solver, atmosphere, and geometry libraries that take time to precompile.
Subsequent runs in the same Julia session or after the compiled cache is
populated are significantly faster.

**Resolution:**
- This is expected behavior. Wait for the first run to complete.
- The compiled cache persists across sessions, so only the very first run per
  Julia install is slow.
- To warm the cache explicitly without running a full simulation:
  ```text
  julia --project=. -e "using SpaceAGORA"
  ```
- The Odyssey surrogate example shows the same effect inside one run: its
  first passage includes compilation and reports a much longer run time than
  the second, whatever the panel caps are.
- Lines such as `WARNING: Imported binding Logging.termlength was undeclared at
  import time during import to WebSockets.` can appear while dependencies
  precompile. They come from a dependency, not from your setup, and the run
  continues; only an `ERROR:` line needs action (see Precompilation errors).

## Odyssey surrogate: setup, offline runs and `native_gram_loaded = false`

**Symptom:** One of these on the native-free Odyssey route:

- the setup script stops in `git submodule update --init` for
  `packages/gnc/SpaceAGORAEDG.jl`, or while adding `GRAMSuite`, with a network
  or Git error;
- `examples/odyssey_surrogate.jl --offline` stops with a missing-asset error;
- `git status` shows `examples/odyssey_surrogate_env/Project.toml` as
  modified;
- every `summary.toml` says `native_gram_loaded = false`.

**Cause and resolution:**

- The first setup needs network access: it clones the EDG guidance companion
  from GitHub, and the package manager downloads the GRAMSuite wrapper and the
  remaining packages. The first example run then downloads the preset grid
  and the public scenario assets. Neither step needs native GRAM or a GRAM
  data directory; see the [Odyssey walkthrough](../tutorials/odyssey_surrogate.md).
- `--offline` refuses to download, so it works once the assets are installed.
  Run the example once with network access; that installs both the preset grid
  and the scenario's SPICE kernels and gravity coefficients. The
  [named surrogate data command](../cli.md#Named-surrogate-data)
  `assets fetch --preset=odyssey_p20_frozen_v1 --version=1.0.0` installs only
  the grid, so an offline run still needs the scenario assets afterwards.
- The modified `Project.toml` is expected: the setup adds the companion to the
  example environment. Leave it as it is, or restore it with Git before
  committing other changes.
- `native_gram_loaded = false` is the correct value for this route. If an
  error mentions `GRAM Suite 2.0`, `libGRAM` or `SPICE_PATH`, you ran one of
  the GRAM-backed examples such as `AGORA_Odyssey.jl`, not the surrogate
  example.

## GRAM assets not found

**Symptom:** `julia --project=. src/interfaces/cli/main.jl assets check` reports `gram_root` or
`spice_directory` as missing, empty or pointer-only, or a GRAM-backed example
errors on load.

**Cause:** The official NASA GRAM Suite files have not been copied into the
expected local path.

**Resolution:** Follow the full setup walkthrough in
[GRAMSuite Setup](gramsuite_setup.md). The key steps are:

1. Pull the `GRAMSuite.jl` submodule:
   ```text
   git submodule update --init --recursive -- data/GRAMSuite.jl
   ```
2. Copy the official GRAM Suite distribution into:
   ```text
   data/GRAMSuite.jl/GRAM Suite 2.0
   ```
3. Build or verify the native shared library:
   ```text
   julia --project=. scripts/ensure_gram_native.jl
   ```
4. Confirm with:
   ```text
   julia --project=. src/interfaces/cli/main.jl assets check
   ```

If the submodule checkout fails with Git LFS `no space left on device`, free
disk space and see [GRAMSuite Setup](gramsuite_setup.md#Git-LFS-reports-no-space-left-on-device).

## Native GRAM library missing or stale

**Symptom:** GRAM assets are present but `GRAMAtmosphereModel` raises a library
load error at runtime.

**Possible causes:** The native `libGRAM` is missing, was copied from an
incompatible host, or cannot load one of its native dependencies.

**Resolution:**

```text
julia --project=. scripts/ensure_gram_native.jl
```

The ordinary command skips the build if the expected library file exists; it
does not check whether that binary is compatible with this host. If you copied
a populated GRAM build from another machine or suspect a stale local build,
force a rebuild:

```text
julia --project=. scripts/ensure_gram_native.jl --clean
```

If loading still fails, retain the complete error. See
[GRAMSuite Setup](gramsuite_setup.md#Build-or-verify-the-native-GRAM-library)
for build prerequisites and expected output, including the GNU Make requirement
on macOS.

## Solver stalls or takes extremely long during entry

**Symptom:** The integrator slows to a crawl during an aerobraking or entry
pass, producing thousands of rejected steps.

**Cause:** The default `dt_max_atmosphere` (1 s) may be too large for a steep
entry with rapidly-changing aerodynamic forces, causing the adaptive solver to
spend time in step-rejection loops.

**Resolution:** Reduce `dt_max_atmosphere` in `IntegrationTolerances`:

```julia
SM.IntegrationTolerances(
    dt_max_atmosphere = 0.1,    # or 0.5 for moderate entries
    reltol_atmosphere = 1e-9,
    abstol_atmosphere = 1e-11
)
```

For very steep entries (ballistic coefficient > 500 kg/m², flight path angle
steeper than −15°), start with `dt_max_atmosphere = 0.05`.

## Output CSV is not written

**Symptom:** The simulation completes but no CSV appears in the output
directory.

**Cause:** Either `simulation_settings.results = false` or
`simulation_settings.save_csv = false`.

**Resolution:** Check the `SimulationSettings` in your configuration:

```julia
SM.SimulationSettings(
    results   = true,
    save_csv  = true,
    results_directory = "output"
)
```

If using `make_example_config`, the `results` and `results_directory`
arguments control this:

```julia
make_example_config(
    ...
    results           = true,
    results_directory = "output/my_run"
)
```

## Concurrent runs overwrite each other's output

**Symptom:** Parallel runs write to the same CSV or produce a file named
`simulation_results_collision_*.csv`.

**Cause:** Multiple `run_simulation` calls are writing to the same
`results_directory`.

**Resolution:** Give each run its own `results_directory` when you build its
configuration: pass `results_directory=` to `make_example_config`, or set it in
the `SimulationSettings` you construct for that run. The simplest pattern is a
function that builds the configuration for a given directory and is called
once per run; [Mission Workflows](mission_workflows.md) shows a complete one,
and its `run_mission` refuses a directory that already holds results.

The collision file (`*_collision_*`) is written as a safety net when two
concurrent writes to the same path are detected.

## `isolate_state` and mutable-state aliasing

**Symptom:** Repeated calls to `run_simulation` with the same configuration
object produce different results, or the configuration appears modified after
the first run.

**Cause:** `run_simulation` deep-copies the configuration by default
(`isolate_state=true`), but some user code is passing `isolate_state=false` for
performance and then reusing a configuration object that has been mutated.

**Resolution:** Either rely on the default `isolate_state=true` (safe,
slightly slower) or ensure you never reuse a configuration instance across
overlapping or state-mutating calls when using `isolate_state=false`:

```julia
run_simulation(config)                        # safe: deep-copies config
run_simulation(config; isolate_state=false)   # fast: config must not be shared or reused
```

## `NRLMSISE00AtmosphereModel` network errors

**Symptom:** `NRLMSISE00AtmosphereModel(use_space_indices=true)` errors on the
first atmosphere evaluation with a network or download error.

**Cause:** `SpaceIndices.jl` needs to download CelesTrak
space weather data on first use, and the download failed.

**Resolution:** Run the prewarm step manually with network access before
submitting to a compute cluster:

```julia
init_nrlmsise_space_indices!()
```

Or use fixed indices instead:

```julia
NRLMSISE00AtmosphereModel(f107a=150.0, f107=150.0, ap=4.0)
```

## `GRAMAtmosphereModel` not defined

**Symptom:** `GRAMAtmosphereModel` raises `UndefVarError` even though GRAM
assets are present.

**Cause:** The `SpaceAGORAGRAMSuiteExt` package extension only loads after
`GRAMSuite` is imported into the session.

**Resolution:** Call `setup_gram_example!()` (from `examples/common.jl`) or
manually import `GRAMSuite` before using `GRAMAtmosphereModel`:

```julia
# Run from the repository root:
include(joinpath(pkgdir(SpaceAGORA), "examples", "common.jl"))
setup_gram_example!()
# GRAMAtmosphereModel is now available via SM.GRAMAtmosphereModel
```

## Verification study threshold failures

**Symptom:** `julia --project=. src/interfaces/cli/main.jl telemetry quick --enforce=1` exits non-zero and
reports threshold violations.

**Cause:** Either the simulation output diverges from the reference telemetry,
or tolerance thresholds are set tighter than the current model accuracy.

**Checklist:**

1. Confirm the run completed without solver errors (check logs for `retcode`).
2. Check `output/telemetry_cli/` for the per-metric report.
3. If you changed integration tolerances, reset them to the defaults in
   `make_example_config` and re-run.
4. If GRAM is involved, verify the asset layout with
   `julia --project=. src/interfaces/cli/main.jl assets check`.
